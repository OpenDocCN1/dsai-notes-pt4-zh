## RAG

让 AI 从"胡说八道"到"有理有据"的技术革命

> 说到 [RAG](https://cloud.google.com/use-cases/retrieval-augmented-generation)，很多人第一反应是"又一个复杂的AI概念"。实际上，它的工作原理出奇简单，就像给 AI 配了个专业的图书管理员。

> 想象这样一个场景：我们问 AI 关于公司最新产品的问题。传统模型会基于训练数据胡乱猜测，而 RAG 系统会首先在我们的企业知识库中搜索相关信息，然后基于实际文档给出精准答案。这种差异，如同盲人摸象与亲眼所见的区别。

### RAG的三步工作流程

![](img/70049781210bdcfe9d09a28b5b0eb196.png)

+ 第一步：问题向量化

+ 第二步：智能检索

+ 第三步：融合生成

> 用户提出问题后，嵌入模型将其转换为高维向量。这个过程就像给问题贴上"语义标签"，让计算机理解问题的本质含义。

> 系统在向量数据库中搜索与问题向量最相似的文档片段。这不是简单的关键词匹配，而是基于语义相似性的深度理解。

> 系统在向量数据库中搜索与问题向量最相似的文档片段。这不是简单的关键词匹配，而是基于语义相似性的深度理解。

### 解决三大痛点

当我们深入分析企业 AI 应用的痛点时，RAG 的价值就变得不言而喻了。

+ 幻觉问题

+ 时效性

+ 数据安全

> 大模型的"一本正经胡说八道"现象，在专业领域尤其严重。医疗 AI 可能会"发明"不存在的药物，法律 AI 可能引用虚构的案例。RAG 通过引入可验证的知识源，让每个回答都有据可查。

> 训练数据的时间截止点，曾是所有大模型的阿喀琉斯之踵。而 RAG 让 AI 能够实时获取最新信息——今天更新的政策文件，明天就能准确回答相关问题。

> 在数据即资产的时代，企业核心信息的安全性比什么都重要。本地部署的 RAG 系统确保敏感数据永远不会离开自己的服务器，这种安心感是任何云服务都无法提供的。

## 环境准备：5分钟搞定基础设施

在动手搭建 RAG 系统之前，我们需要先把基础环境准备好。这个过程就像装修房子前先通水通电，基础设施稳固了，后面的工作才能顺利进行。

### 第一步：`n8n`部署- Docker 一键启动

```
docker volume create n8n_data

docker run -it --rm \
    --name n8n \
    -p 5678:5678 \
    -e GENERIC_TIMEZONE=Asia/Shanghai \
    -e N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true \
    -v n8n_data:/home/node/.n8n \
    docker.n8n.io/n8nio/n8n:1.94.1
```

几分钟后，访问 `http://localhost:5678` 就能看到 `n8n` 的工作界面。这种即开即用的体验，让复杂的工作流设计变得像搭积木一样简单。

### 第二步：`Qwen3 Embedding` 模型下载

数据转化为向量需要嵌入模型的支持，这里我们选择 `Qwen3 Embedding`。为什么选它？

> 看数据说话：在 MTEB 多语言排行榜上，`Qwen3 Embedding` 以95%的检索准确率独占鳌头。更让人惊喜的是，这样的性能完全免费——阿里巴巴开源的这个模型，不仅支持 100 多种语言，还能处理 32K 长度的文档，普通电脑就能跑。

![](img/90abf5f4e537ac4bc41272436db99b57.png)

### 第三步：`Ollama` 集成 - 模型管理的最佳选择

有了模型文件，还需要一个管理工具来调用它。`Ollama` 就是为此而生的——它能把复杂的模型加载、API 调用等工作统统简化成几行命令。

具体操作步骤：

1. 导入模型到`Ollama`

```
# 创建模型文件，指向我们刚才下载的模型
echo "FROM /path/to/Qwen3-Embedding-4B-Q4_K_M.gguf" > Modelfile

# 一键创建模型（这里会自动加载和优化）
ollama create qwen3-embedding -f Modelfile
```

2. 验证模型状态

```
# 查看已安装的模型列表
ollama list
```

你应该能看到 `qwen3-embedding` 出现在列表中

3. 测试模型功能

```
# 发送测试请求，验证嵌入功能是否正常
curl http://localhost:11434/api/embed -d '{
    "model": "qwen3-embedding",
    "input": "测试文本嵌入功能"
}'
```

如果返回一串数字（向量），说明一切正常！接下来就可以在 `n8n` 中愉快地使用这个模型了。

环境准备完成后，我们就可以开始构建真正的 RAG 系统了。整个过程分为两个主要工作流：文档处理和智能问答。

## 构建文档处理工作流

我们需要把文档转换成 AI 能理解的格式。这个过程比想象中更有挑战性，不仅要保证数据的完整性，还要优化检索效果。

### 第一步：用户友好的文档上传

在 `n8n` 中，我们使用 `Form Submission` 节点作为工作流的起始触发器。选择这个节点的原因很简单——它提供了对用户友好的上传界面，无需技术背景的用户也能轻松上传文档。

![](img/0a4ea8c7840e9a5c7733ae6d2bea80a5.png)

### 第二步：向量存储的核心架构

> 数据准备就绪后，建立向量存储的基础架构成为下一个关键环节。但在配置之前，我们先理解一个核心概念：RAG 系统的数据都存储在向量数据库中，这不是普通的文本存储，而是一种特殊的数字化表示方法。

为什么需要向量化存储？

> 传统的关键词搜索只能进行字面匹配，而向量搜索能够理解语义。比如用户问"如何请假"，系统能够匹配到包含"休假申请"、"病假流程"等相关内容的文档，即使这些文档中没有"请假"这个词。

现在我们来配置这个核心组件，`n8n` 平台支持多种向量数据库方案。

![](img/ebcf29c14a652b0246b70cd81b974959.png)

> 创建 `Simple Vector Store` 节点——这是整个知识库系统的核心存储引擎。虽然它存在内存限制，但对于演示和快速原型开发来说，其轻量级特性和零配置优势让它成为理想的起点。

![](img/ff235dc1005fb39874f7dce255288aa1.png)

> 但是需要特别注意其重要限制：

> 所有向量数据仅保存在内存中，`n8n` 服务重启后，所有知识库数据将完全丢失，系统内存不足时，数据可能被自动清除。

> 本教程使用它主要是为了快速演示 RAG 工作原理，生产环境需要选择持久化向量数据库。

`Memory Key` 的设置至关重要：这个唯一标识符将成为你知识库的"数字指纹"，确保不同项目的向量数据能够独立存储和检索。

![](img/e8a2aa1b62774b7dacc7b2fca78104e3.png)

### 第三步：嵌入模型的精准配置

有了存储基础设施，现在需要配置文本向量化的核心引擎。我们需要让 `n8n` 与本地的 `Ollama` 服务建立稳定连接。

![](img/417c3b33abc15ad12f80b35b85353a60.png)

嵌入模型的双重作用

还记得我们刚才提到的向量化存储概念吗？这个关键工作就是由嵌入模型完成的。它在 RAG 系统中扮演着"翻译官"的角色：

+ 存储阶段：将文档内容转换为向量，写入向量数据库

+ 检索阶段：将用户问题转换为向量，在数据库中查找相似向量

两个阶段使用同一个模型至关重要，这确保了语义空间的一致性。就像用同一套"密码本"进行编码和解码，才能保证信息的准确传递。

现在让我们配置这个核心组件。首先创建 `Ollama` 凭证配置，建立 `n8n` 与 `Ollama` 服务的连接通道。

![](img/4af81db3a3ec57043dd61153d819ff2f.png)

### 关键配置要点：

+ `Base URL` 设置：`http://host.docker.internal:11434`（适用于 Docker 部署的 `n8n`）

+ 如果是本地直接安装的 `n8n`，则使用：`http://localhost:11434`

+ 网络连通性测试：确保端口 `11434` 可访问

![](img/4f7bed65373449cce6a999cb1a9213c8.png)

这个 URL 配置看似简单，实则蕴含着容器网络的精妙设计。`host.docker.internal`是`Docker`提供的特殊域名，它能够让容器内的 `n8n` 访问到宿主机上运行的 `Ollama` 服务，巧妙地解决了容器隔离与服务通信的矛盾。

在模型选择环节，我们直接指定前面已经准备好的`qwen3-embedding`模型。

![](img/de7a4499490527da796797b0d5605833.png)

模型配置完成后，系统即具备了将任意文本转换为1024维向量的能力。

### 第四步：智能文档解析

接下来配置 `Document Loader` 节点，选择默认的文件加载器，这是知识库的"入口门户"。

![](img/caeecacdf7c3c6ad23d81eb461ef80f5.png)

关键配置点，数据类型选择 `Binary`，这样系统就能处理各种格式的文件。现代的文档加载器已经足够智能，能自动识别 PDF、Word、TXT 等格式，并提取其中的文本内容。

![](img/e18eca73a81b648a34b63ea91dd1f6b9.png)

### 第五步：智能文本分割

最后添加 `Splitters` 节点，选择`递归文本分割器`。这一步最考验经验，直接影响后续的检索效果。

![](img/5dd4c7ddf795c308665ce08f131721d4.png)

选择`递归文本分割器`而非简单的字符分割，原因在于它能够：

+ 保持语义完整性：避免将有意义的段落生硬地分割

+ 优化检索效果：合适的分块大小能够提升检索精度

+ 处理复杂结构：对于表格、列表等复杂格式有更好的处理能力

核心参数调优：

+ `Chunk Size` 设置为1000-2000字符：这个范围既保证了足够的上下文信息，又避免了单个块过大导致的检索不精确

+ `Overlap` 设置为200字符：重叠部分确保重要信息不会在分割边界丢失

+ 分割策略选择递归模式：先按段落分割，再按句子，最后才按字符，这种层次化方法保持了文本的自然结构

![](img/6a603a001d2cb1f2926ae6c1af8ec893.png)

### 第六步：工作流全貌

![](img/027503ab35ace5ea4aa5b7647de76252.png)

整个数据流程非常清晰：

```
Form Submission → Data Loader → Splitters → Embedding → Vector Store
```

当用户通过表单上传一份技术文档时，系统将按以下步骤处理：

1. 表单触发：用户选择文件并提交，`n8n` 接收到文件数据

2. 格式检测：`Document Loader` 自动识别文件类型并选择合适的解析策略

3. 内容提取：将 PDF、Word 等格式转换为纯文本

4. 智能分割：`Splitters` 将长文档切分为语义完整的块

5. 向量转换：`Embedding` 模型将文本块转换为高维向量

6. 存储入库：向量数据写入 `Vector Store`，完成知识库构建

至此，我们的文档处理工作流就搭建完成了。但知识库建好只是第一步，如何让这些沉睡的知识变成能够对话的智能助手，才是真正的挑战。

## 构建智能问答工作流

有了文档处理流水线，我们的知识库已经"吃饱"了各种文档。现在要解决的问题是：如何让这些静态的知识变成能够交流的智能助手？这需要构建一个完全不同的工作流，够响应用户的实时查询。

![](img/8d2334e732deb46fadee0f14570db9b2.png)

### 第一步：Chat触发器配置

工作流以`Chat Trigger`节点开始。用户的每一个问题都会通过这个节点进入系统，触发后续的智能处理链路。

### 第二步：`AI Agent`智能调度

紧接着是 `AI Agent` 节点——整个 RAG 系统的"指挥中心"。这个节点不仅仅是一个简单的问答机器，它更像是一个智能的信息整合专家，能够：

+ 理解用户意图：解析问题背后的真实需求

+ 决策检索策略：确定是否需要查阅知识库

+ 整合多源信息：将检索结果与模型自身知识融合

+ 优化回答质量：确保回复既准确又易于理解

### 第三步：`Vector Store` 工具集成

在 `AI Agent`中 配置`Answer questions using a Vector Store`工具。它连接着我们之前构建的知识库，能够在毫秒间从成千上万的文档片段中找到最相关的信息。

![](img/06dbcf9567735b961fefef2d5137062c.png)

这个工具的配置需要与文档处理流程工作流保持严格一致：

+ `Vector Store`：必须选择同样的 `Simple Vector Store`

+ `Memory Key`：使用相同的标识符

+ `Embedding Model`：连接 `Ollama` 嵌入模型，与第一个工作流一致的 `embedding` 模型

这种一致性就像钥匙与锁的关系——只有完全匹配，才能打开知识的宝库。任何不一致都会导致检索失败，让精心构建的知识库变成"沉默的金矿"。

![](img/1fe97a4816f4890bab7833ac35b5433a.png)

在这个节点中，我们需要配置 `Chat Model` 为本地的语言模型。虽然实例中配置的是 `Google Gemini`，但在实际部署时，我们可以替换为 `Ollama` 中的本地模型，比如 `Qwen2.5` 或其他支持的开源模型，确保整个系统的本地化和数据安全。

### 第四步：提示词设计

这是整个系统的"灵魂"配置：

```
你是公司的专业知识助手，擅长基于内部文档回答问题。

核心原则：
1. 优先使用检索到的文档内容回答问题
2. 如果文档中没有相关信息，明确告知并建议联系相关部门
3. 回答要准确专业，突出重点信息
4. 适当引用文档原文，增强可信度

回答格式：
- 直接给出核心答案
- 提供必要的详细说明
- 标明信息来源或相关文档
- 建议后续行动（如有必要）
```

这个提示词看似简单，实际上定义了 AI 助手的整个"人格"。它确保 AI 不会胡说八道，也不会超出自己的能力范围回答问题。

### 第五步：工作流全貌

![](img/ad7dfb1360e4182afdd0b0fc1ff78320.png)

整个问答流程的逻辑非常清晰：用户提问 → `Agent`理解 → 检索相关文档 → 生成准确回答。

> 当用户问"公司的年假政策是什么"时，系统会在 HR 文档中检索相关信息，然后基于实际政策内容回答，而不是基于通用知识猜测。这种"有据可查"的回答方式，让 AI 助手的可信度大大提升。

> 两个工作流搭建完成后，你就拥有了一个完整的 RAG 系统——一个能够学习你的文档，并基于这些知识准确回答问题的智能助手。

## 应用场景：个人网站智能客服

想象一下，你的个人网站或企业官网突然有了一个永不疲倦的智能客服，它对你的业务了如指掌，能够准确回答访客的任何问题。这听起来像科幻小说，但用 RAG 系统，分分钟就能实现。

只需要三个步骤，就能让你的网站拥有智能对话能力：

### 第一步：激活聊天功能

在我们搭建好的问答工作流中，找到 `Chat Trigger` 节点，打开 `Make Chat Publicly Available` 开关。然后后续直接使用这个网址，将这个工作流激活以后，就可以使用我们当前的 RAG 系统了。

另外选择`Embedded Chat`模式——这个选择至关重要，它决定了聊天窗口将以嵌入式的形式出现在你的网站中，而不是跳转到新页面。用户体验的连贯性，往往就在这些细节中体现。
