## SplitK & SlicedK

`IterationK` 算法中。

对于结果矩阵的一个元素 `C[i, j]`，该元素的所有（`K` 次）乘加计算都是在同一个 CUDA thread 上完成的。

这意味着，基于 `IterationK` 的算法，每个 thread 至少需要完成 `K` 次乘加运算，对于 `K` 比较大，`M`、`N` 比较小的 `case` 来说，这个算法显然不是最优的，于是这时候我们需要打破这个假设，也就是把 `C[i, j]` 的运算分拆到不同的 thread 来进行。

第一个思路是把原本的一个 warp，再 `K` 方向上拆成若干个 warp，也就是说这若干个 warp 负责 `C` 中的同一部分。这么做可以解决问题，但需要额外增加一个环节——把这个几个 warp 得到的结果做累加。CUTLASS 把这个环节放在了 Kernel 的 `Epilogue` 的部分。这就是 `SlicedK`。

`SplitK` 的思路与 `SlicedK` 类似，只不过方法是把原本的一个 CTA，在 `K` 方向上拆成若干个 CTA。那么这若干个 CTA 之间也需要做累加。CUTLASS 选择额外 launch 一个新的 CUDA Kernel 来完成 CTA 的结果之间的 `Reduction`。

如果不使用乘加指令，而是使用 Tensor Core 指令会有什么影响？

不会有什么很大的影响，无非是把计算的最低层级从 thread 上调到 warp 而已，对 `IterationK` 而言，每个 warp 依旧负责结果矩阵的某一小部分的所有 `K` 方向的累加，只不过计算的粒度变大了，累加的次数就变小了。而 Tensor Core 的使用也要求数据全部在寄存器中，属于对于数据移动部分的流程也没有影响。

### warp level

CUDA Core 上，计算的粒度是 thread。

`TensorCore` 一般用 warp 或更高层的 warp group。因为，Cuda thread 粒度太细了。

1. 分 `x` 个 block (CTA)，每个 block 计算 `m`-`n`-`k` 的 tile，由 1 个 SM 完成。
1. block 分到 warp。`c` 最好是 1 个 warp 完成，否则，需要 warp 间再 `reduce` 一次。

warp 内 thread 共享 `shared memory`。`A` `B` 矩阵部分的加载到 `shared memory` 中，要考虑数据复用效率。

`shared memory` 中的 `data layout`，按照特定维度（`K` 维）进行排序。

这种排序方式有助于减少内存访问延迟，使得线程能够更高效地访问所需的数据。

### Warp-level 的矩阵乘 - `wmma`

warp 内，每个 thread(?) 每次计算的一个 `A tile` * `B tile`，叫 `fragment`。

假设，`A tile` 和 `B tile` 都在 `SMEM` (`shared memory`) 中。

完整计算过程

1. 初始，分 `tile` 存在 `GMEM`。
1. `load`。`tile` 加载到 `SMEM`。`SMEM` 是 block 内 thread 都可访问的 low latency memory pool。
1. `compute`。数据加载到 `TensorCore` 的 `register file` 并执行计算。
1. `store`。计算结果，写回 `SMEM`。`SMEM` 更适合用于中间结果的存储和线程间的数据交换。
1. `move`。写回 `GMEM`。算好 `memory layout` 和 `stride`。多个 thread block 的结果，拼接成最终完整 `GEMM` 结果。

`register files` (`RF`)

`Volta`/`Turing`/`Ampere` 架构，`register files` (`RF`) 是有两组 `sram` `Banks`,每组 `Bank` 的位宽是 `64bit`。

以一个 `FMMA` 指令为例，“`FFMA R6, R97, R99, RX`”，只要三个源寄存器不会同时访问同一个 `Bank` 就不会出现寄存器访问冲突。

对于 `Tensor core` 计算是以一个 `Warp32` 线程为单位执行的，其源数据也是从 `register files` (`RF`) 获取，每个时钟周期 32 个线程并行访问 `32*32bit=128B` 矩阵 `A` 数据。从寄存器文件的角度看，可以满足 `Tensor core` 计算的带宽需求。

对于 `Hopper` 架构而言，因为矩阵 `A` 需要 `256B` 的数据，按照一个 `warp` 还是 32 线程执行，每个线程就需要能够访问 `64bit` 的数据才能满足算力的需求。这里还需实际测试才能确认。

`TensorCore` shape 的特点是：优先做大 `K`，输出的 `mxn` 数据量不变。

然后做大 `m`，解决大 `batch size` 下的 `throughput`。

只要 `m`、`k`、`n` 乘积是 `constant`，`flops` 一样的。

做大 `k`，代价是 `A` 和 `B` 矩阵的 `input bandwidth` 都要加大。

做大 `m` 和 `n` 的话，只增大 1 边 `input`，然后 `output` 得增大。

`input bandwidth` 需求的增大，可以尝试加 `cache` 缓解。

加了 `AccBuf`，就相当于把 `k` 做大了。可以近似的认为，从 `AccBuf` 出来的 `m`、`n` 基本不变。

`FP6` 精度在计算性能上并不比 `FP8` 有显著提升——因为它在 `NVIDIA` 的张量核心中本质上仍然是以类似 `FP8` 的方式进行操作——但由于数据大小缩小了 25%，它在内存占用和带宽需求方面带来了显著的优势。

### cutlass GEMM API

```cpp
// threadblock (CTA) tile M = 128, N = 128, K = 32
// load tile A and Tile B to shared memory
using ShapeMMAThreadBlock = cutlass::gemm::GemmShape<128, 128, 32>;

// warp tile M = 64, N = 64, K = 32
using ShapeMMAWarp = cutlass::gemm::GemmShape<64, 64, 32>;

// MMA Op tile M = 8, N = 8, K = 4
// Single Tensor Core Instruction
using ShapeMMAOp = cutlass::gemm::GemmShape<8, 8, 4>>;
```

用 `tile size` 来除以 `warp size` 就是每个 CTA 的 warp 数（每一维前者都必须是后者的整数倍）

`M` 与 `N` 的含义是该 warp 负责的大小。`warp size.k` 如果小于 `tile_size.k`，那么这里就是使用了 `SlicedK` 的方法，反之则为单纯的 `IterationK`。

如果用户要使用 `SplitK`，那就得使用特别的针对 `SplitK` 的最上层的模板类，具体可以参考 `examples` 路径下的 `06_splitK_gemm`。

### conv support

在 `Tensorflow` 中，有两种数据排列格式：`NHWC` 与 `NCHW`，而 `Tensor Core` 仅支持 `NHWC`

![](img/2158c8057ab2f513a92f7d459018c6f9.png)

我们可以看到，`Tensor core` 在处理 `NCHW` 数据时，会在输入输出阶段进行额外的格式转换，这是需要我们注意的

另外，想要使用 `Tensor core`，在模型设计时有一些要点需要注意：

1. 对于卷积：

+ 早于 `7.2` 的 `cuDNN` 版本，输入通道数与输出通道数必须是 `8` 的倍数才能触发 `Tensor core` 运转。
+ `7.3` 及更高的 `cuDNN` 版本，解除通道数的倍数限制。对于 `NHWC` 格式，矩阵大小不是 `8` 的倍数时，`cuDNN` 会进行自动填充。
+ 在部分情况下 `cuDNN` 可以自动将 `NCHW` 格式进行转换，这里不再展开。

1. 对于矩阵乘法：

+ 以 `A*B` 为例（`A = M x K` ; `B = K x N`），其中 `M`、`N`、`K` 必须是 `8` 的倍数。
+ `K` 越大，单线程的计算密度越大，也可更充分发挥 `Tensor core` 性能。

|  | **Pascal-P4** | **Turing-T4** | **Volta-V100** |
| --- | --- | --- | --- |
| **L2 cache** | 2MiB | 4MiB | 6MiB |
| **L1 cache / SM** | 48KiB | 64KiB | 128KiB |
| Register File Size / SM | 256KiB | 256KiB | 256KiB |
| **SMs** | 20 | 40 | 80 |
| **SM contain** | 128 FP32 ALU | 64 FP32 ALU | 64 FP32 ALU |

尽管三款产品中，每个 `SM` 单元拥有的 `Register File` 总量保持一致——均为 `256KB`。但 `P4` 中，每个 `SM` 单元中有 `128` 个 `FP32` `CUDA` 核心；而 `V100` 与 `T4` 中为 `64` 个 `FP32` `CUDA` 核心。尽管 `Volta` 架构与 `Turing` 架构支持 `FP32` 与 `INT32` 并行计算，应当按双倍单元数来算。但当我们已知主要的计算任务为 `FP32` 时，实际上每个 `CUDA` 核将拥有约两倍于 `P4` 的寄存器文件容量。这将是我们在编程中需要注意的地方。
