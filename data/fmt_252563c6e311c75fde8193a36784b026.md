## 🚁 前言

![](img/cb99264f95636cb9d2b86d720deec0e6.png)

检索增强生成（`RAG`）现在已经成为提升大语言模型回答质量的重要技术。这个技术能够帮助我们解决大模型知识有限、容易"产生幻觉"等问题。`RAG`的核心在于从外部知识库中找到相关信息，然后把这些信息放到提示中，让大模型参考使用。在这个过程里，向量数据库或有向量检索能力的组件扮演了非常关键的角色，它们会把文本转换成向量嵌入，然后通过计算向量间的相似度来找到相关信息。

不过，传统的专用向量数据库虽然功能很强大，但往往也会带来一些额外的麻烦，比如部署复杂、需要维护、资源消耗大等问题。对于很多个人项目、中小型应用，或者想在现有`SQLite`数据基础上快速加入向量检索功能的场景，引入一个重量级的外部依赖可能不是最好的选择。比如，当我们构建像`SmartImageFinder`这样的个人图片搜索系统时，通常希望技术栈尽可能简单，部署过程轻松，资源占用小。这也就是为什么我们需要一些轻量级的、嵌入式的向量检索方案，而`SQLite`作为一个几乎无处不在的轻量级关系型数据库，自然成为一个很好的选择。

这篇文章里，我们会重点看看`SQLite`在向量检索领域的探索和发展，特别是从早期依赖`Faiss`库的`sqlite-vss`，到现在新出现的、更加轻量高效的`sqlite-vec`扩展。我们会了解`sqlite-vec`是如何摆脱外部依赖，为`SQLite`带来原生向量检索能力的。同时，通过一些实际代码和详细的性能测试，比较它与没有扩展的方案在不同数据规模下的表现差异，最后分析一下它在轻量级`RAG`应用中的价值。

## 📒 SQLite向量检索的早期探索：以sqlite-vss为例

在`SQLite`中直接处理和检索向量数据的想法其实已经存在了一段时间。早期尝试中比较有代表性的是`sqlite-vss`，这是一个旨在给`SQLite`添加向量相似度搜索能力的扩展。`sqlite-vss`的核心思路是集成Facebook的`AI`相似度搜索库`Faiss`。`Faiss`是一个功能强大且使用广泛的开源库，专门用于高效地进行稠密向量的相似度搜索和聚类，它提供了很多先进的索引结构和搜索算法。

通过`sqlite-vss`，开发者理论上可以在`SQLite`数据库内部执行向量检索操作，这无疑为`SQLite`的应用场景带来了新的可能性。`Faiss`在其中充当底层引擎的角色，负责处理向量的索引构建和相似度计算。

然而，尽管`sqlite-vss`的初衷是好的，但它对`Faiss`的强依赖也带来了一系列问题，这些问题在追求极致轻量化和广泛适用性的场景中尤为明显：

首先是编译和部署的复杂性。`Faiss`主要用`C++`编写，虽然也有`Python`接口。将它集成到`SQLite`扩展中意味着在构建`sqlite-vss`时需要处理`Faiss`的编译链和各种依赖项。在不同操作系统上可能会遇到各种编译难题和兼容性问题，尤其是在`Windows`上（因为`Faiss`的官方支持和社区资源更偏向`Linux`和`macOS`）。虽然我在`Windows`上使用`faiss-cpu`时似乎没遇到对应问题，但`sqlite-vss`的作者确实提到过这方面的困难。可能是`faiss-gpu`版本的问题，不过作者也提到`sqlite-vss`不支持`faiss-gpu`版本。也许是`Faiss`已经更新了，因为`sqlite-vss`的作者从去年五月开始就没有更新了（核心代码已经两年没动过了）。

其次是资源消耗方面的考虑。`Faiss`为了追求极致性能，索引通常需要完全加载到内存中。`sqlite-vss`的文档中也提到其底层`Faiss`索引的大小上限（如`1GB`的示例），并明确指出索引必须适合`RAM`，这也就意味着内存消耗会比较大。我上一篇文章提到的`duckdb`支持的`hnsw`索引类型也是需要在内存里，除非开启实验版本，所以我才重新找了另一个实现方案，也就是`sqlite-vec`。

还有就是功能和维护上的局限。`sqlite-vss`的某些功能受限于`Faiss`的集成方式。比如，早期版本在`KNN`搜索之上进行额外过滤的支持不完善，仅支持`CPU` `Faiss`索引（不支持`GPU`加速），不支持内存映射（`mmap`）索引等。同时，由于依赖一个庞大且独立的外部库，`sqlite-vss`的开发迭代、问题修复以及与`SQLite`自身事务处理的兼容性都可能受到`Faiss`版本的制约和影响，这也增加了维护的复杂度。用户反馈中也提到`sqlite-vss`存在"各种与事务相关的bug和问题"，并且"编译极其困难且耗时"。

这些因素共同构成了`sqlite-vss`在轻量化和普适性方面的短板，促使社区和开发者开始寻找一种更为原生、更少依赖的`SQLite`向量检索解决方案。

## 🌱 sqlite-vec：一个极小、"足够快"的向量搜索 SQLite 扩展

面对`sqlite-vss`因依赖`Faiss`带来的各种不便，开发者社区中开始有人呼吁打造一个更简洁、更通用且无外部依赖的`SQLite`向量搜索扩展。在这样的背景下，`sqlite-vec`应运而生，它试图为`SQLite`的向量处理能力开创一个新的篇章。

`sqlite-vec`的设计初衷很明确：解决`sqlite-vss`的核心痛点。它采用纯`C`语言编写，不依赖任何外部大型库（如`Faiss`），从根本上解决了编译复杂性、平台兼容性以及运行时依赖的问题。`sqlite-vec`希望打造一个"可在任何支持`SQLite`的地方运行"的向量搜索扩展，让开发者能够轻松地在各种环境中为`SQLite`应用添加向量处理能力。

为了实现这一目标，`sqlite-vec`在设计上有很多特点，让它与`sqlite-vss`相比有一些明显的优势：

首先，它完全没有外部依赖。这是`sqlite-vec`最核心的改进。通过纯`C`语言实现所有核心功能，它摆脱了对`Faiss`等第三方库的依赖。这样一来，开发者在使用`sqlite-vec`时，就不用担心复杂的编译环境配置和外部库的版本兼容问题，大大简化了项目的构建、集成和后续分发流程。

其次，它有很好的跨平台能力。因为是纯`C`实现且没有依赖，`sqlite-vec`在不同平台上的兼容性非常好。它可以在`Linux`、`macOS`、`Windows`等主流桌面操作系统上顺畅运行，甚至可以在浏览器环境（通过`WebAssembly`，`WASM`）、树莓派（`Raspberry Pi`）等嵌入式设备上使用。不过需要注意的是，不同平台需要下载对应的扩展文件，比如`Windows`上就叫做`vec0.dll`，有兴趣的话可以看看我们演示仓库的代码，里面就有这个文件。

第三，它的使用体验非常友好。`sqlite-vec`在`API`设计上充分考虑了开发者的使用体验。它提供了直观易懂的自定义`SQL`函数，比如用于将`JSON`格式的向量数组转换为内部格式的`vec_f32()`函数，以及直接计算向量间距离的`vec_distance_cosine()`、`vec_distance_L2()`等函数。更重要的是，它引入了`vec0`虚拟表接口，让开发者可以通过标准的`SQL DDL`语句（`CREATE VIRTUAL TABLE ... USING vec0`）来创建和管理向量表，并通过简洁的`SQL DML`语句（如`MATCH`子句）进行高效的向量检索，这比手动操作`BLOB`数据和在应用层计算相似度要优雅和高效得多。

尽管追求轻量，`sqlite-vec`在功能上也比较完善。它支持存储和查询多种类型的向量数据，包括常见的32位浮点型（`float32`）、8位整型（`int8`）以及二进制向量。同时，`vec0`虚拟表的设计允许开发者在存储向量的同时，定义并存储相关的元数据列（如文档`ID`、类别标签、原始文本内容等），并可以在查询时利用这些元数据进行过滤或辅助排序，这对于构建实用的`RAG`应用非常重要。

虽然`sqlite-vec`可能无法在超大规模数据集的检索性能上与专门的、分布式的向量数据库集群相媲美，但它的设计目标是为中小型数据集提供"足够快"的向量检索性能。对于个人项目、原型验证、中小型应用或`RAG`流程中的特定轻量级检索节点而言，它的性能通常能够满足需求。

### 方案一：无扩展的纯SQLite与Python实现（"手动挡"）

如果我们没有使用专门的向量检索扩展（比如`sqlite-vec`或`sqlite-vss`），想在`SQLite`中存储和检索向量数据，通常需要在应用层面（比如用`Python`）做很多工作。

#### 创建数据库连接：

```
# 创建一个SQLite数据库连接
no_vec0_db_path = "vec_no_vec1.db"
no_vec0_conn = sqlite3.connect(no_vec0_db_path)
no_vec0_cursor = no_vec0_conn.cursor()
```

#### 数据存储：

向量数据（通常是浮点数列表或`NumPy`数组）需要先被序列化成`SQLite`能够直接存储的格式。常见的做法是用`Python`的`pickle`模块将其序列化为字节串，然后存储在`SQLite`表的`BLOB`（Binary Large Object）类型列中。

```
# 创建表用于存储BLOB向量
no_vec0_cursor.execute("""
CREATE TABLE IF NOT EXISTS vec_documents(
    document_id INTEGER PRIMARY KEY,
    content_embedding BLOB,
    category TEXT,
    original_content TEXT
);""")

# 定义插入函数
def no_vec0_insert_documents(cursor, documents):
    """插入文档"""
    # 清空表
    cursor.execute("DELETE FROM vec_documents")
    
    for doc in documents:
        # 标准表插入
        embedding_bytes = pickle.dumps(doc["embedding"])
        cursor.execute(
            "INSERT INTO vec_documents(document_id, content_embedding, category, original_content) VALUES (?, ?, ?, ?)",
            (doc["id"], embedding_bytes, doc["category"], doc["content"])
        )
    
    no_vec0_conn.commit()
    print(f"成功插入 {len(documents)} 条文档")
```

#### 数据检索（KNN搜索）：

当需要进行相似度搜索时，`Python`程序需要从`SQLite`中查询出所有记录，反序列化向量数据，并在应用层逐一计算相似度：
