RAG（检索增强生成）架构已经成功地克服了 LLM 输入长度的限制和知识截止的问题，突显了在当前 LLM 技术领域中的重要性。RAG 以本地知识为基础，减轻了幻觉，是使 LLM 应用可审核的根本之一。有许多关于如何构建 RAG 应用程序的示例，同时也涉及各种类型的向量数据库。

尽管 RAG 应用程序在演示中表现出色，但许多人注意到其在投入生产中存在一些挑战。本文将深入研究 RAG 应用程序开发的一些实际细节。

## 以完美的 LLM 为基准

假设我们拥有一个生成式 LLM，其输入长度不受限制，那么输入字符串的长度不会对生成式 LLM 的准确性产生影响。此外，它的行为与所有其他流行的 LLM 完全相同。我们将这个模型称为“完美的 LLM ”。我们之所以认为它是完美的，并非因为它具有出色的性能，而是因为它具备我们所需的无限输入长度，但是这在今天是不可能的。无限的输入长度确实是一个令人向往的特性。事实上，一些充满野心的项目已经做好了长期投入 LLM 项目的打算，其中不乏项目正在研究输入长度为100万个 token 的 LLM 的可能性。然而，即使是100万个 token，恐怕在应用程序中仍然不足以满足实际业务中大量文档的需求，因为它仍然只相当于4-5MB。

现在的问题是：当你拥有如此完美的 LLM 时，你是否仍会考虑 RAG 架构呢？毕竟具有无限输入长度的完美 LLM 降低了构建复杂 RAG 的必要性。然而，答案是你仍然需要考虑 RAG 架构。生成式 LLM 必须按顺序处理内容，输入越长，速度越慢。RAG 架构不仅有助于克服 LLM 输入长度的限制，还可以降低 LLM 调用成本并提高处理速度。

在设计 RAG 应用程序时，我们需要以假设的完美 LLM 为基准来审视 RAG 应用程序，以清晰了解 RAG 的优缺点，并找出改进我们 RAG 应用程序的方法。

## RAG 效果预期

通过基线模型，生成式人工智能应用程序的输入一次性直接传递给 LLM。这样，LLM 就有机会充分理解输入文本中的所有信息。最终结果的准确性完全依赖于生成 LLM 的表现。

![](img/0828606e38b4c30e521379b30dcce1f0.png)

图1 完美的LLM

对于普通的 RAG 应用程序，最终性能会受到两个组件的影响：语义搜索方法和 RAG 实现。RAG 架构采用嵌入模型来生成真实知识和查询的向量，然后使用向量相似度函数检索最相关的内容。嵌入模型提取文本含义的能力至关重要。在 RAG 的开发中，除了嵌入模型之外，还有大量的实现细节，这些也会严重影响最终的结果。换句话说，RAG 的输出准确性将取决于生成式 LLM 的准确性、语义搜索的准确性和 RAG 信息保存率的乘积。下文会解释 RAG 信息保存率的概念。

![](img/ff83f027cc940126357bf3675d2f9921.png)

图2 RAG性能链

由于三个因素都不可能100%的达到预期，因此 RAG 应用程序的预期准确性会低于基于相同但完美的 LLM 模型的应用程序。如果 RAG 设计不当，其性能会显著下降。这是在设计 RAG 应用程序时要牢记的第一个要点。否则，意外的表现可能会让我们大吃一惊。

由于最终性能受这三个因素的影响，因此 RAG 应用程序设计必须围绕这三个组件进行，以此来实现令人满意的结果。

## 信息保存

LLM 模型和语义搜索都无法达到100%的准确率，RAG 也是如此。下面来解释一下什么是RAG信息保存率。

我们输入应用程序的文本语料库可以包含非常丰富的信息。让我们看一下语料库中有什么以及这些信息是如何输入到 LLM 中的：

![](img/5df7d39c7d55e2f5caa076dfc300fd6d.png)

图3 文本语料库中的实体关系

实体广泛分布在整个语料库中，引用关系也无处不见。经过分块处理后，实体被限制在各自的孤岛中，且块之间的关系被完全切断。在检索短语的过程中，只有前 `k` 个块有机会通过 LLM 进行传递。这意味着只有部分实体和关系能够传递给 LLM。如果 LLM 在响应查询时需要涉及广泛的关系知识，就可能会面临困难。

除了实体关系之外，分块操作还会对输入中的各种其他类型的信息产生影响：

### 上下文信息

在大多数情况下，文本都包含丰富的上下文信息。以《统计学习的要素》为例，该书包括 18 章，每一章专注于一个特定主题。每章都包含副标题、次级副标题等，读者习惯通过结合上下文来理解文本。然而，分块策略可能导致内容与其上下文失去联系。

### 位置信息

文本的权重会根据其在文档中的位置而异。文档开头和结尾的内容通常比文档中间的更为重要。当这些内容位于章节的开头或结尾时，其重要性更为显著。

### 顺序信息

自然文本经常使用明示或隐含的语言链接来连接主题，例如，一个故事可能以“开始”为起点，然后逐步发展，连接词汇如“然后”、“因此”、“在那之后”，最终以“最终”、“最后”等结束。然而，通过分块策略，这种连接可能不再完整，导致谜题的遗失和排序顺序的混乱。

### 描述信息

描述性信息指的是对单个主题的详细描述。通过分块，可能无法确保描述性信息能够有效地汇聚在一起。举例而言，想象一下你正在打电话，突然电话线断了。这种情况的影响会因这通电话的重要性而异，可能从微不足道到非常令人沮丧。

## RAG 的优点和缺点

如果我们将仅使用分块和向量相似性搜索的 RAG 称为“基本 RAG”，我们会发现它们只能处理几种类型的查询，因为它们失去了我们之前讨论过的一些输入信息：

1. 擅长处理窄范围的查询，例如描述性问题的回答，比如，哪个主题具有某些特征？

2. 不擅长进行关系推理，即寻找从实体 A 到实体 B 的路径或者识别实体的关联。

3. 不善于进行长程总结，例如，“列出哈利·波特的所有战斗”或“哈利·波特经历了多少场战斗？”。

RAG 应用程序在这类任务上表现不佳，因为只有少数分块能够输入到 LLM 中，而且这些分块是分散的。LLM 不可能收集开始所需的全部信息。

RAG 申请大多以生成式 LLM 为基础，这给用户留下了一个印象，即 RAG 申请必须具备类似于完美 LLM 申请的高级推理能力。然而，由于与完美模型相比，LLM 的输入有限，RAG 应用程序并不具备相同水平的推理能力。了解输入信息的限制有助于我们了解 RAG 可以做什么和不能做什么。我们应该在寻找 RAG 应用程序的最适领域时谨慎选择，避免将其强行引导至错误的应用场景。

## 迈向更好的 RAG 应用

讨论了 RAG 应用程序的局限性后，让我们看看如何提高其性能。

### 保证表达正确

很多时候，在处理用户提出的查询时，我们仅仅接受用户发送的所有内容。这并不是理想的做法，不仅因为存在提示泄漏和提示注入等安全风险，而且还因为性能可能会令人失望。

研究人员指出，LLM 对提示中的拼写错误和表达差异非常敏感。为了确保 LLM 能够达到最佳性能，请考虑纠正所有拼写错误，并将输入重新表达为 LLM 更容易理解的形式。

### 将嵌入模型保持在同一页面上

在大多数情况下，用户发送的查询通常很短，例如“告诉我更多有关 Tony Abbott 的信息”。随后，这些查询被转换为嵌入向量，该向量捕捉了特定查询的本质。使用直接查询进行语义搜索可能面临一些挑战，原因如下：

1. 用户的询问通常很短，以问题的形式呈现，其中包含有限的语义特征。

2. 尽管文档嵌入很长，以各种形式的语句存在，但文档嵌入的向量中包含了更丰富的信息。

3. 由于用户查询中的语义特征有限，语义搜索功能容易过度解释查询中的琐碎细节，并且文档嵌入可能含有高水平的噪声。分块进一步恶化了这种情况，因为许多关系、上下文和顺序链接都是无效的。

嵌入模型和生成式 LLM 属于不同的家族，它们接受不同的训练，具有不同的行为。嵌入模型不具备与生成式 LLM 相同水平的推理能力，甚至不像生成式 LLM 那样注重语言细节。直接使用用户输入进行查询，最糟糕的情况下可能将语义搜索功能降级为关键词搜索。

由于嵌入 LLM 和生成 LLM 是两种不同的模型，扮演不同的角色，在整个过程中它们并不在同一页面上。这两个模型根据各自对需求的理解来完成各自的工作，但它们之间没有互相交流的方式。检索到的信息可能不是生成 LLM 产生最佳结果所需的信息。这两个模型缺乏相互协调的能力。

为了避免这个问题，我们可能会选择首先使用生成式 LLM 来增强用户查询。考虑以下示例：

![](img/d246c82d17f2d47d98448bdb39e626c2.png)

图4 使用 Bard 基于原始查询改写的增强查询

通过增强查询，系统提供了更多功能，从而实现更优秀的检索结果。此外，通过发送增强查询，LLM 有机会告知嵌入模型它需要什么，而嵌入模型则能更好地为 LLM 提供高质量的信息块。这就是这两个模型可以协同工作的方式。

### 重视分块策略

块大小是我们可以为 RAG 应用程序调整的少数超参数之一。Microsoft 进行了分析，结果如下所示，可以看出为了获得更好的结果，建议使用较小的块大小。

![](img/945139b728f9c13f6054e8250a9a47b6.png)

图5 不同块大小及其性能

在分割文本时，我们还可以选择不同的分割策略。最简单的方法是在单词中断处中断。我们还可以尝试不同的策略，例如在句子或段落的中断处进行切断。为了获得更好的结果，我们可以重叠相邻的块。Microsoft 分析的分块策略比较：

![](img/170fcb11be6d5eefeaa5b375ae8524cd.png)

图6 不同分块策略的性能

嵌入模型在提取语义方面存在一定的局限性，尤其在呈现多主题、多回合语料库方面，其效果不如处理简单语料库。这就是为什么 RAG 更偏向于处理较短的文本块。那么，究竟哪个块大小是最优的呢？在 Microsoft 的研究中，他们将最小块大小设定为512个 token，而一些商业 RAG 应用程序中的块大小仅为100个 token。然而，最小的块大小是否总能获得更好的结果呢？

正如前文所述，采用分块策略将文本语料库分解成小块，从而可能导致信息丢失。块大小越小，丢失的信息就越多。因此，存在一个最佳的块大小。过小的块可能并非理想之选。然而，寻找最佳块大小就像进行超参数调整一样，需要通过对数据进行实验来确定。

![](img/94497b15b7ed4110ad0faf407de71325.png)

### 减少信息丢失

Microsoft 的研究发现，大量重叠的分块可以提高准确性。这是为什么呢？我们是否可以找到更好的方法来增强 RAG 的性能呢？

重叠之所以有帮助，是因为它能够将相邻的块连接在一起，为块提供更丰富的上下文信息。然而，即使采用激进的25%重叠，准确率也只能提高1.5%，从42.4%提高到43.9%。这意味着这并非是优化 RAG 性能的最有效方法。通过增加更多重叠来进一步提高 RAG 性能是行不通的，尤其对于小块而言，重叠分块甚至不是一个可选的策略。

就像重叠分块策略所证明的那样，保留信息有助于 LLM 做出更好的响应。那么，如何尽可能地保留输入信息呢？

重叠分块策略的目的是希望前一个分块的最后几个句子能够提供更多上下文信息，但我们也理解到，最后几句话可能并不具有很强的代表性。或许，我们可以使用 LLM 生成的前一个块的摘要来替代重叠。

请记住，输入文本包含多层上下文信息。如果我们的应用程序需要考虑这些信息，甚至还希望将分层上下文信息添加到块中。或许更有效的方法可能是将上下文信息存储为元数据。

RAG 与知识图谱现在非常流行。借助知识图谱，RAG 可以将关系存储在图数据库中，从而完全保留 chunk 之间的连接。如果关系推理对项目至关重要，那么这是一个非常重要的解决方案。

然而，带有知识图谱的 RAG 并非没有挑战。从非结构化文本中建立知识图并非易事。有许多实验从文本输入中提取实体关系三元组，但在需要生产解决方案时，情况就不同了。自动提取的实体和关系可能包含大量噪音，并遗漏太多真实信息。必须非常仔细地检查输出的质量。即使在知识图填充之后，支持的查询也与图数据库设计紧密耦合。

支持向量搜索的关系数据库虽然没有带有知识图谱的 RAG 那么花哨，但它们是工具箱中非常重要的组件。像 `pgvector` 这样的数据库允许您将复杂的信息存储为列，同时保留语义搜索功能。它比知识图谱更容易与其他企业系统集成，也更灵活。

这些都是值得考虑的有效选项。唯一需要注意的是，许多支持向量的图形数据库、搜索引擎和关系数据库并未像向量数据库那样完全优化，尤其是在处理大规模矢量索引时的速度可能并不理想，特别是当它们必须经常更新索引时。

### 站在大模型的角度思考

有时候，我们发现RAG在回答问题时表现不佳。或许我们应该考虑以下问题，而不是试图通过调整所有参数来提高其性能：

+ LLM是否具备所有必要的信息？

+ 信息是否以LLM友好的方式组织？

来看一个具体的例子：

我们正在构建一个基于 SharePoint 网站的 RAG 应用程序。其中一个网页包含有关所有项目及其团队成员的信息，包括每个成员的个人资料。我们需要确保 RAG 能够准确回答关于项目和团队成员的问题，但最初的结果却不尽人意。

初步调查显示，SharePoint 网站的内容组织结构存在不合理之处，信息的层次关系难以理解。在去除所有 HTML 标签后，网页内容如下：

![](img/b7307d5fc4dba4156e3f2336b98c10c8.png)

图8 去除所有 HTML 标签后的网页内容

如果说人类很难区分谁是谁，那么 RAG 也会遇到困难。为了使信息更好地组织起来，我们使用 Python 代码根据 HTML 属性将信息聚合在一起，将每个项目和团队成员的姓名分离到一个文本文件中，并将每个人的信息放入自己的文件中：

![](img/601e1271ee955515bdd02038a94e65e2.png)

图9 放入个人信息的文件文本

生成的文本文件相对较小，这似乎与 RAG 分块实践不太一致。原因在于合并后的文件避免了分裂问题，并完全消除了噪音。利用新生成的文件，RAG 可以轻松回答类似“谁在从事x项目？”和“Adam Smith 的爱好是什么？”等问题。

然而，当我们反向提问“Adam Smith 正在从事哪个项目？”时，RAG 却陷入了困境。我们发现 Adam Smith 虽然被列为项目成员，但不太确定为何嵌入模型未能捕捉到这一信息。为了协助 LLM 更好地完成任务，我们可以使相关信息更为突出。我们在个人档案中添加了一行，明确说明了项目参与情况，而这条附加线使得 RAG 应用程序能够 100% 准确地回答上述问题。

## 总结

RAG 作为一项新兴技术，目前正在迅速发展。可以发现对其构建模块进行逐一研究会有很大帮助。通过深入研究细节，能更全面地了解该技术的优劣，并判断新提案的有效性。有一些非常流行的框架可帮助加速 RAG 应用程序的开发。

如果阅读了本文，一定会同意 RAG 是一个复杂的架构。流行的框架可能掩盖了所有的细节，使人误以为这些细节不重要。当人们在项目中遇到问题时，他们会发现很难找到解决方案，因为实施细节过于繁杂。

建议是从基本实现开始学习 RAG，然后再考虑其他功能。因此，我们将了解每个组件的要点和影响。从一个最小的 RAG 开始，并分析它的运作方式并不困难。
