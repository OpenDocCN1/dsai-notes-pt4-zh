
但很多看似简单的东西，其实并不平凡，如何把 AI 训练中涉及到的简单矩阵运算，均匀的分摊给这么成千上万的 `core` 进行并行计算，这就是很大考验了。而英伟达的 CUDA 平台就提供了一站式这样的均衡调度能力。

### 8.3. 大模型并行计算

CUDA 平台要考虑如何把给它的“东西”分发给成千上万的 GPU 内核，而大模型并行训练时，要考虑 以什么维度去并行计算 。例如，在网络负载均衡器上，可以按照五元组加权轮询算法分担流量给到不同后端，也可以按照最小连接数算法，将当前连接分发给连接数最小的后端。

如果你耐着性子，看完前面的章节，我相信你一定对参数和训练数据并不陌生。因为模型参数决定了模型的下限，而训练数据往往能够决定它的上限（仁者见仁，智者见智）。AI 训练的并行方式，也是通过这两个维度进行的划分。一类是 模型并行 ；一类就是 数据并行 。由于模型并行，等同于把权重等参数分布在不同的 GPU 上进行计算，而这些参数本身是由张量来表示的，因此模型并行也称 张量并行 。

数据并行，理解起来最为直观，就是把训练的数据，分散到不同的 GPU 上，每个 GPU 运行相同的模型。不同的 GPU 使用分配给它的局部训练数据，对相同的模型进行并行训练。

![](img/baa0ccbcfa2ee4f5f28ffc5e43dec54f.png)

相比于数据并行，模型并行，理解起来似乎有点吃力。但是如果我说，这就好比，你在一个拼图上画了一张多层的神经网络（你应该还记得前文神经网络的样子吧），此时，你把拼图打乱得支离破碎，好吧，你想像你看到的每一块就是 GPU，而每一块拼图上面画的就是部分神经网络结构。

![](img/955ab4836a04b9a52a5a7eb12f94708c.png)

但凡涉及什么并行计算啊、分布式计算啊、什么微服务啊，必然会由此而增加网络通信，有网络通信就会有网络损耗，这些想都不用想。

### 8.4. 数据并行

数据一旦被分摊到不同的 GPU，意味着每一块 GPU 上存储的模型，不能得到全量的训练数据，只能依赖局部少量的数据来更新参数。这样会使得训练不够充分，这可不是数据并行想要得到的结果。那么数据并行，是如何来更新模型参数呢？

假设有两份训练数据，分布在了两块 GPU 卡上，每块 GPU 卡上，通过反向传播算法，各自计算出所有参数的梯度（回忆一下，梯度就是参数的更新量）。关键的时刻来了：此时每个 GPU 卡上梯度会被传递到中心服务器上，由中心服务器进行 梯度聚合（可以用 `Reduce` 表示聚合）。聚合的方式就是求和再取平均值 。然后中心服务器再把平均梯度广播到所有 GPU 卡上，统一更新参数。这个中心服务器被称为 参数服务器 。

![](img/4ea97d539f9d45c80ecf4d6a5ee1f3d9.png)

但是因为参数服务器会成为通信的瓶颈，现代 AI 训练大多摒弃了中心化的参数服务器。而是通过更优的连接结构和算法，比如环行结构、树形结构等（受限于笔者水平和写作目的不展开，但不是全互联通信方式），这使得所有 GPU 都能得到所有的梯度值，这样的话，每块 GPU 都要进行 `Reduce` 求和平均计算，因此这种通信方式被统称为 `AllReduce` 。

![](img/6eff30bad4664226a79b88ab089c8324.png)

### 8.5. 模型并行

虽然模型并行，像似小朋友的拼图，但理解起来似乎不够具体。我们以简单到极致的两层神经网络为例，它只有输入层和输出层，每一层只有三个神经元。首先我们把它转换为简单的矩阵运算，最后，我们将矩阵运算的过程，拆分到了三块 GPU 卡，分别是 `GPU0`、`GPU1`、`GPU2`。如下图所示，这个过程，我自己理解起来也有点困难，但是写写画画后，便可以大致了解。

由于大模型牵涉的都是深度神经网络，牵涉的矩阵运算很多，我们需要把上一层的矩阵运算结果像前逐步计算传递。因此就需要把上一步每块 GPU 计算的结果传递到负责下一层计算的 GPU 上进行 拼接 ，以获得全局的计算结果。 拼接的过程不涉及计算，或者说，不涉及原有数据的增加或者减少 ，这与 `Reduce` 完全不同。因此人们为拼接又取了一个新名字，叫 `Gather` 。如果所有的 GPU 都需要获取这样的拼接数据，那么整个过程也被称为 `AllGather` 。

### 8.6. NCCL 集合通信

但是对于开发人员来说，它不需要关心 GPU 底层之间如何互联，如何通信。以英伟达 GPU 为例，英伟达提供了一套高度透明的通信库接口即 `NCCL`（读作 NiKal，我也是听得多了，才知道这么读），开发人员只需要调用 `NCCL` 的相关接口函数，例如 `allgather()`、`allreduce()`，就可以完成上面提到的这些通信。

虽然开发人员不需要关注底层的通信细节，但是负责网络的管理员们不得不下功夫。网络通信可不单单是不同服务器间的通信，而且还涉及到服务器内部的通信，那么 GPU 服务器内部长什么样子呢？

### 8.7. GPU 服务器内通信

单块 H100 GPU 拥有 18000 多个计算核心，而一套 H100 整机可集成 8 块这样的 GPU。每两块 GPU 之间，都能通过带宽高达 900GB/s 的高速通道互联 —— 这条通道由 18 条链路构成，每条链路的双向总带宽为 50GB/s，这类专用高速链路就是 NVLink 。

值得注意的是，GPU 之间并非直接互联，而是各自接入平台内部的专用交换机，即 NVSwitch ，一套 H100 整机中通常配置 4 台 NVSwitch。

![](img/12192442ea1d197a9be35f96f5be6f7b.png)

每块 GPU 会同时接入这 4 台不同的 NVSwitch，这种上联至多个物理交换节点、并通过多节点实现 GPU 间数据互访的设计，被称为多平面设计（也叫多轨道设计）。因此，H100 平台的 GPU 互联架构采用的是 4 平面设计。需要强调的是，这类设计无需网络工程师手动接线，所有互联链路都已预先集成在被称为 SXM5 板卡上。如下图所示（来自英伟达官网）：8 块 H100 GPU（黑色盖板下方的组件）与 4 台 NVSwitch（绿框标注部分）共同集成在同一块 SXM5 板卡上，构成了完整的高速互联计算单元。

![](img/bfae9aad1d1422ef105f13b5a3ee5874.png)

### 8.8. GPU 服务器间通信

服务器内部不同 GPU 的互通在内部通过 NVSwitch 就完成了，但是如果涉及跨服务器的通信就需要依赖物理网络把他们打通了。而服务器对外通信时，开放的“窗口”就是网卡，英伟达 GPU 的网卡采用的是被称为 ConnectX 的系列，其中 A100 用的 ConnectX-6，而 H100 用的 ConnectX-7，前者的端口速率是 200Gbps，后者是 400Gbps。

如下图所示，以 A100 为例，这些物理网卡在内部与 GPU 进行了 1:1 的绑定，每块网卡对外提供 200G 的上行链路，对外总计提供 1.6T 的上行带宽。

![](img/e1cccf5a9c2a741ecf11d3a894852092.png)

网络管理员们会把光缆一端接在 GPU 服务器的网卡上，另一端接在交换机上，这类交换机直接与服务器打交道，我们称为 接入交换机（也成 `leaf`） 。注意的是，每个网卡上联不一样的 `leaf`，这样的话，就需要 8 台 `leaf` 交换机。这样的做的目的，一方面通过多平面设计实现容灾；另一方面是可以让单台交换机完成不同服务器上相同编号的 GPU 通信，让网络通信变得更有确定性。

![](img/b21ef46a5c42660c64dc0c2f9170f947.png)

物理网络的管理员们会尽可能把网络设计得扁平，尽量减少网络通信经过的中间节点数量。但问题是，不同平面的 GPU 该怎么通信呢？此时就不得再引入更高层级的设备进行跨平面的打通。位于更高层级的这个设备，我们称之为汇聚交换机（也称 `Spine`），如下图所示，展示了不同 GPU 平面通过 `Spine` 设备进行通信。

## 9. 大模型的使用

### 9.1. 大模型的不足

并不是每个人都买得起 GPU，也并不是每个人都可以训练一个大模型，大多数情况下，我们都在使用别人训练好的模型，来给我们的生活和工作，带来一些改变。每个人的习惯不同，我们不能指望，在广场上跳广场舞的我的大舅妈，和在实验室训练大模型的人，在使用大模型过程，都通过一模一样的调用方式。

模型一旦训练好，参数就会固定，这意味着模型学到的都是历史的、过时的知识。由于模型的训练成本比较高，它没办法实时的更新自己的参数，这是它的局限性。特别是大模型无法解决随着时间改变而改变的知识，也可以称为动态数据，例如天气的变化、猪肉价格的变化、GDP 的同比增长率、实时新闻等。

大模型另一个常见的问题就是幻觉，幻觉是一个被包装的很好的名字，它实际上，是为了“装饰”大模型对于用户提问，回答不准确、答非所问、回答错误等问题的统称。这根本上是因为它是一个概率模型，概率这个词一定程度上就说明它不够准确。

我将结合着大模型的这些局限，来分享一下人们在使用大模型过程中，有哪些好的思路，解决上述问题的。

### 9.2. Agent

从易用性的角度看，`Agent` 的出现，就是为普通人提供了使用大模型的窗口。关于 `agent` 的定义有很多说法，大体上，人们把能够对外部环境进行感知、思考决策，并且具有执行能力的“物体”，叫作 `Agent`。我们人类就是这样一个“物体”。你以为是你在张口吃饭吗？不是，是你在代理你的精神意志在吃饭。

如果在 `Agent` 中，负责思考决策的是一个训练好的大模型，那么它就被称为 `Agent` 智能体。`Agent` 至少要具备感知器和执行器两个组件。它很像是一个人，大模型相当于是我们的大脑，外部感知器就是类似于我们的眼睛、鼻子、耳朵、舌头。当 `Agent` 可以对我们输入的文字作出反馈，那么这个 `agent` 就具备了听觉，而当它可以进行图片识别时，我们就可以说它具备了视觉感知。

`Agent` 的感知器被设计的越易用、越自然、越像是一个善于倾听的知心朋友，可能越会得到普通用户的青睐。

### 9.3. MCP

`MCP` 被称为模型上下文协议，它定义了 `Agent` 与外部系统间交互时的通信标准。`MCP` 的出现，极大的弥补了大模型处理动态数据的窘境，`Agent` 在调用大模型过程中，可以通过 `MCP` 来从外部系统或者外部工具平台获取它想要的动态数据。不过前提是，`Agent` 管理员要提前把他认为可能用到的工具存放（也成注册）在本地。

在 `MCP` 之前，还有一个叫作 `function calling` 的东西，也可以让大模型获取到外部的实时数据，只是 `function calling` 与 OpenAI 深度绑定。他们在调用外部系统前，`Agent` 会把所有的工具列表以及工具的功能描述和用户问题一起发送给大模型，大模型再分析用户意图后，从工具列表选择一个工具后，返回给 `Agent`，告知其进行该工具调用，进而查询动态数据。

`MCP` 极大可能成为 `Agent` 与外部系统之间的标准调用协议，因为在 2025 年 12 月，`mcp` 的发明者 Anthropic 将 `MCP` 捐赠给 Linux 基金会旗下组织 AAIF，使其从单一厂商项目逐步转为中立的行业标准。

### 9.4. RAG

人们通过 `Agent` 使用大模型时，常常被它的幻觉困扰，幻觉产生的根因在于它是概率预测模型，除此之外，也有很大的原因在于，它本身并没有很有效的数据，这导致它会答非所问。由于大模型的知识是陈旧的，人们考虑为它增加一块外部“存储卡”，在这个存储卡中，人们可以把最新的数据、或者私域数据（它没有被大模型充分学习）加载到里面。这个思路最终演变成了一个叫作 `RAG` 的东西，人们把它作为大模型的外部“知识库”。

`RAG` 全称是检索增强生成，我的理解是通过检索知识库增强大模型的生成答案的能力。`RAG` 提供了一种让大模型不需要通过训练就可以获取到新知识的能力，它的核心工作机制：首先对上传的外部知识文档进行分片处理（拆分成几百字左右的小片段，即 `Chunk`）；接着将这些分片内容转化为向量。之所以要进行向量化，是因为模型无法直接理解文字语义，而向量可以将文字的语义转化为一串数字（前文中已经介绍过），后续只需通过向量相似度计算，就能快速找到与用户问题语义最匹配的知识分片。

![](img/7434d7ad2cbc81225f3373a19da37640.png)

匹配完成后，这些高相关度的知识分片会与用户的原始问题整合，一同输入大模型，为其生成答案提供可靠依据。需要注意的是，分片必须控制合理尺寸：如果不分片或分片太大，一方面会降低语义匹配的精准度，另一方面也可能导致整合后的内容总长度，超出大模型的上下文 Token 限制，无法正常输入模型进行处理。

### 9.5. A2A

在 `MCP`、`RAG` 知识库等能力的加持之下，`Agent` 智能体也逐渐的推广，`Agent` 作为 AI 大模型和用户之间的桥梁，换了一种面目，与普通人相遇。可谓是旧时王谢堂前燕，飞入寻常百姓家。

在 AI 不离口，GPU 不离手的现在，各行各业都在探索属于自己的 `Agent`，`Agent` 也如在深圳雨后的蜗牛，让我们目不暇接。`Agent` 之间的通信、调用需求就自然而然的摆在了我们的面前，并没有经过长时的等待，在 `MCP` 出现没多久，Google 于 2025 年 4 月 9 日正式发布 `A2A` 协议，后续捐赠给 Linux 基金会托管，成为不同 `agent` 之间通信的中立的标准协议。
