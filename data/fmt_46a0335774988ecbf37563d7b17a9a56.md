## 介绍

在典型的 MCP 设置中，MCP 服务器公开 LLM 客户端可以使用的功能（工具）、数据（通过资源）和提示。

但是，当服务器本身需要利用 LLM 的智能时会发生什么呢？这正是 MCP 采样旨在解决的问题。

![](img/53126adc2da4883e2dd3ab0e98c5ec77.png)

LLM 采样使服务器能够将任务委托给客户端可用的语言模型。简单来说，MCP 中的采样允许服务器请求客户端的 AI 模型生成文本（补全）并返回结果。

我们将探索使用 `FastMCP` 框架进行采样的概念、实现和应用。

## 概念和动机

LLM 采样创建了反向或双向架构。

通常，LLM 客户端会调用服务器的工具，但通过采样，服务器也可以回调客户端的模型。

这为什么有用？

考虑构建一个 AI 驱动的服务器的场景，该服务器需要执行语言理解或生成作为其功能的一部分。

例如，总结文档或撰写消息。传统上，服务器必须自行集成 LLM API 或在本地运行模型，这不仅成本高昂，而且难以扩展。

MCP 采样则相反：

+   委托 LLM 工作：服务器将语言生成任务交给客户端模型。服务器可以发出“请概括这段文字”的请求，然后客户端的 LLM 会完成繁重的工作。

+   以下是分步流程：

![](img/4db9ad9ba25060d74fcc563430de5a86.png)

1.  服务器的工具功能决定了它需要LLM的帮助（例如分析或生成文本）。

2.  服务器通过采样机制向客户端发送提示/请求。

3.  客户端接收此请求并调用其自己的 LLM（本地模型或 API）来生成完成。

4.  客户端将生成的结果返回给服务器。

5.  然后，服务器的工具功能将根据需要使用 LLM 生成的结果恢复执行，就好像服务器自己生成了该结果一样。

这提供了几个关键优势：

### 可扩展性

服务器避免进行计算密集型推理。

这意味着服务器可以处理更多并发请求，因为它不会因为自身生成大量文本而陷入困境。每个客户端实际上都处理自己的 LLM 工作负载。

### 成本效益

与 LLM 相关的任何 API 费用或计算负载均由客户承担。如果使用付费 API，则客户账户将承担完成费用，而非服务器费用。

这样可以将成本分摊到用户身上，并使服务器所有者免于维护昂贵的基础设施。

### 择的灵活性

客户可以选择针对给定请求使用哪种模型。

一个客户端可能使用 OpenAI 的 GPT-4o，另一个客户端可能使用开源模型，而服务器根本不需要改变。

服务器甚至可以建议模型偏好（我们稍后会讨论模型偏好），但客户端最终控制执行。

### 避免瓶颈

在传统设置中，如果服务器必须处理所有 AI 生成，它可能会成为瓶颈（想象一下数百名用户同时在一台服务器上触发文本生成）。

通过采样，每个用户自己的环境都可以处理他们的请求，从而防止服务器端队列积聚。

---

总而言之，MCP 中的采样允许分布式 AI 计算。

MCP 服务器可以集成强大的 LLM 功能，而无需嵌入模型或调用外部 API。

它是通常确定性的服务器逻辑和动态文本生成之间的桥梁，通过标准化协议调用实现。

接下来，我们将了解它如何适应 MCP 架构。

## 建筑学

从前面的部分我们知道，MCP 采用客户端-服务器架构。

服务器公开工具、资源和提示的界面，客户端连接到服务器以使用这些功能。

服务器除了提供工具、资源和提示之外，还可以请求客户端的 LLM 生成完成（即采样）。

LLM 的输出返回到服务器，从而实现服务器端的 AI 驱动行为。

在正常的交互中，客户端发送请求。服务器执行必要的操作并将结果返回给客户端。采样引入了一种反向交互：现在，服务器在处理请求的同时，可以要求客户端执行 AI 任务。

在底层，MCP 协议支持这种特殊类型的消息，通常称为完成请求或采样请求，客户端可以满足该请求。

![](img/5fd5409f7edb3c9cf1b27ba2f6f80aff.png)

**MCP 服务器（蓝色）**

1.  功能/工具正在服务器上作为代理工作流的一部分运行。

2.  在此函数内部，`ctx.sample()`调用 LLM 来生成响应或做出决定。

3.  本次调用并不在本地执行采样，而是将请求打包后发送给 MCP 客户端。

**MCP 客户端（绿色）**

1.  客户端监听来自服务器的采样请求并接收该请求。

2.  触发用户定义函数 `sampling_handler()`。该函数定义如何处理请求。例如，格式化提示、处理重试等。

3.  客户端使用外部 LLM API（如 OpenAI）或本地模型（如 LLaMA 或 Mistral）来完成请求。

4.  客户端将生成的文本作为响应发回给服务器。

完成后，我们返回 MCP 服务器（蓝色），并根据 LLM 的结果继续执行。服务器接收来自客户端的结果，并使用 LLM 生成的输出继续执行工具函数。

实际上，`FastMCP` 的客户端库帮助我们明确提供了一个采样处理程序（回调函数）来处理这些请求。我们将在本文中简要介绍如何实现这一点。

### 运输和执行

MCP 协议确保这些请求可靠地传输。`FastMCP` 支持多种传输方式（例如`stdio`和`sse`）。

无论使用哪种传输方式，流程都是相同的。服务器在类的实例/对象`Context`（例如`ctx.sample(...)`）上调用采样方法，将其打包成 MCP 消息，发送给客户端，然后等待响应。

客户端调用采样处理程序，该处理程序又调用实际的 LLM，并返回完成结果。所有这些都是异步的，也就是说，服务器的工具协程将暂停，直到结果返回，从而避免阻塞其他任务。

采样请求只是另一种结构化请求，因此所有常见的 MCP 验证均适用。

例如，服务器无法强制客户端运行代码；它只能请求带有特定参数的文本补全。而且从客户端的角度来看，它只会在收到提示时运行自己的 LLM，而不会执行服务器代码。
