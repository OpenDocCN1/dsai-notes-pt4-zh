## 2. 问题陈述

- 问题是什么？
- 为什么痛苦？
- 证据（用户原话、数据、调研）

- 次要画像
- `Jobs-to-be-done`

## 4. 战略背景
- 业务目标（OKR）
- 市场机会
- 竞争格局
- 为什么现在做？

## 5. 方案概述
- 高层描述
- 用户流程图/线框图
- 核心功能列表

## 6. 成功指标
- 核心指标
- 次要指标
- 目标值（当前 → 目标）

## 7. 用户故事与需求
- 史诗假设
- 用户故事 + 验收标准
- 边界情况、约束条件

## 8. 不在范围内
- 明确不做的（及原因）

## 9. 依赖与风险

## 3.5 user-story（用户故事）

**核心功能**：将需求转化为开发可执行的用户故事卡片。

**解决的问题**：

- 如何写清晰的用户故事？
- 验收标准怎么写？
- 如何避免故事过大或过小？

**输出格式**：

```
### 用户故事 [ID]

#### 用例（Mike Cohn 格式):
- 作为 [用户角色]
- 我想要 [执行的动作]
- 以便于 [期望的结果/价值]

#### 验收标准（Gherkin 格式):
- 场景: [场景描述]
- 给定: [前提条件]
- 当: [触发事件]
- 那么: [期望结果]
```

### 使用示例

```
场景：PRD 中有一个功能"自动发送付款提醒"

调用 `user-story`：
输入：功能描述、目标用户
输出：
- 作为 自由职业者
- 我想要 设置自动催款规则
- 以便于 不用手动追客户付款

验收标准：
- 给定 用户设置了催款规则
- 当 发票到期前 3 天
- 那么 系统自动发送催款邮件
```

## 技能协作工作流

### 4.1 标准产品开发生命周期

```
┌────────────────────────────────────────────────────────────────────┐
│                         完整工作流示例                              │
│                    做一个"自动催款"功能                             │
└────────────────────────────────────────────────────────────────────┘

阶段 1: 发现 (Discovery)
════════════════════════════════════════════════════════════════════
1. proto-persona
   → 定义目标用户：自由职业者（设计师/开发者）
   
2. jobs-to-be-done
   → 发现真实需求：不是"更快开票"，而是"别耽误收款"
   
3. customer-journey-map
   → 绘制旅程：发现"催款"环节最痛苦（平均延迟 15 天）
   
4. tam-sam-som-calculator
   → 评估市场：自由职业者发票工具市场约 50 亿
   
5. discovery-interview-prep + discovery-process
   → 访谈 10 个用户，验证假设

产出：用户洞察文档 + 机会评估报告

阶段 2: 定义 (Definition)
════════════════════════════════════════════════════════════════════
6. problem-framing-canvas
   → 定义问题：自由职业者平均晚收款 15 天，影响现金流
   
7. opportunity-solution-tree
   → 探索方案：
     - 机会 1：用户忘记催款 → 方案：自动提醒
     - 机会 2：客户弄丢发票 → 方案：自助查询
     - 机会 3：对账麻烦 → 方案：自动对账
   
8. prioritization-advisor
   → 选择框架：RICE（因为团队有数据）
   → 排序：自动提醒 (RICE=45) > 自助查询 (32) > 自动对账 (28)
   
9. positioning-statement
   → 定位："让自由职业者收款快 2 倍的专业发票工具"

产出：优先级排序 + 产品定位文档

阶段 3: 交付 (Delivery)
════════════════════════════════════════════════════════════════════
10. prd-development
    → 写 PRD：完整的需求文档，包含所有细节
    
11. user-story-mapping
    → 故事地图：把大功能拆成可迭代的片段
    
12. user-story + user-story-splitting
    → 写用户故事：
      - 故事 1：设置催款规则
      - 故事 2：定时发送催款邮件
      - 故事 3：查看催款历史
    
13. storyboard
    → 画故事板：关键界面的用户流程
    
14. press-release
    → 写新闻稿：提前想好怎么对外说

产出：PRD + 用户故事 + 故事板

阶段 4: 验证 (Validation)
════════════════════════════════════════════════════════════════════
15. business-health-diagnostic
    → 上线后评估：收款周期缩短 40%？续费率提升？
    
16. feature-investment-advisor
    → 决定下一步：继续投入还是转向？
    
17. roadmap-planning
    → 更新路线图：基于验证结果调整

产出：健康度报告 + 更新后的路线图
```

## 完整案例演示

### 案例背景

**公司**：一款面向自由职业者的在线发票 SaaS  
问题：用户流失率高，老板要求"提升用户体验"  
你的角色：产品经理

---

### 第 1 步：理解用户（`jobs-to-be-done`）

**调用技能**：`jobs-to-be-done`

**输入**：

- 产品类型：在线发票工具
- 目标用户：自由职业者（设计师、开发者、顾问）
- 表面问题："用户说开票太麻烦"

**输出**（关键洞察）：

```
## Jobs-to-be-Done 分析

### Customer Jobs
#### Functional:
- 月底 2 小时内搞定所有客户的发票
- 跟踪谁付了钱、谁还欠着
- 报税时能快速找到历史记录

#### Social:
- 让客户觉得我是正规公司，不是路边接私活的
- 看起来像有财务团队的专业人士

#### Emotional:
- 别再为发票这种破事焦虑
- 专心做项目，别被行政工作打扰

### Pains
#### Challenges:
- 客户总说"发票没收到"，其实是自己弄丢了
- 不同客户要不同格式的发票
- 记不住谁付了钱

#### Costliness:
- 每月花 6-8 小时折腾发票，时值 3000 元
- 因为发票问题晚收款，平均延迟 15 天

### Gains
#### Expectations:
- 开票时自动填充客户信息
- 一键催款，生成礼貌的提醒邮件

#### Life Improvement:
- 月底不再焦虑，能安心陪家人
- 收款更快，现金流更稳，敢接大项目
```

**洞察**：

> 用户说的"开票麻烦"，真实意思是"从完工到收款的整个流程太折腾"。真正的机会不是"更快开票"，而是自动催款 + 收款跟踪。

---

### 第 2 步：探索方案（`opportunity-solution-tree`）

**调用技能**：`opportunity-solution-tree`

**输入**：

- 期望结果：提升用户留存率 20%
- 来自 JTBD 的洞察

**输出**：

```
                    提升留存率 20%
                           │
           ┌───────────────┼───────────────┐
           │               │               │
    忘记催款          客户弄丢         对账麻烦
   (平均延迟 15 天)      发票          耗时 3 小时/月
       │                 │               │
    ┌──┴──┐           ┌──┴──┐        ┌──┴──┐
    │     │           │     │        │     │
  自动  模板  人工   自助  邮件   自动  导出  人工
  提醒  消息  提醒   查询  重发   对账  Excel  核对
    │                 │               │
  实验                实验            实验
 A/B 测试           可用性测试      时间追踪
```

**决策**：

- 选择 POC：自动提醒（影响力最高，可行性中等）

---

### 第 3 步：确定优先级（`prioritization-advisor`）

**调用技能**：`prioritization-advisor`

**输入**：

- 团队规模：5 人（2 开发、1 设计、1 产品、1 运营）
- 数据可用性：有基础指标（活跃、留存、收款周期）
- 决策风格：数据驱动

**输出**：

```
推荐框架：RICE

评分结果：
1. 自动催款提醒    RICE = 45 (Reach=80%, Impact=3, Confidence=80%, Effort=4 周)
2. 发票自助查询    RICE = 32
3. 自动对账        RICE = 28

建议：先做自动催款提醒
```

### 第 4 步：写 PRD（`prd-development`）

**调用技能**：`prd-development`

**输入**：

- JTBD 文档
- OST 分析结果
- 优先级评分

**输出**（PRD 核心章节）：

```
# 自动催款功能 PRD

## 1. 执行摘要
自由职业者平均晚收款 15 天，影响现金流。自动催款功能可在发票到期前自动发送提醒邮件，目标将收款周期缩短 40%，提升用户留存率 20%。

## 2. 问题陈述
- 谁：自由职业者（设计师、开发者）
- 问题：忘记催款、不好意思催款、催了没效果
- 证据：访谈中 8/10 用户提到"催款尴尬"，平均延迟 15 天

## 3. 目标用户
- 主要：月收入 2 万 + 的自由职业者
- JTBD："别让我为发票焦虑，专心做项目"

## 6. 成功指标
- 核心指标：平均收款周期（当前 25 天 → 目标 15 天）
- 次要指标：催款邮件打开率 (>40%)、续费率 (+20%)

## 7. 用户故事
### 故事 1：设置催款规则
- 作为 自由职业者
- 我想要 设置自动催款规则
- 以便于 不用手动追客户付款

验收标准:
- 给定 用户进入催款设置页面
- 当 用户选择"到期前 3 天发送"
- 那么 系统保存规则并显示确认

### 故事 2：发送催款邮件
- 作为 系统
- 我想要 自动发送催款邮件
- 以便于 提醒客户付款

...
```

### 第 5 步：拆故事（`user-story` + `user-story-splitting`）

**调用技能**：`user-story` + `user-story-splitting`

**输出**：

```
## 迭代 1（MVP）
1. 设置催款规则（开关 + 提前天数）
2. 定时发送催款邮件（默认模板）

## 迭代 2
3. 自定义催款模板
4. 催款历史记录

## 迭代 3
5. 多渠道催款（邮件 + 短信）
6. 智能催款（根据客户行为调整）
```

### 第 6 步：画故事板（`storyboard`）

**调用技能**：`storyboard`

**输出**：关键界面的用户流程草图

[设置页面] → [规则配置] → [确认成功] → [邮件预览] → [发送记录]

---

### 第 7 步：验证结果（`business-health-diagnostic`）

**调用技能**：`business-health-diagnostic`

**上线 6 周后**：

```
## 业务健康度报告

### 核心指标
- 平均收款周期：25 天 → 16 天 (✅ 达成)
- 催款邮件打开率：52% (✅ 超预期)
- 续费率：+18% (接近目标 20%)

### 用户反馈
- "终于不用尴尬地催款了"
- "每月省下至少 4 小时"

### 建议
- 继续迭代：增加短信催款
- 探索：自动对账功能（用户需求上升）
```

### 案例总结

**使用的技能**（按顺序）：

1. `jobs-to-be-done` → 理解真实需求
2. `opportunity-solution-tree` → 探索多种方案
3. `prioritization-advisor` → 选择优先级框架并排序
4. `prd-development` → 写完整 PRD
5. `user-story` + `user-story-splitting` → 拆分开发任务
6. `storyboard` → 设计用户流程
7. `business-health-diagnostic` → 验证结果

**成果**：

- 收款周期缩短 36%
- 续费率提升 18%
- 用户满意度显著提升
