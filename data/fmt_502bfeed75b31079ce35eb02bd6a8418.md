2019.11.22

软件硬件都是开源的，有一个主控的RISCV核，加速器部分是一块脉动阵列，整体结构比较简单，但是结构完整清晰，很适合用来做项目。

## NPU vs CPU

npu和cpu在架构上最大的区别到底在哪里？

1. 访存行为，eyeriss算是npu的一个典型结构，有global buffer，有RF，每个层级都有他的复用；跟cache有相似之处，但是由于AI计算的pattern是可以提前预测和安排的，所以不需要复杂的cache controller的逻辑，一般来说，用DMA来做system memory到global buffer的搬运，用显式的指令让寄存器直接访问片上memory；

2. 计算行为，跟cpu的avx，vector之类的向量指令集比起来，npu并行度很高；npu可以理解成一种专用的矩阵运算单元，每一拍都要进行数百到数千个MAC操作；

3. 控制行为，NPU的控制是粗粒度的，因为NPU的计算具有很强的规律，而且具有很强的局部数据复用性，因此一条粗粒度的指令就可以完成任务，比如说一片连续内存的搬运，或者说矩阵乘的计算，可以用硬件硬化的逻辑来实现，而不需要操作数明确的细粒度指令；

由于有这些区别，使用gem5里面的原生cpu，光靠修改配置是很难实现精确的npu建模的；想做好npu的建模，同样需要对以上的三个区别做好建模，包括：

1. NPU的memory hierarchy，除了cpu里面经典的L1, L2 cache以外，应该对global memory/scratchpad这种NPU特有的片上专用存储空间做建模；

2. 计算上的行为差异，cpu架构里面一百多个的寄存器资源是不够的，通用寄存器的资源更是受限，因此需要为NPU添加充足的寄存器资源，并行计算产生的中间数据会放在NPU大量的最小粒度的寄存器上；

3. 控制上的区别，需要添加NPU访存和计算相关的定制ISA，这里面会涉及到一些粗粒度的指令，执行周期可能长达数百个，NPU会作为cpu的一个专用执行单元，或者说一套协处理器，NPU相关的指令嵌套在cpu原有的ISA里面，而这部分指令的行为需要在gem5中进行建模；

## Memory and Register

![](img/1acf9967630777865d4cda36834c6b12.png)

accelerator部分，数据可以存放在三个地方：Scratchpad，Systolic Array，或者Accumulator SRAM，`mvin`，`mvout`指令可以读写Scratchpad或者Accumulator的数据，而脉动阵列则是从scratchpad里面取数，选择将结果存放在本地（OS模式）或者存放到Accumulator（WS模式）；

而要在gem5里面建模这几片存储空间，最直接的方法就是新增一个NPU寄存器类，按照寄存器的访问index来判断当前想要访问的是哪一个存储部件里面的数据，给每一个存储部件都分配一段地址；这样子每一条指令需要什么数据，就可以直接用访问寄存器的API: `xc -> getRegOperand`，`xc -> setRegOperand`来读写，比较方便；至于如何新增寄存器类，可以参考gem5开发版里面支持 custom Register in arm 的做法；

## ISA support

添加新指令的部分，这又包括两个部分，一是添加新指令的解码逻辑，让模拟器能够正确识别binary，二是添加新指令的执行逻辑，使得仿真器能够正确执行指令所对应的功能，这一部分的基础内容gem5的一个bootcamp里面是有提到的，https://gem5bootcamp.github.io/gem5-bootcamp-env/modules/developing%20gem5%20models/instructions/

gemmini的指令集，其实数量非常少。概括来讲，有三类指令：

1. 配置指令，有三条，`config_load`/`config_store`/`config_ex`，是用来提前配置访存和计算行为逻辑的一些必要参数；

2. 计算指令，也有三条：`preload`/`compute_preload`/`compute_accumulate`，是用来做脉动阵列的累加的；

3. 访存指令，有两条，就是`mvin`/`mvout`

这些指令都可以看作一种协处理器指令，并且他们的Opcode会避免与已有的RV ISA冲突，CPU解码到这些指令时，就知道要让加速器去完成指令执行的部分；而这样子的描述只是一个纯功能性的描述，好像协处理器指令跟CPU指令是等价的，事实上，他们遵循着完全不一样的流水级，而且NPU指令的粒度比较粗，一条指令实际上可能会产生数百次的访存/写回，而且大部分的操作数是隐式计算的，这跟CPU指令有着较大的区别。以`mvin`指令为例，可以看到除了源地址（DRAM），目标地址（Spad）以外，还有需要搬运多少行/列的数据，而这实际上在硬件上是通过DMA Controller完成的：

![](img/ab84a0cf507ce9c9159f86a4b43ed3fd.png)

本文主要讨论怎么在gem5从功能上模拟这样子的行为，如`mvin`指令这种类似于DMA的行为，我们可以在该指令的`execute`模板中（详见gem5 bootcamp），写上一个for循环来模拟这个过程，其伪代码为：

```
Mvin::execute{
    for (int i = 0; i < rows * cols; i++)
    {
        readMemAtomic(DramAddr, val); //Mem[Addr] -> val
        DramAddr += stride;
        xc->setRegOperand(this, SpadAddr + i, Rd); //val -> Reg[SpadAddr + i]
    }
}
```

`mvout`的过程也是类似的：

```
Mvout::execute{
    for (int i = 0; i < rows * cols; i++)
    {
        val = xc->getRegOperand(this, SpadAddr + i); //Reg[SpadAddr + i] -> val
        writeMemAtomic(DramAddr, val); //val -> Mem[Addr]
        DramAddr += stride;
    }
}
```

`compute_acc`或者`compute_preload`，都是在计算一个tile的矩阵乘`C = A * B + D`，他们的实现可以这样子写：

```
Mvin::execute{
    // C[i][j] += A[i][k] * B[k][j]
    for (int i = 0; i < DIM; i++)
    {
        for (int j = 0; j < DIM; j++){
            uint64_t C_elem = getSystolicElem(i, j);
            for (int k = 0; k < DIM; k++){
                uint64_t A_elem = getScratchpadElem(A_scratchpad_addr, i, k);
                uint64_t B_elem = getScratchpadElem(B_scratchpad_addr, k, j);
                C_elem += A_elem * B_elem;
            }                                
            setSystolicElem(C_elem, i, j);
            if(writeAcc){
                setAccumulatorElem(C_scratchpad_addr, final_val, i, j);
            }
        }
    }        
}
```

上面提到的这些`execute`函数，都会生成到`/build/RISCV/arch/riscv/generated/exec-ns.cc.inc`里面，而他们的定义则是在`/src/arch/riscv/isa/formats/*.isa`，`isa`后缀是gem5里面一种独有的domain specific language，会通过一个parser转换成最终执行的C++代码；
