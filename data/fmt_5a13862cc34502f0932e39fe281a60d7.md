## 一、前言

### 1.1 背景

本文是根据`Text2SQL`任务做的业务延伸，主要是在给某客户公司完成相关开发需求时遇到的具体业务问题进行的总结，并针对业务问题进行的优化。`Agent`版本对比`V2.0`等算法优化工作多了额外的数据可视化模块，属于商业交付的业务。算法层面的优化，可以参考作者前面的几篇文章。

这里的任务是国外的客户，数据采用的甲方提供的数据，英文形式，底座模型采用的是`langchain`的`gpt4`模型。

### 1.2 任务描述

给定一个数据库，数据库中包含多张表，然后根据用户输入的`prompt`信息，生成对应的`SQL`语句以及描述`SQL`结构化信息对应的图表类型和参数`K-V`对。（前端`UI`界面由客户公司完成）。

即完整的产品链路为用户在终端界面上输入查询`prompt`信息，通过`LLM`生成对应的`SQL`，完成`SQL`查询操作，然后根据该结果由`LLM`决策用什么形式展示查询结果，并生成对应的参数信息`K-V`对，最终以图表的形式在终端上进行响应，提升交互体验。

本期项目主要支持了基于5种图表的数据可视化，分别为柱状图、折线图、表、箱图和词云，对应了5种不同场景下的数据可视化业务需求。

## 三、业务建模

### 3.1 Text2SQL

本期业务的目标主要是对标了`DIN-SQL`的业务流程，在`Schema Link Extraction`任务上增加了`COT`的优化，并根据业务问题优化了`prompt`结构。在本业务场景下，我们的`prompt`结构可以表示为：

```
prompt = role + instruction + statement + context with cot + style + indicator
```

示例：

```
role = "# You are a professional data analyst and very familiar with SQL functions related to databases."
instruction = "Find the schema_links for generating SQL queries for each question based on the database schema and Foreign keys."
statement = "Step-by-step analysis process is required, including the connection between columns in the table and user input question,
             the definition of related columns, foreign key pairs that may need to be relied on."
context_with_cot = "*****"
style = "SQL should be as concise and efficient as possible."
indicator = The final associated information returned should be started with 'schema_link:' and end with '#'."
```

`Schema Link Extraction`:

这里的处理逻辑和作者在`V1.0`中的方法类似，这块可以看下相关的文章，这里不在赘述。

这里的区别是在对数据库中各表的描述，这里加入了对表的数据描述。

```
{   //这里不暴露企业隐私数据信息，大家参考下格式就好
   "table":"31131434",
   "columns": [
      {"name": "id", "optional": false, "data_type": "string", "desc": "1313133", "primary_key": true},
      {"name": "name", "optional": false, "data_type": "string", "desc": "3131313", "primary_key": false}
   ],
   "foreign_key": [
      "A.id = B.id",
      "A.name = B.name"
   ]
}
```

输出的`Schema Link`信息主要包括和`query`相关的`column`，依赖的数据项，聚合函数定义，外键关系等。如：

```
"schema_link: [TableA.column1, TableA.column2, TableA.column3, TableA.column4, count, avg, 3]."
```

`Task Classification`:

这里的业务定义参考`Spider`数据集，将`SQL Generation`定义分为了三个类别。

`Simple`: 简单的`SQL`查询操作，一般不包括`JOIN`等聚合操作以及嵌套查询操作。（项目交付时根本没这个类型.....）

`Medium`: 中等难度的`SQL`查询，一般会包括`JOIN`等聚合操作，不包含嵌套查询操作。（大部分是这类测试用例。）

`Hard`: 较困难的`SQL`查询，一般会同时包括`JOIN`等聚合操作，并且包括嵌套查询操作。（少量这类测试用例。）

这里加入`Task Classification`子任务主要还是为了针对性的去拟合`few-shot case`。不同难度的类别下的`prompt`会有区别，并且有难度标签在生成数据可视化参数时，能为下游子任务提供额外的信息特征，便于`LLM`更友好的生成对应的参数`K-V`对信息。

`SQL Generation`:

这里的`SQL Generation`是通过上一子任务确认对应的`prompt`模板，根据业务难度筛选“合适”的`few-shot case`示例。同时根据用户输入`query`和`Schema Link`的信息，完成`SQL`语句的生成。

![](img/c01555658754560990580ee290610d7c.png)

同时，这里为提升`LLM`推理的效果，针对性加入了`COT`的推理过程，关于`COT`的实现，可以参考作者`V1.0`版本优化中的介绍。

### 3.2 数据可视化

**业务场景**:

需要支持5种不同类型的图表，每种图表的`API`接口和参数会存在区别，包括数据的数据结构类型和是否非空，如：

```
{ //保护企业隐私，仅参考以下API描述
   "chart_a": [
       {"key": "param1", "value_type": "string", "optional": true},
       {"key": "param2", "value_type": "list[tuple]", "optional": false},
       {"key": "param3", "value_type": "list[string]", "optional": false}
   ]
}
// 如: param1 是简单的string 参数，optional, ex: 'column1'
//     param2 是list[tuple] 参数， required, ex: [('column1', 'column2', 'SUM')]
//     param3 是list[string] 参数, required, ex: ['column1', 'column2']
```

**图表分类**:

和上述的`Task Classification`任务类似，主要负责判断当前任务适合用哪种图表进行结果展示，这里是一个5分类任务（这里的业务未考虑`OOD`情况）。

**参数抽取**:

参数抽取的任务在这个系统中，算得上相对比较困难的一个点，这里涉及到对应`API`的参数取值的抽取和信息组合，可以用下图来表示：

![](img/1bdbc8eeaa146ce351379980fab6119f.png)

这里需要依靠`LLM`抽取出各个候选列和图形`API`参数的映射关系，而且需要根据数据的类型，转成对应的数据格式。涉及的知识推理包括：

```
1. 必要参数该抽取哪些列? 即: `param1`对应哪些`columns`？
2. 候选列该以什么形式组合? 即: `string`, `list`, `sql func`, `tuple`等复杂的组合形式?
3. 可选参数该不该赋值? 
4. 多个参数信息如何排序?
```

**槽位对齐**:

这里的槽位对齐目前是根据业务需求进行编码实现的，解决的是`LLM`生成内容的不确定性问题，避免`LLM`生成非法参数导致`API`调用异常。本模块暂未用`LLM`推理的策略实现。
