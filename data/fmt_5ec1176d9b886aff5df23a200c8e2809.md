## `LDGSTS` - `async_copy`

A100 之前，使用 `SMEM`（`shared memory`）时，数据流是 `Global memory` -> `Register` -> `Shared Memory`，

必须要过一次 `Register`，效率很低。

A100 新增 `LDGSTS`（Load Global Storage Shared）指令，实现异步拷贝，`GMEM` -> `SMEM`，可不经过 `register file`。

Movement Efficiently，3 倍的速度提升。

A100相对于V100，数据相当于少走一次回头路

![](img/4ed1f68a3e0aa9a1d5546886b6bbfa23.png)

A100 之前，整个 `GEMM` 流程中，数据的移动轨迹：：

`Global memory` -> `Register` -> `Shared Memory` -> `Register` -> `Compute` -> `Shared Memory` -> `Register` -> `Gloable memory`

`A`/`B`/`C`/`D` 四个矩阵分布在一个 `warp` 的 32 个线程的 `register` 中。这可能会带来一些问题：

+ 对于 `register` 占用量大

+ 对于 `register` 读写端口压力大，为了性能，必须用好 `register reuse cache`

+ 所有操作数都是寄存器，需要频繁的从 `shared memory` 和 `global memory` 读数据。为了缓解这个问题，A100 已经增加了`async_copy(LDGSTS)`功能，从 `GM` 直接拷贝数据到 `shared memory`

## 多级缓存和数据带宽

在`GPU`中，数据是多级存储的，主要是三级：

`Global memory` -- `Shared Memory` -- `Register`.

`Ampere` 架构中提供异步内存拷贝机制，通过新指令 `LDGSTS`（Load Global Storage Shared），实现全局内存直接加载到共享内存，避免了数据从全局内存到寄存器再到共享内存的繁琐操作，从而减少时延和功耗。

整个`CUDA Kernel`共享一个`Global memory`地址空间.

每个`CTA`有自己的`Shared Memory`, `CTA` 内的 `warps` 共享。

`Math` 模块包括 `Tensor Core` 和 `CUDA Core`

`RF` 是 `register file`

## A100 内存结构简化图

![](img/b59adc1fec7c64157c4b95204c652193.png)

对于任意 `m*n*k` 的 `FP16` 矩阵运算：一个 `tensor core` 的访存计算比 (`Byte/s`) 可以简化表示为：`512*(m+n)/n/m`，因为 `A100` 有 108 `SM`、每个 `SM` 有 4 个 `tensor core`，峰值主频是 1410 `Mhz`，故一共需要：`297*(m+n)/n/m` `TB/s`。

从当前的每一级缓存带宽看上显然不能满足此计算带宽需求，所以首先需要利用`SM`内部`shared memory`缓存数据，保证`SM`内部的4个`tensor core`计算时可以共享数据；其次在`L2` 缓存上也能缓存数据，保证多个`SM`之间计算时可以共享数据，这样才能达到实际的访存计算比，使得算力能够充分发挥。

## 性能推演

推测部分：

对于`MMA.m16n8k16`指令，`tensor core` 执行时会分为4步操作，每一步：执行两次`m8n4k8`的矩阵运算操作，需要两个`cycle`。

第一步：`A0 * B0 + 0 = C0;`

第二步：`A1 * B1 + C0 = D0;`

第三步：`A2 * B0 + 0 = C1;`

第四步：`A3 * B1 + C1 = D1;`

一共需要8个`cycle`。

寄存器的访存次数：

第一步：2 read + 1 write

第二步：2 read + 1 read + 1 write

第三步：2 read + 1 write

第四步：2 read + 1 read + 1 write

一共是14次访问。

所以对于`Ampere`架构，一个`m16n16k16`运算操作，`Tensor core`计算时，需要 16`cycle`， 28次寄存器访问次数。

## TMA 异步加载机制

`Tensor Core` 中引入了 `Tensor Memory Accelerator`（简称`TMA`）。

前三代的 `Tensor Core` 均基于 `Warp-Level` 编程模式进行运作。

尽管 `Nvidia A100` 架构中引入了软件的 `async_copy`，但其核心运算逻辑仍基于 `Warp-Level` 编程模式进行。

这一模式要求先将数据从 `HBM`（全局内存）加载到寄存器中，随后通过`Warp Schedule`调用`Tensor Core`完成矩阵运算，最终再将运算结果回传至寄存器，以便进行后续的连续运算。

（`cuda core` 与 `TensorCore` 想彻底异步，首先，`TensorCore` 的驱动，要脱离 `Warp Scheduler`。这东西是绑在 `cuda core` 上的）

存在 2 个问题：

1. 数据的搬运与计算过程紧密耦合。

1. 可扩展性受到了严重限制。由于多级缓存`Cache`的存储空间限制，单个 `warp` 的矩阵计算规格有上限，这直接限制了矩阵计算的规模。

数据的搬运与计算过程紧密耦合，这导致线程在加载矩阵数据时不得不独立地获取矩阵地址，简而言之，`Tensor Core` 准备数据时，`warp` 内线程分别加载矩阵数据 `Data Tile`，每一个线程都会获取独立矩阵块地址；为了隐藏数据加载的延时（全局内存到共享内存，共享内存到寄存器的数据加载），会构建多层级软流水（`software pipeline`），消耗寄存器数量及存储带宽。这一过程不仅消耗了大量的继承器资源，还极大地占用了存储带宽，进而影响了整体运算效率。

对比 `A100` 与 `H100` 的 `SM` 架构图，下方加了 `Tensor Memory Accelerator`。

硬件化的数据异步加载机制使得全局内存的数据能够更为高效地异步加载到共享内存，进而供寄存器进行读写操作。

![](img/2f9c43e8038d6479d93422613d1b38b4.png)

传统的 `Warp-Level` 编程模式要求所有线程都参与数据搬运和计算过程，这不仅消耗了大量的资源，还限制了计算规模的可扩展性。而单线程 `schedule` 模型则打破了这一束缚，它允许`Tensor Core`在不需要所有线程参与的情况下进行运算。这种设计大大减少了线程间的同步和协调开销，提高了计算效率。此外，使用`TMA`（`Tensor Memory Access`）之前，用户只需要一次性配置好首地址、偏移量等`Tensor`描述信息。这种一次性配置的方式简化了操作流程，减少了重复配置的开销，使得 `Tensor Core` 能够更加专注于计算任务本身。

在`A100`时代，虽然已经实现了软件层面的数据异步加载，但 `TMA` 的硬件化实现无疑将这一功能推向了新的高度。通过 `TMA`，数据搬运与计算之间的耦合度得以降低，从而提高了整体运算效率。

![](img/ee2b4330b940191dee72bf4c90a5b661.png)

通过`TMA`将`SM`组织成一个更大的计算和存储单元，从而实现了数据从全局内存（`global memory`）到共享内存（`shared memory`）的异步加载，以及数据到寄存器的计算和矩阵乘法的流水线处理，最后通过硬件实现了矩阵乘法的流水线。硬件实现的矩阵乘法流水线确保了计算过程的连续性和高效性，使得`GPU`能够更快地处理大规模矩阵运算。

# Turing 架构

## SubCore 微架构

从图片上，基本看不到变化。

1. 拿掉了 `FP64`.

1. `TensorCore` 增加了 `int8`，`int4`。

![](img/d76ef9efe9238a44cc15a216f3a33085.png)

`Turing`架构还引入了`FP16`的`FastPath`，这一创新设计使得每个时钟周期可以执行高达32次的计算操作。与`Volta`架构中需要4到8个时钟周期才能完成单个多线程`GEMM`计算的情况相比，`Turing`架构的计算频率和吞吐量得到了显著提升。

值得一提的是，`Turing`架构还支持通过线程共享数据的本地内存（`Local Memory`）。换句话说，在`Turing`架构的`Tensor Core`层面，每个线程的私有寄存器被设计成了可共享的资源。通过一种透明的共享机制，`Tensor Core`能够充分利用这些寄存器资源，实现更高效的矩阵计算。这种设计使得`Tensor Core`在执行矩阵乘法等计算密集型任务时，能够充分利用线程间的协作，提高计算效率，还降低了系统的整体能耗。

## CPU 矩阵乚

### 3 层循环的 Naive 算法

```
// 假设 A, B, C 都是行主序存储
// C = A * B
for (int i = 0; i < M; ++i)
    for (int j = 0; j < N; ++j)
        for (int k = 0; k < K; ++k) {
            C[i][j] += A[i][k] * B[k][j];  // 3 load + 1 store per loop
        }
```

### 临时变量 - 减少访存次数

优化效果：内层循环访存从 4 次 (`3load+1store`) 降到 2 次 `load`。

关键：临时变量 (`tmp`) 保存在 `register` 中，消除 `C` 的重复 `load/store`。

```
// 假设 A, B, C 都是行主序存储
// C = A * B
for (int i = 0; i < M; ++i)
    for (int j = 0; j < N; ++j) {
        float tmp = 0;
        for (int k = 0; k < K; ++k) {
            tmp += A[i][k] * B[k][j];  // 2 load + 0 store per loop
        }
        C[i][j] = tmp;  // 1 store
    }
```

### 循环分块 - 提升访存局部性

`A` 和 `B` 的 `load`，是无法优化掉的。通过局部性提升性能。

`B`的非连续访问是主要优化目标，循环分块是解决这问题的关键手段。

方法是循环分块（`blocking/tiling`）。

+ 目标：让`block`数据能`fit in cache`

+ `A`的`block`按行访问，`B`的`block`按列访问 → 注意`B`的访存模式

+ `Block`大小选择：`L1 Cache` / 3 ≈ 合适`block`尺寸（如`32x32`）

```
const int BLOCK_SIZE = 32;
for (int i = 0; i < M; i += BLOCK_SIZE)
    for (int j = 0; j < N; j += BLOCK_SIZE)
        for (int k = 0; k < K; k += BLOCK_SIZE)
            for (int ii = i; ii < min(i+BLOCK_SIZE, M); ++ii)
                for (int jj = j; jj < min(j+BLOCK_SIZE, N); ++jj) {
                    float tmp = 0;
                    for (int kk = k; kk < min(k+BLOCK_SIZE, K); ++kk) {
                        tmp += A[ii][kk] * B[kk][jj];
                    }
                    C[ii][jj] += tmp;
                }
```

关键性能洞察

1. `B`矩阵列主序访问是性能瓶颈

1. 理想情况：所有数据在`cache` → 性能接近`CPU`峰值

1. 现实约束：`K`很大时`B`无法全部`cache`，出现`cache thrashing`

## IterationK

数据的移动不是凭空发生的，具体来说也是需要分配到每个`thread`去完成的，这里需要考虑几个问题。

1. 为什么要进 `shared memory`？同一个 `CTA` 的若干个 `warp` 之间需要的数据是有重复的，避免重复读 `global memory`。

1. 数据读到 `Shared Memory` 该如何分工到各个 `thread`？如果还是按照`thread`的计算环节的分工来进行，那毫无疑问就会产生冗余，与我们的初衷不符，所以这个环节要重新进行分工，将整个`CTA`需要读的`A`的部分，分摊到各个`thread`，同样的方法处理`B`。所以对于每个`thread`而言，在读`Global memory`负责的`A`,`B`的部分和在乘加计算要负责的部分是不一样的。

1. 如果`shared memory`一次装不下`CTA`所需的全部`A`,`B`部分怎么办？分 `tile` 块处理，最简单的是 `IterationK`。
