
# 摘要

摘要：大语言模型（LLMs）中的空间推理是具有实体智能基础。然而，即使在简单的迷宫环境中，LLMs仍然在长期路径规划中遇到挑战，主要受空间错觉和长期推理中的环境不一致错觉的影响。为了解决这一挑战，本研究提出了一种创新模型，即空间到关系转换和课程Q学习（S2RCQL）。为了解决LLMs的空间错觉，我们提出了空间到关系方法，将空间提示转化为实体关系和代表实体关系链的路径。这种方法充分发挥了LLMs在顺序思考方面的潜力。最终，我们提出了一种基于Q学习的路径规划算法，以减轻LLMs的环境不一致错觉，增强了LLMs的推理能力。通过将状态-动作的Q值作为提示的辅助信息，我们纠正了LLMs的错觉，从而引导LLMs学习最佳路径。最后，我们提出了一种基于LLMs的逆向课程学习技术，以进一步减轻环境不一致的错觉。通过降低任务难度并利用成功经验，LLMs可以迅速积累成功经验，并用于解决更复杂的任务。我们基于百度自主开发的LLM ERNIE-Bot 4.0进行了全面实验。结果显示，与先进的提示工程相比，我们的S2RCQL在成功率和最优率方面实现了23%到40%的改进。

## 多模态对比上下文学习

贡献人：

链接：http://arxiv.org/abs/2408.12959v1

快速增长的大语言模型（LLMs）的使用突显了无梯度上下文学习（ICL）的重要性。然而，解释它们的内部工作仍然具有挑战性。本文介绍了一种新型的多模态对比上下文学习框架，以增强我们对LLMs中ICL的理解。首先，我们提出了对比学习为基础的ICL在现实世界环境中的解释，将关键值表示的距离作为ICL的差异化因素。其次，我们开发了一个分析框架，以解决多模态输入格式化对现实世界数据集的偏见。我们展示了ICL示例的有效性，即使在未见格式中表示时，基线性能很差。最后，我们提出了一种即时的ICL方法（文本锚定ICL），在检测仇恨表情包等任务中展示了有效性，这是典型ICL由于资源限制而难以处理的任务。对多模态数据集进行的大量实验表明，我们的方法在各种情境下显著提升了ICL的性能，如挑战性任务和资源受限环境。此外，它为LLMs中上下文学习的机制提供了宝贵的见解。我们的发现对于开发更具可解释性、高效性和鲁棒性的多模态人工智能系统具有重要意义，尤其是在挑战性任务和资源受限环境中。

## LLM Decode GQA & GEMV 算子性能分析（二）

贡献人：

https://zhuanlan.zhihu.com/p/715609504?utm_psn=1811339742626856960

1. `GEMV` 算子性能预估

在 LLM 解码阶段，`GEMV` 算子实际运行的是规模较小的 `GEMM`（矩阵乘矩阵）运算。通过 Roofline 模型分析，`GEMM` 算子的算术强度与 A100 GPU 的峰值计算能力和显存带宽进行了对比，推测出这些运算大多属于“Memory Bound”，即性能主要受限于显存带宽，而非计算能力。以 LLaMA 2 70B TP=8 的推理场景为例，推算出其 `GEMM` 算子运行时间约为 11.4 微秒，但实测结果却接近 18 微秒。

2. Roofline 分析与实测结果差异

实测结果显示，`GEMM` 算子的实际算术强度远高于预估值，但仍未达到 A100 的计算资源饱和点。通过 Nsight Compute 的 Roofline 分析，发现算术强度为 63.81，大约是预估的 4 倍，这主要是由于 `cuBLAS` 层面对小规模 M 维度的 `GEMM` 算子进行了填充（padding）操作，导致了额外的浮点运算。

3. 性能瓶颈分析

进一步的分析发现，尽管 `GEMM` 算子属于 Memory Bound，但其显存带宽利用率仅为 1.03 TB/s，远低于峰值 2 TB/s。通过调研 `GEMM` 算子的调度器和 Warp 状态，发现硬件资源利用率不足是主要瓶颈，每个调度器仅能调度 1.2 个 warp，而 warp 的 CPI 高达 8 个周期，这表明算子执行过程中大量时间处于等待内存操作的状态。

4. 并发度与负载不均衡的影响

通过调整 `GEMM` 算子的 N 维度发现，增加并发度（即增加 Grid 大小）能够提升显存带宽利用率，但同时也引入了负载不均衡问题。特别是在跨越特定 Grid 大小时，部分 SM（流处理器）的负载显著增加，导致整体性能下降。实验验证了在 Grid 大小跨越 A100 SM 数量倍数时（如 108 或 216），负载不均衡问题更加严重，从而拖累了算子的性能。

5. 总结与建议

文章最后总结指出，A100 GPU 在处理小规模 Batch 和低延迟推理任务时，性能受限于显存带宽和硬件资源利用率，实际表现未达预期。相比之下，L20 类 GPU 虽然规格不如 A100，但在小规模 `GEMV` 运算中的性能利用率更高，性价比可能更优。这一分析对当前流行的分离式部署方案如 Splitwise 等也提供了有效性验证。

## LLM 实践--Huggingface & vLLM + Spark 集群

https://zhuanlan.zhihu.com/p/715290922?utm_psn=1811339369920991232

本文介绍了如何利用 Spark 框架在 GPU 集群上进行大规模 LLM 推理，结合 Huggingface 和 `vLLM` 库实现高效的模型推理。本文详细描述了在创业公司资源有限的情况下，如何通过配置 Spark 集群来充分利用机器的 CPU 和内存资源，尤其是针对 GPU 资源的分配与管理。

1. **Spark 环境搭建**：包括安装 JDK、下载与配置 Spark、以及安装英伟达的 `Spark-Rapids` 插件，用于 GPU 资源的管理。

2. **Spark 配置**：通过配置 `conf/spark-env.sh` 文件设置 Spark 路径、通信端口、Python 环境以及资源限制，确保每台机器的 CPU、内存和 GPU 资源得到合理分配。

3. **任务提交与执行**：

   - **CPU 任务**：利用 Spark 和 Huggingface 的 `AutoTokenizer` 批量处理文本数据，将明文转为 Token。
   - **GPU 任务**：两种示例，一是利用 Huggingface 模型进行推理，二是通过 `vLLM` 库实现大模型推理。配置了 Spark 任务与 GPU 资源的对应关系，确保每个任务能够高效利用 GPU 资源。

4. **`vLLM` 推理示例**：采用 `vLLM` 实现并行化的 LLM 推理，通过 Tensor 并行技术和自定义的 `SamplingParams` 控制推理输出，适用于处理复杂的大规模生成任务。

文章详细阐述了从 Google TPU v1 到 TPU v4 的演进过程，包括每一代 TPU 的技术参数、性能提升、以及在 AI 计算中的应用场景。TPU v1 作为第一代 AI 芯片，采用了脉动阵列和低精度计算等创新技术，专注于推理任务。TPU v2 则在此基础上增加了训练能力，引入了 `BFloat16` 数据格式和可编程的向量存储区，提高了芯片的灵活性和性能。TPU v3 进一步提升了计算能力和内存带宽，芯片性能有显著提升。TPU v4 作为最新一代产品，采用了更先进的 7 纳米工艺，MXU 数量翻倍，缓存内存和内存带宽均有大幅提升，同时引入了光电路交换机和稀疏结构硬件支持，极大地提升了大模型推理的效率和性能。

## CMU 10-414 Deep Learning System Assignments hw3 实验笔记

https://zhuanlan.zhihu.com/p/716400560?utm_psn=1811146788939374592

这篇实验笔记详细记录了 CMU 10-414 深度学习系统课程中 HW3 的实现过程，聚焦于手动构建 CPU 和 GPU 版本的底层 `NDArray` 库，而不依赖现有的高效库。实验分为多个部分，从 Python 数组操作、CPU 后端的紧凑性和逐元素操作、到 GPU 后端的 CUDA 实现，各个部分详细描述了底层实现的技术细节。

1. **Python 数组操作**：实现了 `reshape()`、`permute()`、`broadcast_to()` 等函数，通过调整内存布局和步长，实现了对数组形状和维度的灵活操作。

2. **CPU 后端实现**：

   - **紧凑性和 `setitem`**：通过索引遍历和步长转换，将数据紧密排列并实现赋值操作，采用了循环展开的策略来处理多维数组的遍历。
   - **逐元素和标量操作**：引入模板和宏简化代码，注册了常见的算子如乘法、除法、对数、指数等操作。

3. **CUDA 后端实现**：

   - **紧凑性和 `setitem`**：实现了在 CUDA 环境下的内存紧凑排列和赋值操作，使用了索引到内存位置的转换。
   - **逐元素和标量操作**：通过模板和设备函数实现了一系列算子，优化了代码结构以适应 CUDA 的并行计算模型。
   - **矩阵乘法**：通过共享内存、线程协作和分块技术实现了高效的矩阵乘法，虽然调试过程中遇到了不少挑战，但最终成功实现了优化的 CUDA 版本矩阵乘法。

最后，作者总结了在实现 CUDA 代码过程中遇到的挑战和解决思路，特别是在矩阵乘法的实现中，通过理解理论课程中的伪代码并结合实际编程，最终克服了困难。
