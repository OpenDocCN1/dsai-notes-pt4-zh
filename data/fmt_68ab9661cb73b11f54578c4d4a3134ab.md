## 第一部分：大模型的核心概念

大模型的核心概念主要分为六个模块：LLM（大语言模型）、Prompt（提示词）、Token（计量单位）、Context（上下文）、Tool Calling（工具调用）和MCP（模型上下文协议）。

### 大语言模型（LLM: Large Language Model）

LLM可以被视为一个非常复杂的函数。它的工作原理是接收一串文本序列作为输入，然后预测文本序列中的下一个词是什么。它会不断重复预测直到生成一串完整的回复。

+ **预测与选择策略：** 模型会为所有可能的下一个词赋予一个概率值，并通过选择策略来决定输出。虽然模型可能倾向于选择概率最高的词，但实际输出不一定总是概率最高的。

+ **输出的多样性（随机性）：** 模型可以根据设定的机制和参数随机选择候选词，这使得模型输出具有多样性。即使输入完全相同的文本，也可能得到不同的结果。

+ **Temperature参数：** 模型的随机性主要由 `temperature` 参数控制。

+ 取值范围从0开始。当值为0时，输出更保守、确定。

+ 值越大，随机性越高，表现出的创造性和创造力也越高（例如用于AI生成视频或图片）。一般聊天场景下，该值常设为0.7。

### 提示词（Prompt）

提示词是掌握与模型沟通的技巧。它分为系统提示词和消息提示词。

+ 系统提示词（System Prompt）：

+ 用于指导和约束模型行为和响应的初始指令。

+ 可以定义模型的角色、能力和回答风格。

+ 它位于上下文空间的前面，具有更强的约束性，能够显著提升模型输出质量和一致性。

+ 消息提示词（Message Prompt）： 根据来源可分为三类：

+ **用户消息：** 用户发给模型的问题或指令。

+ **助手消息：** 模型生成的回应，包括模型思考过程（thought source）。

+ **工具消息：** 模型在处理请求时触发的 `tool call` 消息，以及工具调用完成后的 `tool result` 消息。

+ 优秀提示词的四个要素（Prompt Engineering）：

+ **明确目标：** 任务目标越清楚、越具体，模型输出越精准。

+ **设置输出结构和形式：** 明确要求返回格式（如 `JSON` 或表格形式）。

+ **注意事项：** 提前提醒模型容易忽略的细节，提高输出可靠性。

+ 背景信息（Context/Background）： 提供所有必要的背景信息，帮助模型理解任务场景和需求（如代码错误日志或堆栈跟踪信息）。

### Token（计量单位）

Token是模型内部的计量单位，主要体现在两个方面：

+ **性能指标：** 评估模型性能的单位（每秒生成多少个token）。

+ **计费单位：** 大模型服务通常按token计费。

+ **输入Token：** 用户发给模型的所有内容（包括系统提示词、用户问题、上传文档）。

+ **输出Token：** 模型返回给用户的生成内容（文本、代码、工具调用）。

+ **成本差异：** 输出 `Token` 在算力消耗上超过输入Token，因此价格通常更贵。

+ 模型处理流程（Tokenization）：

+ **编码 (Encoding)：** 用户输入的句子首先被切分成token，模型通过词汇表将每个token对应到一个 `tokenID`，形成一个数字序列。

+ **计算：** 大模型在数字向量空间进行计算，而不是直接处理文本字符。

+ **解码 (Decoding)：** 模型产生另一串数字序列，通过词汇表解码成最终的文本结果。

+ **Token与词语的关系：** 很多单词对应一个token，但并非所有单词都如此（例如 indivisible 是两个token，而 understandable 是一个token）。分词策略因模型而异。

### 上下文（Context）

上下文可以理解为一个不断增长的列表，它包含系统提示词、用户提问、模型输出、用户上传的文档以及工具调用的结果。

+ **上下文窗口限制：** 目前每个模型都有窗口大小限制（如200K或1MB），超过限制会导致模型中断处理或无法接收更多消息。

+ **上下文管理策略：**

+ 压缩（Summarization）： 当上下文过长，可以总结关键信息，带入新的对话，保证上下文空间充裕（例如Claude的 `summarization`能力）。

+ **开启新对话：** 处理与先前对话无关的新任务时，应开启新对话，以避免旧信息干扰，并降低输入token的成本。这是非常好的习惯。

+ Lost in the Middle现象： 当输入内容过多时，大模型的输出效果会下降。

+ **模型对上下文中的内容权重不同。** 它更关注输入的前面和后面的内容，中间的内容可能会被忽略或遗忘。

+ **启示：** 如果对话很长，应在输入开始和结束时特别强调任务目标和关键要求。同时，要控制单次输入的信息量，将大任务拆分成小任务。

+ 上下文工程（Context Engineering）： 相比提示词工程，业界现在更关注上下文工程。

+ 目标是给模型提供更好的上下文，比单纯优化提示词更重要。

+ 涉及整理、排序（如将系统提示词、相关性强的文档和工具提前）以及移除无关信息（噪声），确保信息的相关性和时效性。

### 工具调用（Tool Calling）

工具调用（Tool Calling，简称TC）可以大大扩展大模型的边界能力，使其不仅限于生成文本。

+ **能力扩展：** 允许大模型具备自主调用外部工具的能力，完成实际操作任务（如AI Code Agent具备文件操作、代码搜索、命令执行等能力）。

+ **定义方式：** 工具定义在系统提示词的固定区域内。每个工具包括名称、描述及其调用的参数。

+ **数量限制：** 由于工具定义占用上下文空间，不宜过多。一般推荐只定义核心工具，数量控制在六个以内。

+ **工作流程：** 应用程序声明工具 -> 用户请求传入模型 -> 模型决策并触发 `tool call` -> 应用程序执行工具并返回 `tool result` -> 结果作为上下文反馈给模型 -> 模型分析并生成最终回复。

### 模型上下文协议（MCP: Model Context Protocol）

MCP是一个开放标准协议，用于将大模型与外部世界的服务和数据库进行连接。它常被称为“AI世界里的USB”。

+ **统一接口规范：** MCP定义了统一的接口规范。只要实现了该协议，同一工具（如发邮件的Gmail）就能被不同的应用（如Claude、ChatGPT）使用。

+ **组成部分：**

+ **`MCP Host`：** 支持MCP协议的客户端应用（如Claude或ChatGPT）。

+ **`MCP Client`：** 本地用于连接 `MCP Server` 的客户端。

+ **`MCP Server`：** 提供工具服务的后端（可本地通过标准输入输出连接，或通过网络通信连接，如AMQP）。

+ MCP与Tool Calling的关系： MCP用于扩展核心工具列表，使其能够操作第三方工具。TC是提供给模型最核心的工具（文件读写、执行命令、网络搜索）。两者相辅相成。

+ **工具发现：** `MCP Client`连接 `Server` 后，通过 `listTools` 即可获取 `Server` 提供的可调用工具列表。

+ **应用示例：** 通过引入支持MCP的地图服务（如高德地图 `MCP Server`），模型可以调用其工具（地点搜索、路线规划等），获取更准确、更具时效性的实时信息，而非依赖训练时的知识库。

## 第二部分：AI编程工具的演进和使用经验

AI编程工具的演进和使用经验主要围绕管理上下文这一核心主线展开。

### 主流编程大模型

目前主流的编程大模型包括：

+ **OpenAI GPT系列：** 例如GPT-4/GPT-5 Codex，在代码生成方面表现优秀。

+ Google Gemini系列： 优势在于多模态，能够理解和处理多种类型数据。

+ Anthropic Claude系列： 上下文窗口较大，在处理长文本和编程方面表现突出。

+ **国内开源大模型：** 如DeepSeek-V3.2、智谱GLM-4.5K、千问、Kimi等。

### AI编程工具的演进（基于上下文管理）

AI编程工具的发展是围绕上下文管理方式的创新和优化。

### 提高AI编程效率的策略（上下文优化）

高效进行AI编程的核心在于优化上下文，即优化上下文列表中的各个组成部分：

#### (1) 优化系统提示词（Rules）

在编程工具中，系统提示词体现为代码规范和约束（如Celo Rules）。

+ 全局规则（`User Rules`）： 对模型回答风格、代码设计、复杂度等提出普遍要求。

+ 项目规则（`Project Rules`）： 针对特定项目的规范。

+ **注意点：** 规范内容不能过多，因为它占据上下文最前面的位置。

+ **`Agents.md`：** 行业内正推动采用 `agents.md` 文件来统一存放规范，以便被不同的编程工具读取和遵守。

#### (2) 优化用户输入（提示词）

遵循优秀提示词的四个核心要素。在AI编程中，除了描述问题，必须补充必要的背景信息。

+ **信息补充：** 如果出现界面异常，附上截图；如果服务故障，附上服务端或客户端日志，帮助模型定位问题。

#### (3) 优化文档内容（Docs）

提供足够的文档信息（项目架构、模块设计、核心接口说明）对模型输出高质量代码至关重要。

+ **文档获取方式：**

+ **文档抓取：** 使用工具抓取网站文档，保存在本地向量数据库中，提问时进行语义检索。

+ **手动复制/存储：** 将网页内容复制成 `Markdown` 文件保存在代码仓库。

+ **模型生成：** 养成习惯，让AI为复杂的模块或接口沉淀 `Markdown` 文档，保存起来供后续使用（例如，记录需求说明、技术方案和任务列表）。

+ **时效性：** 对于频繁更新的文档，可以使用支持 `context` 的 `MCP Server`，检索最新文档。

+ **开源项目：** 使用工具（如 `DeepWiki` 或 `RepoReader`）阅读开源项目并生成文档。

#### (4) 优化工具调用

工具调用包括内置Agent工具和通过MCP扩展的外部工具。

+ **内置工具：** 例如Agent模式下的代码检索、文件编辑、构建命令执行等。

+ **外部工具（MCP）：** 通过MCP引入外部能力（如 `Chrome Dev Tools` 用于分析性能，`Next.js Dev Tools` 用于项目升级）。

+ **按需开启：** 必须根据实际情况按需开启MCP工具，不使用时应关闭。

+ 原因：MCP工具信息（名称、描述）占用上下文空间。如果开启过多工具（如超过80个），会占据大量上下文，导致模型输出性能下降。

### AI编程工具的未来发展趋势

AI编程工具的后续发展仍聚焦于上下文管理和开发模式的创新。

+ **基于规范的开发（`Specification-Based Development`）：** 强调文档优先。开发流程遵循：需求评审 -> 需求文档 -> 技术实现方案（计划文档） -> 任务拆分 -> 模型执行。

+ **提高开发效率的扩展：**

+ 多Agent（`Multiple Agents`）： 开启多个Agent，分工处理不同的任务和功能需求。

+ 后台Agent（`Background Agents`）： 通过手机或网页提交任务，让模型在后台持续开发。

+ 上下文管理创新（提升优化效率）：

+ 子Agent（`Sub-Agents`, `sagent`）： 借鉴分额制思想，将任务交给子Agent，由子Agent加载相应的工具和文档上下文，保持主Agent的上下文干净，避免过快被占满。

+ **Cloud Skills：** 进阶版功能，将特定技能（提示词、脚本、资源）打包，并用 `skill.md` 声明。采用三层上下文加载机制：先加载基础信息，当模型确定需要该技能时，再逐步加载详细描述和完整资源（如脚本），从而避免不必要的上下文占用和优化效率。

**总结：** 上下文是AI编程的核心之一。无论是工具的演进还是个人高效使用AI编程，其关键都在于管理和优化上下文，确保上下文空间充足，信息相关且低噪声。
