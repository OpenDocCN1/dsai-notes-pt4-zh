
## 负责任 AI 仪表板（RAI）生成流程

### 初始化 RAIInsights 并添加组件

```
from raiwidgets import ResponsibleAIDashboard
from responsibleai import RAIInsights

# ... load model and data ...

# 1. Initialize the RAIInsights object
rai_insights = RAIInsights(model, train_data, test_data, target_column, 'classification')

# 2. Add specific RAI components (insights)
rai_insights.explainer.add()
rai_insights.error_analysis.add()
rai_insights.fairness.add(
    sensitive_features=test_data['AgeGroup'],
    fairness_metric='accuracy_score'
)
```

`RAIInsights()`： 这是构建仪表板的中心对象。你需要用你的模型、训练数据、测试数据和目标列来初始化它。

`.add()` 方法：

`rai_insights.explainer.add()`： 添加可解释性组件。

`rai_insights.error_analysis.add()`： 添加错误分析组件。

`rai_insights.fairness.add(...)`： 添加公平性组件。这个组件需要额外的配置：

`sensitive_features=...`： 明确告诉它我们要基于哪个敏感特征（这里是 `AgeGroup`）来评估公平性。

`fairness_metric=...`： 指定用于比较不同群体性能的指标（这里是 `accuracy_score`）。

### 计算洞察并生成仪表板

```
# 3. Compute the insights
rai_insights.compute()

# 4. Generate the dashboard in the notebook
ResponsibleAIDashboard(rai_insights)
```

`rai_insights.compute()`： 这是一个计算密集型的步骤。它会触发后台的所有分析计算（例如，训练解释器模型、构建错误分析树、计算各种公平性指标）。

`ResponsibleAIDashboard(rai_insights)`： 当计算完成后，这一行代码会读取 `rai_insights` 对象中所有计算好的结果，并在 Jupyter Notebook 的输出单元格中渲染出一个可交互的仪表板。这使得你可以在开发环境中就进行初步的探索和分析。

### 通过管道作业大规模生成和持久化

在更正式的 MLOps 流程中，通常会将上述步骤封装在一个管道中，以便在大规模数据上运行，并将生成的仪表板持久化地保存在 Azure ML 中。Notebook 中通常会展示如何构建这样的管道。

```
# This is a conceptual representation
from azure.ai.ml.entities import PipelineJob
from azure.ai.ml.components import CommandComponent

# Create a component that runs the RAI generation script
rai_component = CommandComponent(
    name="generate_rai_dashboard",
    command="python generate_rai.py --model ${{inputs.model}} --test_data ${{inputs.test_data}}",
    # ... inputs, outputs, environment ...
)

# Build a pipeline with this single component
@pipeline
def rai_pipeline(model_input, test_data_input):
    rai_job = rai_component(model=model_input, test_data=test_data_input)

# Submit the pipeline
# ...
```

封装为组件： 最佳实践是将 `RAI Insights` 的生成逻辑封装在一个独立的 Python 脚本中，然后为这个脚本创建一个组件。

构建管道： 创建一个包含这个 RAI 组件的管道。这个管道的输入是你想要分析的模型和数据，输出则是生成的仪表板。

提交运行： 提交这个管道作业。作业成功后，你就可以在 Azure ML Studio 的作业详情页找到一个永久的、可供团队共享的链接，指向这个完整的、可交互的 RAI 仪表板。

## Log and register models with MLflow

`https://github.com/MicrosoftLearning/mslearn-azure-ml/blob/main/Instructions/10-Log-mlflow-models.md`

**这个实验是对之前多个实验中已经接触过的 MLflow 功能的一次深度聚焦和总结。** 它旨在巩固和深化你对“将模型作为标准产物进行规范化记录”的理解，并将其正式与 Azure ML 的模型注册表 `Model Registry` 连接起来。

### 实验特点与知识点分析 （基于 `Instructions/10-Log-mlflow-models.md`）

#### 核心目标

这个实验的核心目标是让你掌握使用 MLflow 记录和注册模型的完整流程，并深刻理解一个被 MLflow 记录的“模型”不仅仅是一个模型文件，而是一个包含了元数据、环境依赖和部署规范的、自包含的“标准软件包”。最终目标是让你学会如何将实验产出的最佳模型，从一个临时的“运行产物”提升为一个版本化的、可在生产中复用的正式“资产”。

#### 流程分析

这个实验在 Jupyter Notebook 中完成，其流程将模型从训练产出到正式注册的路径清晰地展现出来：

1.  准备工作 （Preparation）: 首先，连接到工作区，并准备好数据和计算资源。

1.  在训练脚本中集成 MLflow （Integrate MLflow in Training Script）: 编写一个训练脚本 `main.py`，并在其中集成 MLflow。这个实验会同时展示两种核心的记录方式：

+   手动记录 （Manual Logging）: 使用 `mlflow.log_metric` 和 `mlflow.sklearn.log_model` 等命令，精确地、手动地记录你关心的每一个指标和最终的模型。

+   自动记录 （Autologging）: 使用 `mlflow.autolog()`，让 MLflow 自动捕获所有相关的指标、参数和模型。

1.  运行训练作业 （Run Training Job）: 将上述脚本封装在一个命令作业 （Command Job） 中并提交运行。作业成功后，一个包含了所有 MLflow 记录信息的“运行 （Run）”对象就被创建了。

1.  从运行中获取模型 （Retrieve Model from Run）: 这是流程的关键一步。你会学习如何通过编程方式：

+   查询一个特定的 `Run`。

+   从这个运行的 `Artifacts` 中，找到由 MLflow 记录的那个模型。

1.  注册模型 （Register the Model）: 这是最终的目标。你会调用 `mlflow.register_model()` 函数，或者使用 `MLClient` 的方法，将上一步中找到的模型注册到 Azure ML 的模型注册表中。在注册时，你需要为其指定一个在注册表中唯一的名称，Azure ML 会自动为其分配一个版本号。

1.  审查注册的模型 （Review Registered Model）: 最后，在 Azure ML Studio 的“模型”页面，你可以看到刚刚注册的模型。你会发现它拥有一个清晰的名称、递增的版本号，并且其“产物”标签页下包含了所有 MLflow 记录的标准化文件（`MLmodel`， `conda.yaml` 等）。

#### 关键知识点介绍

+   模型注册表 （`Model Registry`）: 这是 Azure ML 工作区中一个用于集中管理、版本化和追踪所有生产级模型的中央存储库。它就像一个专业的“成品仓库”，而不是存放临时实验结果的“车间”。

+   注册模型 vs。 运行产物： 这是理解本实验的核心。

+   运行产物 （`Run Artifact`）: 是某一次特定实验运行的直接输出。它与那次运行紧密绑定，比较临时，可能有很多个版本，好坏不一。

+   注册模型 （`Registered Model`）: 是你从众多运行产物中精挑细选出来的、被认为是“最佳”或“可用于生产”的模型。它被赋予了一个正式的、业务相关的名称（如 `diabetes-prediction-model`）和递增的版本号（`v1`， `v2`， ...），脱离了单一的实验运行，成为了一个独立的、可被长期管理和追踪的一等资产。

+   MLflow 模型“风格” （`Model Flavor`）: 当你使用 `mlflow.sklearn.log_model` 这样的命令时，MLflow 不仅保存了模型本身（例如 `model.pkl`），还创建了一个名为 `MLmodel` 的配置文件。这个文件定义了模型的“风格”，例如 `sklearn` 风格。这个“风格”告诉下游工具（如部署服务）应该如何加载和使用这个模型，极大地提升了模型的互操作性。

+   模型签名 （`Model Signature`）: （可选但推荐）在使用 MLflow 记录模型时，可以为其定义一个“签名”，它清晰地描述了模型的输入数据格式（例如，需要哪些列、各列的数据类型）和输出数据格式。这就像一个函数的 API 文档，使得模型的集成和部署更加可靠。

+   环境依赖 （`conda.yaml`）: MLflow 在记录模型时，会自动生成一个 `conda.yaml` 文件，其中记录了训练该模型时所使用的所有 Python 库及其精确版本。这确保了无论模型被部署到哪里，都可以为其重建一个完全一致的运行环境，从而保证了预测结果的可复现性，避免了“在我电脑上能跑”的问题。

### 实验核心流程分析 （基于 `Labs/10/Log models with MLflow.ipynb` 代码）

接下来，我们深入分析该 Notebook 中的核心代码。

1.  运行一个会记录模型的训练作业

这部分与之前的实验类似，首先会提交一个 command 作业，其核心的 `main.py` 脚本中包含了 MLflow 记录逻辑。

```
# In main.py
import mlflow
mlflow.autolog() # Or manual mlflow.sklearn.log_model(...)
# ... training logic ...
```

作业运行成功后，我们就有了一个包含模型产物的 `run` 对象。

1.  从运行中获取并注册模型

```
from azure.ai.ml.entities import Model
from azure.ai.ml.constants import AssetTypes

# 1. Get the latest run from the experiment
runs = ml_client.jobs.list(experiment_name=experiment_name)
latest_run = next(iter(runs)) # A simplified way to get the latest run

# 2. Define the path to the model artifact in the run
model_path_in_run = "runs:/{}/model".format(latest_run.name)

# 3. Create a model definition
model_to_register = Model(
    path=model_path_in_run,
    name="mlflow-diabetes-model",
    description="MLflow model to predict diabetes",
    type=AssetTypes.MLFLOW_MODEL
)

# 4. Register the model using MLClient
registered_model = ml_client.models.create_or_update(model_to_register)
```

#### 核心步骤分解

**1. `runs = ml_client.jobs.list(...)`**： 首先，我们使用 `MLClient` 来查询指定实验 （`experiment_name`） 下的所有历史运行记录。

**2. `model_path_in_run = "runs:/{}/model".format(latest_run.name)`**： 这是最关键的一步。我们构造了一个特殊的 URI 字符串。

+   `runs:/...`： 这是一个 Azure ML 特有的命名空间，表示我们要引用的是某次运行的产物。

+   `{latest_run.name}`： 这是我们想要引用的那次运行的唯一 ID。

+   `/model`： 这是由 MLflow（特别是 `autolog()` 或 `log_model()`）在该运行的产物中创建的文件夹的标准名称。

+   这个完整的路径 `runs:/<run_id>/model` 就精确地指向了我们想要注册的那个由 MLflow 生成的“模型软件包”。

**3. `model_to_register = Model(...)`**： 我们创建了一个 `Model` 实体对象，它定义了我们想要在注册表中创建的模型的元数据。

+   `path=model_path_in_run`： 核心！ 我们告诉注册表，这个新模型的源文件在哪里。

+   `name="mlflow-diabetes-model"`： 我们为这个模型在注册表中指定一个正式的、业务相关的名称。如果这个名称的模型已经存在，`create_or_update` 会为其创建一个新的版本；如果不存在，则会创建 `v1`。

+   `type=AssetTypes.MLFLOW_MODEL`： 我们明确地告诉 Azure ML，这是一个 MLflow 风格的模型。这会让 Azure ML 在后续操作（如无代码部署）中对其进行优化。

**4. `ml_client.models.create_or_update(model_to_register)`**： 这是“执行注册”的命令。`MLClient` 会找到 `path` 指向的源文件，将它们复制到模型注册表的存储中，并记录下所有相关的元数据，最终创建一个新的、版本化的模型资产。

这个流程清晰地展示了如何将一个实验性的、与特定运行绑定的产物，“晋升”为一个持久的、版本化的、准备好被部署的生产级资产。
