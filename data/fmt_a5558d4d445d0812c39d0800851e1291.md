## 概述

### 动态 shape 是什么

动态 shape，一般是 2 个问题：

1. `Tensor` 的 `shape` 是动态的。

2. Control flow 的动态性。即 `if-else` / `loop` 类的结构。比如，`where`，`while`，`Switch` 等。

`Tensor` `shape` 的动态性，类型比较多。比如：

1. 变化的 `batch size`。

2. 变化的 `input shape`。`CV` 模型的 `image resolution`，`NLP` 模型的 `input sequence length`。

3. 算子逻辑导致的。`unique`，`nonzero`。

4. 稀疏矩阵导致的。输入本身可以是静态的，但为了节约存储空间，使用稀疏矩阵表示输入。搜推模型用的多。

5. 其他特殊情况。比如，`random` 算子，可能间接导致动态 `shape`。

解决方案，集中在 `compiler` 层面。核心是如何 static 化，基本靠 padding。

“解决” 基本是不可能的，只能 case by case 的绕过去。

### 动态 shape 的挑战

`Compiler` 不擅长处理动态 `shape`。

静态 `shape` 语义下比较确定性的问题，动态 `shape` 场景很复杂。比如：

1. 算子占用的显存预估 & 调度策略，

2. 是否需要 implicit broadcast，`https://numpy.org/doc/stable/user/basics.broadcasting.html`

3. 指令层的向量化，

4. `codegen` 模版选择。

### 解决思路

分 3 大类。

1. 软件层面。主要是 `compiler` 相关，核心是如何 static 化，基本靠 padding。

2. Hardware 层面支持。没怎么关注，不了解。有些在尝试支持 control flow，比如 `tensorrent`。

4. 标量运算特别慢。比如 `topk`

### 1. Padding 成 static shape

Padding 也分两种情况：

1. 模型的 `input`，可以在 `CPU` 上做 padding，灵活性很高，方案很多。

2. `Model` 内部算子的 `input`，padding 不好做，有需求，但相对也少。

模型的 `input` 的常见 padding 方案：

| 方案 | 说明 | 分析 |

| --- | --- | --- |

| `Naive padding` | 把变化的维度，padding 到最大长度。 | 1. 问题：`Shape length` 变化很大时，计算效率非常低。 |

| 多个模型，分桶 | 1. 准备 `N` 个模型，最大长度 `64`，`128`，`512`，`2048`。 | 1. 使用最广泛。一般，模型只需要训练一个最大的即可。 |

| 动态编译 | 1. 第一次执行时，不优化。 | 1. 一些 `AI compiler`、算子库开始采用。不用提前调研用户需求。`cann` |

| `crop` 数据 | 针对特别长的 `input`，数据截断不处理。 | 1. 作为系统健壮性的兜底方案，一般都会做，区别只是 `threshold`。 |

1. `cv` 场景把 `225*226` 的图片 `crop` 成 `224 * 224`。

2. `Bert` 模型按 `max length 512` 截断。

Padding 的主要难点

1. 引入较少/更少的无效数据。如表格里的方案。除了占用 `memory` / `bandwidth`，也可能增加 `compute` 时间。

2. Padding 策略不能（明显）影响模型的精度表现。

3. 新策略，一般需要数学、算法实验论证。有工作量和研发成本。

4. 尺寸的局限性。以 `CV` 模型为例，`700*700` 的图片，padding 成 `800*800`，一般是可以的，但如果 padding 成 `1600*1600`，算法精度可能急剧下降。

5. Padding 导致的内存搬运 or 不连续。

6. `Tensor` 一般是高维的，但内存里通常是一维的排列。比如，灰度图的长宽是 2 维，`RGB` image 的 3 个 `channel`。

7. `CPU` 的计算通常不是瓶颈，在 `CPU` 上做 padding，计算效率的影响会小一些。

以二维数据（`image`）为例，多种 padding 策略，算法精度、计算效率的影响是很丰富的。

![](img/6538a2f3fb2a7616de1d8c0c7e8e3a9a.png)

### 2. 消除“伪”动态 shape

很多看似是动态的模型，在推理时，完全等价于静态模型。

推理框架、`AI compiler` 可以自动的静态化，模型精度无损失。

典型场景：

1. 动态 `batch size` 引入 `shape` 等额外算子。如果固定 `batch size`，可以消除掉动态性。

2. 能静态化的算子。比如，`flatten`, `gather`, `expand`, `slice` 等。

以 `flatten` 为例。

1. `flatten` 有 2 个输入：`data` 和 `axis`。`axis` 取值不一样，`Output shape` 很可能会变，即，动态 `shape`。

2. 推理时，算子的 `axis` 一般是 `constant` 参数，不会变。即，可以处理成静态 `shape`。

| `Data` (`Input`) `shape` | `axis` | `Output shape` |

| --- | --- | --- |

| `(2, 3, 4, 5)` | `0` | `(1, 120)` |

|  | `1` | `(2, 60)` |

|  | `2` | `(6, 20)` |

|  | `3` | `(24, 5)` |

### 3. Shape Constraint - 缩小动态的范围

推理框架、`AI compiler` 尝试的另一个方向。

有些“真”动态的算子，可以通过前后算子推演出 `shape` 的约束关系。

`AI compile` 知道算子内存的 `upper bound`，可以明显缩小搜索空间。

比如：

1. `Int8` 推理时，`unique` 算子的输出，`shape` 的 `upper bound` 是 `min(input length, 255)`。

2. `A + B = C` 场景，`Add` 算子的输入 `vector A` 和 `vector B`，`shape` 是相同的。

### 5. Control Flow 的支持

分 2 种情况：

1. 尝试消除 `Control flow`。

2. 基本就是编译原理、`cpu pipeline` 中 `control flow` 消除的方法。

3. 比如，`loop unrolling` (循环展开), `Polyhedral Model` （多面体模型）

4. 消除不掉的：

   - `if-else`、`switch` 等条件选择分支，每个分支都编译，`cache` 起来。`runtime` 动态选择。
   - `Loop` / `while` 等结束条件动态的循环，暂不知道加速方法。也比较少见。

以 `Polyhedral Model` 为例，

当 `if...else` / `loop` 的判断条件全部已知时，实际触发 `compute` 计算的，是 `N` 维空间里的一个 `subset` 子集。

`Compilation time` 可以精确枚举 `subset` 子集，`transform` 成 1 层的 `loop` 循环。

然后 `loop unrolling` (循环展开)，消掉了所有的 `control flow` 指令。

详见 `https://www.cse.iitk.ac.in/users/swarnendu/courses/autumn2020-cs610/intro-to-polyhedral-model.pdf`

## 业界 compiler 调研

主要看了 3 条线：

1. `NV` 的 `TensorRT`

2. `MLIR`。阿里的 `BladeDISC`。

3. `TVM` 方向。`relax`，`Amazon` 的 `Nimble` 和 `DietCode` 2 个工作。

具体的实现上，主要是 3 类工作。前 2 个是辅助，最后一个是目的。

1. `Shape` 的语义编码 & `IR` 中的传递。

2. `shape function`。运行时的 `shape inference`、`shape` 估算、上下界约束。

3. 调度。

4. 单算子分：计算密集型、访存密集型。另外，还有算子融合、自动 `codegen` 等。

5. 基本都是拿时间换空间，比如，申请个稍微偏大的内存（冗余计算）、保持多个版本的 `cache`（知识库）。

解决方案，本质都是：静态化。区别只是 `coding` 的工作量、`overhead` 的来源和大小。

1. `Padding` / `mask`

2. 预分配更大的内存，比如，`NMS`。

数学的说，

`static shape` -> `global observation`

`Dynamic shape` -> `partial observation`，部分可观察。难以实现全局最优解。

求解的方法和难度，完全不一样。

### TVM - Relax

`https://zhuanlan.zhihu.com/p/627449108?utm_id=0`

（`TVM`）Dynamic shape 目标

1. `shape` 可以通过 `symbolic` 表达，并且将 `shape` 推断作为一等公民支持

```
@R.function
def shape_example(x: R.Tensor[(n, 2, 2), "f32"]):
    with R.dataflow():
        lv0: R.Tensor[(n, 4), "f32"] = R.reshape(x, (n, 4)) 
        lv1: R.Tensor[(n * 4,), "f32"] = R.flatten(lv0)
        lv2: R.Shape = (n * 4,)
        lv3: R.Shape = R.call_packed("myshape_func", lv2)
```

这段代码可以体现了想达到的效果：

1）`shape` 可以在 `IR` 语言中单独作为表达式存在了（`lv2`），以前在 `relay` 中 `shape` 必须作为 `tensor` 的附属；

2）`shape` 中可以包含 “`n`” 这样的未知变量了，这类变量不需要在编译时确定具体数值，而是可以在运行时再确定。而且 “`n`” 虽然未知但并不会完全破坏 `shape` 的语义，比如我们可以推断出 `R.Tensor[(n, 4), "f32"]` 需要的存储空间是 `R.Tensor[(n, 2), "f32"]` 的两倍。

动态 `rank` 支持吗？看起来不支持。

D2: `Shape refinement`

参考以上的例子，在 `V2` 的 `case` 中，`lv5` 的 `shape` 直接用 `None` 表示，意思是 `lv5` 对应的 `op` 是 `data dependent`，编译时无法推断 `shape`，只能在运行时获取。但是后面的程序希望这个 `shape` 能给出一个 `symbolic` 的表达，以支持后面程序潜在的优化，这就需要 “`match_shape`” 了。

```
value = match_shape(lhs, pattern)
```

`lns` 既可以是 `tensor`，也可以是 `shape`。`pattern` 是一个带符号的表达式。

值得一提的是 `match_shape` 使得 `relax` 对于数据的表达更加灵活，比如稀疏的数据。

编译时无需为 `shape` 负责，其实也负责不了，所以它们的结果也无法提前分配内存，需要运行时动态分配。这种状态在官方文档中称作 “`no shape computation land`”。

### Nimble - AWS 基于 TVM

将动态 `shape` 模型的运行时控制逻辑预构建为 `VM` 解释执行

1. 支持动态 `shape` 的编译优化框架，包括类型系统、内存优化、算子生成等；

2. 基于 `Virtual Matchine` 的轻量级跨平台 `runtime`。

支持动态 `shape` 的额外开销：
