
### 降低认知负荷

**降低认知负荷：** 让 LLM 只需关注当前任务相关的少数几个工具，而不是从庞大的列表中选择，可能提高其决策的准确性和效率。

### § 4.2.2 实现机制

实现动态发现与选择通常涉及以下机制：

1. **基于描述的检索与选择 （Description-based Retrieval & Selection）** :

**核心思想：** 将每个可用工具都配上一个**高质量的自然语言描述**，详细说明其功能、适用场景、输入参数和预期输出。将这些工具描述存储在一个可检索的工具库 （Tool Library） 中（例如，向量数据库、简单的文本索引）。

**流程：**

1. 当 Agent 需要执行某个子任务或获取某种信息时，它将当前的需求（例如，“查询北京明天的天气预报”）表述为一个查询 （Query）。

1. 使用这个查询，在工具库中进行**语义搜索或关键词搜索**，检索出描述与查询意图最匹配的几个候选工具。

1. Agent （LLM） 分析这些候选工具的描述，最终选择一个最合适的工具来调用。

**关键：** 工具描述的质量和检索算法的准确性至关重要。RAG 技术在此处被反向应用于工具发现。

1. **LLM 生成即时工具 （LLM-Generated Just-in-Time Tools）** :

**概念：** 对于一些相对简单的、可以通过代码实现的特定需求（例如，执行一个特殊的数学计算、格式化一段文本），如果现有工具库中没有完全匹配的，Agent （LLM） 可以尝试动态生成一个满足该需求的一次性代码片段（通常是 Python），然后请求执行这个临时工具。

**优势：** 提供了极大的灵活性，使得 Agent 能应对一些未预见的、需要少量定制逻辑的情况。

**挑战：** LLM 生成的代码可能存在错误或安全风险，需要非常可靠的代码审查和沙箱执行环境。目前仍处于探索阶段。

1. **标准化发现协议 （Standardized Discovery Protocols）** :

**如 `MCP`:** 模型上下文协议 （MCP） 等标准化接口，其设计就包含了能力发现 （Capability Discovery） 机制。Agent 可以通过协议查询连接到的 `MCP` 服务器，动态获取该服务器提供的可用工具 （Tools）、资源 （Resources） 和提示 （Prompts） 列表及其描述。

### § 4.2.3 框架与实现支持

**Agent 开发框架：** `LangChain`、`LlamaIndex` 等框架通常提供了注册大量工具并进行检索式选择的机制（例如，通过 `ToolRetriever` 或类似组件）。

**LLM 能力：** 底层 LLM 需要具备较强的理解能力，才能准确地从描述中判断工具的功能并做出选择。

动态工具发现与选择是构建能够适应庞大、不断变化的工具生态系统的高级 Agent 的关键技术，它将 Agent 从使用固定工具列表的“瑞士军刀”转变为能够按需查找和使用“专业工具箱”的“工匠”。

## § 4.3 高级工具编排：顺序、并行与组合交互

许多复杂的任务并非调用单个工具就能完成，而是需要 Agent 编排 （Orchestrate） 多个工具的调用，管理它们之间的依赖关系、执行顺序，并整合它们的结果。高级工具编排是实现复杂工作流自动化的核心。

### § 4.3.1 编排模式

根据任务的结构和工具间的关系，存在多种编排模式：

1. **顺序执行 （Sequential Execution / Chaining）** :

**机制：** 一个工具的输出直接作为下一个工具的输入。工具按严格的线性顺序执行。

**例子：** 先调用 `get_customer_id(name)` 获取客户 ID，再用 ID 调用 `get_order_history(customer_id)` 查询订单历史。

**适用场景：** 任务步骤具有明确的先后依赖关系。

**实现：** 可以通过 Agent 的内部逻辑（LLM 规划）或使用专门的顺序执行器（如 `LangChain` 的 `SequentialChain` 或 Google ADK 的 `SequentialAgent`）来实现。

1. **并行执行 （Parallel Execution）** :

**机制：** 当多个工具调用或子任务**相互独立**时，可以同时（并发地）执行它们，以缩短总的处理时间。

**例子：** 同时查询北京、上海、广州三个城市的天气；或者同时从三个不同的新闻源 API 获取信息。

**适用场景：** 需要从多个独立来源收集信息，或者可以将大任务分解为互不干扰的子任务时。

**实现：** 需要框架或底层执行环境支持并发（如 `Python` 的 `asyncio`， `multithreading`， 或专门的并行 Agent/工具，如 Google ADK 的 `ParallelAgent`， `Spring AI` 的并行函数调用）。管理并发执行和结果收集需要额外的逻辑。`LLMCompiler` 等研究专注于优化 LLM 触发的并行 API 调用。

1. **条件执行 （Conditional Execution）** :

**机制：** 根据某个工具的输出结果或当前状态，有条件地决定是否调用下一个工具或选择调用哪个工具。

**例子：** 先调用 `check_inventory(product_id)` 检查库存，如果库存充足 （`result > 0`），则调用 `create_order(product_id, quantity)`；否则，调用 `notify_restock_interest(product_id, user_id)`。

**实现：** 通常需要 Agent （LLM） 或专门的控制流逻辑（如 `LangGraph` 中的条件边）来进行判断和路由。

1. **组合/聚合 （Composition / Aggregation）** :

**机制：** 将来自多个工具（可能是顺序、并行或条件执行的结果）的输出整合、处理或合成，以形成最终答案或驱动下一步决策。

**例子：** 获取了 A 公司的财报（工具 1）和 B 公司的财报（工具 2）后，将两者数据输入给 LLM（作为“工具”或直接推理）进行比较分析。

**实现：** 可以由 LLM 负责最终的综合分析，也可以通过专门的数据处理工具或函数来聚合结果。

### § 4.3.2 实现工具编排的框架与方法

**Agent （LLM） 驱动的动态编排：** 让 Agent 的核心 LLM 负责分析任务、规划步骤（包括决定调用顺序、是否并行、条件判断），并根据工具执行结果动态调整。这是最灵活但也最依赖 LLM 规划能力的方法。

**基于图的编排 （Graph-based Orchestration）：** 使用像 `LangGraph` 这样的框架，将工具调用、LLM 推理、条件判断等表示为图中的节点 （`Nodes`），将执行流程和数据流表示为边 （`Edges`）。图结构可以清晰地表示顺序、并行、条件和循环等复杂逻辑，提供了更结构化、更可控的编排方式。

**角色化协作编排 （Role-based Collaboration）：** 使用像 `CrewAI` 这样的框架，将任务分解给具有特定角色的 Agent，每个 Agent 可能负责调用特定的工具。通过定义 Agent 之间的协作流程（如顺序传递任务）来实现隐式的工具编排。

**专用工作流引擎：** 对于流程非常固定的场景，也可以使用传统的工作流引擎（如 `Airflow`， `Prefect`）来编排包含 Agent 工具调用的任务。

选择哪种编排方法取决于任务的复杂度、对灵活性 vs。 可控性的要求，以及开发团队的技术偏好。

## § 4.4 健壮的工具错误处理：重试、回退与告知 Agent

工具调用是 Agent 与外部世界交互的桥梁，而这个桥梁可能并不总是畅通。网络问题、`API` 限流、服务器错误、无效输入、外部服务变更等都可能导致工具调用失败。健壮的错误处理机制对于保证 Agent 在面对这些不可避免的问题时能够继续运行或优雅失败至关重要。

### § 4.4.1 错误检测与分类

Agent 首先需要能够检测到工具调用失败，并最好能区分错误的类型，因为不同的错误类型需要不同的处理策略。常见的检测方法包括：

+ 检查 API 调用的 HTTP 状态码 （例如，`4xx` 代表客户端错误，`5xx` 代表服务器端错误，`429` 代表速率限制）。

+ 设置合理的网络 `Timeout` 机制。

+ 解析工具或 API 返回的错误消息体。

+ 捕获执行本地函数时抛出的 `Exceptions`。

### § 4.4.2 核心错误处理策略

一旦检测到错误，可以采取以下一种或多种策略：

1. **重试机制 （Retry Mechanisms）** :

**适用场景：** 针对 `Transient` 错误，如网络抖动、服务器临时过载 （`503 Service Unavailable`）、或速率限制 （`429 Too Many Requests`）。

**策略：**

+ **简单重试：** 立即或间隔固定时间后重试。

+ 指数退避 （`Exponential Backoff`）: 每次重试的等待时间指数级增加（例如 `1s`， `2s`， `4s`， `8s`...），避免在服务持续有问题时不断冲击。

+ **增加抖动 （`Jitter`）:** 在退避等待时间上增加一个小的随机量，防止多个 Agent 实例在完全相同的时间点同步重试，加剧负载（"惊群效应" `Thundering Herd`）。

+ **实现：** 可以使用 `tenacity` 等 Python 库轻松实现复杂的重试逻辑。需要设定最大重试次数或总重试时间限制。

1. **回退到备选方案 （Fallback to Alternatives）** :

**机制：** 如果主要工具持续失败或返回无效结果，尝试调用一个预定义的备选工具 （`Alternative Tool`），该工具提供类似的功能但可能来源或实现方式不同。

**例子：** 如果主天气 API 失败，尝试调用另一个备用天气 API；如果 RAG 知识库检索失败，尝试调用 Web 搜索工具。

**前提：** 需要在 Agent 设计时预先定义好工具之间的替代关系。

1. **使用缓存数据 （Use Cached Data）** :

**机制：** 如果允许使用稍微过时的数据，并且之前成功调用过该工具并缓存了结果，可以在工具调用失败时返回缓存的数据。

**适用场景：** 对于变化不那么频繁或对实时性要求不极高的信息（如公司地址、产品描述等）比较适用。

**注意：** 需要明确缓存的有效期 （`TTL` - Time To Live）。

1. **优雅降级 （Graceful Degradation）** :

**机制：** Agent 认识到无法获取所需信息后，调整其目标或回答策略，尝试在信息不完整的情况下继续任务或给出部分答案，并明确告知用户哪些信息无法获取。

**例子：** "我无法获取最新的销售数据，但根据上个月的报告..."

1. **将错误信息反馈给 Agent （Inform the Agent）** :

**核心步骤：** **必须**将工具调用失败的事实以及（如果可能）具体的错误信息，作为一次观察 （`Observation`） 或 `role: tool` 的消息，反馈给 Agent 的核心 LLM。

**目的：** 让 LLM 能够理解发生了什么错误，并在其下一步的 `Thought` 或 `Planning` 中考虑这个错误。

**效果：** LLM 可能会决定：

+ **修正输入参数**后重试该工具。

+ **选择另一个工具**。

+ **调整计划**以绕过这个失败的步骤。

+ **向用户请求**更多信息或指示。

+ **承认失败**并告知用户无法完成任务。

**实现：** 需要精心设计传递给 LLM 的错误消息格式，使其既简洁又能提供足够的信息供 LLM 理解。

1. **熔断器模式 （Circuit Breaker Pattern）** :

**机制：** 为了防止 Agent 不断地重试一个持续失败的工具（例如，外部服务完全宕机），可以实现熔断器。当某个工具连续失败达到一定次数后，熔断器“跳闸 （`trips`）”，在接下来的一段时间内，所有对该工具的调用都会被立即阻止（直接返回错误或默认值），给外部服务恢复的时间。一段时间后，熔断器可以尝试进入“半开 （`half-open`）”状态，允许少量请求通过，如果成功则恢复闭合，否则继续保持断开。

**价值：** 保护 Agent 自身资源（避免无效等待和重试），也避免对下游故障服务造成更大压力。

健壮的错误处理是生产级 Agent 的必备特性，它显著提高了 Agent 在面对现实世界不可靠性时的生存能力和用户体验。

## § 4.5 工具使用的安全风险与最佳实践 （深度）

赋予 Agent 调用外部工具的能力，如同给了它一把打开外部世界大门的钥匙，这在释放巨大潜力的同时，也引入了严峻的安全风险。确保工具使用的安全性是设计和部署 Agent 系统时的首要考虑因素之一。

### § 4.5.1 威胁模型：Agent 工具使用的安全风险

Agent 工具使用面临的主要安全威胁包括：

1. **间接提示注入 （Indirect Prompt Injection）** :

**机制：** 攻击者将恶意的指令隐藏在 Agent 可能通过工具获取的外部数据源中（例如，一个被 Agent 抓取的网页、一个被 Agent 读取的文档或邮件、甚至另一个被控 Agent 的回复）。当 Agent 将这些包含恶意指令的数据纳入其 `Prompt` 上下文时，这些指令可能被核心 LLM 执行，导致 Agent 偏离其原始任务，执行非预期操作。

**危害：** 可能导致数据泄露、执行恶意代码（如果 Agent 有代码执行工具）、传播错误信息、绕过安全策略等。这是极其隐蔽且危险的攻击方式。

1. **不安全的工具输出处理 （Insecure Output Handling）** :

**机制：** 工具返回的输出本身可能包含恶意内容，例如跨站脚本 （`XSS`） 载荷、恶意链接、或者格式错误的数据。如果 Agent 或前端应用在处理或展示这些输出时没有进行充分的清理 （`Sanitization`） 和验证 （`Validation`），可能导致安全漏洞。

**危害：** 可能导致用户浏览器被攻击 （`XSS`）、用户被诱导点击恶意链接、系统因处理错误数据而崩溃等。

1. **不安全的工具/插件设计 （Insecure Tool/Plugin Design）** :

**机制：** Agent 调用的工具（无论是内置的、第三方的还是自定义的）本身可能存在安全漏洞，例如输入验证不足、权限控制不当、硬编码密钥、存在命令注入或 `SQL` 注入漏洞等。

**危害：** 攻击者可能直接利用工具的漏洞来攻击底层系统或获取未授权访问。

1. **过度授权/权限提升 （Excessive Agency / Privilege Escalation）** :

**机制：** 赋予 Agent 或其使用的工具过高的权限，超出了完成其任务所需的最小范围。例如，一个只需要读取数据库的 Agent 被赋予了写入权限；或者一个 Agent 如果被 `Prompt` 注入攻击成功，能够调用其本不应调用的高权限工具。

**危害：** 一旦 Agent 被误导或控制，可能造成严重破坏，如删除数据、修改配置、访问敏感信息等。

1. **数据泄露 （Data Exfiltration）** :

**机制：** 被控制的 Agent 或存在漏洞的工具可能被用来窃取和发送敏感数据（如用户个人信息、公司内部数据、`API` 密钥等）到攻击者控制的外部服务器。

1. **拒绝服务 （Denial of Service， `DoS`）** :

**机制：** 攻击者可能通过构造大量请求或触发计算密集型工具调用，耗尽 Agent 系统或其依赖服务的资源，导致服务不可用。

### § 4.5.2 安全最佳实践与防御策略

应对上述威胁需要采取多层次的纵深防御策略：

1. **严格的输入/输出验证与清理 （Rigorous I/O Validation & Sanitization）** :

**输入验证：** 在将用户输入或任何外部数据传递给 LLM 或工具之前，进行严格的格式检查、类型检查和内容过滤，拒绝或清理可疑输入。

**工具参数验证：** 在执行工具调用前，再次验证 LLM 生成的参数是否符合工具的预期格式和约束。

**输出清理 （Crucial for `Indirect Injection`）: 绝不能直接信任来自外部工具（尤其是访问互联网或用户生成内容的工具）的输出。在将工具返回的数据整合进 LLM 的 `Prompt` 上下文之前，必须进行彻底的清理和转义，移除任何潜在的指令性语言、脚本代码、或可疑的控制字符。只将数据作为纯粹的“信息”而非“指令”提供给 LLM。

**前端展示清理：** 在将 Agent（尤其是可能包含工具输出的）最终响应展示给用户时，确保前端界面进行了适当的 `HTML` 转义等处理，防止 `XSS` 攻击。

1. **最小权限原则 （Principle of Least Privilege）** :

**Agent 权限：** Agent 本身应只被授予完成其预定任务所需的最小权限集合。

**工具权限：** 每个工具应只拥有执行其单一功能所需的最小权限。例如，数据库查询工具应使用只读账户（如果可能）。

**`API Key` 权限：** 为 Agent 或特定工具生成的 `API Key` 应限制其可访问的资源范围和操作类型。

**定期审计：** 定期审查和更新权限设置。

1. **环境隔离与沙箱化 （Isolation & Sandboxing）** :
