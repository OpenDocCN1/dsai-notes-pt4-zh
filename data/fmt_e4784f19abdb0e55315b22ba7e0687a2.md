## 第一部分：基本概念和功能

### Git 介绍

#### 版本控制系统

版本控制系统（Version Control System，简称 VCS）是一种程序或一系列程序，用于跟踪文件集合的变化。

**版本控制系统的主要目标包括：**

+ 轻松召回早期版本：VCS 的一个目标是能够轻松地召回单个文件或整个项目的早期版本。

+ 促进团队协作：VCS 的另一个目标是允许多名团队成员同时处理一个项目，即使是在同一个文件上工作，也不会相互影响。

通过使用版本控制系统，你可以实现以下功能：

+ 查看所有更改：能够查看项目中的所有更改、更改发生的时间以及由谁进行了更改。

+ 附带更改消息：可以在每次更改时附带一条消息，解释更改的原因。

+ 创建分支：可以创建“分支”（branches），在其中进行实验性更改。这个功能使得可以同时处理几组不同的更改（例如，新功能或错误修复），可能由不同的人完成，而不会影响主分支。之后，可以将需要保留的更改合并回主分支。

+ 附加标签：可以为版本附加一个标签，例如，标记一个新的发布版本。

**相关概念：**

+ 软件配置管理（SCM）：VCS 的另一个名称是软件配置管理（SCM）系统。这两个术语经常可以互换使用，实际上 Git 的官方文档就位于 `git-scm.com`。从技术上讲，版本控制只是 SCM 实践中的一部分。

+ 不限于软件项目：VCS 除了用于软件项目外，还可以用于其他项目，包括书籍和在线教程。

**Git 作为一种 VCS：**

+ `Git` 是一种快速、多功能、高度可扩展的免费开源版本控制系统。它的主要作者是 Linux 的创建者 Linus Torvalds。

+ 分布式版本控制：早期的 VCS，如 `CVS`、`Subversion`（`SVN`）和 `Perforce`，使用集中式服务器存储项目历史记录，这可能导致单点故障。而 `Git` 是“分布式”的，这意味着项目的完整历史记录同时存储在客户端和服务器上。你可以在没有网络连接的情况下编辑文件，在本地进行提交，并在连接可用时与服务器同步。即使服务器出现故障，你仍然拥有项目的本地副本。

+ 工作原理：`Git` 通过记住对文件的更改来工作，就像它正在对文件系统进行“快照”一样。

+ 核心操作：`Git` 的核心操作包括 `git status`（查看工作树状态）、`git add`（暂存更改）、`git commit`（将暂存的更改保存为快照，每次提交都有唯一的身份，包含作者、日期、评论等信息）和 `git log`（查看以前提交的信息）。

#### 分布式版本控制系统

分布式版本控制系统（Distributed Version Control System，简称 DVCS）是一种版本控制系统，它与早期的集中式版本控制系统有所不同。

**分布式版本控制的特点包括：**

+ 项目历史记录的存储方式：`Git` 就是一个“分布式”版本控制系统。这意味着项目的完整历史记录同时存储在客户端和服务器上。

+ 无需网络连接即可工作：由于历史记录存储在本地，开发者可以在没有网络连接的情况下编辑文件，并在本地进行提交。当网络连接可用时，再与服务器同步更改。

+ 更高的韧性：如果服务器出现故障，你仍然拥有项目的本地副本，因为完整的历史记录也保存在本地客户端。

+ 与集中式 VCS 的对比：早期的版本控制系统，如 `CVS`、`Subversion`（`SVN`）和 `Perforce`，都使用一个集中式服务器来存储项目的历史记录。这种集中化意味着单个服务器也可能成为单点故障。

简而言之，分布式版本控制系统赋予了开发者更大的灵活性和项目韧性，因为每个客户端都拥有项目的完整副本。

#### Git 的核心操作和功能

`Git` 通过一系列核心操作和功能来跟踪和保存文件更改，其工作原理类似于对文件系统进行“快照”。

以下是 `Git` 跟踪和保存文件更改的核心操作和功能：

1. 跟踪更改的基本理念 `Git` 的工作方式是记住对文件的更改，就像它正在对文件系统进行“快照”一样。版本控制系统（VCS）的一个目标是能够轻松地召回单个文件或整个项目的早期版本。

1. `git status` 命令

+ 这是第一个也是最常用的 `Git` 命令之一。

+ `git status` 命令显示工作树的状态（以及暂存区的状态）。

+ 它让你能够看到 `Git` 当前正在跟踪哪些更改，从而决定是否要让 `Git` 进行另一次快照。

1. `git add` 命令

+ `git add` 命令用于告诉 `Git` 开始跟踪某些文件中的更改。

+ 技术术语是“暂存（staging）”这些更改。

+ 你将使用 `git add` 来暂存更改，为提交做准备。

+ 所有已添加但尚未提交的文件中的更改都存储在“暂存区（staging area）”中。

1. `git commit` 命令

+ 一旦你为提交暂存了一些更改，就可以通过调用 `git commit` 命令将你的工作保存为快照。

+ “提交（Commit）”既是动词也是名词。作为动词，提交更改意味着你将文件、目录或其他“内容”的副本作为新版本放入仓库中。作为名词，一次提交是一个小数据块，它赋予你提交的更改一个唯一的身份。

+ 保存到提交中的数据包括作者的姓名和电子邮件地址、日期、关于你做了什么（以及为什么）的评论、可选的数字签名，以及前一次提交的唯一标识符。

+ “提交”意味着你正在提交所做的更改，以便其他人最终也能看到它们。

+ 一个“提交对象（commit object）”代表工作树的一个特定版本。

1. `git log` 命令

+ `git log` 命令允许你查看以前提交的信息。

+ 每次提交都附带一条消息（提交消息），`git log` 命令会打印最近提交的信息，例如它们的时间戳、作者和提交消息。

+ 这个命令可以帮助你跟踪你一直在做什么以及保存了哪些更改。

1. 核心术语与概念

+ 工作树（Working tree）：包含正在处理的项目的嵌套目录和文件集。

+ 仓库（Repository/Repo）：位于工作树顶层的目录，`Git` 在其中保存项目的所有历史记录和元数据。

+ 哈希（Hash）：`Git` 使用 160 位长的哈希值来表示文件或其他对象的内容。使用哈希的一个优点是，`Git` 可以通过对其内容进行哈希并将其结果与先前的哈希进行比较来判断文件是否已更改。即使文件的时间戳改变了，但如果哈希值没有改变，`Git` 也知道文件内容没有改变。

1. `git help` 命令

+ 你可以使用 `git help` 命令轻松获取关于所有已学命令及更多命令的信息。

+ 每个命令都有其自己的帮助页面，你可以通过键入 `git <command> --help` 来查找，例如 `git commit --help` 会显示关于 `git commit` 命令及其使用方法的更多信息。

通过这些机制，`Git` 能够系统地跟踪文件的每一次更改，将它们保存为可追溯的快照，并提供查看历史记录的功能。

#### Git 和 Github 的联系和区别

`Git` 和 `GitHub` 之间存在着显著的区别，尽管它们紧密相关：

+ `Git` 是一种分布式版本控制系统（DVCS）：

+ `Git` 是一个快速、多功能、高度可扩展的免费开源版本控制系统（VCS）。

+ 它的主要作者是 Linux 的创建者 Linus Torvalds。

+ 作为一种 DVCS，项目的完整历史记录存储在客户端和服务器上。这意味着开发者可以在没有网络连接的情况下编辑文件，在本地进行提交，并在连接可用时与服务器同步。

+ `Git` 通过记录文件更改的方式工作，就像对文件系统进行“快照”一样。

+ 它提供了一种使用一个或多个本地分支并将它们推送到远程仓库的方式。

+ `Git` 命令包括 `git status`（显示工作树和暂存区的状态）、`git add`（告诉 `Git` 开始跟踪文件更改并暂存这些更改）、`git commit`（将暂存的更改保存为快照，每次提交都有唯一的身份，包含作者、日期、评论等信息）、`git log`（查看以前提交的信息，如时间戳、作者和提交消息）和 `git help`（获取命令信息）。

+ `Git` 功能强大，可以通过命令行界面完全访问其所有功能。

+ `GitHub` 是一个基于 `Git` 技术的云平台：

+ `GitHub` 是一个以 `Git` 为核心技术的云平台。

+ 它简化了项目协作过程，并提供了一个网站、更多的命令行工具以及开发者和用户可以协同工作的整体流程。

+ `GitHub` 充当了 `Git` 中提到的远程仓库。

+ `GitHub` 提供了一些关键功能，以增强团队协作和项目管理，包括：

+ 议题（Issues）

+ 讨论（Discussions）

+ 拉取请求（Pull requests）

+ 通知（Notifications）

+ 标签（Labels）

+ 操作（Actions）

+ 分支（Forks）

+ 项目（Projects）

简而言之，`Git` 是底层工具和版本控制系统，而 `GitHub` 是一个基于 `Git` 构建的平台，它提供了托管远程仓库、协作功能和图形界面来简化开发流程。

### Github 简介

#### Github 基础构件

`GitHub` 建立在 `Git` 的基本概念之上，并在此基础上增加了协作工具、自动化功能和用户友好的网页界面。以下是其核心组件：

+ `Git`：作为基础，`Git` 是一个分布式版本控制系统，允许开发者跟踪代码变更、协同工作并管理版本历史。

+ 仓库（Repositories）：仓库是项目的核心组织单元，包含所有项目文件及其修订历史。它们是管理工作、跟踪变更以及与他人协作的关键部分。仓库可以是公开的（对所有人可见）或私有的（仅限授权用户访问）。

+ 分支（Branches）：分支是 `GitHub` 体验的重要组成部分，它允许用户在不影响默认分支（通常是主分支）的情况下进行修改。分支提供了一个安全的实验空间，用户可以在其中尝试新功能或修复问题，直到准备好合并。

+ 提交（Commits）：提交是对分支上一个或多个文件的变更。每个提交都有唯一的 ID、时间戳和贡献者，无论是通过命令行还是 `GitHub` 网页界面创建。提交提供了清晰的审计跟踪，便于审查文件历史或相关项（如议题或拉取请求）。文件在 `Git` 仓库中经历不同的状态，包括未跟踪（Untracked）和已跟踪（Tracked），其中已跟踪文件又分为未修改（Unmodified）、已修改（Modified）、已暂存（Staged）和已提交（Committed）等子状态。

+ 拉取请求（Pull Requests）：拉取请求是用于表示一个分支上的提交已准备好合并到另一个分支的机制。提交拉取请求的团队成员会邀请一名或多名评审员验证代码并批准合并。评审员可以在拉取请求上评论变更、添加自己的变更或用于进一步讨论。`GitHub` 也支持草稿拉取请求（Draft Pull Requests），允许在代码尚未准备好审查时就开启拉取请求。

+ `GitHub Flow`：这是一种简单的工作流程，通过分支、拉取请求和合并，帮助团队安全地进行和分享变更，非常适合尝试想法和团队协作。其流程包括创建分支、进行更新、开启拉取请求邀请反馈、根据反馈进行更新、获得批准并合并到主分支，最后删除分支以保持仓库整洁。

+ `Git Flow`：作为 `GitHub Flow` 的替代方案，`Git Flow` 是一种更结构化的分支模型，常用于发布驱动的环境，它使用多种长期和临时分支，如 `master`、`develop`、`feature/`、`release/`和 `hotfix/`等。

#### Github Flow 流程

`GitHub flow` 是一种简单的、帮助您安全地进行和分享变更的工作流程。它非常适合尝试新想法以及使用分支、拉取请求和合并与团队协作。`GitHub flow` 是建立在 `Git` 的基本概念之上的。

`GitHub flow` 的核心组件包括：

+ 分支（Branches）：分支是 `GitHub` 体验的重要组成部分，它允许您在不影响默认分支（通常是主分支）的情况下进行修改。分支提供了一个安全的实验空间，您可以在其中尝试新功能或修复，直到准备好将变更合并回默认分支。

+ 提交（Commits）：提交是对分支上一个或多个文件的变更。每个提交都由唯一的 ID、时间戳和贡献者跟踪，无论它是在命令行还是通过 `GitHub` 网页界面创建的。提交提供了清晰的审计跟踪，便于审查文件历史或相关项。

+ 拉取请求（Pull Requests）：拉取请求是用来表示一个分支上的提交已准备好合并到另一个分支的机制。提交拉取请求的团队成员会邀请一名或多名评审员验证代码并批准合并。评审员可以在拉取请求上评论变更、添加自己的变更或用于进一步讨论。`GitHub` 也支持草稿拉取请求，允许您在代码尚未准备好审查时就开启拉取请求。

`GitHub flow` 的工作流程

`GitHub flow` 的步骤如下：

1. 创建分支：首先创建一个分支，以便您的变更、功能或修复不会影响主分支。

1. 进行更新：在该分支中进行您的更新。如果您的工作流程支持，您可以在合并之前部署变更进行测试。

1. 开启拉取请求：然后，开启一个拉取请求以征求反馈并开始审查。

1. 根据反馈更新：接着，审查评论并根据团队的反馈进行任何必要的更新。

1. 获得批准并合并：最后，一旦您对自己的变更充满信心，获得批准并将拉取请求合并到主分支。

1. 删除分支：合并后，删除该分支以保持仓库整洁并避免使用过时的分支。

值得注意的是，`GitHub flow` 是一种为持续交付设计的轻量级工作流程，而 `Git flow` 是一种更结构化的分支模型，通常用于发布驱动的环境。对于许多使用 `GitHub` 的团队来说，`GitHub flow` 更简单、更快速。

#### 团队协作功能

协作是 `GitHub` 一切工作的核心。`GitHub` 提供了丰富的工具来帮助团队高效协同工作，减少延迟并简化工作流程。

**议题（Issues）**

`GitHub` 议题用于跟踪工作中的想法、反馈、任务或错误。议题可以从多种方式创建，包括任务列表项、项目备注、议题或拉取请求评论、特定代码行或 URL 查询。议题可以分配给特定人员、添加到项目面板、关联到里程碑或应用标签，这些功能有助于有效管理协作并提高议题可见性。议题模板有助于为贡献者保持一致的结构和期望。当一个讨论产生需要跟踪的工作时，可以将其转换为议题。

讨论（Discussions）：

讨论功能适用于不一定与代码相关的对话，如问答、想法或一般反馈。它们支持在共享论坛中进行开放、持续的交流，并可根据仓库可见性设置为公开或私有。仓库维护者可以启用讨论功能，并创建不同类别的讨论，如公告、通用、想法、投票、问答和展示。在问答式讨论中，可以将某个评论标记为问题的答案。重要的讨论可以被置顶（Pinning a discussion）以提高可见性。

**通知和订阅（Notifications and Subscriptions）**

+ 通知帮助用户及时了解仓库和团队的重要活动。用户可以订阅特定议题、拉取请求、Gist、仓库活动或工作流状态的通知。当用户参与对话（评论、开启议题、被分配）时，会自动订阅，也可以手动管理订阅。用户可以取消订阅、取消关注或自定义接收通知的类型。

+ `GitHub` 还允许用户通过观察设置（watch settings）过滤通知，包括观察中（Watching）（接收所有活动通知）、未观察（Not watching）（仅在参与或被提及时接收通知）、忽略（Ignore）（不接收任何通知）和自定义（Custom）（微调触发通知的活动类型）。提及（@mentions）：通过使用搜索限定符 `mentions:<username>`，用户可以找到所有提到特定用户的对话。

+ 通知可以通过电子邮件、网页或移动应用接收。

**其他功能**

**Gist**：`Gist` 是 `GitHub` 的一项功能，允许用户以轻量级方式分享代码片段、笔记或其他少量信息。它们本质上是迷你的 `Git` 仓库，支持分支、克隆和版本控制。`Gist` 可以是公开的（Public Gists）（所有人可见且可搜索）或秘密的（Secret Gists）（不可搜索，但知道 URL 的人可以访问）。`Gist` 支持版本控制、克隆、嵌入到网页/博客、Markdown 格式以及轻量级协作。

**维基（Wikis）**：每个 `GitHub` 仓库都配备了一个维基部分，用于托管项目的长篇文档，例如如何使用项目、设计理念或核心原则。维基的访问权限与仓库的读取权限相关。

**AI 赋能功能**：`GitHub Enterprise` 平台通过 AI 赋能的拉取请求和议题增强协作，提高生产力，并通过提供更快的反馈来改善安全性。

**自动化**：平台通过内置的 CI/CD（持续集成和持续交付）工具加速生产力，自动化重复性任务，从而简化工作流程并支持协作。

**GitHub Pages**：用户可以使用 `GitHub Pages` 直接从仓库托管关于自己、组织或项目的网站。它是一个静态网站托管服务，可以将 HTML、CSS 和 JavaScript 文件从仓库中发布为网站。

### 策略和高级工具
