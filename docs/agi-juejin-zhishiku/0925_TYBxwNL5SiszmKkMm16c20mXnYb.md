在最近对大型语言模型 (LLM) 的概述中，Karpathy 将 LLM 描述为一种新型操作系统的内核进程。正如现代计算机拥有 RAM 和文件访问权限一样，LLM 也有一个上下文窗口，可以加载从众多数据源检索到的信息。

![](img/5918cd2927ff76b63a5d2a43e22d6ac6.png)

检索到的信息被加载到上下文窗口中并用于 LLM 输出生成，该过程通常称为检索增强生成 (RAG)。RAG 是 LLM 应用程序开发中最重要的概念之一，因为它是一种将外部信息传递给 LLM 的简单方法，与更复杂的微调相比具有优势。

通常，RAG 系统涉及：确定要检索哪些信息的问题（通常来自用户）、从数据源检索信息的过程以及将检索到的信息作为一部分直接传递给 LLM 的过程提示符。

近几个月来，RAG 方法的范围大大扩展，导致用户在某种程度上对从哪里开始以及如何考虑各种方法产生了过载或困惑。在过去的几个月里，`Langchain` 致力于将 RAG 概念分为几个类别，并为每个类别发布了指南。下面将总结这些概念并介绍一些未来的工作。

![](img/f4bf3fd093181ab92d1a0c15ffcd26e1.png)

## #1 查询转换

考虑 RAG 时要问的第一个问题：我们如何才能使检索对用户输入的变化具有鲁棒性？例如，对于具有挑战性的检索任务，用户问题的措辞可能很糟糕。查询转换是一组专注于修改用户输入以改进检索的方法。

### 查询扩展

举个例子，对于“Red Sox 和 Patriots 谁最近赢得了冠军？” 这个问题，提出两个具体的子问题可以帮助回答：

+ “Red Sox 上次赢得冠军是什么时候？”
+ “Patriots 上次夺冠是什么时候？”

查询扩展将输入分解为子问题，每个子问题都是一个更细的检索挑战。多查询检索器执行子问题生成、检索，并返回检索到的文档的唯一并集。RAG-Fusion 通过对每个子问题返回的文档进行排名来构建。后退提示提供了第三种方法，即生成后退问题，以更高层次的概念或原则为答案综合奠定基础。例如，关于物理的问题可以退回到关于用户查询背后的物理原理的问题（以及 LLM 生成的答案）。

### 查询重写

为了解决框架或措辞不当的用户输入，重写-检索-读取是一种重写用户问题以改进检索的方法。

### 查询压缩

在某些 RAG 应用程序中，例如 `WebLang`（`Langchain` 的开源研究 Agent），用户问题遵循更广泛的聊天对话。为了正确回答问题，可能需要完整的对话上下文。为了解决这个问题，我们使用此提示将聊天记录压缩为最终问题以供检索。

## #2 路由

考虑 RAG 时要问的第二个问题：数据存放在哪里？在许多 RAG 演示中，数据位于单个向量存储中，但在生产环境中通常并非如此。当跨一组不同的数据存储进行操作时，需要路由传入的查询。LLM 可用于有效支持动态查询路由。

## #3 查询构造

考虑 RAG 时要问的第三个问题：查询数据需要什么语法？虽然路由问题采用自然语言，但数据存储在需要特定语法才能检索的关系数据库或图形数据库等来源中。甚至向量存储也利用结构化元数据进行过滤。在所有情况下，查询中的自然语言都需要转换为查询语法以供检索。

![](img/db589233239669e9f817e8b7bba6cc21.png)

### 文本转SQL

相当多的努力集中在将自然语言转换为 SQL 请求上。通过向 LLM 提供自然语言问题以及相关的表格信息，可以轻松完成文本到 SQL；事实证明，开源 LLM 在这项任务上是有效的，可以实现数据隐私。

关系数据库中的混合类型（结构化和非结构化）数据存储越来越普遍；可以使用 `PostgreSQL` 的开源 `pgvector` 扩展来包含嵌入式文档列。还可以使用自然语言与这种半结构化数据进行交互，将 SQL 的表达能力与语义搜索结合起来。

### 文本到密码

虽然向量存储很容易处理非结构化数据，但它们不理解向量之间的关系。虽然 SQL 数据库可以对关系进行建模，但架构更改可能会造成破坏且成本高昂。知识图可以通过对数据之间的关系进行建模并扩展关系类型来解决这些挑战，而无需进行重大修改。对于具有难以以表格形式表示的多对多关系或层次结构的数据来说，它们是理想的选择。

与关系数据库一样，图形数据库受益于使用 text-to-`Cypher` 的自然语言界面，这是一种结构化查询语言，旨在提供匹配模式和关系的可视化方式。

### 文本到元数据过滤器

配备元数据过滤功能的 `Vectorstore` 支持结构化查询来过滤嵌入的非结构化文档。自查询检索器可以使用向量存储中存在的元数据字段的规范，通过元数据过滤器将自然语言转换为这些结构化查询。

## #4 索引

考虑 RAG 时要问的第四个问题：如何设计我的索引？对于向量存储，有相当多的机会调整块大小和/或文档嵌入策略等参数以支持可变数据类型。

### 块大小

`OpenAI` 的 RAG 策略通过在文档嵌入过程中对块大小进行实验而看到的性能显著提升。这是有道理的，因为块大小控制我们加载到上下文窗口（或我们的 LLM 操作系统类比中的 “RAM”）中的信息量。

由于这是索引构建的核心步骤，因此 `Langchain` 有一个开源 `Streamlit` 应用程序，我们可以在其中测试各种块大小以获得一些直觉；特别是，值得检查使用各种分割大小或策略分割文档的位置，以及语义相关的内容是否被不自然地分割。

### 文档嵌入策略

索引设计中最简单、最有用的想法之一是将我们嵌入的用于检索地内容与传递给 LLM 用于答案生产的内容分离。例如，考虑一段包含大量冗余细节的文本。我们可以嵌入一些不同的表示形式来改进检索，例如摘要或小块以缩小嵌入信息的范围。无论哪种情况，我们都可以检索全文以传递给 LLM 。这些可以分别使用多向量和父文档检索器来实现。

多向量检索器也适用于包含文本和表格混合的半结构化文档。在这些情况下，可以提取每个表，生成非常适合检索的表摘要，但将原始表返回给 LLM 进行答案合成。

![](img/d51d1f1993b915ca564e9913eb948493.png)

我们可以更进一步：随着多模式 LLM 的出现，可以使用生成和嵌入图像摘要作为包含文本和图像的文档的图像检索手段之一（见下图）。

这可能适用于多模态嵌入并不希望可靠地检索图像的情况，例如复杂的图形或表格的情况。例如，在 `Langchain` 的食谱中，我们使用这种方法来处理财务分析博客中的数据。然而，我们还有另一本使用开源多模态嵌入的食谱：`OpenCLIP`，用于基于更简单的视觉概念检索图像。

![](img/d6f7c0c84e6e66cda7cbe64803165cfa.png)

## #5 后期处理

考虑 RAG 时要问的最后一个问题：如何合并我检索到的文档？这很重要，因为上下文窗口的大小有限，并且如来自不同来源的冗余文档，将利用令牌而不向 LLM 提供独特的信息。已经出现了许多文档后处理方法，例如，提高多样性或过滤新近度，`Langchain` 在有关 `OpenAI` 的 RAG 策略的博客文章中讨论了其中一些方法。

### 重新排名

当我们检索大量文档时，`Cohere ReRank` 端点可用于文档压缩（减少冗余）。类似的，RAG-fusion 使用倒数排名融合对检索器返回的文档进行重新排名（类似于多查询）。

### 分类

`OpenAI` 根据其内容对每个检索到的文档进行分类，然后根据该分类选择不同的提示。这将用于分类的文本标记 与基于标签的逻辑路由（在本例中为提示）结合起来。

## 未来计划

展望未来，`Langchain` 将重点关注至少两个扩展这些主题的领域。

### 开源

许多改进 RAG 的任务都是狭窄且定义明确的。例如，用于元数据过滤的查询扩展（子问题生成）或结构化查询构造是狭窄的、定义明确的任务，也可以重复完成。反过来，他们可能不需要大型且成本最高的通用模型来实现可接受的性能。相反，可能需要微调的较小的开源模型可能就足够了。`Langchain` 将发布一系列模板，展示如何在适当的情况下在 RAG 堆栈中使用开源模型。

### 基准测试

在努力测试开源 LLM 的同时，`Langchain` 最近推出了可以为评估提供基本事实的公共数据集，将扩展这些挑战，以包括一些更具体的 RAG 挑战，并使用它们来评估上述方法的优点以及开源 LLM 的纳入。
