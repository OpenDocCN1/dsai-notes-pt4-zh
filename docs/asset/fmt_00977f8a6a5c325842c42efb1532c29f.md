## 大语言模型的分词策略

贡献人：

https://medium.com/@sahin.samia/decoding-tokenization-strategies-for-large-language-models-llms-ffc3fa51aff6

为何 Tokenization 重要 Tokenization 是一种将自然语言分解成模型可以理解的“tokens”过程。LLMs 能够解析这些 tokens 从而捕捉语言的细微差别。Tokenization 不仅关乎文本分割，它还决定了模型对语义和上下文的掌握程度。

**对模型性能的影响** 选择适当的 tokenization 策略能优化模型处理速度、减少内存消耗，并提升响应的准确性。

Tokenization 类型解析

1. 词级别 (Word-Level)：每个单词作为独立 token，适合简单的应用，但处理稀有词汇表现差。

2. 子词级别 (Subword-Level)：通过子词分割（如 BPE 和 WordPiece）有效处理稀有词汇，适用于包含复杂词形变化的文本。

3. 字符级别 (Character-Level)：以字符为基础分割，适合形态学丰富的语言，但代价是生成较长的序列。

4. Unigram Tokenization：基于词概率的单字模型，通过删除低频 token 来优化词汇库。

## Stream of Search: 教语言模型搜索的语言

https://www.llmwatch.com/p/stream-of-search-teaching-language

**概述** 在语言处理和代码生成中，语言模型的表现非常出色，但它们在需要计划、搜索和回溯的复杂问题上常常显得力不从心。Gandhi 等人（2024）提出了“搜索流” (Stream of Search, SoS) 框架，旨在通过在语言中表示搜索过程来提高语言模型的解决问题能力，而不依赖于外部模块。

**搜索流框架核心** SoS 框架将搜索元素系统化为一套通用语言，支持多样化的搜索策略在模型中以一致格式表示。通过使用这些“搜索流”训练语言模型，SoS 模型能够有效地学习解决问题的能力，优于仅训练于最优解路径的模型。此外，通过强化学习方法 (如 STaR 和 APA)，SoS 模型能够在准确性上自我优化。

**主要技术组件**

1. 状态和目标：当前状态、目标状态和状态队列分别表示搜索中的起始、目标和待探索状态。

2. 状态扩展函数：基于转换函数探索相邻状态。

3. 搜索选择与回溯：选择广度或深度优先的搜索顺序，并支持在已探索节点间回溯。

4. 启发式函数：估算当前状态与目标状态的距离，引导搜索过程。

通过在语言中表示这些操作，SoS 可以生成包含不同搜索策略的数据集，既包括显式表示的状态和目标，也包括隐式的启发式和剪枝策略。

**实验与性能** 作者通过 Countdown 游戏（类似于 24 点游戏）的挑战性问题来测试 SoS 框架，生成了 50 万条基于广度和深度优先策略的搜索路径数据集。GPT-Neo 250M 模型分别使用 SoS 和最优路径 (OP) 训练集进行训练，结果显示 SoS 模型在验证集上的准确率达到 51.27%，显著优于 OP 模型的 25.73%。此外，使用 STaR 和 APA 强化学习技术进一步微调模型，使其在未解决问题的准确率上分别提升了 5% 和 6%。

**未来方向** SoS 框架开创了通过语言学习搜索策略的新途径，具备拓展至更复杂实际任务的潜力。未来研究可进一步探索子目标、层次规划的整合以及反思和自我评估能力的加入，以便模型发现并改进新的搜索策略。

## Reward / Embed Model Sever Engine 现状浅析

https://zhuanlan.zhihu.com/p/4148050391

**背景与挑战** 在大语言模型的推理任务中，通常涉及 embed、reward、和 decode 三类请求。特别是在实现 In-Context Learning 的项目中，embedding 的需求尤为重要。当前主流的推理引擎（如 SGLang 和 vllm）已逐步支持 embedding 接口。然而，在实际操作中，embedding 请求效率未如预期。

**技术细节分析** 现代的推理请求中，embed 和 reward 与 decode 请求的执行流程类似：均经历 prefill 阶段得到 hidden states 和 KV cache，区别在于后续不同的 pooling 操作。decode 则会进入 autoregressive 阶段，逐步生成每个新 token。

decode 请求通常采用 P/D（Prefill/Decode）分离架构以优化计算资源的利用率。prefill 阶段为计算密集型，decode 阶段则是内存密集型，需进行连续批处理 (continuous batching)，以达到最大化吞吐量的效果。

**效率问题探讨** 用户反馈中，token usage 在 embed 和 reward 请求中为 0，难以衡量推理效率。SGLang 中，token usage 依赖于 unevictable KV cache 的大小，但 embedding 请求不涉及 decode stage，故 KV cache 会进入 evictable cache，从而 token usage 为 0。同时，decode 请求的高效 batch 组装在 prefill 阶段已实现，而 embed 请求需更多线程以达到类似效果。

**优化建议** 尽管目前 token usage 对 embed 和 reward 请求的效率不适用，SGLang 团队优化了 CPU overlap 和大批量处理，减小了 GPU 利用率受 CPU 影响的瓶颈。

## 图解大模型训练系列：序列并行1，Megatron SP

https://zhuanlan.zhihu.com/p/4083427292

**序列并行的概念** 序列并行 (SP) 是在序列维度上对计算过程进行分割的技术方案。不同框架的实现方式各异，但其核心目标是减少单卡的激活值大小，以减少重计算需求、提升训练效率。常见的 SP 框架有 Megatron Sequence Parallelism 和 DeepSpeed Ulysses 等。

Megatron 序列并行的实现 Megatron SP 的主要思想是将激活值存储分散到多卡上，与 Tensor Parallelism (TP) 结合，实现对 Attention 和 MLP 层的激活值优化。通过在 TP 的基础上增加序列维度上的切分，SP 进一步降低了单卡激活值的显存需求，同时维持了与 TP 一致的通讯量。例如，MLP 层采用行/列切割方式存储激活值，Attention 层对 Q/K/V 矩阵进行列切割，减少了单卡存储。

Selective Activation Recomputation 在显存不足时，SP 结合选择性激活重计算策略 (Selective Activation Recomputation)，仅保留部分激活值，重计算计算量较小但存储需求大的激活值，如 Attention score 的 softmax 结果。该策略进一步降低显存压力，同时保持计算效率，使得 Megatron 在通信和计算开销之间找到平衡。

## 在中国 CPU （龙芯3A6000、3A5000、兆芯等）上运行 SPEC CPU2017

https://zhuanlan.zhihu.com/p/3943366501

在最新的 SPEC CPU2017 基准测试中，中国 CPU（如龙芯 3A6000 和兆芯 KX-6640MA）被广泛测试，以评估其与全球主流 CPU 的单线程性能比较。SPEC CPU2017 是行业标准的基准测试工具，能够全面测试 CPU 在整数和浮点任务中的性能。

龙芯 3A6000

+ **架构与指令集**：龙芯 3A6000 采用 6 宽 LA664 内核，支持 SMT，具备 256 位矢量执行能力，且使用 Loongarch64 指令集。其架构旨在提高 IPC，但时钟速度较低（2.5 GHz），限制了性能表现。

+ **单线程表现**：在 SPEC CPU2017 的整数和浮点任务中，3A6000 的单线程性能仍低于英特尔 E-Core 和 AMD Zen 1。虽然其 IPC 较高，但缺乏足够的时钟速度。

+ **分支预测**：3A6000 的分支预测精度较高，尤其在运行两个 SMT 线程时表现稳定，表明其预测器的有效设计。

+ SPEC CPU2017 浮点测试优势：3A6000 在特定的浮点任务中表现优于 E-Core，但在多数测试中仍然落后于同代及更老的 x86 架构 CPU。

兆芯 KX-6640MA

+ **架构与性能**：兆芯 KX-6640MA 采用 2 宽的 LuiJiaZui 内核架构，较低的无序处理能力使其性能局限于低功耗领域。SPEC CPU2017 测试显示其与 Arm Cortex A73 相当，但略逊于英特尔 Goldmont Plus。

+ SPEC CPU2017 整体表现：在整数和浮点任务中，兆芯与低功耗 CPU 性能接近，但明显低于主流桌面和服务器 CPU。

## 使用 Nvidia Triton Inference Server 扩展机器学习工作负载

https://blog.qburst.com/2024/10/scaling-ml-workloads-using-nvidia-triton

1. 设置和模型目录结构

Triton需要一个模型仓库，每个模型存放在独立目录中，带有版本控制子目录。配置文件`config.pbtxt`允许用户指定输入/输出、批处理大小等参数。例如，对象检测模型的输入可以设定为三通道的640x640图像。

2. 内存优化

默认情况下，Triton加载模型仓库中的所有模型，增加内存使用。可通过`--model-control-mode=explicit`和`--load-model`参数，仅加载特定模型。此外，可通过`version_policy`限制模型的版本数量，从而减少不必要的内存占用。

3. 性能优化

+ **多实例配置**：通过增加模型实例数量来提升吞吐量。可以在不同的GPU上运行多个实例，或指定每个实例所用的GPU ID，提高GPU利用率。

+ **批处理和动态批处理**：增加输入和输出维度以支持批处理或动态批处理，通过组合推理请求提升吞吐量。

+ **垂直和水平扩展**：通过在单个VM上配置多GPU实现垂直扩展；设置多台Triton服务器并使用负载均衡器（如HAproxy）实现水平扩展，从而高效分配请求。

4. GPU/CPU加速优化

+ **TensorRT加速**：配置`TensorRT`提供更高效的GPU推理，尤其是支持`FP16`精度模式的模型。`TensorRT`可优化网络中的支持算子。

+ **CUDA执行提供者**：`CUDA`作为`TensorRT`的备用选项，当算子不被`TensorRT`支持时，由`CUDA`执行。此外，还可以通过配置`cudnn_conv_use_max_workspace`来调优。

+ **OpenVINO加速（CPU）**：在仅使用CPU的模型中，通过`OpenVINO`实现加速，可在配置文件中添加`openvino`选项，提供CPU层面的优化。

## GPT 时代，精进编程思维 + 熟练 Prompt 是否是新的编程范式?

https://www.zhihu.com/question/1918968340/answer/17065727080

在 GPT 时代，虽然AI辅助编程提供了新的工作方式，但不会形成全新的编程范式。参考象棋领域的“Freestyle Chess”悖论，人机协作能暂时提升中低层次开发者的效率。然而，AI的快速发展将让低级别编程岗位变得类似呼叫中心工作，编程质量受限于低端化。此类岗位将逐渐被AI辅助团队取代，大型企业通过AI生成庞大代码库挤压个人开发者空间。

中层岗位如业务翻译的需求将短暂增多，但最终也会被AI取代。至于高级开发人员，AI仅为其提供战术辅助，不会根本改变其工作逻辑。随着窗口期消退，高层开发将专注于学术研究和系统安全验证，使用更接近汇编的低级语言，而AI生成的黑盒代码将形成接口防火墙机制的操作系统动态组装模式。

最终，编程职业将面临下层岗位进一步低端化、中层消失、高层转向科研化的趋势，对未来编程行业而言，AI辅助编程带来的新范式影响将是深远且不可逆的。
