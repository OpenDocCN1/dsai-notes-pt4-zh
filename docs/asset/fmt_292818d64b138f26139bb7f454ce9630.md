
# 动态 Shape 相关技术调研

## 与 TVM 静态模型对比

+   相比 TVM 静态模型性能降低 5%~25%，性能降低主要来自于动态 shape 算子 `index` 的计算和 VM 引入的指令开销；

+   相比 TVM 额外占用 8% 内存

+   `Dense` 算子 `Full Dispatch` 性能基本持平静态 shape，`No Dispatch` 性能最差。

## shape function

根据算子的不同特性，将 shape function 分成 3 类：

+   数据无依赖型，输出 shape 只与输入 Tensor 的 shape 相关；

+   数据依赖型，输出 shape 需要输入 Tensor 的 value 计算得到；

+   上边界型。

数据无依赖型的动态 shape 算子在编译阶段可以很容易的融合。在实现中 shape function 是作为一个算子注册到框架中，所以 shape function 本身也是可融合的。以下是我们在 TVM 代码里面找到的 shape function：

| type | Is Data Dependent |

| --- | --- |

| `elemwise_shape_func` | No |

| `no_data_full_shape_func` | Yes |

| `full_shape_func` | Yes |

| `broadcast_shape_func` | No |

| `conv_shape_func` | No |

| `pool2d_shape_func` | No |

| `global_pool2d_shape_func` | No |

| `reduce_shape_func` | No |

## VM-based Runtime

设计了一套 CISC-style 的指令集，采用变长指令格式，优化时可用无限寄存器。

经过编译优化后的模型可执行件包含两部分：

+   平台无关的字节码，包含模型的控制执行逻辑；

+   平台相关的高性能 kernel。

可执行件由专门设计的解析器负责加载和执行。得益于粗粒度的指令集设计，VM 带来的运行时开销极小，其轻量级特性也保证了平台间的可移植性。

1.  输入本身动态。一般是算法/业务逻辑决定的。

1.  非 batch 轴动态。比如，CV 模型的 image resolution，NLP 模型的 input sequence length。

消除动态性主要有以下方法：padding、修改动态性代码、回 cpu

1 Padding & Bucketing

+   对 `Compiler` 在圈图过程中的自动化干预；

+   在编译期内部自动对变化维度做 bucketing 补齐并将子图计算结果做自动的 slicing。

前者只能适配于小部分子图 shape 变化剧烈的情况，后者在很多模型上都无法得到自动 slicing 的完备数学推导。

对 Sequence Length 的变化，可以通过 padding 到固定长度来解决。但如果全部 padding 到最大长度，会影响效率。因此可以用分桶（Bucketing）的办法，将较短的 sequence 放在一起，padding 到较短的长度，将较长的放在一起，padding 到较长的长度。需要考虑到 `batch_size`，小 Bucketing 可以用较大的 `batch_size`，大 Bucketing 则需要调小 `batch_size`。
