## 写在前面

我观察到一个现象：大多数人用 AI 编程做全栈项目，不是倒在"AI 写不出代码"这一步，而是倒在"写出来的代码串不起来"这一步。原型跑得好好的，一加功能就崩，一联调就对不上，一换会话就失忆。

下面这 10 个翻车场景，是我从大量实际项目和社区反馈中归纳出来的高频问题。不是理论假设，每一条都是真实踩过的坑。

## 场景 1：AI 改了一个模块，顺手把另一个也改了

### 症状

你让 AI 修复用户列表页的分页 bug，结果它把订单详情页的数据获取逻辑也一起改了。上线后发现订单页挂了。

### 根因分析

AI 在修改代码时会扫描相关文件，发现"类似的代码"后倾向于"统一风格"。它没有"这个文件是别人负责的"这种边界感。AI 天然倾向于做你没要求但它认为"合理"的额外修改。

### 实际发生过的情况

你让 AI 改前端组件的颜色，结果它把你写好的 API 调用逻辑也一起重构了——它觉得"顺手优化一下更好"。

### 修复提示词

```
你刚才除了修改 [目标文件] 之外，还改动了其他文件。
请列出你本次改动的所有文件清单。

然后：
1. 撤销对 [被误改的文件] 的所有改动，恢复到修改前状态
2. 只保留我明确要求修改的部分

以后执行任何任务前，先列出你计划修改的文件清单，
我确认后再执行。清单外的文件不要碰。
```

### 预防措施

在 `CLAUDE.md` 中加入以下约束：

```
## 变更纪律
- 每次修改前必须列出变更文件清单，获得确认后才执行
- 不得在修改过程中"顺手"修改不在清单内的文件
- 如果发现其他文件也需要修改，停下来先报告，不要直接改
```

## 场景 2：前后端接口字段名对不上

### 症状

前端代码写 `userName`，后端返回 `username`。前端发送 `pageSize`，后端期望 `page_size`。页面不报错但数据展示不出来，或者报 `undefined`。

### 根因分析

这个问题在没有规范文档的项目中出现概率几乎是 100%。原因很简单：前端和后端通常在不同的会话中开发，AI 每次会话都是"失忆"的，它不记得上一次用了什么命名风格。JavaScript 习惯 `camelCase`（`userName`），Python 习惯 `snake_case`（`user_name`），Go 习惯 `PascalCase`（`UserName`）——AI 会根据语言习惯自动选择，但前后端语言不同时就出问题了。

### 修复提示词

```
前后端字段命名不一致，导致数据无法正确传递。
请执行以下排查：

1. 列出所有 API 接口的请求体和响应体字段名（从后端代码中提取）
2. 列出前端调用这些接口时使用的字段名（从前端代码中提取）
3. 对比两者，标出不一致的字段

然后：
- 以规范文档 §4 中定义的字段名为准（如果有的话）
- 如果规范文档中没有定义，统一使用 `camelCase` 格式
- 同时修改前端和后端，确保完全一致
- 列出所有修改项，我确认后执行
```

### 预防措施

规范文档 §4 中每个接口的每个字段都写清楚名称和类型。这不是废话——字段名是接口定义中最容易被忽视但影响最大的细节。

补充一个容易忽略的细节：HTTP Header 名也要统一。有些项目在 Header 里传 token，`Authorization` 和 `authorization`（注意大小写）在某些框架中是不同的。

## 场景 3：加新功能导致已有功能崩溃

### 症状

前 3 个功能一切正常，做到第 4 个功能时，第 1 个功能开始报错。改完第 4 个的 bug，第 2 个功能又坏了。陷入"打地鼠"循环。

### 根因分析

这是 AI 编程中最深的坑之一。这个问题的本质是：直接把 demo 代码演进成生产级代码。demo 能跑、能看，但架构一塌糊涂。

AI 生成的初始代码通常把所有逻辑写在一个文件里（路由处理、业务逻辑、数据库操作全部混在一起）。功能少时看不出问题，功能一多，修改一处会牵连其他功能，因为它们共享了不应该共享的状态或逻辑。

### 典型表现

有人用 AI 搭一个商品管理系统，本来以为几小时搞定，结果搞了几天。时间不是花在写代码上，而是花在修复"改了 A 坏了 B"的连锁 bug 上。

### 修复提示词

```
项目当前的代码结构有耦合问题——修改一个功能会影响其他功能。
请做一次结构重构，目标是按"三层架构"解耦：

第一层：路由层（Routes）
- 只负责接收请求参数、调用服务层、返回响应
- 不包含任何业务逻辑

第二层：服务层（Services）
- 包含所有业务逻辑
- 每个功能模块一个独立的 service 文件
- service 之间不互相调用（如果需要共享逻辑，提取为 utils）

第三层：数据层（Data/Repository）
- 所有数据库操作封装在这里
- 提供简洁的 CRUD 方法给服务层调用

重构规则：
- 不改变任何 API 的外部行为（请求参数和响应格式不变）
- 每重构完一个模块，立刻测试该模块的所有接口
- 如果发现公共逻辑，提取到 `lib/utils/` 中，不要在 service 间直接 import
```

### 预防措施

在项目初始化阶段就在 `CLAUDE.md` 中定义架构约束：

```
## 架构约束
- 代码必须遵循 路由层(`routes/`) → 服务层(`services/`) → 数据层(`data/`) 的三层架构
- 路由层不包含业务逻辑，只负责参数校验和响应格式化
- 服务层之间不互相引用
- 所有数据库操作通过数据层进行，不在路由层或服务层直接写 SQL/ORM 查询
```

## 场景 4：AI 自作主张添加了你没要求的功能

### 症状

你让 AI 做一个简单的待办事项列表，它给你加了用户认证系统、多语言切换、深色模式、WebSocket 实时同步、PWA 离线支持……你的 MVP 变成了一个"功能齐全但到处有 bug"的半成品。

### 根因分析

AI 被训练在大量"最佳实践"上，它倾向于按照"一个生产级 Web 应用应该有什么"来补全你没说的部分。这里有一条很重要的经验：在 AI 协作中，"非目标"比"目标"更重要。你写了要做什么，AI 不一定全做；但你没写不做什么，AI 很可能自行添加——因为"大多数 Web 应用需要它"。

### 典型表现

本来只想做个简单功能，AI 给你加了一堆你没要的东西，删都删不干净——因为新功能的代码和原有功能已经交织在一起了。

### 修复提示词

```
你添加了以下我没有要求的功能：
- [列出被添加的功能]

请执行以下操作：
1. 完整删除这些功能相关的代码、组件、路由、数据模型
2. 删除因为这些功能而引入的 npm 包依赖
3. 检查删除后是否有遗留的 import 或引用导致报错
4. 运行项目确认核心功能不受影响

以后严格按照 `CLAUDE.md` §6.2 `非目标`清单执行：
清单中列出的功能在本阶段不做，无论你认为"应该有"还是"最好加上"。
只做我明确要求的功能。
```

### 预防措施

`非目标`清单是你能写在规范文档里的最高杠杆操作。每个你不想做的功能，都用一行话明确排除：

```
## 非目标（本阶段不做的事）
- 不做用户认证 / 登录注册 / 权限管理
- 不做国际化 / 多语言
- 不做移动端适配 / 响应式
- 不做深色模式 / 主题切换
- 不做 WebSocket / 实时功能
- 不做自动化部署 / CI/CD / Docker
- 不做性能优化 / 缓存 / CDN
- 不做单元测试 / E2E 测试
- 不做数据导出 / 报表
- 不做消息推送 / 邮件通知
```

写得越具体，AI 越不会擅自添加。

## 场景 5：数据库 Schema 和代码不同步

### 症状

你（或 AI）修改了数据模型——加了一个字段、改了字段类型——但应用代码还在用旧的字段名。运行时报 `column does not exist` 或 `undefined`。

### 根因分析

AI 修改 Prisma Schema 或 SQL 后，经常忘记做两件事：(1) 运行数据库迁移命令，(2) 更新引用了该表的应用代码。特别是当一张表被多个模块引用时，AI 可能只更新了它正在处理的那个模块，漏掉了其他模块。

### 修复提示词

```
数据库 Schema 可能和应用代码不同步了。请执行完整排查：

1. 读取当前的数据库 Schema 定义文件
2. 全局搜索代码中所有引用了数据库表/字段的位置
3. 逐一对比，找出以下不一致：
   - Schema 中新增了字段，但代码中没有使用
   - 代码中引用了某个字段，但 Schema 中不存在
   - 字段类型发生了变化（如 String → Int），但代码中没有处理
4. 列出所有不一致项
5. 以 Schema 为准，修改代码
6. 运行数据库迁移（`npx prisma db push` 或相应的迁移命令）
7. 如果有种子数据脚本，同步更新并重新执行
8. 更新规范文档 §5 的数据模型定义，保持文档和代码一致
```

### 预防措施

每次修改数据模型后，追加一句：

```
Schema 修改完成后，请：
1. 全局搜索引用了该表的所有文件，同步更新
2. 运行迁移命令
3. 更新规范文档中的数据模型定义
```

## 场景 6：前端看起来有数据，但全是 Mock / 硬编码

### 症状

页面看起来内容丰富、运行正常，但仔细检查后发现——数据是前端代码里写死的 JSON，并没有真正调用后端 API。换一条新数据就看不到了。

### 根因分析

AI 在开发前端时，如果后端 API 还没跑通或者返回格式有问题，它会"贴心地"用硬编码的假数据先把页面撑起来，让你看到"效果"。问题是它有时候忘了标注"这是临时数据"，你以为前端已经对接好了。

### 修复提示词

```
请逐页检查前端代码，确认数据来源是否为真实的 API 调用：

对于每个页面/组件：
1. 找到数据获取代码（`fetch` / `axios` / `useSWR` / `useQuery` 等）
2. 确认请求地址是否指向真实的后端 API（`/api/xxx`）
3. 如果发现以下情况，标记为"需修复"：
   - 数据直接写在代码中（`const data = [{...}, {...}]`）
   - 请求地址是注释掉的，用的是本地 JSON 文件
   - 有 `// TODO: 替换为真实 API` 的注释但没替换
4. 将所有"需修复"的位置替换为真实 API 调用
5. 替换后运行页面，确认数据来自后端
```

### 预防措施

在前端开发的提示词中明确要求"发送真实请求，不要用 Mock 数据"。并在开发完成后做一次"数据真实性验证"：在后端数据库中新增一条记录，看前端能不能展示出来。如果展示不出来，说明前端用的是假数据。

## 场景 7：环境变量配置问题

### 症状

- 你的电脑上项目跑得好好的，换台电脑就报错
- API Key 过期了，不知道在哪个文件里改
- 数据库路径硬编码在代码里，换个目录就找不到 db 文件

### 修复提示词

```
请做一次环境变量健康检查：

1. 全局搜索代码中所有 `process.env.XXX` 或 `os.environ['XXX']` 的引用
2. 列出完整的环境变量清单（变量名 + 用途 + 是否必填 + 默认值）
3. 对比 `.env.example` 文件：
   - 代码中用了但 `.env.example` 中没有的 → 补充
   - `.env.example` 中有但代码中没用的 → 考虑删除
4. 搜索代码中硬编码的配置值（API 地址、端口号、文件路径等）
   → 提取到 `.env` 中
5. 为 `.env.example` 中每个变量添加注释，说明用途和格式

最终确保：
- `.env.example` 是完整的、自描述的
- 新同事拿到 `.env.example`，复制为 `.env` 后只需填 API Key 就能跑
```

## 场景 8：越改越乱，感觉不如重来

### 症状

修了 10 轮，每轮修一个 bug 引入两个新 bug。你已经不知道项目的"正确状态"是什么样了，AI 也不知道。继续改下去只会更乱。

### 根因分析

这个状态在 AI 协作中有一个专门的名字叫"混沌阈值"。一旦代码的混乱度超过这个阈值，AI 每次修复一个问题时，由于无法完整理解混乱的上下文，会以为某段混乱的代码是"有意为之"，从而基于错误的理解做出新的修改。结果就是越修越乱。

在实际项目中，这个状态通常出现在项目的第 7-10 天。到这个时候，修改一个功能的成本已经和重写差不多了。

### 修复方案

不要在烂摊子上继续修补。按以下步骤做一次"战略重来"：

```
1. 保存当前代码（`git commit -m "暂存当前状态"` 或复制到备份目录）

2. 从当前项目中提取"还能用的部分"：
   - 数据库 Schema（表结构通常没问题）
   - API 接口定义（路径和参数格式）
   - 前端页面的 HTML 结构（布局通常没问题，逻辑有问题）
   - `.env` 配置

3. 写一份规范文档（这次认真写，照着工具包中的模板填每一个字段）

4. 新建空项目，从阶段 1 重新开始
   - 但这次你有规范文档兜底
   - 有旧代码作为参考（不是复制，是参考）
   - 知道哪些地方会出问题（上次踩过的坑不会再踩）

5. 预估时间：有了上一轮的经验 + 规范文档，重来一遍通常只需要
   第一次用时的 1/3 到 1/2
```

### 一个反直觉的事实

重来看起来浪费时间，但几乎所有经历过"越改越乱"的开发者事后复盘都会说同一句话："早知道就早点重来了，拖着改反而更浪费时间。"判断标准是：如果你已经修了 3 轮以上，每轮都在修上一轮引入的 bug——停下来，考虑重来。

## 场景 9：AI 引入了你没指定的框架或依赖库

### 症状

你用 Tailwind CSS，AI 突然引入了 `styled-components`。你用 Express，AI 写出了 NestJS 风格的装饰器语法。`package.json` 里出现了你不认识的依赖。

### 修复提示词

```
请检查 `package.json`，找出不在 `CLAUDE.md` §2 技术栈清单中的依赖：

1. 列出 `dependencies` 和 `devDependencies` 中的每个包
2. 标出哪些是规范文档中指定的，哪些是额外引入的
3. 对于额外引入的包：
   - 如果是规范指定的包的依赖（transitive dependency）→ 保留
   - 如果是 AI 自作主张引入的替代方案 → 删除，用规范指定的替代
4. 删除后检查代码是否有 import 报错，改为使用规范指定的库
5. 运行 `npm install` 确认依赖树正常
```

## 场景 10：联调时数据在某个环节"消失"了

### 症状

前端发了请求，后端也收到了，也返回了数据，但前端页面上不显示。数据在某个环节"蒸发"了。你不知道断在哪里。

### 修复提示词

```
数据从后端到前端的某个环节断了。请按以下顺序逐层排查，
每一层都打印日志确认：

第 1 层：请求发出了吗？
- 在浏览器 DevTools 的 Network 面板看请求是否发出
- 请求的 URL、Method、Headers、Body 是否正确

第 2 层：后端收到了吗？
- 在后端的路由处理函数入口加 `console.log`，打印收到的参数
- 确认参数格式和预期一致

第 3 层：后端处理对了吗？
- 在业务逻辑处理后、返回响应前，打印将要返回的数据
- 确认数据内容正确

第 4 层：响应格式对吗？
- 比对实际返回的 JSON 和规范文档 §4 中的定义
- 特别注意嵌套层级（前端取 `response.data.answer` 还是 `response.data.data.answer`？）

第 5 层：前端解析对了吗？
- 在前端收到响应后、更新 state 前，打印原始响应
- 检查字段路径是否匹配

第 6 层：状态更新触发了重渲染吗？
- 确认 `setState` / `store.update` 被调用了
- 确认组件订阅了正确的状态

找到断裂点后修复，然后移除调试日志。
```

### 补充：一个常被忽略的断裂点

CORS（跨域资源共享）。如果前后端运行在不同端口（比如前端 3000，后端 8080），浏览器会拦截跨域请求。后端需要配置 CORS 白名单。这个问题的症状是：Network 面板显示请求被 CORS 拦截（红色），控制台有 `Access-Control-Allow-Origin` 相关错误。

修复方法：在后端添加 CORS 中间件，或者使用前端代理（Next.js 的 rewrites / Vite 的 proxy）把 API 请求代理到后端端口。
