## 资源

资源是模型上下文协议（MCP）的基本原语之一。

工具与做事（执行动作）有关，而资源与知识有关。

它们将上下文数据暴露给语言模型，使它们能够推理而不会产生任何副作用。

在编程和系统中，“副作用”指的是系统状态中任何可观察到的变化，而不仅仅是返回一个值。这包括写入文件、更新数据库、进行 API 调用、修改外部系统或资源等操作。

### 直觉

资源是将数据公开为结构化、上下文信息的只读接口。

它们充当智能知识库或参考库，允许模型访问和推理信息。

将资源想象成一个组织良好的图书馆：它们提供可阅读和参考的书籍（数据），但书籍本身不能通过阅读过程进行改变。

> 人们普遍误以为资源就是数据。然而，重要的是要记住，资源并非数据本身，而是一个以结构化和受控的方式提供数据访问的接口。

### 资源可以代表什么？

资源可以代表各种类型的信息：

+ 文件的内容
+ API 的缓存响应
+ 数据库快照
+ 从文档中提取的片段
+ 系统日志、配置或文档

由于资源不应用于执行或修改数据，因此它们提供了一种安全且可预测的方式来向 AI 工作流提供上下文，尤其是在处理静态或半静态知识时。

> 如果底层数据发生变化，更新的内容不会自动传播到模型的上下文中。必须将资源重新加载到上下文中才能反映新的状态。

### 基于URI的资源识别

资源通过遵循结构化格式的唯一 URI（统一资源标识符）进行标识：

![](img/9ee84b21f36767361975a7fe1831d681.png)

协议和路径结构完全特定于 MCP 服务器实现，允许服务器创建适合其特定用例的自定义 URI 方案。

例如：

```
file:///home/user/documents/report.pdf
postgres://database/customers/schema
papers://arxiv/2405.18239
```

### 资源类型

资源可以包含两种不同类型的内容：文本或二进制数据。因此，我们定义了文本资源和二进制资源。

让我们了解它们！

#### 文本资源

文本资源包含UTF-8编码的文本数据，适用于：

![](img/4ada88521b3d08a83762ebd0bca80788.png)

+ 源代码文件
+ 配置文件
+ 日志文件
+ JSON/XML 数据
+ 纯文本文档

#### 二进制资源

二进制资源包含以 编码的原始二进制数据base64，适用于：

![](img/005e48bf1511c9dc121745ad10751b12.png)

+ 图像和图形
+ PDF 文档
+ 音频和视频文件
+ 任何非文本文件格式

### 资源发现机制

MCP 为资源发现提供了两种互补的方法：

#### 直接资源

在这种机制中，MCP 服务器可以通过`resources/list`端点公开具体的资源，同时还提供元数据，包括 URI、人类可读的名称、可选描述、MIME 类型和大小信息。

```
{
  uri: string;           // Unique identifier for the resource
  name: string;          // Human-readable name
  description?: string;  // Optional description
  mimeType?: string;     // Optional MIME type
  size?: number;         // Optional size in bytes
}
```

![](img/7d970026daa4412c78efcbaba9d9530d.png)

这种方法对于已知的、始终可用的静态资源非常有效。

👉静态资源是指具有固定 URI 的资源。

#### 资源模板

对于动态内容，服务器可以`file://{path}`按照 RFC 6570 标准公开类似的 URI 模板。

```
{
  uriTemplate: string;   // URI template following RFC 6570
  
  name: string;          // Human-readable name for this type
  
  description?: string;  // Optional description
  
  mimeType?: string;     // Optional MIME type for all matching resources
}
```

👉RFC 6570 是由互联网工程任务组 (IETF) 发布的一份文档，定义了 URI 模板的语法和规则。

资源模板对于可扩展的实现特别有用。

服务器无需注册数千个单独的文件，而是可以公开一个涵盖整个资源系列的模板，从而大大降低复杂性，同时保持完整的功能。

👉如果你不明白也没关系。一旦我们深入实施，一切都会变得清晰。

### 应用程序控制的访问模式

MCP 资源的一个关键方面是其应用程序控制的访问模式。

与工具等模型控制的原语不同，资源需要明确的客户端管理。

具体来说，当工具被调用时，LLM 会返回所需的工具调用。客户端在获得用户许可后，调用驻留在 MCP 服务器中的工具并接收响应。这表明模型处于控制之中，并且由模型决定要调用什么：

![](img/0cfb0d9f9dfe3f2c7668b84775aa196b.png)

但是对于资源，客户端应用程序必须显式地从资源中获取和管理数据，然后再将其提供给LLM，而无需LLM本身发起任何操作。这表明应用程序在资源方面处于主导地位。

这种设计选择提供了几个重要的好处。
