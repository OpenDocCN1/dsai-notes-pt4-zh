## 1. 为什么要重构

前面一个每一个 `llm` 的配置项过多，并且不同 `llm` 之间有大量重复的配置项，使用起来不方便。

```

                       path=&#x27;internlm/internlm2_5-7b-chat&#x27;,
                       model_name=&#x27;internlm2&#x27;,
                       meta_template=INTERNLM2_META,
                       top_p=0.8,
                       top_k=1,
                       temperature=0,
                       max_new_tokens=8192,
                       repetition_penalty=1.02,
                       stop_words=[&#x27;&lt;|im_end|&gt;&#x27;])

            key=os.environ.get(&#x27;QWEN_API_KEY&#x27;, &#x27;YOUR QWEN API KEY&#x27;),
            openai_api_base=url,
            meta_template=[
                dict(role=&#x27;system&#x27;, api_role=&#x27;system&#x27;),
                dict(role=&#x27;user&#x27;, api_role=&#x27;user&#x27;),
                dict(role=&#x27;assistant&#x27;, api_role=&#x27;assistant&#x27;),
```

将其中的配置项进行分组组合，这样可以提高代码的复用率，让用户使用起来更简便。

```
internlm_server = dict(type=Internlm2Chat,
                       backend=&#x27;lmdeploy&#x27;，
                       **backend_cfg
                       )
```

`llm` 推理由两部分组成：

+ `llm`：用哪个大模型
+ `backend`：由什么推理框架提供服务

最终应该实现 m 种 `llm` 和 n 种 `backend`，m*n 种组合任意配置（排除个别情况，比如闭源模型只能通过 API 访问，或者推理框架还不支持某些模型的情况）。

mindsearch 现有的代码 `model.py` 中采用了比较复杂的配置，其中引用了 lmdeploy 项目中 LLM 相关的 `GPTAPI`、`INTERNLM2_META`、`HFTransformerCasualLM`、`LMDeployClient`、`LMDeployServer` 类。代码在这里。

## 3. 重构方案

每个模型一个类作为入口，初始化一个 `self.model`。实际上这个 model 可能是一个模型对象的实例，也可能是一个 server，还可能是针对另外已经存在的服务的 client。

在 model 的基础上实现 `completion` 和 `chat_completion`。

```
class Interlm2Chat(LLMMixin):
    def __init__(self, backend: Union[str, object]=&#x27;lmdeploy&#x27;, chat_template:str=&#x27;jinja2 模板&#x27;, **kwargs):
        self.model = dispatch(backend, chat_template, **kwargs)
        
class LLMMixin:
    def chat_completion
    def completion
```

> Mixin 是接口规范，定义了接口有哪些，具体每个接口怎么实现是由 `InternLM` 这个 model 决定的。

> 实际现在 lagent 里边不同的 backend 已经基本实现了这些接口，也能调用各家模型，只是需要选 `Backend` 类，然后初始化的时候自己传入路径、模型名称、模板等。

> 还有一个问题，比如 `APIBackend` 各家模型实际有些细微区别，但是现在 lagent 强行融合在了一个类里。实际这种有些特殊模型的 API backend 应该在 `xxx_model.py` 里边 `XXXModel` 指定 API backend 时切换到这些特殊。

> 或者某些 backend 只支持某几个模型，那其他家模型选 backend 如果选到这个 backend 应该有错误反馈。

### 3.1 重构思路

不同后端和模型输入参数、输出接口的统一。我们提供统一的使用方式，不同后端/模型的差异我们来处理。

### 3.2 各种 backend 怎么改

#### LMDeployServer/LMDeployClient

[原代码](https://github.com/InternLM/lagent/blob/906845f1af47fcb7d81c5c32ec44b0cc22204f8a/lagent/llms/lmdeploy_wrapper.py#L271) 中目前只支持了 `completions_v1` 接口，两个方法分别对应是否 stream 的方式。

+ 增加 `chat_completions_v1` 接口的支持。
+ `top_p`、`top_k`、`temperature`、`max_new_tokens`、`repetition_penalty`、`stop_words` 这些参数合并为一个 `backend_cfg`。

`LMDeployClient` 继承 `LMDeployServer` 类，所以 Server 实现过的方法可以沿用。

#### HFTransformerCasualLM

`completion` 和 `chat_completion` 都已经实现。

+ 合并 `backend_cfg` 即可。

#### APIBackend

[openai 代码](https://github.com/InternLM/lagent/blob/906845f1af47fcb7d81c5c32ec44b0cc22204f8a/lagent/llms/openai.py#L152) 中搜 `qwen`，有三个地方是针对不同模型的 if else，抽到各自模型的类中。（这块新代码已经搜不到了？）

#### Vllm

[目前代码](https://github.com/InternLM/lagent/blob/906845f1af47fcb7d81c5c32ec44b0cc22204f8a/lagent/llms/vllm_wrapper.py#L33) 使用的是 `vllm.LLM` 类，文档说

> The [`LLM`](https://docs.vllm.ai/en/latest/dev/offline_inference/llm.html#vllm.LLM) [`class wraps th`](https://docs.vllm.ai/en/latest/dev/engine/async_llm_engine.html#vllm.AsyncLLMEngine)is class for offline batched inference and the `AsyncLLMEngine` class wraps this class for online serving.

是否需要换成 [`AsyncLLMEngine`](https://docs.vllm.ai/en/latest/dev/engine/async_llm_engine.html#vllm.AsyncLLMEngine) 类？

> 新版本代码里 https://github.com/Harold-lkk/lagent/tree/lkk/lagent_v0.3.0/lagent/llms 这部分实际对大部分的 LLM Backend 主持了异步的接口。
