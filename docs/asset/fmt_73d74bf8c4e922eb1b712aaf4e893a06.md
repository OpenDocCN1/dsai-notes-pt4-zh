
## VI — 代码审查与质量门禁

你也可以自己在 `diff` 中留评论。比如你看到某一行觉得不对，就点那一行，写"这里应该处理 `null` 的情况"，然后跟 Claude 的评论一起提交。Claude 会读取所有评论，自动修改代码，生成新的 `diff` 供你再次审查。

如果你在 CLI 里工作怎么办？两个选择：

第一，直接用自然语言让 Claude 做文本形式的审查，"帮我查看当前所有改动，找出 bug、安全隐患、性能问题"。效果一样，只是没有可视化标注。

第二，运行 `/desktop`，把当前会话转到 Desktop 里做可视化审查。这正是 `/desktop` 命令存在的意义之一。

还有一层自动化审查，你在第二段初始化对话中配置的 GitHub Actions CI。每次创建 PR，CI 会自动跑 `lint`、类型检查和测试。只有全部通过才能合并。如果 CI 失败了，在 Desktop 里开启 `auto-fix`，Claude 会自动尝试修复失败的检查。

所以你的代码在进入主分支之前，至少经过了三层过滤：Claude 作为审查员的自审、你的人工判断、以及 CI 自动化测试。

我知道有人会觉得"这也太麻烦了吧"。但我想让你算一笔账：修复一个已经上线的 bug 需要多长时间？排查原因、定位问题、修复、测试、重新部署，可能要半天甚至更久。而在 PR 阶段就发现并修复它，可能只需要五分钟。

你现在花五分钟做审查，是在给未来的自己省五个小时的排错时间。

这笔账，任何理性的人都应该算得过来。

## VII — 并行思维：一个人如何同时推进多个任务

到这儿，你可能已经注意到一个贯穿全文的主题，并行。

传统的开发方式是串行的：写代码 → 测试 → 修 bug → 写文档 → 部署。一件事做完才能做下一件。

Claude Code 的三个环境让你可以同时在多条线上推进。这才是它真正厉害的地方，不是 AI 帮你写代码快了多少，而是你可以同时推进的任务数量从 1 变成了 N。

但并行不是说你同时盯着四个屏幕手忙脚乱。

并行的正确姿势是分清什么需要你的大脑，什么不需要。

**需要你盯着的任务**，在本地做。比如核心功能的开发，你需要跟 Claude 来回对话、实时查看效果、做判断和决策。这种任务需要你的专注力。

**不需要你盯着的任务**，用 `&` 扔到云端。比如补测试、更新文档、修 `lint` 错误、大范围重构，这些任务你只需要给一个清晰的指令，然后等结果就行。

```
& 对整个项目运行完整的测试套件，修复所有失败的测试
& 检查项目中是否有安全漏洞
& 检查代码中是否有未处理的 Promise rejection
```

三个任务在云端同时跑。你在本地继续专注开发。半小时后 `/tasks` 看一眼，都完成了，`/teleport` 拉回来，快速审查，创建 PR。

Desktop 也支持并行，你可以在同一个项目中同时开多个会话，Desktop 会自动为每个会话创建独立的 `Git worktree`，互不干扰。一个会话写功能，另一个写测试，第三个更新文档。

**你的大脑在任何时刻只专注一件事**，但 Claude 在同时帮你执行多件事。

当你习惯了这种工作方式，再回到"一次只能做一件事"的模式，你会觉得难以忍受。

## VIII — 当你真正熟练之后：编排你自己的系统

前面七节讲的所有东西，产品经理思维、`CLAUDE.md`、三个环境的切换、Git 工作流、代码审查、并行任务，如果你只是零散地使用它们，你已经能比大多数人高效很多了。

但真正的高手会做一件事：把这些全部编排成一个自动运转的系统。

### 什么意思？

你可以把整个工作流程、规则、甚至 Claude 应该扮演的角色，全部写进 `CLAUDE.md` 和各种 skill 文件里。比如：

你可以设定一个"毒舌产品经理"skill，每次你给出需求的时候，Claude 不是直接开干，而是先扮演一个挑剔的产品经理，反复追问你"这个功能的用户是谁？""边界情况想过没有？""你确定这是 MVP 需要的吗？"，直到你的需求被拷问得足够清晰，它才开始写代码。

你可以设定一个代码审查 skill，规定 Claude 在每次完成一个功能后必须自动做哪些检查，安全审计、性能评估、测试覆盖率检查，而不需要你每次都手动提醒它。

你可以在 `CLAUDE.md` 里写好完整的分支策略、`commit` 规范、PR 模板，Claude 会在每次会话中自动遵守这些规则，你不需要重复说"记得用 `feature/` 前缀""记得写 Conventional Commits"。

你甚至可以设定工作流编排，比如"每次我说'发布'的时候，自动执行：跑完整测试套件 → Review Code → 创建 PR → 开启 `auto-merge`"。

当你把这些东西都配置好之后，会发生一个质变：你不再是在使用一个工具，你是在操作一个你自己设计的开发系统。

这个系统知道你的项目规范，会主动追问你的需求漏洞，在你犯错之前就拦住你，按照你定义的流程自动推进。你只需要跟着这个系统走，就能把前面七节的所有方法论自动落地，而不需要靠自己的记忆力和自律来维持。

但我要强调一个前提：你必须先深入理解前面七节的每一个概念，才有资格做编排。

如果你不理解为什么要做代码审查，你就不可能写出好的审查 skill。如果你不理解 Git 分支的意义，你就不可能设计出合理的工作流。编排是把理解变成自动化，但如果你没有理解，你自动化的只是一堆你自己都不明白的规则，迟早会出问题。

先学会手动挡，再切自动挡。

## IX — 这些不是理论：看看 OpenClaw 是怎么做出来的

前面八节讲了思维方式、讲了工具用法、讲了编排。你可能会想：这些东西叠在一起，实际做出来到底是什么效果？

看一个正在发生的案例。

🦞 OpenClaw 你一定听过，它 是目前 GitHub 上增长最快的开源项目，截至今天已经超过 21.5 万颗星。它的作者 Peter Steinberger 在 The Pragmatic Engineer 的播客中分享了一个数字：2026 年 1 月，他一个人提交了超过 6600 次 `commit`。 项目规模超过 30 万行代码。

他说："从提交记录看，你可能以为这是一家公司。但不是。这就是一个人坐在家里找乐子。"

他怎么做到的？如果你认真读了前面的内容，答案其实并不意外。

他把自己的工作方式叫做"agenting engineering"，不写代码，指挥 Agent 写。他做的是判断方向、拆分任务、把控质量。这就是第一节说的角色转变：他是产品经理，不是程序员。

他同时跑五份仓库副本来并行推进任务，哪个空闲用哪个，做完就测试、推送、同步。这就是第七节说的并行思维。

他说"I ship code I don't read"（我发布我自己没读过的代码）。听起来大胆，但他敢这么做是因为他有完善的测试覆盖兜底。没有测试，这句话就是灾难；有了测试，它就是效率。这就是第六节说的：防护网不是拖慢你的东西，恰恰是让你敢快起来的东西。

当然，他是一个有 20 年经验的资深工程师，工程判断力不**是工具能替代的。但他的案例说明了一件事：这篇文章讲的这些思路**，角色转变、并行推进、测试兜底，不是空谈，而是真正在做到极致的人，就是这么做的。

区别只在于程度。

我写这篇文章不是为了给你一个"Claude Code 使用手册"。手册这种东西，去看官方文档就好了，比我写的详细一百倍。

我想传达的是一种思维方式的转变。

当你理解了"你是产品经理不是程序员"，你就知道该怎么跟 Claude 对话。当你理解了 `CLAUDE.md` 的价值，你的每次会话都不再从零开始。当你理解了三个环境各自的特点，你就知道什么时候该用什么。当你理解了 Git 分支的心智模型，你不用记任何命令也能给出正确的指令。当你理解了代码审查的意义，你就不会让未经检验的代码溜进主分支。当你理解了并行思维，你就能一个人顶一个团队。当你把这一切编排成系统，你就不再是在用工具，你是在运行一个为你量身定制的开发流程。

工具会迭代，功能会更新，但这些底层的思维方式不会过时。

就像开头说的，问题从来不在工具上。

问题在于你有没有理解这个工具该怎么用。
