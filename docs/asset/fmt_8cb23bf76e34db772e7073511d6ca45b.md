
# Claude Code：从会用到用好

![](img/7cf0cac19d6085608b1bb47032ef4905.png)

大多数人对 AI 写代码，或者说对 Vibe Coding 的理解，仅仅停留于用大白话来提需求。

装个工具，打几句话，坐等代码从天而降。于是他们兴冲冲地装好 Claude Code，对着终端说"帮我做一个 App"，发现 AI 吐出来一堆文件，自己完全不知道该怎么推进，也不知道哪里出了问题，更不知道下一步该做什么。

最后得出结论：AI 写代码不过如此。

但问题从来不在工具上。

问题在于，你在用一个全新范式的工具，却还带着旧范式的思维方式。

如果你正在用 Claude Code（或者刚打算用），我想跟你分享一套我感受颇深的经验和思路总结。这不是一篇安装教程，也不是功能清单的罗列。这是关于怎么想的文章，从一个空文件夹到一个真实可用的产品，中间每一个环节的思维方式、决策逻辑和具体方法。

这篇文章会比较长。

它不是那种你扫两眼就关掉的东西。

如果你真的想搞明白怎么高效地用 AI 来开发项目，建议你找一段完整的时间，认真读完。

我们开始。

## I — 你需要转变的第一个认知：你不是程序员，你是产品经理

先说一个大多数人不愿意面对的事实。

用 Claude Code 开发的时候，你写的每一句话，本质上都不是在"写代码"，你是在下达指令、描述需求、做决策。你的角色从一个"动手写代码的人"，变成了一个"想清楚要做什么的人"。

这个转变听起来简单，但绝大多数人做不到。

为什么？因为他们要么描述得太模糊，要么太具体。

太模糊的人会说："帮我做一个登录功能。"然后 Claude 做出来的东西跟他想象的完全不同，他就觉得 AI 不行。但问题是，你自己都没想清楚登录功能长什么样，AI 怎么可能帮你想清楚？

太具体的人会说："在 `src/pages/login.tsx` 第 15 行加一个 `useState`。"这种人把 AI 当成了一个听话的打字员，完全没有利用它真正的能力，理解上下文、做架构决策、同时处理多个关联文件。

真正高效的指令长这样：

> 开发用户登录功能。登录表单包含邮箱和密码输入框。需要前端表单验证：邮箱格式检查、密码至少 8 位。调用 `/api/auth/login` 接口，登录成功后跳转首页，失败则显示错误提示。要有 `loading` 状态。写对应的单元测试。

你看出区别了吗？

它描述的是"做什么"和"为什么"，但把"怎么做"留给了 Claude。它给出了足够的约束条件，让 AI 不会跑偏，但又没有细到每一行代码，给 AI 留出了发挥空间。

这就是产品经理思维。你不需要知道代码怎么写，你需要知道产品应该是什么样的。

我见过太多人卡在这一步了。他们不是不够聪明，而是没有意识到自己的角色已经变了。你不是在跟一个搜索引擎对话，你是在跟一个极其能干但需要清晰指令的工程师协作。

你给他越清晰的需求，他交付的东西就越接近你想要的。

这是所有后面内容的前提。如果你不接受这个认知转变，后面的技巧和方法论全部白搭。

## II — 一个你绝对不能跳过的步骤：给你的项目建一个"大脑"

你有没有过这种体验，每次开一个新的 Claude Code 会话，都要重新跟它解释一遍项目是做什么的、用了什么技术栈、有什么规范要遵守？

这不是 AI 的问题，是你的工作流有问题。

Claude Code 有一个极其重要但被大多数人忽视的机制：`CLAUDE.md`。

这是一个放在项目根目录的 Markdown 文件，Claude 在每次会话启动时会自动读取它。你可以把它理解成你给 Claude 写的一份"项目说明书"，项目是做什么的、技术栈是什么、开发规范有哪些、目录结构是怎样的、有哪些需要特别注意的地方。

一旦你创建了这个文件，不管你在 CLI、Desktop 还是 Web 云端开新会话，Claude 都会自动了解你的项目上下文，不需要你每次重复说明。

这就是为什么有些人用 Claude Code 的体验丝滑得像魔法，而另一些人每次都在从零开始，差距不在工具上，在于你有没有给这个工具建立"记忆"。

那这个文件应该写什么？

```
帮我创建一个 CLAUDE.md 文件，内容包括：
- 这个项目是做什么的（一句话说明）
- 技术栈（比如 Next.js + TypeScript + Tailwind）
- 开发环境怎么启动
- 测试怎么跑
- 代码风格规范（缩进、引号、分号等偏好）
- 分支命名规范（feature/xxx、fix/xxx）
- commit 信息规范（使用 Conventional Commits）
- 目录结构说明
```

你甚至不需要自己写这个文件。把上面这段话直接发给 Claude，它会帮你生成一个结构完整的 `CLAUDE.md`。然后随着项目迭代，你只需要定期告诉它"帮我更新 `CLAUDE.md`，新增了 `auth` 模块和数据库 schema 的说明"就行。

这个文件就是你整个项目的大脑。没有它，你的每一次会话都是失忆的。

而且这个东西有一个隐藏的好处：当你强迫自己把项目的规范和结构写清楚的时候，你自己对项目的理解也会变得更深。很多时候你觉得"我知道这个项目是怎么回事"，但直到你把它写成文字，你才发现有很多地方其实根本没想清楚。

这一步我放在这么前面说，是因为它决定了后面所有环节的效率。我见过太多人项目做到一半才发现没有这个文件，然后回头补，能补，但不如一开始就做对。

## III — CLI、Desktop 和云端：三个环境，三种用法

Claude Code 给了你三个环境：CLI（终端）、Desktop（桌面应用）和 Web 云端。

很多人以为这三个只是同一个东西的三件不同的衣服。不是的。它们各自擅长的事情完全不同，搞清楚什么时候该用哪个，是你效率能翻倍的关键。

**CLI 适合干活，尤其是需要精确控制的时候。**

如果你习惯在终端里工作，CLI 就是你最趁手的环境。项目初始化、配置文件修改、脚本化操作、以及任何你想快速搞定的事情，CLI 都很顺手。它还有一个独特的优势：可以嵌入到自动化脚本和 CI/CD 流水线里，这是另外两个环境做不到的。

但 CLI 最被低估的能力是 `&` 前缀。

在 CLI 里，你在任何指令前面加一个 `&`，这个任务就会被送到云端后台运行。你的终端立刻空闲出来，你可以继续干别的事。任务在 Anthropic 的服务器上跑着，你关掉电脑去吃饭都没关系，它还在跑。

```
& 帮我给所有现有的组件补上单元测试
& 更新 README.md，加上最新的 API 文档
& 检查整个项目的代码风格，修复所有 lint 错误
```

这三个任务会在云端同时并行执行。你用 `/tasks` 随时查看进度。

想想这意味着什么，你一边在本地专注开发核心功能，一边让云端同时帮你跑三个不那么需要你盯着的任务。这不是"提高效率"，这是在同一个时间维度上，一个人干四个人的活。

**Desktop 的核心价值在于看代码，而不是写代码。**

CLI 写代码其实更快。但当你需要审查代码改动的时候，Desktop 的优势就体现出来了。

2 月 20 日，Claude Code 在 Desktop 上线了一个全新的功能，Review Code。点一下这个按钮，Claude 就会以"代码审查员"的身份重新审视你的所有改动，然后直接在 diff 视图的具体代码行上留下评论。它可能会告诉你这里有个潜在的 bug、那里缺了错误处理、这个地方有性能隐患。

你也可以自己在任意代码行上点击留评论，比如"这里应该用 `async/await` 而不是回调"，然后一次性提交所有评论，Claude 会根据评论自动修改代码。

这个功能在 CLI 里做不到，不是因为 CLI 能力不够，而是因为纯文本终端没有图形化的 diff 视图来承载这种"在具体代码行上标注"的交互。

Desktop 还有一个实时应用预览功能，它可以直接启动开发服务器，在桌面界面里预览你正在开发的 Web 应用。Claude 能看到 UI、读取控制台日志、捕获错误，然后持续帮你迭代。你不再需要切到浏览器去手动描述"我看到了一个按钮错位了"，Claude 自己就能看到。

所以记住这个分工：CLI 用来做，Desktop 用来看。

**云端适合你不需要盯着的任务。**

Web 云端（`claude.ai/code`）本质上是一个远程容器，它会 clone 你的 GitHub 仓库，在云端执行代码修改和测试，完成后把改动存在一个新的 Git 分支上。你可以从云端直接发起 PR，也可以用 `/teleport` 把分支拉回本地继续。

它最大的价值是**解放你的时间和本地资源**。耗时很长的重构、大范围的测试、不需要你盯着的文档更新，全部用 `&` 扔到云端去。你的电脑只需要跑你当前最需要专注的那一个任务。

三者之间的切换。

这三个环境还可以互相转移会话：

+   CLI → Desktop：在终端里运行 `/desktop`，当前会话转移到桌面应用。你在 CLI 里写了一堆代码，想用 Desktop 的可视化 diff 来审查，就用这个。

+   CLI → 云端：指令前加 `&`，任务发送到云端后台运行。

+   云端 → CLI：运行 `/teleport`，把云端完成的任务拉回本地终端继续。

有一个重要的细节：这些切换目前都是单向的，不是实时双向同步。 你不能在 CLI 和 Desktop 上同时操作同一个会话。但这已经足够了，关键是你知道在什么时候该切换到什么环境。

一个高效的工作日可能是这样的：

早上在 Desktop 里开始核心功能的开发，利用实时预览边做边看效果。中午出门前，在 CLI 里用 `&` 把几个不需要盯着的小任务扔到云端。外出时用手机上的 Claude 应用查看进度。回来后用 `/teleport` 把云端完成的任务拉回本地，快速审查一下就发 PR。然后继续在 Desktop 里做上午没做完的核心功能。

你一个人，但同时在三个环境里推进不同的事。

## IV — 从空文件夹到一个正规项目，中间只需要三段对话

很多人对"项目初始化"有一种恐惧感，觉得要配置一大堆东西、学一大堆概念，光是 Git 那些命令就够喝一壶的。

实际上，用 Claude Code 从零搭建一个正规项目，你只需要三段对话。

第一段对话：创建项目并推送到 GitHub。

```
我要做一个个人博客网站，技术栈用 Next.js 14 + TypeScript + Tailwind CSS。
请帮我：
1. 初始化项目和合理的文件结构
2. 初始化 git
3. 在 GitHub 上创建一个叫 my-blog 的私有仓库
4. 生成合适的 .gitignore
5. 做第一次 commit 并推送到 GitHub
6. 创建 CLAUDE.md 文件，写好项目说明和开发规范
```

一段话，六件事，Claude 会逐一执行完。如果你电脑上缺了什么工具（比如 GitHub CLI），它也会帮你安装或者告诉你怎么配置。

第二段对话：搭建安全网。

```
帮我完成以下配置：
1. 创建 GitHub Actions CI 工作流，每次 PR 自动跑 lint 和测试
2. 给 main 分支设置保护规则，不允许直接推送，必须通过 PR 合并，CI 必须通过
3. 运行 /install-github-app 安装 Claude GitHub App
```

这段对话做的事情，本质上是在给你的项目装上"安全气囊"。从这一刻起，任何代码想进入主分支，都必须经过 PR 审查和自动化测试。你不小心手滑直接往 `main` 上推代码？推不上去。CI 测试没跑过就想合并？合并不了。

你可能觉得"我一个个人项目搞这么正规有必要吗？"

有必要。非常有必要。

因为这些规则不是用来约束你的，是用来保护你的。你以为你不会犯错，但你会。尤其是当你让 AI 帮你写大量代码的时候，你更需要一套机制来确保每一次改动都经过审查。代码生成的速度越快，防护网就越不能少。

第三段对话：开始开发第一个功能。

```
创建一个新分支 feature/home-page，开发博客的首页：
- 顶部导航栏
- 文章列表（从 MDX 文件读取）
- 响应式布局
开发完后帮我 commit 并推送分支
```

三段对话，你的项目就从一个空文件夹变成了一个有完整基础设施、有安全机制、正在开发第一个功能的正规项目。

整个过程中你打了多少个 Git 命令？

零个。

你需要知道 `git init`、`git remote add origin`、`git push -u origin main` 这些命令的语法吗？不需要。Claude 替你执行了所有这些操作。你只需要知道你想要什么。

但，这不意味着你不需要理解 Git。恰恰相反，你必须理解 Git 背后的概念，才能给出正确的指令。下一节我们来聊这个。

---

## V — 你必须理解的 Git 心智模型（不需要记命令）

我要说一句可能会得罪一些人的话：你不需要记住任何 Git 命令，但你必须理解 Git 在做什么。

这两件事是完全不同的。

记命令是体力活，Claude 比你记得熟一万倍。理解概念是脑力活，这部分只有你自己能做。你不需要知道 `git checkout -b feature/xxx` 的语法，但你必须知道"创建一个新分支"意味着什么、为什么要这么做、什么时候该这么做。

我用一个比喻来解释整个 Git 工作流。

把 Git 想象成一棵树。

你的主分支 `main` 就是树干。每一个 `commit` 就是树干上的一个节。你做了 10 个功能，树干上就有 10 个节，按时间顺序排列。

当你说"创建一个新分支"的时候，你不是把树干复制了一份，Git 没那么蠢。你是从树干的最新一个节上长出了一根新枝。这根新枝和树干共享之前的所有历史，它只是在第 10 个节的基础上"岔"出去了。

```
              功能11 ← feature/login 分支
             /
1→2→3→...→10  ← main 主分支
```

树干的部分只存了一份，不会因为你多了十根树枝就变成十份。Git 用的是指针，不是复制。

当你在新枝上开发完功能 11，测试通过，代码审查完毕，你就把这根新枝"嫁接"回树干，这就是合并（merge）。合并后，`main` 包含了 11 个功能，那根临时的新枝完成了使命，可以删掉了。

```
合并后：
1→2→3→...→10→功能11  ← main
                       feature/login 可以删掉了
```

这就是 Git 分支的全部核心概念。没了。

理解了这个，你就能理解我们为什么要遵循"分支开发 → PR → 合并"的流程，

每开发一个功能，从 `main` 拉一个新分支。 在这个分支上随便折腾，不会影响主分支的稳定性。

开发完之后，不是直接把代码塞进 `main`。 而是发起一个 Pull Request（PR），意思是"请审查我的代码，没问题就合并进主分支"。

PR 给了你一个审视的机会。你、Claude、或者你的队友可以看到每一行改了什么，可以在具体的代码行上留评论。等审查通过、CI 测试也跑过了，PR 才会被合并。

合并后，删掉临时分支，切回 `main`，拉最新代码，再开下一个分支。 如此循环。

这个流程看起来好像很繁琐。但它解决了一个致命问题：隔离风险。

如果你的功能 11 写到一半发现有严重 bug，你只需要丢掉这个分支就行，`main` 完全不受影响。如果你直接在 `main` 上写代码，出了问题你可能要花好几个小时来修复，甚至可能把整个项目搞崩。

用 Claude Code 的时候，这个流程尤其重要。因为 AI 生成代码的速度非常快，如果没有分支隔离和 PR 审查，你可能在几分钟之内就让一堆未经检验的代码污染了你的主分支。速度快是优势，但速度快加上没有防护就是灾难。

关于 `commit`，记住一个核心原则：小步提交，每个 `commit` 只做一件事。

不要等整个功能做完才 `commit` 一次。每完成一个有意义的小步骤就提交：

```
feat: add login form UI
feat: add form validation
feat: add login API integration
test: add login unit tests
```

而不是一个巨大的 `commit` 里面什么都有。原因很简单，如果第三步出了问题，你可以精确地回退到第二步，而不用把前两步的工作也丢掉。这就是"存档点"，你在游戏里也不会只在最终 boss 前存一次档吧？

你不需要手动输入这些 Git 命令。你只需要说"帮我 `commit` 当前的改动，信息写 `feat: add login form UI`"，Claude 替你执行。你要做的只是在正确的时机告诉它该保存了。

## VI — 代码审查：最容易被跳过，但可能是最重要的环节

我注意到一个现象：大多数用 AI 写代码的人，几乎从来不审查 AI 生成的代码。

他们看一眼"好像能跑"，就觉得 OK 了。然后项目越做越大，bug 越积越多，到某个节点整个项目变成了一团无法维护的乱麻，不得不推倒重来。

这就像你雇了一个打字速度极快的实习生，他一天能写你三天的量，但你从来不检查他写的东西，你觉得这能有好结果吗？

Claude 写代码很快，但"快"从来不等于"对"。

这就是代码审查存在的意义。

在 Desktop 里，当 Claude 改完代码后，你会看到一个 diff 统计指示器（比如`+52 -3`）。点开它，左边是文件列表，右边是每个文件的具体改动，哪些行是新增的、哪些被删了、哪些被改了，一目了然。

然后你点 Review Code 按钮。

这一步发生的事情很有意思：Claude 会切换到一个完全不同的角色。它不再是那个帮你写代码的"开发者 Claude"，它变成了一个审查代码的"审查员 Claude"。它会用审查者的眼光重新看一遍所有改动，然后在 diff 的具体代码行上留下评论。

这些评论可能是"这里有一个潜在的竞态条件"，可能是"这个函数缺少错误处理"，可能是"这里的性能可以优化"。有时候它会发现自己刚才写代码时犯的错误，这不矛盾，写代码和审查代码本来就是两种不同的思维模式，人类也一样。
