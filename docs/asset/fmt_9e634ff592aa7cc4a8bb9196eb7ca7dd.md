
## § 2.2 超越 ReAct：探索式与结构化规划算法

为了克服 ReAct 线性思维的局限，研究者们开发了多种允许 Agent 进行更广泛探索、更结构化思考的规划与推理算法。

### § 2.2.1 思维树（Tree of Thoughts，ToT）：探索多重推理路径

+ **动机：** 传统的思维链（Chain-of-Thought，CoT）或 ReAct 中的思考步骤通常是线性的，如果某一步出错或选择了次优路径，很难回溯或探索其他可能性。思维树（Tree of Thoughts，ToT）旨在通过显式地探索和维护一个包含多个并行推理路径的树状结构来克服这一限制。

+ **核心机制：** ToT 将问题解决过程建模为一个在“思维树”中进行的搜索。树的节点代表部分解（"thoughts"），边代表将一个思维扩展到下一个思维的操作。其运作包含四个关键要素：

    1. 思维分解（Thought Decomposition）：将原始问题分解为一系列中间步骤或“思维单元”。例如，写文章可以分解为构思大纲、撰写段落、修改润色等步骤。

    2. 思维生成（Thought Generation）：对于树中的某个节点（当前思维状态），生成多个潜在的下一步思维。这可以通过让 LLM 多次采样（增加随机性）或提出不同的下一步建议来实现。

    3. 状态评估（State Evaluation）：至关重要的一步。使用启发式方法（通常也依赖 LLM）来评估每个生成的思维或状态的“价值”或“前景”，判断其是否有助于最终解决问题。评估可以是数值评分（如 1-10 分）或类别判断（如“肯定有希望”、“可能没用”）。

    4. 搜索算法（Search Algorithm）：利用经典的树搜索算法（如广度优先搜索 BFS、深度优先搜索 DFS 或更复杂的 A*、MCTS 变种）来系统地探索思维树。根据状态评估的结果，优先扩展更有希望的分支，并可能剪枝掉价值低的分支。

+ **优势：**

    + **系统性探索：** 允许 Agent 考虑多种解决方案或推理路径，提高了找到最优解的可能性，尤其是在需要探索或没有唯一正确路径的问题上（如数学题、创意写作）。

    + **结合 LLM 推理与搜索：** 将 LLM 强大的局部推理/生成能力与经典的符号搜索算法相结合。

    + **自我反思/评估：** 显式的状态评估步骤引入了自我反思的能力。

+ **劣势：**

    + **计算复杂度高：** 生成和评估大量的思维节点会消耗显著的计算资源（多次 LLM 调用）和时间。

    + **评估的可靠性：** 状态评估的质量（通常依赖 LLM）直接决定了搜索效率和最终结果的好坏，而 LLM 的自我评估能力本身可能并不可靠。

    + **实现复杂：** 相较于 CoT 或 ReAct，实现 ToT 框架（包括思维生成、状态评估和搜索逻辑）更为复杂。

+ **适用场景：** 适合那些解空间较大、需要探索不同可能性、或者初始步骤对最终结果影响重大的复杂问题，例如数学推理、逻辑谜题、创意生成、需要多角度分析的任务。

+ **相关变种：** Tree-of-Code 将 ToT 的思想应用于代码生成和规划；多 Agent ToT 通过引入专门的验证 Agent 来提高状态评估的可靠性；Chain of Preference Optimization 则通过学习 ToT 搜索过程中的偏好，试图用更简单的 CoT 解码达到类似效果，降低推理成本。

### § 2.2.2 蒙特卡洛树搜索（MCTS）的应用：平衡探索与利用

蒙特卡洛树搜索（Monte Carlo Tree Search，MCTS）是一种在决策空间巨大且难以精确评估中间状态价值时非常有效的搜索算法，因其在 AlphaGo 等棋类 AI 中的成功而闻名。它通过随机模拟（Simulation/Rollout）来估计不同选择的长期价值，并利用这些估计来平衡对已知较好选择的利用（Exploitation）和对未知选择的探索（Exploration）。MCTS 同样被应用于增强 LLM Agent 的规划和推理能力。

+ 核心机制（应用于 Agent）：

    1. 选择（Selection）：从根节点（当前状态）开始，根据一定的策略（如 UCT - Upper Confidence bounds applied to Trees，它平衡了节点的已知价值和探索潜力）向下遍历现有的搜索树，选择一个最有希望进行扩展的叶子节点。

    2. 扩展（Expansion）：在选中的叶子节点处，生成一个或多个可能的下一步动作或思维（可以由 LLM 生成）。将这些新动作/思维作为新的子节点加入搜索树。

    3. 模拟（Simulation/Rollout）：从一个新扩展的子节点开始，执行一系列（通常是快速的、随机的或基于简单策略的）后续动作或思维，直到达到一个终止状态（如任务完成、失败或达到预设深度）。LLM 可以用于生成模拟过程中的步骤。

    4. 反向传播（Backpropagation）：根据模拟最终得到的结果（如任务成功/失败的奖励值，或一个评估分数），向上更新从模拟起点到根节点的路径上所有节点的统计信息（如访问次数、累积奖励/价值）。

+ 这个“选择-扩展-模拟-反向传播”的循环会重复进行很多次，逐步构建出一个信息更丰富的搜索树，使得高价值的路径更容易被选中。

+ **LLM 的角色：** LLM 可以在 MCTS 的不同阶段发挥作用：

    + 作为策略网络（Policy Network）指导选择和扩展阶段（倾向于选择更有前景的节点/动作）。

    + 作为价值网络（Value Network）或启发式评估函数用于模拟阶段的快速评估或直接评估节点价值。

    + 用于生成扩展节点（可能的下一步行动或思维）。

    + 用于评估最终模拟结果的质量或奖励。

+ **优势：**

    + **强大的探索能力：** MCTS 能够有效地在巨大的、难以直接评估的搜索空间中找到好的解决方案。

    + **无需完整领域模型：** 它不要求对环境有完美的模型，可以通过模拟来估计价值。

    + **Anytime 算法：** 搜索时间越长，通常结果越好，可以在资源允许的情况下持续改进。

+ **劣势：**

    + **计算成本极高：** 需要进行大量的模拟（Rollouts），计算开销巨大，延迟很高。

    + **依赖模拟质量：** 模拟的准确性（或评估函数的质量）对最终结果影响很大。如果模拟/评估不准确，MCTS 可能被误导。

+ **适用场景：** 适合状态空间或动作空间极其庞大、中间状态价值难以评估、但最终结果（如游戏胜负、任务成功）相对容易判断的复杂规划或推理任务。特别是在需要优化长期策略的场景下有潜力。

### § 2.2.3 计划-执行分离（Plan-and-Act/Solve）：明确分工

标准 ReAct 将思考（计划）和行动紧密耦合。计划-执行（Plan-and-Act/Solve）框架则认为，对于复杂任务，将高层次的战略规划（Planning）和低层次的具体执行（Acting/Solving）分离开来会更有效。

+ **核心机制：** 通常包含两个主要的 Agent 或模块：

    1. 规划器（`Planner`）：通常是一个 LLM。接收用户的高层目标，将其分解为一系列更小、更抽象的子目标或步骤，形成一个结构化的计划。规划器关注的是“做什么”以及步骤之间的逻辑顺序和依赖关系。

    2. 执行器（`Executor`/`Actor`）：也是一个 LLM 或更专业化的模块/工具调用器。接收规划器生成的某一步计划，将其转化为具体的、可在环境中执行的动作（如 API 调用、代码执行、UI 操作）。执行器关注的是“如何做”。

+ 两者之间通过计划进行交互，规划器生成计划，执行器执行计划中的步骤，并将执行结果反馈给规划器（用于监控进展或触发重规划）。

+ **与 ReAct 的关键区别：** ReAct 在每一步都混合了思考和行动，而 Plan-and-Act 则有一个显式的、预先的（或阶段性的）规划阶段。

+ **优势：**

    + **处理复杂长时序任务：** 通过先分解再执行，降低了单一 LLM 同时处理宏观战略和微观细节的认知负荷，提高了处理复杂、多步骤任务的成功率。

    + **模块化：** 规划和执行的分离使得可以独立优化或替换这两个模块。例如，可以使用不同的 LLM 或算法进行规划和执行。

    + **可解释性：** 生成的显式计划有助于理解 Agent 的整体策略。

+ **劣势：**

    + **规划的准确性是关键：** 如果初始计划质量不高或缺乏对环境细节的考虑，执行阶段可能会遇到困难。训练 `Planner` 生成高质量、可执行的计划本身就是一个挑战。

    + **潜在的延迟：** 显式的规划阶段会增加任务启动的初始延迟。

    + **对环境变化的适应性：** 如果环境在执行过程中发生显著变化，可能需要频繁地回到规划阶段进行重规划，增加了复杂性。

+ **适用场景：** 特别适合那些可以被清晰分解为多个步骤、需要预先制定策略的长时序任务，例如复杂的网页导航、多步数据分析流程、项目管理、需要遵循特定流程的操作任务等。当任务的准确性和鲁棒性比最低延迟更重要时，这是一个值得考虑的架构。

### § 2.2.4 基于图的规划（Graph-based Planning）：建模依赖与并行

当任务中的子步骤之间存在复杂的依赖关系时，使用图（Graph）结构来表示和规划任务流程成为一种自然的选择。

+ **核心机制：**

    1. 任务图构建（Task Graph Construction）：首先，将整体任务分解为一系列子任务（图的节点），并识别它们之间的依赖关系（图的有向边，例如，任务 B 必须在任务 A 完成后才能开始）。这个图通常是一个有向无环图（Directed Acyclic Graph，DAG）。任务图的构建可以由人类专家预先定义，也可以尝试让 LLM 从任务描述中自动生成。

    2. 图上规划（Planning over Graph）：规划过程转化为在任务图上寻找一个有效的执行路径或调度方案。这可能涉及：

        + 拓扑排序：确定一个满足所有依赖关系的线性执行顺序。

        + 关键路径分析：识别影响整体完成时间的关键任务链。

        + 并行调度：识别图中没有依赖关系的节点（可以同时执行），并将它们分配给不同的执行单元（如并行的 Agent 或线程），以缩短总执行时间（Makespan）。

        + 与 GNN 的结合：标准 LLM 处理图结构信息的能力有限。可以结合图神经网络（Graph Neural Networks，GNNs）。例如，LLM 负责初步的任务分解和图构建，然后 GNN 在图的嵌入表示上进行更有效的节点选择、路径规划或资源分配决策。

+ **优势：**

    + **显式建模依赖关系：** 清晰地表示任务间的复杂约束。

    + **支持并行优化：** 图结构天然地揭示了可并行的部分，有助于优化执行效率。

    + **结构化表示：** 为复杂任务提供了一个结构化的、可视化的表示。

+ **劣势：**

    + **任务图构建困难：** 从自然语言描述自动、准确地生成任务图仍然是一个挑战。

    + **LLM 处理图的能力：** LLM 直接理解和推理图结构的能力可能不足，可能需要结合 GNN 或特殊的提示技巧。

    + **动态性处理：** 如果任务依赖关系在执行过程中发生变化，更新和维护图结构可能比较复杂。

+ **适用场景：** 适用于那些可以被明确分解为具有清晰依赖关系的子任务、并且存在并行执行潜力的复杂工作流，例如软件构建流程、数据处理管道、复杂的项目管理、需要协调多个并行资源的场景。

## § 2.3 层次化规划与控制：分解复杂目标

正如 § 2.2.3 和 § 2.2.4 所暗示的，许多高级规划方法天然地蕴含或促进了层次化（Hierarchical）的思想。面对极其复杂或宏大的目标，直接生成一个扁平的、包含所有细节的行动序列往往是不切实际的。层次化规划通过将复杂目标递归地分解为越来越简单的子目标或子任务，直到达到可以直接执行的原子动作层级，从而有效地管理了复杂性。

### § 2.3.1 层次化规划的原理与优势

+ **原理：** 模仿人类解决复杂问题的方式，建立一个目标/任务的层级结构。顶层是最终目标，中间层是实现该目标所需的关键阶段或子目标，底层是具体的、可执行的动作。

+ **优势：**

    + **降低复杂度：** 将一个大问题分解为多个小问题，使得每个层级的规划更加聚焦和易于管理。

    + **提高模块化与复用性：** 中间层的子目标或子任务可能在不同的高层目标中被复用。

    + **支持抽象推理：** 允许 Agent 在不同的抽象层次上进行规划和推理（例如，先规划“去机场”，再细化为“打车”、“导航”、“支付”等具体步骤）。

+ 促进专业化分工（在 MAS 中）：便于将不同层级或不同分支的任务分配给具有专门能力的 Agent。

### § 2.3.2 实现层次化控制的模式

在 LLM Agent 中实现层次化控制可以采用多种模式：

+ Plan-and-Act/Solve 的自然延伸：Plan-and-Act 框架本身就构成了一个两层结构（规划层 vs。执行层）。可以通过让规划器递归地调用自身或子规划器来处理更深层次的分解。

+ **显式任务树/图构建：** 如 `ReAcTree` 框架，显式地构建一个包含目标分解和控制流（顺序、并行、条件）的任务树。LLM Agent 被分配到树的不同节点执行特定子任务。

+ 多 Agent 层次结构（MAS）:

+ 监督者-工作者模式（`Supervisor`-`Worker`）：一个高层 `Supervisor` Agent 负责整体规划和分解，将子任务分配给下层的 `Worker` Agents。`Worker` Agent 完成任务后向 `Supervisor` 汇报，`Supervisor` 再根据全局状态决定下一步。`LangGraph` 等框架提供了实现这种模式的工具。

+ **分层专家团队：** 构建不同层级的专家团队，例如，顶层战略规划团队，中层领域规划团队（如市场、技术），底层具体执行 Agent。

+ **结合形式化方法（HTN）：** 尝试将 LLM 与传统 AI 中的层次任务网络（Hierarchical Task Networks，HTNs）结合。HTN 提供了预定义的任务分解知识（方法 Methods 和操作符 Operators）。LLM 可以辅助理解自然语言目标、选择合适的 HTN 方法、或在规划过程中提供启发式信息，而 HTN 框架则负责保证规划的结构性和逻辑性。

### § 2.3.3 挑战与考量

+ **分解的质量：** 如何确保 LLM 能够有效地、合理地将复杂目标分解为有意义且可执行的子目标？这通常需要精心设计的 Prompt 或专门训练。

+ **跨层级协调：** 如何确保不同层级之间的信息传递顺畅、目标一致？

+ **灵活性 vs。结构性：** 过于僵化的层次结构可能降低 Agent 对意外情况的适应性；过于灵活的结构则可能导致规划混乱。需要在两者之间找到平衡。

层次化规划是 Agent 应对复杂性的关键策略，它使得 Agent 能够像人类一样，通过“分而治之”的方式来处理宏大或精细的目标。

## § 2.4 健壮执行：动态重规划与错误修正策略

在现实世界中，环境是动态的，执行是可能出错的。一个预先制定的完美计划在执行过程中几乎总会遇到各种意外情况：外部环境变化、工具 API 返回错误、Agent 自身理解偏差导致执行错误等。因此，高级 Agent 必须具备健壮执行（Robust Execution）的能力，即能够在遇到问题时检测错误、适应变化、并修正其行为或计划。

### § 2.4.1 动态重规划（Dynamic Replanning）

+ **核心思想：** 在 Agent 执行计划的过程中，持续监控环境状态和动作执行结果。一旦发现当前状态与计划预期不符，或者某个关键步骤执行失败，就触发重新规划的过程，生成一个基于当前最新信息的、修正后的计划来继续完成任务。

+ **触发条件：**

    + **环境变化：** 外部状态发生重要改变（如目标位置移动、资源变得不可用）。

    + **执行失败：** 工具调用失败、动作未能达到预期效果。

    + **新信息出现：** 获得可能影响原计划关键信息。

+ **实现机制：**

    + Plan-and-Act 框架：天然支持在每一步执行后或出错时重新调用 `Planner` 进行重规划。

    + **监控与反馈：** 需要 Agent 具备监控能力（感知环境、检查工具返回值）和将偏差/错误信息反馈给规划模块的能力。

    + **高效重规划：** 重规划不一定需要从头开始，可以尝试只修改原计划中受影响的部分，或者复用未受影响的子计划，以提高效率。

### § 2.4.2 错误修正策略（Error Correction Strategies）

除了调整计划，Agent 还需要能够直接修正错误的行为或从错误中学习。

+ **基于反馈的修正：**

    + **环境/工具反馈：** 利用工具返回的错误代码或描述信息，LLM 尝试理解错误原因并生成修正后的动作（例如，修正 API 调用参数、尝试不同的工具）。

    + **人类反馈：** 在关键节点引入人类审核，如果 Agent 执行出错，人类提供修正指令或正确示范。

+ 从错误中学习（Learning from Errors）:

    + **目标：** 让 Agent 不仅能修正当前的错误，还能“记住”这次失败，避免将来犯类似错误。

    + **方法：**

        + **错误经验存储：** 将失败的动作序列、错误原因、以及（可能的）成功修正后的序列存入 Agent 的记忆库（可能是专门的“错误知识库”）。

        + **反思与泛化：** 利用 LLM 对失败经验进行反思，总结出导致失败的模式或规则。

        + **在规划/行动时参考：** 在未来的规划或决策过程中，检索并参考这些错误经验，避免重蹈覆辙。
