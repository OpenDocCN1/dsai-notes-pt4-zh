
这个实验的核心目标是让你从“执行单个、庞大的脚本”，升级为“编排多个、模块化的组件”。你将学会如何将一个端到端的机器学习流程（例如，数据准备 -> 模型训练 -> 模型评估与注册）拆分成多个独立的、可复用的组件（Components），然后将它们以管道（Pipeline）的形式串联起来。这极大地提升了工作流的模块化、可复用性和团队协作效率，是 MLOps 实践的基石。

## 流程分析

这个实验在 Jupyter Notebook 中完成，其流程展示了如何定义和运行一个现代化的管道作业：

1. 为每个步骤创建脚本（Create Scripts for Each Step）: 将原本可能在一个大脚本中的逻辑，拆分成多个独立的 Python 脚本。例如：

- `prep.py`: 负责数据清洗和预处理。
- `train.py`: 负责模型训练。
- `register.py`: 负责评估模型并将其注册到工作区。

这些脚本都被设计成通过命令行参数接收输入和指定输出路径。

2. 将脚本封装成组件（Wrap Scripts into Components）: 这是流程的核心之一。为上一步中的每一个脚本，创建一个对应的命令组件（Command Component）定义。这个定义就像一个函数的“签名”，它清晰地声明了：

- 组件的名称和版本。
- 输入（Inputs）: 组件需要接收哪些数据或参数（例如，`train.py` 需要接收处理好的训练数据）。
- 输出（Outputs）: 组件会产生哪些数据（例如，`prep.py` 会输出清洗后的数据文件夹）。
- 执行逻辑（Command & Environment）: 组件内部具体要执行什么命令，以及在什么软件环境中执行。

3. 将组件组装成管道（Assemble Components into a Pipeline）: 这是流程的另一个核心。你会定义一个管道函数（Pipeline Function），在函数内部：

- 实例化你在上一步中定义的各个组件。
- “连接”组件：将上一个组件的输出，作为下一个组件的输入进行传递。这种连接方式清晰地定义了组件之间的依赖关系和数据流。

4. 提交管道作业（Submit the Pipeline Job）: 将定义好的管道实例化，并像提交普通作业一样，使用 `ml_client.jobs.create_or_update()` 将其提交到 Azure ML。

5. 审查结果（Review Results）: 提交后，你会在 Azure ML Studio 中看到一个图形化的管道视图，可以清晰地看到每个组件的执行状态、数据流向，并能独立查看每个组件的日志和输出。

## 关键知识点介绍

- 管道（Pipeline）: 一个由多个按顺序或并行执行的组件（Components）组成的、自动化的工作流。它定义了一个端到端的机器学习流程，并管理着组件之间的数据依赖关系。
- 组件（Component）: 管道中的一个独立、可复用的计算单元。你可以把它想象成一个带有一组明确输入和输出的“黑盒子”。最常见的组件是命令组件（Command Component），它本质上是对我们之前学习的命令作业（Command Job）的一次“标准化封装”，使其变得可复用。
- 模块化（Modularity）: 这是管道带来的最大好处。将流程拆分成组件后，每个组件都可以被独立开发、测试、版本化和复用。例如，数据科学家可以专注于优化 `train` 组件，而数据工程师可以专注于维护 `prep` 组件。
- 可复用性（Reusability）: 一旦一个组件被定义并注册到工作区，它就可以像函数一样，在任何其他管道中被直接调用，极大地减少了重复工作。
- 智能重运行（Intelligent Rerun / Caching）: Azure ML 的管道非常智能。当你重新运行一个管道时，如果某个组件的代码、输入数据和配置都没有发生变化，Azure ML 会自动跳过这个组件的执行，直接复用它上一次的运行结果。这在开发和调试大型管道时，可以节省大量的时间和计算成本。
- 有向无环图（Directed Acyclic Graph - DAG）: 管道的底层结构是一个 DAG。“有向”意味着数据流是有方向的（从上游组件到下游组件），“无环”意味着工作流中不存在循环依赖，保证了流程可以从一个明确的起点执行到一个明确的终点。

## 实验核心流程分析（基于 `Labs/09/Run a pipeline job.ipynb` 代码）

接下来，我们深入分析该 Notebook 中的核心代码。

### 将脚本封装成组件

```
from azure.ai.ml import load_component

# Load components from YAML files
prep_component = load_component(source="./components/prep.yml")
train_component = load_component(source="./components/train.yml")
register_component = load_component(source="./components/register.yml")
```

- **最佳实践 - YAML 定义**：这个实验采用的是最佳实践，即将每个组件的定义写在独立的 YAML 文件中，而不是在 Python 代码里动态定义。这样做实现了组件定义与管道逻辑的彻底分离。

- `prep.yml`（示例）:

```
$schema: https://azuremlschemas.azureedge.net/latest/commandComponent.schema.json
name: prep_diabetes_data
version: 1
display_name: Prepare Diabetes Data

inputs:
  raw_data:
    type: uri_folder
outputs:
  prep_data:
    type: uri_folder

code: ../src/prep/
command: >-
  python prep.py 
  --raw-data ${{inputs.raw_data}} 
  --prep-data ${{outputs.prep_data}}
environment: azureml:AzureML-sklearn-1.0-ubuntu20.04-py38-cpu@latest
```

- `load_component(...)`：这个函数会读取 YAML 文件，并将其解析成一个可以在 Python 管道中调用的“函数”。

### 将组件组装成管道

```
from azure.ai.ml.dsl import pipeline

# Define a pipeline function using the @pipeline decorator
@pipeline(
    compute="aml-cluster",
    description="Diabetes training pipeline"
)
def diabetes_pipeline(pipeline_input_data):
    
    # 1. Call the 'prep' component
    prep_job = prep_component(
        raw_data=pipeline_input_data
    )
    
    # 2. Call the 'train' component, using the output of the 'prep' component
    train_job = train_component(
        training_data=prep_job.outputs.prep_data
    )
    
    # 3. Call the 'register' component, using outputs from 'prep' and 'train'
    register_job = register_component(
        evaluation_output=prep_job.outputs.prep_data, # Assuming some data is needed
        model_output=train_job.outputs.model_output
    )

    # Return the outputs of the pipeline
    return {
        "pipeline_job_model_output": register_job.outputs.model_output
    }
```

- `@pipeline` 装饰器：这是定义一个管道的标准方式。它将一个普通的 Python 函数转换成一个管道构造器。你可以在这里定义管道级别的默认设置，如默认的计算集群。
- 管道函数 `diabetes_pipeline(...)`：
  - 实例化组件：`prep_job = prep_component(...)` 这一行看起来就像在调用一个函数，实际上它是在管道的“图”中创建了一个节点。
  - 连接组件（数据流）：这是最核心的部分。`training_data=prep_job.outputs.prep_data` 这行代码清晰地声明了：`train` 组件的 `training_data` 输入，来自于 `prep` 组件的 `prep_data` 输出。这就建立起了两个组件之间的依赖关系。Azure ML 会自动理解，必须等 `prep_job` 成功完成后，才能开始运行 `train_job`。

### 提交管道作业

```
# Instantiate the pipeline by calling the pipeline function
pipeline_job = diabetes_pipeline(
    pipeline_input_data=Input(type="uri_folder", path="azureml:diabetes-folder")
)

# Submit the pipeline job
returned_job = ml_client.jobs.create_or_update(pipeline_job)
```

- `pipeline_job = diabetes_pipeline(...)`：调用我们之前定义的管道函数，并为整个管道的初始输入（`pipeline_input_data`）提供具体的数据源。
- `ml_client.jobs.create_or_update(...)`：提交。Azure ML 会接收到这个管道的完整定义（所有组件及其依赖关系），然后按照这个“有向无环图”来调度和执行每一个组件。

### 实验特点与知识点分析（基于 `Instructions/10-Compare-models.md`）

#### 核心目标

这个实验的核心目标是让你学会使用 Azure ML 的负责任 AI 仪表板（Responsible AI Dashboard），对单个模型进行全面的、多维度的诊断。你将超越简单的准确率和 AUC 指标，深入探索模型的内部行为，评估其在不同数据子集上的公平性，并理解其决策的原因。这旨在培养一种超越性能指标、关注模型社会影响和可靠性的思维模式。

#### 流程分析

这个实验在 Jupyter Notebook 中完成，其流程展示了如何为已训练好的模型构建和生成 RAI 仪表板：

1. 准备工作（Preparation）: 首先，需要准备好一个已经训练好的模型和一个用于评估的测试数据集。这通常是之前实验中产出的最佳模型。

2. 构建 RAI 组件（Build RAI Components）: 这是流程的核心。你需要通过代码来定义想要在仪表板中包含的“洞察”（Insights）组件。常见的组件包括：

- 可解释性（Interpretability）: 配置工具来解释模型的整体行为（哪些特征最重要）和单个预测的原因。
- 错误分析（Error Analysis）: 配置工具来自动识别和诊断模型在哪些数据子集上表现最差。
- 公平性评估（Fairness）: 配置工具来评估模型在受保护的敏感特征（如性别、种族等）的不同群体之间是否存在性能偏差。

3. 定义管道作业（Define the Pipeline Job）: 将上一步中定义的所有 RAI 组件，组装成一个特殊的管道作业。这个管道作业的输入是你的模型和数据，它的输出则是生成好的、可交互的 RAI 仪表板。

4. 提交并运行管道（Submit and Run the Pipeline）: 提交这个管道作业。Azure ML 会在后端运行一系列复杂的分析，计算出可解释性、错误分析和公平性评估所需的所有数据。

5. 审查和交互（Review and Interact）: 作业完成后，你可以在 Azure ML Studio 的作业详情页找到生成的 RAI 仪表板。这是一个可交互的 Web UI，你可以：

- 查看全局和局部的特征重要性。
- 通过决策树的形式，下钻到模型错误率最高的特定人群（例如，“年龄大于 50 且 BMI 小于 25 的男性”）。
- 比较模型在不同性别或年龄段的性能指标（如准确率、假阳性率），以发现潜在的偏见。

#### 关键知识点介绍

- 负责任的人工智能（Responsible AI - RAI）: 这是一个涵盖了多种工具、实践和原则的广义术语，旨在确保 AI 系统的开发和运作是安全、可信和合乎道德的。其核心支柱包括：公平性、可靠性与安全性、隐私与保密、包容性、透明度、问责制。
- RAI 仪表板（RAI Dashboard）: Azure ML 提供的一个集成化、可交互的可视化工具，它将多种 RAI 工具（如可解释性、错误分析、公平性评估）的洞察力整合在一个视图中，帮助开发者和利益相关者全面诊断和评估模型。
- 可解释性（Interpretability / Explainability）: 理解模型为何做出特定决策的能力。
- 全局解释（Global Explanation）: 解释模型在整体层面上的行为，例如“在所有预测中，血糖浓度是最重要的特征”。
- 局部解释（Local Explanation）: 解释模型对单个数据点的预测原因，例如“对于这位特定患者，我们预测他患有糖尿病，主要是因为他的血糖值很高，而且年龄也偏大”。
- 错误分析（Error Analysis）: 一种超越整体错误率的诊断技术。它帮助你自动识别出模型表现不佳的特定数据队列或子集。这对于发现模型的盲点、指导数据增强和模型改进至关重要。
- 公平性（Fairness）: 评估模型是否对其预测结果在不同人群（由敏感特征定义，如性别、年龄、种族等）之间造成了不成比例的伤害或偏见。
- 差异指标（Disparity Metrics）: 用于量化不公平性的指标，例如比较不同群体之间的准确率差异、假阳性率差异等。
