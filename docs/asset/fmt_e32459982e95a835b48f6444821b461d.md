## 自动机器学习 (AutoML) 分类作业配置

```python
from azure.ai.ml import automl

# 1. 配置分类作业
classification_job = automl.classification(
    compute="aml-cluster",
    experiment_name="auto-ml-class-dev",
    training_data=my_training_data_input,
    target_column_name="Diabetic",
    primary_metric="accuracy",
    n_cross_validations=5,
    enable_model_explainability=True
)

# 2. 设置限制（可选）
classification_job.set_limits(
    timeout_minutes=60,
    trial_timeout_minutes=20,
    max_trials=5,
    enable_early_termination=True,
)

# 3. 设置训练属性（可选）
classification_job.set_training(
    blocked_training_algorithms=["LogisticRegression"],
    enable_onnx_compatible_models=True
)
```

### 核心步骤分解

#### `automl.classification(...)`：定义核心问题

这是整个 AutoML 作业的灵魂，它精确地定义了我们要解决的问题是什么。

+   `compute="aml-cluster"`：在哪里运行？ 指定使用名为 `aml-cluster` 的计算集群来执行这个任务。

+   `experiment_name="..."`：记录在哪里？ 将本次 AutoML 运行的所有结果记录到这个实验名下。

+   `training_data=...`：用什么数据？ 指定输入的训练数据。

+   `target_column_name="Diabetic"`：预测什么？ 明确指出 `Diabetic` 列是我们的预测目标（标签 y）。

+   `primary_metric="accuracy"`：成功的标准是什么？ 告诉 AutoML，我们的最终目标是找到准确率（`accuracy`）最高的模型。

+   `n_cross_validations=5`：如何验证模型的可靠性？ 指示 AutoML 使用 5 折交叉验证来评估每个子模型的性能。这比简单的训练/测试集拆分更稳健，可以有效避免偶然性，确保评估结果的可靠性。

+   `enable_model_explainability=True`：需要解释吗？ 要求 AutoML 在找到最佳模型后，自动为其计算并生成可解释性报告。

#### `set_limits(...)`：设置“防护栏”

这个部分用于控制 AutoML 作业的资源消耗（时间和金钱），确保它不会无休止地运行下去。

+   `timeout_minutes=60`：整个 AutoML 作业（父运行）最多运行 60 分钟。

+   `trial_timeout_minutes=20`：任何一个子模型的训练（子运行）最多只能花费 20 分钟。

+   `max_trials=5`：最多只尝试 5 个不同的模型（子运行）。

+   `enable_early_termination=True`：启用智能停止。这是一个非常重要的优化。如果 AutoML 发现后续尝试的新模型性能不再有显著提升，它就会提前终止整个搜索过程，从而节省时间和计算资源。

#### `set_training(...)`：定制训练过程

这个部分允许你对 AutoML 的默认行为进行一些微调和控制。

+   `blocked_training_algorithms=["LogisticRegression"]`：不想用什么算法？ 在这里，我们明确告诉 AutoML 不要尝试逻辑回归算法。这可能是因为我们已经知道它在这个数据集上表现不佳，或者我们想专注于探索更复杂的模型。

+   `enable_onnx_compatible_models=True`：需要为部署做准备吗？ 这是一个高级选项。ONNX 是一种开放的神经网络交换格式，可以让模型在不同平台间轻松迁移并进行性能优化。将此项设为 `True` 会确保最终找到的最佳模型是与 ONNX 格式兼容的，这极大地便利了后续的生产部署。

## 在 Notebook 中使用 MLflow 追踪模型训练

https://github.com/MicrosoftLearning/mslearn-azure-ml/blob/main/Instructions/07-Notebooks-mlflow-tracking.md

### 实验特点与知识点分析（基于 `Instructions/07-Notebooks-mlflow-tracking.md`）

#### 核心目标

这个实验的核心目标是引入行业标准的实验跟踪框架 `MLflow`，让你学会如何将训练过程中的关键信息系统性地记录下来。这解决了手动运行实验时信息混乱、结果难以比较和复现的痛点。你将从简单的 `print()` 结果输出，升级为对每一次训练尝试的参数、指标和产出模型进行精细化、可追溯的监控。

#### 流程分析

这个实验在 Jupyter Notebook 中通过 Python SDK 和 `MLflow` 库完成，其流程体现了“为代码注入监控能力”的思想：

1.  准备工作（Preparation）：与之前的实验类似，首先连接到 Azure ML 工作区，并准备好用于训练和测试的数据集。

2.  设定实验循环（Set up Experiment Loop）：流程的核心是建立一个循环，该循环会遍历一个或多个需要尝试的超参数（例如，本例中的不同正则化率 `reg_rate`）。

3.  在循环中注入 `MLflow`（Inject `MLflow` in the loop）：在每一次循环（即每一次独立的训练尝试）中，执行以下操作：

    +   开始一次运行（Start a Run）：使用 `mlflow.start_run()` 来声明一次新的实验运行的开始。这会在 Azure ML 中创建一个用于记录所有后续信息的“容器”。

    +   记录参数（Log Parameters）：使用 `mlflow.log_param()` 记录本次运行时所使用的超参数（例如，`reg_rate` 的具体值）。

    +   执行模型训练（Train Model）：正常执行 `model.fit()` 来训练模型。

    +   记录指标（Log Metrics）：模型训练和评估后，使用 `mlflow.log_metric()` 记录衡量模型性能的关键指标（例如，`Accuracy` 和 `AUC`）。

    +   记录产物（Log Artifacts）：使用 `mlflow.sklearn.log_model()` 将训练好的模型文件本身保存为这次运行的“产物”，它会被上传到 Azure ML。

4.  结果审查与查询（Review and Query Results）：实验循环结束后，你将学会如何利用这些被记录下来的信息：

    +   通过 UI 审查：在 Azure ML Studio 的“实验”页面，你可以看到所有运行的列表，清晰地比较不同参数下的性能指标，并查看图表。

    +   通过 SDK 查询：编写代码来获取本次实验的所有运行记录，以编程方式找出主要指标最高（例如 `AUC` 最高）的那一次“最佳运行”，并下载其对应的模型文件用于后续部署。

#### 关键知识点介绍

+   `MLflow`：一个用于管理整个机器学习生命周期的开源平台。它主要包含四个组件，本次实验的核心是 `MLflow Tracking`。

+   `MLflow Tracking`：`MLflow` 的核心组件，提供了一套 API，用于记录和查询实验代码的参数、指标、代码版本和产出文件。它使得实验过程变得高度结构化和可追溯。

+   Azure ML 与 `MLflow` 的集成：这是本实验的一个关键优势。你不需要自己搭建和维护 `MLflow` 服务器。Azure ML 工作区可以无缝地充当 `MLflow Tracking` 的后端。当你调用 `mlflow.log_*` 等命令时，所有的数据都会被安全、可靠地记录到你的 Azure ML 工作区中，并与你的实验运行关联起来。

+   运行（`Run`）：在 `MLflow` 的语境中，一次运行是指你的训练脚本的一次完整执行。每一次运行都像一个独立的实验记录，包含了它的输入（参数）、输出（指标）和产物（模型文件等）。

+   参数（`Parameters`）：运行的输入配置，通常指模型的超参数（如学习率、正则化率、树的数量等）。它们是键值对，用于记录“我们是用什么配置跑出这个结果的”。

+   指标（`Metrics`）：运行的输出结果，用于衡量模型的性能（如准确率、`AUC`、`MSE` 等）。它们是数值，可以随时间变化（例如，记录每个 epoch 的损失），用于回答“这次运行的结果怎么样”。

+   产物/工件（`Artifacts`）：运行产生的任何文件。最常见的产物是训练好的模型文件（`.pkl` 文件），但也可以是图片（如混淆矩阵图）、特征重要性文件（`.csv`）等。

### 实验核心流程分析

接下来，我们深入分析该 Notebook 中的核心代码片段。

```python
# Iterate through a range of regularization rates
for reg_rate in np.arange(0.01, 0.1, 0.01):
    
    # Start a new MLflow run
    with mlflow.start_run():
        
        # Log the regularization rate parameter
        mlflow.log_param("reg_rate", reg_rate)
        
        # Train a logistic regression model
        model = LogisticRegression(C=1/reg_rate, solver="liblinear").fit(X_train, y_train)
        
        # calculate and log performance metrics
        y_hat = model.predict(X_test)
        acc = np.average(y_hat == y_test)
        auc = roc_auc_score(y_test, y_hat)
        mlflow.log_metric("Accuracy", acc)
        mlflow.log_metric("AUC", auc)
        
        # Log the model as an artifact
        mlflow.sklearn.log_model(sk_model=model, artifact_path="logistic_regression_model")
```

#### 核心步骤分解

##### `for reg_rate in ...`：实验循环

这行代码建立了一个循环，目的是系统性地探索不同的正则化率 `reg_rate`（从 0.01 到 0.1，步长 0.01）对模型性能的影响。这个循环结构是进行系统性实验的基础。

##### `with mlflow.start_run():`：启动并管理一次运行

这是 `MLflow` 的核心用法。`with` 语句确保了：

+   在代码块开始时，一个新的“运行”被创建并设为活动状态。

+   在代码块结束时（无论成功或失败），这个“运行”都会被正确地关闭。

+   所有在这个代码块内部的 `mlflow.log_*` 调用都会被自动关联到这一次特定的运行中。

##### `mlflow.log_param("reg_rate", reg_rate)`：记录超参数

这行代码将当前循环中使用的 `reg_rate` 值以键值对（`"reg_rate": 0.01`）的形式记录下来。这至关重要，因为它确保了我们事后可以准确地知道每一个性能指标是对应于哪一个参数配置的，实现了结果的可复现性。

##### `model.fit(...)` & `y_hat = model.predict(...)`：标准的训练和预测

这两行是标准的 scikit-learn 模型训练和预测代码，与不使用 `MLflow` 时完全一样。这体现了 `MLflow` 的一个优点：它可以非侵入式地集成到你现有的代码中，你只需要在关键位置添加记录语句即可。

##### `mlflow.log_metric(...)`：记录性能指标

在计算出准确率 `acc` 和 `auc` 之后，这两行代码将它们作为数值指标记录下来。这些指标会自动与当前运行（以及该运行的参数）关联。在 Azure ML Studio 中，你可以基于这些指标对所有运行进行排序和可视化，轻松找出性能最佳的运行。

##### `mlflow.sklearn.log_model(...)`：记录模型产物

这是非常关键的一步。它不仅仅是保存了一个 `model.pkl` 文件。`mlflow.sklearn` 是 `MLflow` 的一个“风格”（`flavor`），它在保存模型的同时，还会额外记录下：

+   环境依赖：一个 `conda.yaml` 文件，记录了训练该模型时所使用的 Python 库及其版本。

+   加载方式：一个 `MLmodel` 文件，定义了如何加载和使用这个模型。

这种“带风格”的模型记录方式极大地增强了模型的复现和部署能力。其他人或下游系统不仅能得到模型文件，还能准确地知道该如何重建环境并使用它。

我们来详细对比实验 07（`MLflow Tracking`）和实验 **06（`AutoML`）**。这两个实验都致力于提升模型开发的效率和规范性，但它们通过截然不同的哲学和路径来实现这一目标。

### `AutoML` 和 `MLflow Tracking` 核心理念与角色的根本差异

#### 流程与方法的对比

+   `AutoML`（实验 06）就像是去一家高级的自助餐厅。

    +   你只需要告诉服务员你的偏好（比如“我喜欢海鲜，并且预算是 500 元”）。

    +   餐厅（`AutoML` 引擎）会自动为你呈上由大厨精心搭配好的、各式各样的菜品（尝试不同模型）。

    +   最后，还会为你推荐一道综合评价最高的菜（最佳模型）。你不用关心每道菜具体的烹饪过程。

+   `MLflow Tracking`（实验 07）就像是你在一个设备齐全的专业厨房里自己做菜，并带着一个非常认真的助手。

    +   你（科学家）亲自挑选食材（数据），设计菜谱（算法），控制火候（超参数）。

    +   你的助手（`MLflow`）则在一旁一丝不苟地记录下你用的每一种配料的克数（`log_param`），每道菜的出锅时间和顾客评分（`log_metric`），并把做好的成品菜肴贴上标签、妥善保存（`log_model`）。

    +   最终，你得到的是一本详尽的烹饪日志，可以帮你分析和改进你的厨艺。

总而言之，`AutoML` 是一个强大的“问题解决者”，而 `MLflow` 是一个强大的“过程记录者”。它们服务于机器学习流程的不同需求，前者追求自动化的最优结果，后者追求手动的精确控制和可追溯性。在实际项目中，两者也常常结合使用：先用 `AutoML` 快速找到一个高性能的模型方向，然后再用 `MLflow` 对这个方向的模型进行更精细、更深入的手动调优和研究。

### 实验特点与知识点分析

#### 核心目标

这个实验的核心目标是向你介绍 Azure ML Python SDK v2 的核心设计理念，即通过“作业（Job）”来提交和管理你的工作。它将之前实验中分散的配置（如 `ScriptRunConfig`）整合成一个更现代化、更结构化的命令作业（`Command Job`）对象。目标是让你学会如何以一种更规范、更灵活的方式，将你的本地 Python 脚本封装成一个独立的、可在云端重复执行的作业。

#### 流程分析

这个实验在 Jupyter Notebook 中完成，其流程展示了 SDK v2 提交作业的标准模式：

1.  连接工作区（Connect to Workspace）：使用 `MLClient` 对象通过身份验证连接到你的 Azure ML 工作区。这是所有 v2 SDK 操作的入口。

2.  准备数据和计算资源（Prepare Data & Compute）：确保用于训练的数据（`diabetes` 数据集）和计算资源（`aml-cluster`）已经存在或被创建。

3.  创建训练脚本（Create Training Script）：编写一个包含完整训练逻辑的 Python 脚本（`main.py`）。这个脚本被设计成可以通过命令行参数来接收输入（如数据路径、超参数）。
