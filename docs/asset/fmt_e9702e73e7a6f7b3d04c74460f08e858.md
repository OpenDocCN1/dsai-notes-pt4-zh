## 基于`GPU`的树状结构构建

贡献人：

`https://zhuanlan.zhihu.com/p/669019977`

本文探讨了如何使用包围体层次结构（`BVH`）来进行高效的碰撞检测，重点介绍了如何优化这些结构以适应大规模并行处理器（如`GPU`）。在展示了减少`BVH`遍历过程中的分歧（divergence）对性能的重要性后，文章转向讨论如何并行构建`BVH`树。

文章介绍了线性`BVH`（`LBVH`）方法，该方法通过使用`Z-Order`曲线（莫顿码）对对象进行排序，以保持空间邻近性，从而简化树结构的构建。在动态场景中，由于对象的移动，每个时间步都需要重新构建`BVH`树，这对并行化提出了挑战。

技术上，文中强调了"占用率"（occupancy）的优化，即在任意时刻`GPU`中活跃线程的比例。传统的自上而下`BVH`构建方法在树的高层级时占用率低，导致性能下降。相对而言，Tero Karras提出的全并行`BVH`生成算法通过消除节点之间的依赖关系，使得每个节点的覆盖范围能够直接计算，避免了父子节点间的顺序依赖问题，从而显著提升了性能，使得构建时间相比自上而下方法缩短了50倍。

该算法依赖于高效的位运算，包括莫顿码的生成和二分查找来划分对象范围。尽管每个节点的计算量增加，但由于其完全并行的特性，`GPU`利用率大幅提高，即便在小规模数据集下也表现出色。文章最后指出，并行编程与传统的串行编程有根本性区别，需要重新思考算法设计，以最大化并行计算的潜力。

## 浅析字节事件的Checkpoint安全问题

`https://zhuanlan.zhihu.com/p/2148291162`

**漏洞来源**：`PyTorch` 采用了 Python 原生的 `pickle` 模块进行模型序列化，导致反序列化时可以执行任意代码。这并非 `Huggingface` 独有的问题，而是 Python `pickle` 模块的长期问题。

**漏洞原理**：攻击者可以通过模型的序列化文件植入恶意代码。反序列化时，由于 `pickle` 模块的特性，恶意代码在与执行程序同权限下运行。

**关键技术分析**：

+   `Pickle` 注入：通过修改序列化数据，恶意代码会在反序列化时执行。例如攻击者可以通过重载 Python 对象的 `reduce` 方法注入系统调用。

+   `Monkey Patching`：动态替换函数或模块，例如在运行时劫持 `PyTorch` 的 `all_reduce` 方法，导致梯度操作被篡改。

**解决方案**：

+   安全序列化：使用 `Huggingface` 提供的 `safetensors` 或 `Google` 的 `Protobuf` 作为替代，可以有效防止代码注入。

+   文件校验：通过检查 `ckpt` 文件的哈希值检测文件篡改。

+   重载 `find_class`：在 `pickle` 反序列化时通过重载 `Unpickler.find_class` 限制可反序列化的类型。

+   `Monkey Patching` 检测：利用 Python 的 `sys.settrace()` 跟踪代码调用，检测可能的运行时修改。

## `LLM`在`Reranker`任务上的最佳实践？A simple experiment report（with code）

`https://zhuanlan.zhihu.com/p/987727357`

在`BERT`时代，`Reranker`任务通常通过encoder-only的`BERT`，将`query`与文档拼接输入，并通过`CLS`向量及`MLP`得出评分。然而，随着大语言模型（`LLM`）的发展，研究者开始探索使用decoder-only的`LLM`作为`Reranker`任务的基座。

本实验报告探索了两种使用`LLM`做`Reranker`的方法并与`BERT`类模型对比：

1.  **生成方法**：将`Reranker`任务建模为生成任务，让模型预测`query`与`doc`的相关性（是/否）。该方法充分利用`LLM`预训练和监督微调（`SFT`）的能力，采用交叉熵`loss`进行训练。

1.  **判别方法**：类似于`BERT`，使用`LLM`的`last_hidden_state`通过`MLP`层得到评分，将任务视为二分类问题，使用`BCEWithLogitsLoss`训练。

实验旨在回答以下问题：

+   `LLM`是否在`Reranker`任务上优于`BERT`？

+   生成方法与判别方法的效果对比？

+   是否可以将`LLM`的信号蒸馏到`BERT`中？

**实验结果**：

+   在小规模数据下，`LLM`（尤其是生成方法）表现优于`BERT`，生成方法的MAP比`BERT`高0.62，比判别方法高0.30。

+   难负例较少时，`LLM`仍优于`BERT`，生成方法的MAP比`BERT`高1.61。

+   在数据量充足和难负例丰富的情况下，`LLM`和`BERT`的差距缩小，但生成方法依然略优。

**蒸馏结果**： 将生成方法的`LLM`蒸馏到`BERT`中，在数据较少的情况下，蒸馏后的`BERT`模型表现接近`LLM`，MAP提升1.45。

**总结**：

+   `LLM`在数据少或难负例少的情况下优于`BERT`。

+   生成方法略优于判别方法。

+   蒸馏技术可在兼顾效果和效率的前提下，将`LLM`的信号传递给`BERT`。

**最佳实践**：

+   数据充足时，`BERT`是较好的选择，具有高效推理性能。

+   数据较少或需多语言支持时，优先选择`LLM`生成方法，并可通过蒸馏优化推理效率。

实验代码可在[`RAG-Retrieval`仓库](https://github.com/NLPJCL/RAG-Retrieval)中获取。
