## 第一部分：基本概念和功能

### Git 介绍

#### 版本控制系统

版本控制系统（Version Control System，简称 VCS）是一种程序或一系列程序，用于跟踪文件集合的变化。

**版本控制系统的主要目标包括：**

+ 轻松召回早期版本：VCS 的一个目标是能够轻松地召回单个文件或整个项目的早期版本。

+ 促进团队协作：VCS 的另一个目标是允许多名团队成员同时处理一个项目，即使是在同一个文件上工作，也不会相互影响。

通过使用版本控制系统，你可以实现以下功能：

+ 查看所有更改：能够查看项目中的所有更改、更改发生的时间以及由谁进行了更改。

+ 附带更改消息：可以在每次更改时附带一条消息，解释更改的原因。

+ 创建分支：可以创建“分支”（branches），在其中进行实验性更改。这个功能使得可以同时处理几组不同的更改（例如，新功能或错误修复），可能由不同的人完成，而不会影响主分支。之后，可以将需要保留的更改合并回主分支。

+ 附加标签：可以为版本附加一个标签，例如，标记一个新的发布版本。

**相关概念：**

+ 软件配置管理（SCM）：VCS 的另一个名称是软件配置管理（SCM）系统。这两个术语经常可以互换使用，实际上 Git 的官方文档就位于 `git-scm.com`。从技术上讲，版本控制只是 SCM 实践中的一部分。

+ 不限于软件项目：VCS 除了用于软件项目外，还可以用于其他项目，包括书籍和在线教程。

**Git 作为一种 VCS：**

+ `Git` 是一种快速、多功能、高度可扩展的免费开源版本控制系统。它的主要作者是 Linux 的创建者 Linus Torvalds。

+ 分布式版本控制：早期的 VCS，如 `CVS`、`Subversion`（`SVN`）和 `Perforce`，使用集中式服务器存储项目历史记录，这可能导致单点故障。而 `Git` 是“分布式”的，这意味着项目的完整历史记录同时存储在客户端和服务器上。你可以在没有网络连接的情况下编辑文件，在本地进行提交，并在连接可用时与服务器同步。即使服务器出现故障，你仍然拥有项目的本地副本。

+ 工作原理：`Git` 通过记住对文件的更改来工作，就像它正在对文件系统进行“快照”一样。

+ 核心操作：`Git` 的核心操作包括 `git status`（查看工作树状态）、`git add`（暂存更改）、`git commit`（将暂存的更改保存为快照，每次提交都有唯一的身份，包含作者、日期、评论等信息）和 `git log`（查看以前提交的信息）。

#### 分布式版本控制系统

分布式版本控制系统（Distributed Version Control System，简称 DVCS）是一种版本控制系统，它与早期的集中式版本控制系统有所不同。

**分布式版本控制的特点包括：**

+ 项目历史记录的存储方式：`Git` 就是一个“分布式”版本控制系统。这意味着项目的完整历史记录同时存储在客户端和服务器上。

+ 无需网络连接即可工作：由于历史记录存储在本地，开发者可以在没有网络连接的情况下编辑文件，并在本地进行提交。当网络连接可用时，再与服务器同步更改。

+ 更高的韧性：如果服务器出现故障，你仍然拥有项目的本地副本，因为完整的历史记录也保存在本地客户端。

+ 与集中式 VCS 的对比：早期的版本控制系统，如 `CVS`、`Subversion`（`SVN`）和 `Perforce`，都使用一个集中式服务器来存储项目的历史记录。这种集中化意味着单个服务器也可能成为单点故障。

简而言之，分布式版本控制系统赋予了开发者更大的灵活性和项目韧性，因为每个客户端都拥有项目的完整副本。

#### Git 的核心操作和功能

`Git` 通过一系列核心操作和功能来跟踪和保存文件更改，其工作原理类似于对文件系统进行“快照”。

以下是 `Git` 跟踪和保存文件更改的核心操作和功能：

1. 跟踪更改的基本理念 `Git` 的工作方式是记住对文件的更改，就像它正在对文件系统进行“快照”一样。版本控制系统（VCS）的一个目标是能够轻松地召回单个文件或整个项目的早期版本。

1. `git status` 命令

+ 这是第一个也是最常用的 `Git` 命令之一。

+ `git status` 命令显示工作树的状态（以及暂存区的状态）。

+ 它让你能够看到 `Git` 当前正在跟踪哪些更改，从而决定是否要让 `Git` 进行另一次快照。

1. `git add` 命令

+ `git add` 命令用于告诉 `Git` 开始跟踪某些文件中的更改。

+ 技术术语是“暂存（staging）”这些更改。

+ 你将使用 `git add` 来暂存更改，为提交做准备。

+ 所有已添加但尚未提交的文件中的更改都存储在“暂存区（staging area）”中。

1. `git commit` 命令

+ 一旦你为提交暂存了一些更改，就可以通过调用 `git commit` 命令将你的工作保存为快照。

+ “提交（Commit）”既是动词也是名词。作为动词，提交更改意味着你将文件、目录或其他“内容”的副本作为新版本放入仓库中。作为名词，一次提交是一个小数据块，它赋予你提交的更改一个唯一的身份。

+ 保存到提交中的数据包括作者的姓名和电子邮件地址、日期、关于你做了什么（以及为什么）的评论、可选的数字签名，以及前一次提交的唯一标识符。

+ “提交”意味着你正在提交所做的更改，以便其他人最终也能看到它们。

+ 一个“提交对象（commit object）”代表工作树的一个特定版本。

1. `git log` 命令

+ `git log` 命令允许你查看以前提交的信息。

+ 每次提交都附带一条消息（提交消息），`git log` 命令会打印最近提交的信息，例如它们的时间戳、作者和提交消息。

+ 这个命令可以帮助你跟踪你一直在做什么以及保存了哪些更改。

1. 核心术语与概念

+ 工作树（Working tree）：包含正在处理的项目的嵌套目录和文件集。

+ 仓库（Repository/Repo）：位于工作树顶层的目录，`Git` 在其中保存项目的所有历史记录和元数据。

+ 哈希（Hash）：`Git` 使用 160 位长的哈希值来表示文件或其他对象的内容。使用哈希的一个优点是，`Git` 可以通过对其内容进行哈希并将其结果与先前的哈希进行比较来判断文件是否已更改。即使文件的时间戳改变了，但如果哈希值没有改变，`Git` 也知道文件内容没有改变。

1. `git help` 命令

+ 你可以使用 `git help` 命令轻松获取关于所有已学命令及更多命令的信息。

+ 每个命令都有其自己的帮助页面，你可以通过键入 `git <command> --help` 来查找，例如 `git commit --help` 会显示关于 `git commit` 命令及其使用方法的更多信息。

通过这些机制，`Git` 能够系统地跟踪文件的每一次更改，将它们保存为可追溯的快照，并提供查看历史记录的功能。

#### Git 和 Github 的联系和区别

`Git` 和 `GitHub` 之间存在着显著的区别，尽管它们紧密相关：

+ `Git` 是一种分布式版本控制系统（DVCS）：

+ `Git` 是一个快速、多功能、高度可扩展的免费开源版本控制系统（VCS）。

+ 它的主要作者是 Linux 的创建者 Linus Torvalds。

+ 作为一种 DVCS，项目的完整历史记录存储在客户端和服务器上。这意味着开发者可以在没有网络连接的情况下编辑文件，在本地进行提交，并在连接可用时与服务器同步。

+ `Git` 通过记录文件更改的方式工作，就像对文件系统进行“快照”一样。

+ 它提供了一种使用一个或多个本地分支并将它们推送到远程仓库的方式。

+ `Git` 命令包括 `git status`（显示工作树和暂存区的状态）、`git add`（告诉 `Git` 开始跟踪文件更改并暂存这些更改）、`git commit`（将暂存的更改保存为快照，每次提交都有唯一的身份，包含作者、日期、评论等信息）、`git log`（查看以前提交的信息，如时间戳、作者和提交消息）和 `git help`（获取命令信息）。

+ `Git` 功能强大，可以通过命令行界面完全访问其所有功能。

+ `GitHub` 是一个基于 `Git` 技术的云平台：

+ `GitHub` 是一个以 `Git` 为核心技术的云平台。

+ 它简化了项目协作过程，并提供了一个网站、更多的命令行工具以及开发者和用户可以协同工作的整体流程。

+ `GitHub` 充当了 `Git` 中提到的远程仓库。

+ `GitHub` 提供了一些关键功能，以增强团队协作和项目管理，包括：

+ 议题（Issues）

+ 讨论（Discussions）

+ 拉取请求（Pull requests）

+ 通知（Notifications）

+ 标签（Labels）

+ 操作（Actions）

+ 分支（Forks）

+ 项目（Projects）

简而言之，`Git` 是底层工具和版本控制系统，而 `GitHub` 是一个基于 `Git` 构建的平台，它提供了托管远程仓库、协作功能和图形界面来简化开发流程。

### Github 简介

#### Github 基础构件

`GitHub` 建立在 `Git` 的基本概念之上，并在此基础上增加了协作工具、自动化功能和用户友好的网页界面。以下是其核心组件：

+ `Git`：作为基础，`Git` 是一个分布式版本控制系统，允许开发者跟踪代码变更、协同工作并管理版本历史。

+ 仓库（Repositories）：仓库是项目的核心组织单元，包含所有项目文件及其修订历史。它们是管理工作、跟踪变更以及与他人协作的关键部分。仓库可以是公开的（对所有人可见）或私有的（仅限授权用户访问）。

+ 分支（Branches）：分支是 `GitHub` 体验的重要组成部分，它允许用户在不影响默认分支（通常是主分支）的情况下进行修改。分支提供了一个安全的实验空间，用户可以在其中尝试新功能或修复问题，直到准备好合并。

+ 提交（Commits）：提交是对分支上一个或多个文件的变更。每个提交都有唯一的 ID、时间戳和贡献者，无论是通过命令行还是 `GitHub` 网页界面创建。提交提供了清晰的审计跟踪，便于审查文件历史或相关项（如议题或拉取请求）。文件在 `Git` 仓库中经历不同的状态，包括未跟踪（Untracked）和已跟踪（Tracked），其中已跟踪文件又分为未修改（Unmodified）、已修改（Modified）、已暂存（Staged）和已提交（Committed）等子状态。

+ 拉取请求（Pull Requests）：拉取请求是用于表示一个分支上的提交已准备好合并到另一个分支的机制。提交拉取请求的团队成员会邀请一名或多名评审员验证代码并批准合并。评审员可以在拉取请求上评论变更、添加自己的变更或用于进一步讨论。`GitHub` 也支持草稿拉取请求（Draft Pull Requests），允许在代码尚未准备好审查时就开启拉取请求。

+ `GitHub Flow`：这是一种简单的工作流程，通过分支、拉取请求和合并，帮助团队安全地进行和分享变更，非常适合尝试想法和团队协作。其流程包括创建分支、进行更新、开启拉取请求邀请反馈、根据反馈进行更新、获得批准并合并到主分支，最后删除分支以保持仓库整洁。

+ `Git Flow`：作为 `GitHub Flow` 的替代方案，`Git Flow` 是一种更结构化的分支模型，常用于发布驱动的环境，它使用多种长期和临时分支，如 `master`、`develop`、`feature/`、`release/`和 `hotfix/`等。

#### Github Flow 流程

`GitHub flow` 是一种简单的、帮助您安全地进行和分享变更的工作流程。它非常适合尝试新想法以及使用分支、拉取请求和合并与团队协作。`GitHub flow` 是建立在 `Git` 的基本概念之上的。

`GitHub flow` 的核心组件包括：

+ 分支（Branches）：分支是 `GitHub` 体验的重要组成部分，它允许您在不影响默认分支（通常是主分支）的情况下进行修改。分支提供了一个安全的实验空间，您可以在其中尝试新功能或修复，直到准备好将变更合并回默认分支。

+ 提交（Commits）：提交是对分支上一个或多个文件的变更。每个提交都由唯一的 ID、时间戳和贡献者跟踪，无论它是在命令行还是通过 `GitHub` 网页界面创建的。提交提供了清晰的审计跟踪，便于审查文件历史或相关项。

+ 拉取请求（Pull Requests）：拉取请求是用来表示一个分支上的提交已准备好合并到另一个分支的机制。提交拉取请求的团队成员会邀请一名或多名评审员验证代码并批准合并。评审员可以在拉取请求上评论变更、添加自己的变更或用于进一步讨论。`GitHub` 也支持草稿拉取请求，允许您在代码尚未准备好审查时就开启拉取请求。

`GitHub flow` 的工作流程

`GitHub flow` 的步骤如下：

1. 创建分支：首先创建一个分支，以便您的变更、功能或修复不会影响主分支。

1. 进行更新：在该分支中进行您的更新。如果您的工作流程支持，您可以在合并之前部署变更进行测试。

1. 开启拉取请求：然后，开启一个拉取请求以征求反馈并开始审查。

1. 根据反馈更新：接着，审查评论并根据团队的反馈进行任何必要的更新。

1. 获得批准并合并：最后，一旦您对自己的变更充满信心，获得批准并将拉取请求合并到主分支。

1. 删除分支：合并后，删除该分支以保持仓库整洁并避免使用过时的分支。

#### 团队协作功能

协作是 `GitHub` 一切工作的核心。`GitHub` 提供了丰富的工具来帮助团队高效协同工作，减少延迟并简化工作流程。

**议题（Issues）**

`GitHub` 议题用于跟踪工作中的想法、反馈、任务或错误。议题可以从多种方式创建，包括任务列表项、项目备注、议题或拉取请求评论、特定代码行或 URL 查询。议题可以分配给特定人员、添加到项目面板、关联到里程碑或应用标签，这些功能有助于有效管理协作并提高议题可见性。议题模板有助于为贡献者保持一致的结构和期望。当一个讨论产生需要跟踪的工作时，可以将其转换为议题。

讨论（Discussions）：

讨论功能适用于不一定与代码相关的对话，如问答、想法或一般反馈。它们支持在共享论坛中进行开放、持续的交流，并可根据仓库可见性设置为公开或私有。仓库维护者可以启用讨论功能，并创建不同类别的讨论，如公告、通用、想法、投票、问答和展示。在问答式讨论中，可以将某个评论标记为问题的答案。重要的讨论可以被置顶（Pinning a discussion）以提高可见性。

**通知和订阅（Notifications and Subscriptions）**

+ 通知帮助用户及时了解仓库和团队的重要活动。用户可以订阅特定议题、拉取请求、Gist、仓库活动或工作流状态的通知。当用户参与对话（评论、开启议题、被分配）时，会自动订阅，也可以手动管理订阅。用户可以取消订阅、取消关注或自定义接收通知的类型。

+ `GitHub` 还允许用户通过观察设置（watch settings）过滤通知，包括观察中（Watching）（接收所有活动通知）、未观察（Not watching）（仅在参与或被提及时接收通知）、忽略（Ignore）（不接收任何通知）和自定义（Custom）（微调触发通知的活动类型）。提及（@mentions）：通过使用搜索限定符 `mentions:<username>`，用户可以找到所有提到特定用户的对话。

+ 通知可以通过电子邮件、网页或移动应用接收。

**其他功能**

**Gist**：`Gist` 是 `GitHub` 的一项功能，允许用户以轻量级方式分享代码片段、笔记或其他少量信息。它们本质上是迷你的 `Git` 仓库，支持分支、克隆和版本控制。`Gist` 可以是公开的（Public Gists）（所有人可见且可搜索）或秘密的（Secret Gists）（不可搜索，但知道 URL 的人可以访问）。`Gist` 支持版本控制、克隆、嵌入到网页/博客、Markdown 格式以及轻量级协作。

**维基（Wikis）**：每个 `GitHub` 仓库都配备了一个维基部分，用于托管项目的长篇文档，例如如何使用项目、设计理念或核心原则。维基的访问权限与仓库的读取权限相关。

**AI 赋能功能**：`GitHub Enterprise` 平台通过 AI 赋能的拉取请求和议题增强协作，提高生产力，并通过提供更快的反馈来改善安全性。

**自动化**：平台通过内置的 CI/CD（持续集成和持续交付）工具加速生产力，自动化重复性任务，从而简化工作流程并支持协作。

**GitHub Pages**：用户可以使用 `GitHub Pages` 直接从仓库托管关于自己、组织或项目的网站。它是一个静态网站托管服务，可以将 HTML、CSS 和 JavaScript 文件从仓库中发布为网站。

# Git flow 分支模型与 GitHub 产品计费

## Git flow 分支模型

Git flow 是一种结构化的分支模型，常用于以发布为驱动的环境中。它与 GitHub Flow 不同，GitHub Flow 是一种为持续交付设计的轻量级工作流，而 Git flow 则更为“重量级”，因为它涉及额外的分支管理。Git flow 比 GitHub Flow 出现得更早，所以在提及默认分支时，你可能会看到使用`master`而不是`main`的术语。

### Git flow 的分支类型

Git flow 使用多种长期和临时分支：

+   `master`：始终反映可用于生产环境的代码。

+   `develop`：包含下一个版本最新的开发工作。

+   `feature/`：用于创建新功能；从 `develop` 分支出来，完成后再合并回去。

+   `release/`：用于准备从 `develop` 分支出来的新的生产版本；允许进行最终测试和小的 bug 修复。

+   `hotfix/`：用于快速修补生产环境中的问题；从 `master` 分支出来。

### Git flow 的工作流程

Git flow 的处理过程如下：

1. 开发者从 `develop` 分支创建功能分支（feature branches）来开发新功能。

2. 当需要发布时，从 `develop` 创建一个发布分支（release branch）。这会将发布准备工作隔离起来，以便开发可以不间断地继续。

3. Bug 修复可以添加到发布分支，但主要功能应该等待未来的发布。

4. 一旦准备就绪，发布分支会合并到 `master` 分支并打上版本号标签。GitHub 可以使用这些标签来帮助生成发布说明。

5. 同一个发布分支也应该合并回 `develop`，以保持同步。

6. 如果出现关键的生产 bug，会从 `master` 分支创建一个热修复分支（hotfix branch）。修复后，它会合并到 `master` 和 `develop` 两个分支。

### 何时使用 Git flow

Git flow 最适合以下项目：

+   具有**计划或版本发布**的项目。

+   需要维护**多个生产版本**（例如，长期支持分支）的情况。

+   适用于**较慢、结构更严谨的开发周期**（例如，企业或受监管的环境）。

需要注意的是，Git flow 假设使用合并提交来集成分支。使用 `rebase` 或 `squash` 合并可能会干扰其分支结构和历史跟踪。对于许多使用 GitHub 的团队来说，GitHub Flow 更简单、更快。但如果你的团队重视可预测性并需要更多的发布计划，Git flow 可能更适合。

## GitHub 产品简介

### GitHub 账户类型和计划

首先，了解 GitHub 账户类型和订阅计划之间的区别很重要。

#### GitHub 账户类型

+   个人账户（Personal Accounts）：每个使用 GitHub.com 的用户都登录到个人账户，这是您在 GitHub.com 上的身份，拥有用户名和个人资料。个人账户可以拥有仓库、包和项目等资源，并且可以直接管理权限。您在 GitHub.com 上的操作（如创建问题或审查拉取请求）都归属于您的个人账户。

+   组织账户（Organization Accounts）：组织账户是共享账户，无限数量的人可以在其中同时协作处理许多项目。与个人账户不同，组织账户的权限采用分层管理。组织可以拥有仓库、包和项目，但您不能直接登录组织。每个人都登录自己的个人账户，对组织资源进行的任何操作都归因于其个人账户。每个个人账户都可以是多个组织的成员。组织内的个人账户可以被赋予不同的角色，以获得不同级别的访问权限。只有组织所有者和安全管理员才能管理组织设置和控制数据访问。

+   企业账户（Enterprise Accounts）：GitHub.com 上的企业账户允许管理员集中管理多个组织的策略和计费，并支持组织间的内部源协作。企业账户必须有一个句柄，类似于 GitHub 上的组织或用户账户。企业所有者可以在企业设置中邀请现有组织加入企业账户、在企业账户之间转移组织或创建新组织。企业账户允许您管理和强制执行企业拥有的所有组织的策略。

#### GitHub 订阅计划

GitHub 提供多种免费和付费产品，以改进软件管理流程和团队协作。

+   **`GitHub Free`**：为个人账户和组织提供基本功能。

+   个人账户的 `GitHub Free`：包括无限的公共和私有仓库以及无限的协作者。提供 GitHub 社区支持、Dependabot 警报、双因素身份验证强制执行、500MB GitHub Packages 存储、每月 120 小时 GitHub Codespaces 核心使用时间和每月 15GB GitHub Codespaces 存储。`GitHub Actions` 每月提供 2,000 分钟，并为公共仓库提供部署保护规则。

+   **组织的 `GitHub Free`**：与无限协作者在无限公共仓库上工作，功能齐全；或在有限功能集下使用无限私有仓库。除了个人账户的 `GitHub Free` 功能外，还包括用于管理团队的访问控制。

+   **`GitHub Pro`**：与 `GitHub Free` 类似，但提供升级功能，专为希望在仓库中获得高级工具和洞察力，但不属于团队的个人开发者设计。包括 `GitHub Free` 账户的所有功能，外加通过电子邮件获得 GitHub 支持、每月 3,000 分钟 `GitHub Actions`、2GB `GitHub Packages` 存储、每月 180 小时 `GitHub Codespaces` 核心使用时间和每月 20GB `GitHub Codespaces` 存储。在私有仓库中提供高级工具和洞察力，如必需的拉取请求审查者、多重拉取请求审查者、受保护分支、代码所有者、自动链接引用、`GitHub Pages`、维基以及用于脉冲、贡献者、流量、提交、代码频率、网络和分支的仓库洞察图。

+   **`GitHub Team`**：专为需要超越组织版 `GitHub Free` 所提供的增强协作、安全和工作流管理功能的组织设计。它提供更慷慨的使用限制（如额外的 `GitHub Actions` 分钟和 `Packages` 存储），但其真正价值在于支持团队高效安全协作的高级功能。包括通过电子邮件获得 GitHub 支持、每月 3,000 分钟 `GitHub Actions`、2GB `GitHub Packages` 存储。在私有仓库中提供高级工具和洞察力，如必需的拉取请求审查者、多重拉取请求审查者、草稿拉取请求、团队拉取请求审查者、受保护分支、代码所有者、计划提醒、用于文档和网页内容的 `GitHub Pages` 和维基，以及富有洞察力的仓库图表。还能够启用或禁用 `GitHub Codespaces` 以进行云开发。

+   `GitHub Enterprise`：为大规模组织提供增强支持、强大安全、合规能力和高级部署控制。注册 `GitHub Enterprise` 后，您将创建一个企业账户。作为企业所有者，您可以在一个伞形结构下管理多个组织、控制管理员访问并强制执行整个企业的统一安全策略。除了 `GitHub Team` 的所有功能外，`GitHub Enterprise` 还增加了专用 `GitHub Enterprise` 支持、扩展的安全、合规和部署功能、通过外部身份提供商进行集中用户身份验证和管理、用于私有或内部仓库的部署保护规则、`GitHub Connect`（允许在 `GitHub Enterprise Server` 和 `GitHub Enterprise Cloud` 之间安全共享选定数据）、以及购买 `GitHub Advanced Security` 的选项。`GitHub Enterprise` 选项：有 `GitHub Enterprise Server`（GHES）和 `GitHub Enterprise Cloud` 两种选项。

+   `GHES` 是一个自托管解决方案，允许组织完全控制其基础设施。

+   `GitHub Enterprise Cloud` 提供了更多的 `GitHub Actions` 分钟数和 `GitHub Packages` 存储，例如每月 50,000 分钟 `GitHub Actions` 和 50GB `GitHub Packages` 存储，并提供 99.9% 月度正常运行时间的服务级别协议。它还允许通过企业账户集中管理多个 `GitHub.com` 组织的策略和计费，并可通过企业托管用户（EMU）供应和管理开发人员的用户账户。`EMU` 允许组织使用其身份提供商控制身份，实现集中访问管理和增强安全性。

+   **`GitHub Copilot`** 默认不包含在任何计划中，但 `Copilot Business` 和 `Copilot Enterprise` 可以添加到符合条件的计划中。

### GitHub 计费模型

GitHub 根据账户类型（个人、组织或企业）进行计费。个人账户和大多数组织会收到单独的账单，而企业账户可以整合多个组织的账单或根据内部配置将费用路由到不同的成本中心。

每张账单都反映了订阅和基于使用量的费用组合：

+   订阅（Subscriptions）：包括账户的计划（如 `GitHub Pro` 或 `GitHub Team`）以及 `GitHub Copilot` 或 Marketplace 应用程序等产品的固定月费。

+   基于使用量的计费（Usage-based billing）：适用于成本随使用量变化的产品，例如 `GitHub Actions`（基于运行时分钟数和制品存储）或 `GitHub Packages`。大多数计划都包含一定数量的免费使用分钟数或存储空间，例如 `GitHub Pro` 包括每月 3,000 分钟免费 `GitHub Actions`。您可以通过设置支出限额来管理超额使用。

了解 GitHub 的计费模型有助于规划预算、跟踪使用情况和管理账户成本。

### 特定产品的计费管理和优化

#### a. `GitHub Actions`

`GitHub Actions` 支持在仓库内自动化工作流。

+   **定价模型**：根据仓库可见性和账户类型而异。

+   **公共仓库**：`GitHub Actions` 的使用是免费的，在 `GitHub` 托管的运行器上提供无限分钟数。

+   **私有仓库**：每个账户根据其计划获得一定数量的免费分钟数和存储空间。例如，个人账户的 `GitHub Free` 包括每月 2,000 分钟 `CI/CD`。超出包含额度的使用由支出限额管理。

+   **追踪消耗**：在 `GitHub` 组织或账户的 `Settings → Billing` 中，可以查看 `GitHub Actions` 的使用分钟数，并按仓库、运行器类型（Linux、macOS、Windows）和剩余配额进行细分。

+   **优化策略**：

+   对于高流量工作流，使用**自托管运行器**以降低成本。

+   通过缓存依赖项和减少冗余作业来优化工作流脚本。

+   仅在必要时触发工作流（例如，仅推送到 `main` 分支时）。

#### b. `GitHub Packages`

`GitHub Packages` 允许存储制品、容器镜像和依赖项。存储根据存储数据量和数据传输使用量进行计量。

+   **追踪消耗**：在 `Settings → Billing → GitHub Packages` 中查看存储使用情况。细分包括每个仓库使用的存储（GB）和数据传输（GB）。

+   **计费详情**：

+   **免费分配**：公共仓库免费存储和带宽。私有仓库最多 2GB 存储，每月最多 1GB 数据传输。

+   **优化策略**：

+   定期**删除未使用的包**或启用保留策略。

+   将常用镜像存储在**集中式注册表**中，以减少重复。

+   使用**压缩格式**以减少存储消耗。

#### c. `GitHub Enterprise` 许可证

**`GitHub Enterprise`** 为组织提供高级功能，活跃用户的数量决定了许可证的消耗。

+   **计费模型**：每个访问私有仓库的用户消耗一个许可证。组织按用户按年或按月支付。如果用户在一个月内开始消耗许可证，组织将按比例支付该用户的使用费用。如果用户在一个月内停止消耗许可证，下个月的计费将反映此变化，确保组织只为活跃用户付费。

+   **追踪消耗**：在 `Enterprise Settings → Billing` 中查看许可证使用报告。监控活跃用户与分配的许可证。企业管理员可以使用 `GitHub Enterprise Cloud` 管理面板、企业账户计费页面、`GitHub Enterprise Server` 仪表板以及 `GraphQL API` 或 `REST API` 来跟踪许可证使用情况。

+   **优化策略**：

+   审核**非活跃用户**并撤销其访问权限以释放许可证。

+   使用 `SSO` 和 `SCIM` 供应来自动化用户管理。

+   **定期审计**：每月或每季度进行审查以控制成本。

+   **回收未使用的席位**：识别非活跃用户并释放未使用的许可证。

#### d. `GitHub Advanced Security`（`GHAS`） 许可证

`GHAS` 提供代码扫描、秘密扫描和依赖项审查以增强安全性。

+   **计费模型**：`GHAS` 计费基于在过去 90 天内向启用了 `GHAS` 的仓库推送至少一次提交的唯一活跃提交者数量。如果提交者贡献到多个仓库，他们只计算一次。

+   **追踪消耗**：在 `GitHub.com` 上，选择 `Enterprises`，然后选择您的企业，导航到 `Billing → Advanced Security` 查看 `GHAS` 使用情况。

+   **优化策略**：

+   将 `GHAS` 限制在**真正需要高级安全**的仓库。

+   使用**分支保护**来限制功能分支上不必要的扫描。

#### e. `GitHub Copilot`

`GitHub Copilot` 提供 AI 驱动的代码补全和建议，按用户计费。

+   **追踪消耗**：管理员可以在组织设置的 `Billing → Copilot` 下跟踪 `Copilot` 使用情况。报告显示活跃用户和每月估计账单。

+   **计费详情**：可供个人和企业使用，并提供不同的订阅选项。学生和经过验证的开源维护者可免费使用。部分企业客户可免费试用。

+   **优化策略**：

+   定期**审查并停用**不需要 `Copilot` 的用户。

+   **鼓励开发人员在不需要** AI 生成代码的项目中禁用 `Copilot`。

#### f. `GitHub Codespaces`

使用 `GitHub Codespaces` 会根据存储和计算时间产生额外费用，具体取决于您的计划。

+   **免费分配**：`GitHub Free` 个人账户每月包含 120 小时核心使用时间和 15GB 存储。`GitHub Pro` 账户每月包含 180 小时核心使用时间和 20GB 存储。

#### g. 大文件存储（`LFS`）

`GitHub LFS` 用于将大型二进制文件与 `Git` 仓库分开存储。

+   **追踪消耗**：在 `Billing → LFS Usage` 中查看 `LFS` 使用情况。报告包括存储（GB）和带宽使用量（GB）。

+   **计费详情**：

+   **免费额度**：每个账户每月 1GB 存储和 1GB 带宽使用量。

+   **优化策略**：

+   对于大文件，使用**外部存储服务**（如 `AWS S3`、`Azure Blob Storage`）。

+   **删除未使用的**大文件以优化存储。

+   启用 `Git LFS` 文件修剪以删除未引用的对象。

### 账户管理和最佳实践

#### 多账户管理

+   **企业账户**：允许管理员为多个组织集中管理策略和计费，并实现组织间的内部源协作。企业所有者可以管理多个组织，控制管理员访问，并在整个企业强制执行一致的安全策略。企业账户可以合并多个组织的账单，或根据内部配置将费用路由到不同的成本中心。

+   **个人账户**：通常与组织账户分开计费。

+   **精细的支出控制**：管理员可以为 `GitHub Actions` 和 `GitHub Packages` 等服务设置特定的支出限额，防止意外超额。当接近支出限额时，管理员可以通过 `GitHub UI` 和电子邮件通知接收警报。

+   **详细的使用洞察**：增强的计费平台提供对产品使用的深入可见性，允许组织监控消耗模式并优化资源分配。

+   **自动化报告**：自动化使用报告功能简化了财务监督并促进内部费用分摊。

#### 许可证使用情况管理最佳实践（适用于企业）

+   **自动化监控**：使用 `GraphQL` 或 `REST API` 查询来跟踪使用趋势。

+   **回收未使用的席位**：识别非活跃用户并释放未使用的许可证。

+   **启用基于使用量的计费**：使计费与实际消耗保持一致。对于新企业客户，通常默认采用按使用量付费（`PAYG`）模式，计费基于实际使用量（活跃席位）。

+   **定期审计**：每月或每季度进行审查以控制成本。

#### 管理机器账户和外围服务许可证

+   **机器账户**：用于自动化、运行脚本或与第三方工具集成的 `GitHub` 账户。每个机器账户都会消耗一个 `GitHub` 许可证。

+   **外围服务**：通过 `API` 请求与 `GitHub` 交互的外部集成，如 `CI/CD` 流水线、安全扫描工具和第三方集成。

+   **追踪和优化**：追踪这些账户和服务的许可证使用对于成本优化、安全合规至关重要。可以通过 `GitHub Enterprise Admin Console`、`GraphQL API` 或 `REST API` 来识别活跃机器账户、上次活动日期、自托管运行器数量以及 `API` 调用日志，以识别不活跃的账户、优化使用并防止不必要的支出。

+   **最佳实践**：

+   **定期审计机器账户**：识别并停用未使用的机器账户，以减少安全风险和不必要的许可证分配。

+   **监控 `API` 使用情况**：跟踪消耗企业许可证的第三方工具，防止过度 `API` 调用和安全漏洞。

+   **优化运行器使用**：识别空闲的自托管运行器并降低 `GitHub` 托管运行器的成本。

+   **限制机器账户权限**：限制其对仓库的不必要访问，并强制执行安全策略，以最小化潜在的泄露风险。

## Github 代码扫描

代码扫描可以通过多种方式整合到现有开发工作流程中，以显著提高软件安全性。其核心目标是发现、分类并优先修复代码中现有的安全漏洞和编码错误，并防止开发者引入新的问题。

以下是代码扫描如何整合到开发工作流程中的具体方法：

### 选择合适的设置方式

- 默认设置（Default Setup）：这是最快的配置方式，适用于希望快速启用 `CodeQL` 分析的仓库。它会自动选择分析语言、查询套件以及触发扫描的事件。默认设置将代码扫描作为 `GitHub Actions` 运行，无需手动维护工作流文件。

- 高级设置（Advanced Setup）：此选项提供更高的灵活性。它会生成一个可定制的工作流文件（通常是 `codeql-analysis.yml`），您可以直接提交到您的仓库。通过高级设置，您可以精确控制扫描的频率、要扫描的语言或目录、`CodeQL` 在代码中查找的内容，甚至编译代码的特定命令。如果已使用默认设置，可以切换到高级设置以获得更多控制。

- 在外部 CI 系统运行 `CodeQL CLI` 并上传结果（Run CodeQL CLI in an external CI system）：如果您有现有的持续集成（CI）系统，可以在其中直接运行 `CodeQL CLI` 进行代码分析，并将生成的静态分析结果交换格式（SARIF）文件上传到 GitHub。

### 配置扫描触发事件和频率

- 按推送扫描（Scan on Push）：默认 `CodeQL` 分析工作流使用 `on:push` 事件，在每次代码推送到仓库的默认分支和任何受保护分支时触发代码扫描。扫描结果会显示在仓库的“安全”选项卡中。当检测到的问题可以映射到开放的拉取请求时，这些警报也会自动出现在拉取请求中。

- 按拉取请求扫描（Scan on PR）：默认 `CodeQL` 分析工作流使用 `on:pull_request` 事件，在针对默认分支的拉取请求被创建时触发代码扫描。扫描结果会作为警报显示在拉取请求检查中。扫描拉取请求的合并提交通常比每次推送都扫描分支头更高效和准确。

- 定期扫描（Scheduled Scan）：除了事件触发的扫描外，默认 `CodeQL` 分析工作流每周会以随机生成的时间表扫描一次代码。您可以修改工作流中的 `cron` 值来调整此计划，例如，将其设置为每周一特定时间运行。定期扫描有助于发现 GitHub、安全研究人员和社区发现的最新漏洞和错误，即使开发者不经常维护仓库也是如此。

- 避免不必要的扫描：可以通过在代码扫描工作流中指定 `on:pull_request:paths-ignore` 或 `on:pull_request:paths` 来避免对特定文件更改（例如 `.md` 或 `.txt` 文件）的拉取请求进行扫描。

### 集成第三方工具

- 上传 SARIF 文件：您可以将外部生成或使用 `GitHub Actions` 生成的 SARIF 文件上传到 GitHub，以便在仓库中查看来自第三方工具的代码扫描警报。GitHub 使用 SARIF 文件中的信息来创建代码扫描警报，且结果必须使用 SARIF 版本 2.1.0。

- 通过 `CodeQL CLI` 上传：`CodeQL CLI` 是一个独立的工具，可以生成代码库的数据库表示，然后运行查询生成 SARIF 格式的结果，并将其上传到 `GitHub.com`。

- 通过 `代码扫描 API` 上传：`代码扫描 API` 允许您检索和更新代码扫描警报、分析、数据库和默认设置配置，也可以用于上传使用离线代码扫描工具生成的分析结果。

- 通过 `GitHub Actions` 上传 SARIF：可以使用 `github/codeql-action` 仓库中的 `upload-sarif` 动作来上传第三方 SARIF 文件。该动作可以在 `push` 和 `scheduled` 事件发生时运行。这对于将外部生成的 SARIF 文件提交到仓库后进行上传，或作为 CI 工作流的一部分生成 SARIF 文件并进行上传非常有用，例如与 `ESLint` 等静态分析工具结合使用。

### 管理警报和拉取请求检查

- 定义导致拉取请求检查失败的严重级别：默认情况下，只有严重级别为“错误”或安全严重级别为“关键”或“高”的警报才会导致拉取请求检查失败。拉取请求失败会阻止代码合并，但不会停止代码扫描。您可以在仓库设置中更改这些级别。

- 去重机制：每次上传新的代码扫描结果时，GitHub 会处理这些结果并将警报添加到仓库。它使用指纹识别（`partialFingerprints` 字段）来匹配不同运行中的相同问题，以防止重复警报。

通过将代码扫描配置为在关键开发事件（如代码推送和拉取请求）发生时自动运行，或者根据预设的时间表定期运行，开发团队可以在代码更改进入生产环境之前捕获潜在的安全漏洞和编码错误。这有助于早期发现并解决问题，从而提高整体软件安全性。

`GitHub Actions` 对于公共存储库是免费使用的。

对于私有存储库，每个 GitHub 账户会根据其所使用的产品获得一定数量的免费分钟数和存储空间。超出这些免费额度的使用将受消费限额控制。

`CodeQL` 作为 GitHub 代码扫描的核心分析引擎，其分析结果也会作为代码扫描警报显示在 GitHub 中。`CodeQL CLI` 对于在 `GitHub.com` 上维护的公共存储库是免费使用的。对于客户拥有的私有存储库，使用 `CodeQL CLI` 则需要 GitHub Advanced Security 许可证。

运行 `GitHub Actions` 中的代码扫描工作流会消耗 `GitHub Actions` 的分钟数。

## Codespaces 概述

### 运作机制

### 可配置的开发环境

GitHub `Codespaces` 旨在为项目创建可配置的自定义开发环境，确保所有项目用户都能获得可重复的 `Codespace` 配置。它的生命周期从创建开始，到删除结束。

### 创建流程

创建 `Codespace` 时，会发生四个主要进程：

- 分配虚拟机（VM）和存储。

- 创建一个容器。

- 建立与 `Codespace` 的连接。

- 执行创建后设置。这个过程可能需要几分钟来创建开发环境。

### 持久性与保存

你的工作保存到云中的虚拟机上。

- 通过 Web 连接到 `Codespace` 时，自动保存会自动启用。

- 通过桌面版 Visual Studio Code 连接时，需要手动启用自动保存。你可以关闭并停止 `Codespace`，之后返回到保存的工作，不会丢失对项目所做的更改。

### 恢复与重新连接

你可以断开连接并重新连接到活动的 `Codespace`，而不会影响其正在运行的进程。可以随时从 `GitHub.com`、JetBrains IDE、Visual Studio Code 或通过 `GitHub CLI` 重新打开任何活动或已停止的 `Codespace`。

### 超时与停止

如果 `Codespace` 处于非活动状态或未显式停止，它会在一段时间（默认 30 分钟）后超时并停止运行。停止的 `Codespace` 仅产生存储成本。当 `Codespace` 超时时，将保留上次保存更改时的数据。

### 网络连接

`Codespace` 需要 Internet 连接。如果连接丢失，你将无法访问 `Codespace`，但所有未提交的更改都会保存。重新建立连接后，可以访问 `Codespace`。

### 重新生成

你可以重新生成 `Codespace` 以实施对开发容器配置的更改。在重新生成时，`/workspaces` 目录中的更改（包括存储库克隆）会得到保留，而该目录之外的更改会被清除。

### 删除

完成任务并将更改推送到远程分支后，可以安全地删除 `Codespace`。如果 `Codespace` 包含未推送的 `Git` 提交，编辑器会通知你，你可以选择推送、删除（并丢失未提交更改）或将代码导出到新分支。非活动的已停止 `Codespace` 也会在指定时间后自动删除（默认 30 天，可自定义保留间隔）。

### Codespace 与 GitHub.dev 的对比

以下是它们之间的主要区别：

1. 核心用途和计算能力

+ `GitHub.dev`：主要用于导航文件和源代码存储库，以及进行代码更改并提交代码更改。它没有关联的计算资源，因此无法用于构建、运行或调试代码。它更适合于轻量级的浏览和编辑。

+ GitHub Codespaces：适用于更繁重的工作，如测试代码。它具有关联的计算资源，可以让你生成代码、运行代码并具有终端访问权限。它提供了个人虚拟机 （VM） 的强大功能，就像在使用自己的本地环境一样，只是在云中。

1. 成本

+ `GitHub.dev`：免费使用。

+ GitHub Codespaces：个人账户每月有免费使用配额。只有正在运行的 Codespace 才会产生 CPU 费用，而停止的 Codespace 仅产生存储成本。

1. 启动时间

+ `GitHub.dev`：按下按键时立即打开，可以马上开始使用，无需等待配置或安装。

+ GitHub Codespaces：创建或继续 Codespace 时，需要分配虚拟机和存储，创建一个容器，建立连接，并执行创建后设置。这个过程需要几分钟时间来创建开发环境。

1. 终端访问

+ `GitHub.dev`：不提供终端访问。

+ GitHub Codespaces：默认提供一组通用工具的集成终端访问，可以像在本地环境一样使用终端。

1. 扩展支持

+ `GitHub.dev`：在扩展视图中，只有可以在 Web 中运行的扩展子集会显示并可以安装。

+ GitHub Codespaces：可以使用 Visual Studio Code Marketplace 中的大部分扩展。

1. 持久性与生命周期

+ `GitHub.dev`：没有持久的云环境的概念。

+ GitHub Codespaces：拥有一个从创建到删除的生命周期，可以断开连接并重新连接，停止并重启，而不会丢失更改。你的工作会保存到云中的虚拟机上。当 Codespace 处于非活动状态或未显式停止时，它会在一段时间后超时并停止运行，但数据会被保留。

尽管两者有所不同，但你可以在 `GitHub.dev` 中启动工作流，并在需要“运行和调试”视图或终端等计算功能时，选择“继续处理...”，在 Codespace 中继续工作。

GitHub Projects 是一个功能强大的规划和追踪工具，提供灵活的视图选项，帮助团队组织工作并掌握全局。它可以让团队在一个位置轻松地组织、设置优先级和跟踪所有的功能需求和其他内容。

### 核心功能与组件

GitHub Projects 旨在提供更丰富的体验，以跟踪工作和办公位置。其核心功能和组件包括：

1. 灵活的视图选项：

+ 表格视图 （Tables）：可以按自定义字段（如文本、数字、日期、迭代和单选）对项目进行排序、设置级别和分组。

+ 看板视图 （Boards）：用于直观地查看和管理任务，支持自定义卡片和分组。

+ 时间轴视图 （Timelines）：作为一种布局选项，帮助可视化工作进度。

1. 数据与自定义字段 （Data and Custom Fields）：

+ 可以定义多种类型的自定义字段，包括文本、数字、日期、迭代和单选。

+ 迭代字段支持灵活的日期范围和中断，可用于表示冲刺 （sprint）、周期或季度路线图。

+ 支持草稿问题，包含详细说明和元数据。

+ 在表格和看板视图中查看已链接的拉取请求和审阅者。

1. 见解 （Insights）：

+ 提供当前图表和历史图表，用于创建视觉效果以加强对工作的理解，帮助了解项目的趋势和进度。

+ 可以创建和配置自定义的条形图、柱形图、折线图和堆积面积图。

+ 支持使用 `sum`、`count`、`average`、`min` 和 `max` 等聚合函数获取见解。

+ 图表可以保存并使用 URL 共享。

1. 自动化 （Automation）：

+ 内置的自动化工作流可帮助自动组织和更新项目项。

+ 支持通过 `GraphQL ProjectsV2 API` 和 GitHub Actions 进行高度自定义的自动化。

+ Webhook 事件用于项目项元数据更新。

1. 任务分解与跟踪：

+ 支持将清单项转换为子问题，以便更好地进行任务分解和跟踪。这会在项目视图中创建一个关联的问题，具有自身的状态和元数据。

1. 项目可见性和访问权限 （Visibility and Access Control）：

+ 可以控制项目是公共还是专用。

+ 组织拥有项目的管理员可以管理整个组织、团队、单个组织成员和外部协作者的访问权限（不允许访问、读取、写入、管理员）。

+ 个人拥有项目的管理员可以邀请单个协作者和管理其访问权限（读取、写入、管理员）。

### 使用方法

GitHub Projects 的使用方法涵盖了从创建到管理和自动化等多个方面：

1. 创建项目：

+ 在 GitHub.com 的右上角选择个人资料照片，然后选择“你的组织”或直接导航到“项目”选项卡。

+ 选择“新建项目”按钮。

+ 可以选择从头开始并选择“表”模板来创建项目。

+ 项目可以在组织级别创建，也可以通过选择个人资料照片并导航到“项目”来创建个人项目。

+ 还可以直接从存储库创建项目，这会自动将存储库链接到项目。

1. 设置项目信息：

+ 导航到新创建的项目，选择右上角的三点图标，然后选择“设置”。

+ 可以编辑项目名称、添加简短说明和编写自述文件，以便团队了解项目目的和目标。

1. 添加问题和拉取请求：

+ 添加现有项：复制现有问题或拉取请求的 URL，粘贴到项目底行的 `+` 旁边。

+ 搜索现有项：在项目底行输入 `#` 搜索存储库，然后键入问题或拉取请求的标题进行查找。

+ 批量添加：选择项目底行中的 `+`，然后选择“从存储库添加项”，可以全选或选择特定项。

1. 组织项目：

+ 创建自定义字段：在表视图最右侧的字段标题中选择 `+`，选择“新建字段”，键入名称（如“优先级”），选择字段类型（如“单一选择”），然后添加选项（如“紧急”、“高”、“中”、“低”）。

+ 按优先级分组：选择当前打开的视图名称旁边的向下箭头，选择“分组依据”，然后选择“优先级”。

+ 添加迭代字段：在表视图中选择 `+`，选择“新建字段”，添加字段名称（如“项目阶段”），在“字段类型”下选择“迭代”，设置“开始”日期和“持续时间”。

+ 创建看板视图：在当前打开的视图中，选择向下箭头，然后在“布局”下选择“版块”。可以将问题和拉取请求拖放到各个列中。

1. 自动化项目：

+ 启用内置工作流：打开项目，选择右上角的三点菜单，然后选择“工作流”。

+ 选择触发器（如“添加到项目的项”），设置值（如 `Status: Todo`），然后选择“保存并开启工作流”。

+ 对于更高级的自定义自动化，可以使用 GitHub Actions 和 `GraphQL` API。

1. 管理项目可见性和访问权限：

+ 控制可见性：导航到项目，选择右上角的三点图标，选择“设置”，在“危险区域”下更改“可见性”为“专用”或“公开”。

+ 邀请协作者和更改角色：在项目设置中选择“管理访问权限”，通过搜索栏邀请个人和团队，并更改其角色。

+ 将项目添加到团队：在组织设置的“团队”选项卡下，选择团队名称，然后选择“项目”和“链接项目”。

+ 将项目添加到存储库：导航到存储库主页，选择“项目”选项卡，然后选择“链接项目”。

1. 将清单项转换为子问题：

+ 打开包含清单的问题，将鼠标悬停在清单项上，点击 ... 菜单，然后选择“转换为子问题”。

1. 关闭和删除项目：

+ 导航到项目，选择右上角的三点图标，然后选择“设置”。

+ 在“危险区域”部分，选择“关闭项目”（保留内容，可重新打开）或“删除项目”（永久移除所有内容）。

## 在 Github 使用 Markdown

Markdown 和 GitHub-Flavored Markdown （GFM） 通过提供精简且易于编辑的方法来简化内容创建，并相较于 HTML 具有显著优势。

Markdown 和 GFM 如何简化内容创建：

Markdown 通过保护内容创建者免受 HTML 的繁琐影响，提供了一种精简的内容编辑方法。它在内容描述的 HTML 功能与易于编辑的纯文本之间取得了有效的折衷。GFM 则通过集成 GitHub 功能的扩展进一步增强了内容创建。

具体来说，它们通过以下方式简化内容创建：

+ 强调文本：使用单个星号 `*` 或下划线 `_` 实现斜体，使用双星号 `**` 或双下划线 `__` 实现粗体。还可以混合使用不同的强调效果，例如 This is italic and bold text。如果需要显示星号或下划线本身，可以使用反斜杠转义字符 `\`。

+ 声明标题：通过 `#` 符号实现 HTML 的 `<h1>` 到 `<h6>` 标题功能，从一个 `#` 到六个 `#` 分别对应不同级别的标题。

+ 链接图像和站点：图像链接遵循 `![Link an image.](/path/to/image.png)` 的结构，而网站链接则使用 `[Link to Microsoft Training](/training)`。

+ 创建列表：可以定义有序列表（以数字开头）和无序列表（使用星号 `*` 或破折号 `-`），并通过缩进创建嵌套项。

+ 构建表格：使用竖线 `|` 作为分栏符，并使用破折号 `-` 将上一行指定为标题来构造表格。

+ 引用文本：使用大于号 `>` 字符来创建块引用。



# 第一部分：GitHub Flavored Markdown（GFM）功能

+   **使用代码**：使用反撇号 `` ` `` 字符分隔内联代码块。对于跨越多行的代码段，可以使用三个反撇号 `` ``` `` 创建隔离代码块。GFM 更进一步，支持通过在三个反撇号后指定语言（如 `javascript`）来突出显示热门语言的语法。

+   **交叉链接问题和拉取请求**：GFM 支持多种短代码格式，如 `#ID`（例如 `#3602`），以轻松链接到问题和拉取请求。GitHub 还会自动调整较长的链接为这种格式。

+   **链接特定提交**：可以通过粘贴提交 ID 或直接使用提交的安全哈希算法（SHA）来链接到提交。

+   **提及用户和团队**：键入 `@` 符号后跟 GitHub 用户名，系统会向该用户发送通知，这称为“`@mention`”。

+   **跟踪任务列表**：可以在问题或拉取请求中创建任务列表，例如 `- [x] First task`（已完成）或 `- [ ] Third task`（未完成），以帮助跟踪进度。

+   **斜杠命令**：`/` 命令可以减少创建结构化内容所需的键入，例如 `/code` 插入代码块，`/table` 插入表格，`/tasklist` 插入任务列表等。

## 与 HTML 相比的优势

+   **简化编辑和开销**：`Markdown` 是一种标记语言，它通过保护内容创建者免受 `HTML` 开销的影响，提供了一种精简的内容编辑方法。`HTML` 虽然非常适合内容呈现，但它会占用大量空间，而且使用起来会很麻烦，即便使用量很小。`Markdown` 在 `HTML` 功能与易于编辑的纯文本之间提供了有效的妥协。

+   **可读性高**：`Markdown` 语法更接近自然语言，例如使用 `bold` 比 `<b>bold</b>` 更直观，这使得纯文本格式的 `Markdown` 文件更易于阅读和编写。

+   集成 `GitHub` 功能（`GFM`）：`GFM` 扩展了 `Markdown`，集成了许多 `GitHub` 特有的功能，如语法高亮、交叉链接问题/拉取请求、提及用户和团队以及任务列表，这在 `GitHub` 生态系统中提供了无缝的体验。

+   **灵活性**：如果遇到 `Markdown` 不支持的 `HTML` 场景，可以内联使用 `HTML` 来填补空白，这意味着 `Markdown` 并非完全排斥 `HTML`，而是提供了一个补充和简化的层。

# 第二部分：Github 的协作和管理

## 为 GitHub 上的开源项目做出贡献

要有效地发现、选择并开始参与开源项目，您可以遵循以下步骤：

### 有效发现开源项目

1.  **从您已使用或想使用的项目开始**：考虑那些您当前正在使用或希望使用的项目。当您熟悉项目及其社区时，做出贡献会更容易。您可能会在阅读项目的 `README` 文件时发现断开的链接、拼写错误，或者发现某些功能未按预期工作、文档已过期，这些都是很好的贡献机会。

1.  **使用 GitHub 搜索**：

    +   前往 GitHub 搜索页面，输入您感兴趣的主题词（例如“机器学习”）。

    +   然后，通过选择左侧边栏上的“主题”来缩小搜索范围。

    +   在这里，您可以找到与搜索关键字相关的存储库以及由社区成员精选的存储库。

1.  **加入社区和参加活动**：

    +   在问题和拉取请求的注释部分可以找到经常参与项目的贡献者。您还可以通过选择存储库导航中的“见解”，然后选择“参与者”来查找其他活跃的社区成员。

    +   关注 GitHub 上的组织和企业，个人仪表板会显示您关注的每个企业、用户或组织的公共活动。

    +   通过参加开源主题的交流会或会议来找到志趣相投的人。

    +   查找过去事件的谈话录音存档、播客、时事通讯和邮件列表。

    +   查看项目网站或 `README` 文件中是否有集群通信信息，例如 `Discord` 服务器、`Slack` 社区、`Gitter`、`IRC` 或常规的“办公时间”。

### 选择合适的开源项目

在找到感兴趣的项目后，您需要熟悉该项目及其参与指南。以下是一些关键的评估点：

1.  **熟悉项目文档和社区友好度**：

    +   **`LICENSE`**：项目必须包含开源许可证，否则它不是开源项目。

    +   **`README`**：通常是项目的欢迎页面，提供如何开始使用项目和参与社区的信息。

    +   **`CONTRIBUTING`**：提供如何为项目做出贡献的指导，包括贡献过程和开发环境设置。

    +   **`CODE_OF_CONDUCT`**：行为准则为社区成员制定基本规则，有助于使社区成为一个安全友好的环境。具备 `CONTRIBUTING` 或 `CODE_OF_CONDUCT` 文档是项目友好和受欢迎程度的良好标志。

1.  **关注社区沟通渠道**：熟悉项目使用的沟通渠道是一个好方法。

    +   **问题跟踪器（`Issues`）**：人们在此讨论与项目相关的问题和任务。您可以在 GitHub 存储库主页的 URL 末尾添加 `/issues` 来查找。

    +   拉取请求（`Pull Requests`）：人们在此讨论和评审对项目的更改。您可以在项目的 URL 后添加 `/pulls` 来查找。

    +   **聊天通道和论坛**：某些项目使用 `Slack`、`Gitter`、`IRC` 等聊天通道或 `Discourse` 等论坛进行对话和讨论。

1.  **初次交互的核对清单**：

    +   项目是否具有许可证？

    +   维护人员和参与者是否积极使用问题和拉取请求进行讨论？

    +   项目是否为新用户使用 `help wanted` 或 `good first issue` 等标签？

    +   项目是否具有行为准则？

    +   项目是否有明确的贡献指南？

请记住，所有类型的贡献都很有价值，您的项目经验或知识水平并不重要。最重要的是要有提供帮助的意愿。

### 开始参与开源项目并贡献

1.  **识别要处理的任务**：

    +   如果您已经确定了要处理的工作（例如修复断开的链接或更新文档），可以直接着手。

    +   若要查找适合初学者的问题，可以访问项目的 `/contribute` URL（例如 `https://github.com/jupyter/notebook/contribute`）。您会发现这些问题通常带有 `good-first-issue`、`help wanted`、`beginner-friendly` 等标签。

    +   您也可以转到标签页（例如 `https://github.com/jupyter/notebook/labels`），然后选择带有 `help wanted`、`discussion` 等标签或其他您感兴趣的贡献类型的问题。

1.  **沟通是关键**：

    +   在开源贡献工作中，**沟通是成功的关键因素**。

    +   积极沟通可以避免浪费时间处理他人已在处理的任务，或在与项目目标不符的功能上花费时间。

    +   尽量保持开放的心态，善于接纳反馈，并保持耐心。维护人员通常有自己的日常工作和私人生活，如果没有立即获得答案，请稍等一段时间。

    +   在做任何实际工作之前，始终应该首先传达您的贡献意图。

1.  **向维护人员传达意图**：

    +   问题跟踪器通常是传达意图的最佳位置，除非 `README` 文件中另有说明。

    +   **如果要处理现有问题**：检查“代理人”部分以确认是否已有人分配到此问题，并查看“链接的拉取请求”部分。查看评论，看看是否有人表达了处理该问题的兴趣。如果一切都清楚，请发布有关该问题的评论，表明您有兴趣处理它，以便其他人知晓。维护人员会回复并提供指南和建议。

    +   如果要处理新功能或问题跟踪器中尚未存在的 bug：创建新问题。如果提供了问题模板，请务必遵循模板，并清楚地表达您处理该问题的意图。如果这是一个新功能建议，或者问题需要许多更改，请务必在进入下一步之前获得维护人员的批准。

1.  **创建拉取请求 （`PR`）**：您的贡献将以“拉取请求”的形式提交。

    +   **分叉存储库**：打开要做出贡献的项目的 GitHub 页面，选择“分支”按钮在您的 GitHub 帐户中创建存储库的副本。

    +   **克隆到本地**：从您的帐户配置文件菜单中选择“您的存储库”，选择分叉的存储库。选择“代码”按钮，获取将 Git 存储库克隆到本地计算机的信息，复制存储库 URL，然后在终端中输入 `git clone <REPOSITORY_URL>`。

    +   **创建新分支（推荐）**：克隆后，进入项目文件夹 `cd <PROJECT_FOLDER>`。然后可选地使用 `git checkout -b <BRANCH_NAME>` 命令创建新分支，这使得您可以分别处理多个贡献。

    +   **进行更改并提交**：对项目进行所需更改，并使用 `git add .` 和 `git commit -m "<COMMIT_MESSAGE>"` 命令提交。请务必在提交消息中准确描述您的更改，并检查 `CONTRIBUTING` 文件中是否存在需要遵循的提交消息约定。

    +   **推送到远程分支**：使用 `git push --set-upstream origin <BRANCH_NAME>` 命令将更改推送到远程库（您的分支）。

    +   在 GitHub 上创建拉取请求：打开 GitHub 上的项目分支，并在出现的建议框中选择“比较和拉取请求”按钮。

    +   **填写标题和说明**：填写标题和说明。如果有拉取请求说明的模板，请花时间填写所有必需的信息。提供足够的上下文，让维护人员了解您建议的更改以及原因。还应使用 `#<ISSUE_NUMBER>` 提及相关问题的编号，以链接回相关问题。

1.  **通过状态检查**：

    +   创建拉取请求后，您可能会在底部看到一个带有状态检查的部分。这些是维护人员为确保项目质量一致而设置的自动检查。

    +   若要使拉取请求被接受，它需要通过所有自动检查。如果检查失败，请选择“详细信息”按钮了解详细信息，找出修复它所需的操作。如果您不确定如何处理失败的检查，可以使用评论请求维护人员指导或帮助修复。

1.  **请求指导或评审**：

    +   如果您不确定所做的某些更改，并希望获取维护人员的意见，最佳方法是直接对拉取请求进行注释。

    +   如果您认为更改正在进行中，还可以选择创建草稿拉取请求。

1.  **处理评审反馈**：

    +   项目维护人员收到您的拉取请求后，他们可以回复对话或直接查看您的更改。

    +   请记住，在所有的交流中要始终尊重他人，并遵循行为准则。

    +   如果拉取请求需要进行一些更改，请仔细查看提供的反馈。如果您执行了要求的更改，并将其作为新提交推送到分支，拉取请求将自动更新。

    +   **参与开源项目需要耐心**。有时您不会获得即时反馈。**请勿为了更快获得答复而通过电子邮件、`X` 或任何其他方式**与维护人员私下联系，这被认为是有害的行为。公开讨论事情也让其他参与者或路人有机会了解更改背后的过程以及要遵循的最佳做法。

## 使用 GitHub 管理 InnerSource 程序

### InnerSource 核心理念和优势

InnerSource 是一种将开源（Open Source）模式应用于具有有限受众的项目实践。

其核心理念可以理解为：

+   **内部开源**：它类似于典型的开源项目结构，但仅限于公司内部的员工才能访问。从效果上看，InnerSource 是一个受公司防火墙保护的开源程序。

+   **自由使用、修改和共享**：就像开源软件一样，InnerSource 项目允许公司内部的任何人自由地使用、修改和共享项目代码。通过共享代码，可以使软件更完善、更可靠。

InnerSource 程序能够提供传统闭源模型所不具备的诸多优势，主要包括：

+   **支持内部可见性**：开发人员可以访问公司内其他项目的源代码，这有助于他们更高效地处理自己的项目，发现可重用的代码和其他资产。同时，他们还能通过访问团队的问题、拉取请求和项目计划，更好地了解项目开发的速度和方向。

+   **减少冲突**：当消费者团队依赖于其他团队的 Bug 修复或新功能时，InnerSource 提供了一个渠道来提出所需的更改。如果这些更改无法合并，消费者团队可以选择对项目进行分支以满足其需求。

+   **标准化实践**：InnerSource 计划是采用标准约定的好机会，这些约定可以被不同的开发团队所采纳，即使这些团队原本不遵循相同的做法。例如，标准化公开流程可以使任何人更容易参与其中。

**在 `GitHub` 上设置 InnerSource 程序时，通常会使用内部存储库（`Internal repository`），这种可见性级别仅对拥有内部存储库的企业成员可见，非常适合 InnerSource 项目。**

### InnerSource 的工作方式

以下是 InnerSource 如何实现这些目标的具体方式：

1.  **提高协作：**

    +   **支持内部可见性**：InnerSource 程序允许开发人员访问公司内其他项目的源代码。这种可见性使他们能够了解其他团队如何解决类似问题，并发现可重用的代码和其他资产。

    +   **减少冲突**：当消费者团队依赖于其他团队的错误修复或新功能时，InnerSource 提供了一个渠道来提出所需的更改。如果这些更改无法合并，消费者团队可以选择对项目进行分支以满足其需求，从而减少潜在冲突。

    +   **标准化实践**：InnerSource 计划是采用标准约定的大好机会，这些约定可以被不同的开发团队所采纳，即使这些团队原本不遵循相同的做法。例如，标准化公开流程可以使任何人更容易参与其中。

    +   **跨团队协作工具**：`GitHub Discussion` 和 `GitHub Projects` 等工具可以进一步支持跨团队的 InnerSource 协作。

    +   **清晰的贡献策略**：通过在存储库中包含 `CONTRIBUTING.md` 文件，项目可以解释其贡献策略，包括拉取请求的查找位置、错误报告所需的详细信息等，从而指导潜在贡献者。

    +   **代码所有者定义**：添加 `CODEOWNERS` 文件可以定义负责评审代码修改的个人或团队，确保代码评审责任明确。

    +   **问题和拉取请求模板**：`GitHub` 支持为新问题和拉取请求创建模板，提供初始描述文本，使用户可以像填写表单一样提交，从而简化贡献流程。

    +   **定义工作流**：为鼓励外部贡献的项目指定工作流（例如 `GitHub` 流），详细说明如何使用分支、如何打开拉取请求以及其他贡献者应知晓的细节，从而促进有序协作。

1.  **提高效率：**

    +   **代码和资产重用**：通过内部可见性，开发人员可以找到并重用其他内部项目的代码和其他资产，从而避免重复造轮子，提高开发效率。

    +   **加速项目开发**：访问团队的问题、拉取请求和项目计划提供了更好的数据，使开发人员能够了解项目开发的速度和方向，从而更高效地处理自己的项目。

    +   **项目可发现性**：为了在 InnerSource 项目数量显著增加时仍能高效找到内容，最佳实践包括：

        +   使用描述性存储库名称（例如 `warehouse-api` 或 `supply-chain-web`）。

        +   包含简要说明，让潜在用户快速了解项目是否符合其需求。

        +   通过许可存储库，让客户了解如何使用、更改和分发软件。

        +   在存储库中包含一个 `README.md` 文件作为登陆页面，清晰表述项目目的和愿景，并提供视觉帮助、链接、先决条件和部署过程期望等。

    +   **简化贡献流程**：清晰的贡献策略、模板和定义的工作流使得内部贡献者可以更容易地参与，减少了入职时间和学习曲线。

1.  **提高代码质量：**

    +   **增加代码可见性**：当更多内部团队的开发人员可以查看和修改项目代码时，这相当于为代码带来了“更多双眼睛”，有助于发现和修复错误，从而提高代码质量。

    +   **内部“外部”贡献**：InnerSource 鼓励来自组织内部不同团队的拉取请求，这些请求可以用于修复错误和添加新功能，从而促进代码的持续改进和质量提升。

    +   **强制代码评审**：通过 `CODEOWNERS` 文件，可以定义负责评审代码修改的个人或团队，确保所有的代码更改都经过专业的审查，这对于保持高代码质量至关重要。

    +   **标准化和一致性**：采纳标准约定和统一的工作流有助于生成更一致、更易于维护和理解的代码，从而间接提高代码质量。

    +   **积极的讨论与反馈**：围绕项目及其未来的积极讨论参与者可以为代码改进提供宝贵的反馈和见解，进一步提升项目质量。

    +   **度量指标**：虽然传统指标（如“上市时间”和“报告的错误”）仍然适用，但 InnerSource 鼓励添加指标来衡量外部参与对提升项目质量的作用，例如接收到的可修复错误和添加功能的拉取请求数量，以及围绕项目的讨论活跃度，这些指标可以间接推动代码质量的提升。

### 如何衡量 InnerSource 的成功

衡量 InnerSource 程序的成功，需要考虑的指标不应只局限于传统的“面市时间”或“报告的 Bug 数量”，而应更加关注外部参与对项目质量和组织效益的提升。

以下是衡量 InnerSource 程序成功的一些关键方法和导则原则：

1.  **衡量外部参与对项目质量的提升**：

    +   **接收到的拉取请求数量**：评估存储库是否接收到来自外部（即组织内其他团队）的拉取请求，这些请求是否用于修复 Bug 和添加新功能。

    +   **积极的讨论参与者**：衡量围绕项目及其未来的讨论中是否存在积极的参与者。这反映了社区的活跃度和项目的吸引力。

1.  衡量 InnerSource 的扩展性和对组织的整体效益：

    +   程序是否激励了 InnerSource 的扩展：考察该 InnerSource 程序是否鼓励了其他团队也采纳 InnerSource 模式，从而在其他方面使组织受益。

1.  **指标的选取原则**：

    +   **衡量过程，而非输出**：关注流程效率，例如：

        +   **代码评审周转时间**：代码评审完成所需的时间。

        +   **拉取请求大小**：拉取请求中包含的代码量。

        +   **正在进行的工作**：同时进行中的任务数量。

        +   **打开时间**：问题或拉取请求从创建到关闭的时间。

    +   **针对目标而不是绝对指标进行度量**：这意味着要根据项目的具体目标来设置和评估指标，而不是单纯追求某个数字的绝对值。

    +   **度量团队而非个人的贡献**：关注整体协作和共享，例如：

        +   **项目的唯一参与者数**：有多少个不同的个人参与了项目。

        +   **重用代码的项目数**：有多少个其他项目重用了当前项目的代码。

        +   跨团队 `@mentions` 的数量：衡量不同团队之间通过 `@mentions` 进行协作和沟通的频率。

    需要注意的是，指标的选择和使用非常重要。如果误用，指标可能会损害文化和现有流程，还可能对组织或领导团队的集体情绪产生负面影响。

## 使用 GitHub 维护安全的存储库的最佳做法

在软件开发生命周期中，增强 GitHub 存储库的安全性需要采取多方面策略，并且安全性必须是开发生命周期中每个阶段的组成部分，而不能事后添加。以下是一些关键策略：

### 核心安全理念与实践

1.  安全左移 （`Shift Left`）

    +   这是一种流程变更，意味着在开发生命周期的早期阶段完成安全工作，让所有安全性更加以开发人员为中心，并在开发人员所在的地方为他们提供安全反馈。

    +   通过将步骤从部署时的最终关口移动到早期步骤，可以减少错误，开发人员可以更快地移动。

    +   在开发生命周期早期将安全性添加到 `DevOps` 实践中，可以提前发现问题，从而减少开发高质量软件所需的整体时间。

1.  **持续教育与培训 （`Ongoing Education and Training`）**

    +   许多开发人员和其他员工假设他们理解安全性，但实际上并非如此。网络安全是一个不断发展的学科，因此持续的教育和培训计划至关重要。

1.  **安全地创建代码与合规性 （`Secure Code Creation and Compliance`）**

    +   需要确保代码被正确且安全地创建，并以安全为前提设计所需功能。

    +   应用程序必须遵守规则和法规。必须在生成代码时测试合规性，即使在部署之后也要定期重新测试。

### GitHub 提供的安全功能与工具

GitHub 在其“安全”选项卡中提供了多种功能，可帮助确保存储库和数据的安全：

1.  安全策略 （`Security Policy`）

    +   通过向存储库添加 **`SECURITY.md` 文件**，可以指定如何报告项目中的安全漏洞。

    +   这有助于负责任地披露安全问题，并加快关键问题的解决速度。

1.  **依赖项管理与警报 （`Dependency Management and Alerts`）**

    +   **存储库依赖项关系图 （`Repository Dependency Graph`）**：`GitHub` 默认扫描常见的包清单（如 `package.json`、`requirements.txt`），允许项目所有者以递归方式跟踪其项目依赖的所有依赖项。

    +   `Dependabot` 警报 （`Dependabot Alerts`）：当 `GitHub` 检测到存储库正在使用易受攻击的依赖项或恶意软件时，会通知你。它通过监视依赖项关系图，并与已知漏洞列表进行交叉引用来发现风险。

    +   **`Dependabot` 自动更新 （`Dependabot Automated Updates`）**：`Dependabot` 可以扫描依赖项警报并创建拉取请求，以便参与者可以验证更新并合并请求，从而自动更新依赖项。

1.  代码扫描 （`Code Scanning`）

    +   代码扫描有助于查找、审查和修复代码中的漏洞和错误。

    +   它可以查找现有问题，确定修复优先级，并有助于防止开发人员引入新的安全问题。

    +   它还可以使用 `CodeQL`，允许将代码查询为数据，以便创建自定义查询或使用开源社区维护的查询，从而灵活地自定义扫描方式。

1.  **机密扫描与推送保护 （`Secret Scanning and Push Protection`）**

    +   机密扫描功能能够检测存储在存储库中的令牌、凭证和机密信息。

    +   推送保护 （`Push Protection`） 默认在公共存储库上启用，可以在推送操作之前拦截机密信息。对于私有存储库，管理员或组织所有者可以启用机密扫描。

    +   当机密扫描检测到凭据时，`GitHub` 会通知颁发服务的提供商，由其验证并决定是撤销、发出新机密还是直接联系受影响方。

1.  安全公告 （`Security Advisories`）

    +   `GitHub` 安全公告允许存储库维护人员私下讨论、修复和发布有关存储库中安全漏洞的信息。

    +   维护人员协作处理修补程序后，可以发布安全公告，向项目社区公开披露漏洞。

    +   `GitHub` 将已发布的公告存储在“常见漏洞和暴露 （`CVE`）”列表中，并用于自动通知受影响的存储库。

### 存储库和工作流安全策略

1.  .gitignore 文件管理

    +   生成和维护 `.gitignore` 文件可以帮助避免将敏感数据（如 `API` 密钥或专用配置数据）意外提交到存储库。

    +   这些文件指示客户端工具（如 `git` 命令行实用工具）在聚合提交文件时忽略特定路径和模式。

    +   一个存储库可以包含多个 `.gitignore` 文件，子目录中的设置会覆盖父目录的设置。

1.  敏感数据移除 （`Sensitive Data Removal`）

    +   虽然 `.gitignore` 文件能帮助避免提交敏感数据，但它只是一种强烈建议，开发人员仍可能绕过它。

    +   应假定任何已提交到 GitHub 的数据都已泄露，仅覆盖提交不足以确保数据将来不可访问。如果敏感数据不慎提交，应遵循完整的指南从存储库中删除。

1.  分支保护规则 （`Branch Protection Rules`）

    +   可以创建分支保护规则，为一个或多个分支强制实施某些工作流。

    +   例如，可以要求所有合并到受保护分支的拉取请求都必须经过批准的审查或通过状态检查。

    +   保护分支的工作流可以用于运行构建、`Linter` 或自动化测试。

1.  拉取请求中的所需审阅者 （`Required Reviewers in Pull Requests`）

    +   在代码合并到重要分支之前，可以要求评审来提高存储库安全性，这有助于强制实施质量、安全性和责任。

    +   在没有管理员权限的情况下，无法绕过所需的评审，它们确保在合并之前由另一个参与者或指定的代码所有者审查建议的更改。

1.  `CODEOWNERS` 文件 （`CODEOWNERS File`）

    +   通过将 `CODEOWNERS` 文件添加到存储库，可以将单个团队成员或整个团队作为代码所有者分配给存储库中的特定路径。

    +   这些代码所有者需要对向其配置的路径中的文件的任何更改进行拉取请求评审。

1.  安全公告 （`Security Advisories`）：`GitHub` 安全公告允许存储库维护人员私下讨论、修复和发布有关存储库中安全漏洞的信息。修补完成后，可以发布安全公告向社区公开披露漏洞。`GitHub` 会将已发布的公告存储在“常见漏洞和暴露 （`CVE`）”列表中，并用于自动通知受影响的存储库。

1.  代码扫描 （`Code Scanning`）：代码扫描有助于查找、审查和修复代码中的漏洞和错误。它能查找现有问题，确定修复优先级，并有助于防止开发人员引入新的安全问题。代码扫描还可以使用 `CodeQL`，允许将代码查询为数据，以便创建自定义查询或使用开源社区维护的查询，从而灵活地自定义扫描方式。

1.  **机密扫描与推送保护 （`Secret Scanning and Push Protection`）**：机密扫描功能能够检测存储在存储库中的令牌、凭证和机密信息，并能够在推送操作之前对其进行拦截。推送保护 （`Push Protection`） 默认在公共存储库上启用。当机密扫描检测到凭据时，`GitHub` 会通知颁发服务的提供商，由其验证并决定是撤销、发出新机密还是直接联系受影响方。

#### 三、存储库和工作流安全策略

1.  **.gitignore 文件管理**：生成和维护 `.gitignore` 文件可以帮助避免将敏感数据（如 `API` 密钥或专用配置数据）意外提交到存储库。这些文件指示客户端工具（如 `git` 命令行实用工具）在聚合提交文件时忽略特定路径和模式。一个存储库可以包含多个 `.gitignore` 文件，子目录中的设置会覆盖父目录的设置。

1.  **敏感数据移除**：尽管 `.gitignore` 文件有助于避免提交敏感数据，但这只是一种强烈建议。如果开发人员有足够的积极性，他们仍然可能绕过 `.gitignore` 文件添加文件。应假定任何已提交到 GitHub 的数据都已泄露，仅覆盖提交不足以确保数据将来不可访问。如果敏感数据不慎提交，应遵循完整指南从存储库中删除。

1.  分支保护规则 （`Branch Protection Rules`）：可以创建分支保护规则，为一个或多个分支强制实施某些工作流。例如，可以要求所有合并到受保护分支的拉取请求都必须经过批准的审查或通过状态检查。保护分支的工作流可以用于运行构建、`Linter` 或自动化测试。

1.  **拉取请求中的所需审阅者 （`Required Reviewers in Pull Requests`）**：在代码合并到重要分支之前，可以要求评审来提高存储库安全性。所需的审阅者有助于强制实施质量、安全性和责任。在没有管理员权限的情况下，无法绕过所需的评审，它们确保在合并之前由另一个参与者或指定代码所有者审查建议的更改。

1.  `CODEOWNERS` 文件 （`CODEOWNERS File`）：通过将 `CODEOWNERS` 文件添加到存储库，可以将单个团队成员或整个团队作为代码所有者分配给存储库中的特定路径。这些代码所有者需要对向其配置的路径中的文件的任何更改进行拉取请求评审。`CODEOWNERS` 文件可以在存储库根目录中，或者在 `docs` 或 `.github` 文件夹中创建。

通过综合应用这些策略和功能，可以显著增强 GitHub 存储库的安全性。

## GitHub 管理简介

在 GitHub 管理中，权限模型和访问控制机制是分层运作的，主要涵盖存储库、团队、组织和企业四个级别。这些层级共同作用，确保用户只拥有执行其任务所需的最低访问权限，从而实现安全和合规性。

### 运作方式

以下是 GitHub 中不同层级的权限模型和访问控制机制的运作方式：

---

#### I. 存储库权限级别 （`Repository Permission Levels`）

存储库级别的权限是针对单个代码库定制访问权限的方式。管理员可以通过分配特定的权限级别来管理对每个存储库的访问。

**存储库的标准权限**

**用户获得存储库访问权限的方式**

用户可以通过多种方式成为存储库的协作者并获得权限，这些权限来源包括：

1.  直接协作者 （`Direct Collaborator`）：显式添加到存储库，具有特定的角色（阅读、审查、写入、维护或管理）。

1.  团队成员身份 （`Team Membership`）：用户通过其团队成员身份继承存储库访问权限。团队权限通常在组织级别设置，以便进行一致的可缩放管理。

1.  **组织默认权限 （`Organization Default Permissions`）**：如果存储库是组织的一部分，所有组织成员可能具有默认权限级别（例如 `None`、`Read`）。

**有效权限的确定**

存储库中用户的有效权限受到各种因素（如存储库角色、团队成员身份和组织成员身份）的影响。`GitHub` 在合并这些不同的权限源时，会向用户应用最高级别的访问权限。例如，如果用户通过团队获得了“阅读”访问权限，但同时由于被分配为协作者而直接获得了“写入”访问权限，则他们实际上拥有“写入”权限。

---

#### II. 团队权限级别 （`Team Permission Levels`）

`GitHub` 组织中的团队是一组协作处理共享存储库的用户，目的是通过一次性对多个存储库应用一致的权限，简化访问管理和通信。

**团队结构和权限继承**

+   **集中式访问控制**：将存储库权限（例如，读取、写入）分配给整个团队，而不是单独管理每个用户。

+   **权限级联**：子级团队成员会继承父级团队的权限设置，这提供了一种简单方法，可以基于公司自然结构轻松地级联权限。

**团队的角色权限**

团队级别有两个内部权限级别：

**团队对存储库的访问权限**

向团队授予对存储库的访问权限时，可选择的权限模型与存储库的标准权限模型相同，包括：阅读、审查、写入、维护、管理员。

**最佳实践**：始终遵循**最低特权原则**，为每个团队分配有效执行其任务所需的最低权限级别，以降低意外或未经授权的更改的风险。

---

#### III. 组织权限级别 （`Organization Permission Levels`）

组织提供了一种集中的方式，使团队能够协作处理项目，同时保持对存储库和敏感数据的控制访问权限。

**组织的角色权限**

**默认权限设置**

组织所有者可以设置适用于所有组织成员的默认权限级别（例如“无”或“阅读”）。

+   默认读取 （`Default Read`）：建议为所有组织成员授予默认的读取权限，并根据具体情况调整他们对存储库的访问权限，以改善管理和安全性。

+   默认写入 （`Default Write`）：如果组织较小，并且信任所有成员向任何存储库推送更改，则默认情况下可能会授予写入权限。

---

#### IV. 企业权限级别 （`Enterprise Permission Levels`）

企业帐户（包括 `GitHub Enterprise Cloud` 和 `Enterprise Server` 实例）是组织的集合，它允许所有者集中管理多个组织的策略和计费。

**企业角色权限**

**企业级策略和治理**

企业所有者可以：

+   **强制执行策略**：设置适用于企业中所有组织、存储库和成员的存储库管理策略、团队策略和其他安全设置。

+   **默认存储库权限策略**：可以在所有组织中设置默认存储库权限的策略。建议使用默认读取权限模型，选择性地授予写入访问权限，以遵循最低权限原则。

---

#### V. 访问控制机制和管理工具

`GitHub` 提供了多种工具和机制来管理和审核不同层级的访问权限：

**身份验证与安全**

访问控制的基础是身份验证：

+   **令牌和密钥**：强烈建议使用个人访问令牌 （`PAT`） 替代密码进行 `Git` 操作或 `API` 使用。用户还可以使用 `SSH` 密钥连接到远程服务器和服务进行身份验证。部署密钥是另一种 `SSH` 密钥类型，可授予对单个存储库的访问权限。

+   **多重身份验证 （`2FA`）**：组织所有者可以要求成员和外部协作者为其个人帐户启用 `2FA`，这为 `GitHub` 帐户添加了额外的保护层。

+   **单一登录 （`SSO`）**：可以配置 `SAML SSO`，以使用标识提供者 （`IdP`） 集中管理用户身份，从而保护 `GitHub` 上的组织资源。

**自动化和同步**

+   **团队同步**：`GitHub` 允许同步团队与标识提供者 （`IdP`） 组（如 `Microsoft Entra ID` 或 `Active Directory`），从而自动将成员身份更改复制到 `GitHub`，简化载入、卸载和角色更新。此功能减少了手动更新的需求。

+   **脚本自动化**：可以使用 `GitHub REST API` 或 `GraphQL API` 以编程方式列出协作者、团队和权限。对于大规模企业，可以使用自定义脚本来自动执行团队创建和权限分配，以及应用组织范围或企业范围的更改。

**监视和审核**

定期审核谁有权访问存储库，可确保适当的安全性和合规性：

+   **存储库设置**：在存储库设置中查看用户和团队的列表及其权限级别。

+   **组织和企业审核日志**：组织所有者可以查看组织审核日志中成员身份、存储库访问权限和权限的更改。如果管理多个组织，可以使用企业帐户的审核日志跟踪所有组织和存储库中的更改，这对于合规性报告和大规模安全评审非常有用。

### 最佳实践

在 `GitHub` 管理中，优化协作和安全性的策略和最佳实践主要围绕权限管理、身份验证、自动化和持续审核这四个核心领域展开。这些做法旨在遵循最低特权原则，并确保组织内的用户访问权限与其职责相匹配。

以下是根据来源信息总结的 `GitHub` 管理策略和最佳实践：

#### 协作与权限优化的最佳实践 （`Optimizing Collaboration and Permissions`）

1.  权限分级和最低特权原则

    +   **分配恰当的权限级别**：始终遵循**最低特权原则**。为项目中的每个人或团队角色选择最适合他们的权限级别，不要向其授予超过其所需的项目访问权限。

    +   例如，对于只需要管理问题和拉取请求但不需要修改代码的项目经理，建议分配**“审查”**权限。

    +   对于积极推送内容到项目的开发人员，标准权限是**“写入”**。

    +   对于只需要查看或讨论项目的非代码参与者，建议分配**“阅读”**权限。

    +   对于处理常规存储库管理但不需要完全管理员权限的项目维护人员，建议分配**“维护”**权限。

    +   **使用团队进行可缩放管理**：通过在组织中创建团队，实现更灵活的协作。将存储库权限分配给整个团队（集中式访问控制），而不是单独管理每个用户，从而简化访问管理。

    +   **嵌套团队结构**：**创建嵌套团队**以反映你的公司或组的层次结构。子级团队成员会继承父级团队的权限设置，这有助于级联权限。

    +   **按兴趣创建团队**：通过基于兴趣或特定技术（如 `JavaScript`、`数据科学` 等）创建团队，可以帮助简化 `PR`（拉取请求）评审流程。

1.  存储库治理和分叉管理

    +   **分支保护规则和所需的评审**：**设置分支保护规则和所需的评审**，为所有代码更改添加另一层安全性和责任。

    +   **管理分叉权限**：管理员应控制是否可以分叉存储库。

    +   公共存储库始终允许分叉。

    +   专用存储库的分叉可以被禁用或限制为组织成员。

    +   内部存储库只能在同一企业帐户内分叉。

1.  组织和企业默认权限策略

    +   **默认“读取”建议**：组织和企业级别**建议使用默认“读取”权限模型**，并根据具体情况调整对存储库的访问权限，选择性地授予写入访问权限。这有助于遵循最低权限原则，增强安全性和管理。

    +   **权衡组织结构**：在构建企业时，需权衡使用**单个组织**还是**多个组织**。

    +   **单个组织的优点**包括简化管理、策略一致性和资源共享。

    +   **多个组织的优点**包括增强隔离性（限制安全漏洞对单个组织的影响）和定制策略，但会增加管理复杂性和开销。

#### 安全性和访问控制的最佳实践 （`Security and Access Control`）

1.  强化身份验证和访问控制

    +   使用个人访问令牌 （`PAT`） 和 `SSH` 密钥：**强烈建议使用个人访问令牌 （`PAT`） 替代密码进行 `Git` 操作或 `API` 使用。此外，用户应使用 `SSH` 密钥连接到远程服务器和服务进行身份验证，以避免每次交互时都提供 `PAT`。

    +   强制实施双因素身份验证 （`2FA`）：组织所有者可以要求成员、外部协作者和计费管理员为其个人帐户启用 `2FA`。`2FA` 为 `GitHub` 帐户增加了额外的保护层，有助于保护组织免受未经授权的访问。

    +   **实施 `SAML` 单一登录 （`SSO`）**：如果组织使用身份提供者 （`IdP`） 集中管理用户身份，应配置 `SAML SSO`。这允许组织所有者控制和保护对存储库等组织资源的访问。

    +   **管理外部协作者**：组织所有者和团队维护者可以添加或删除外部协作者（非组织正式成员，如顾问或临时工）。外部协作者通常对存储库具有有限的访问权限。

1.  自动化和集成策略

    +   **团队与 `IdP` 同步**：在 `IdP`（如 `Microsoft Entra ID`）与 `GitHub` 之间启用团队同步。这可以自动将更改复制到 `GitHub`，简化新成员的加入、权限的授予以及成员对组织访问权限的删除等管理任务，从而减少手动更新和自定义脚本的需求。

    +   **`API` 自动化管理**：

        +   使用 `GitHub REST API` 或 `GraphQL API` 以编程方式列出协作者、团队和权限。

        +   使用自定义脚本来**提取有关存储库和组织的信息**。

        +   使用自定义脚本**应用组织范围或企业范围的更改**，例如迁移。

    +   **脚本自动化实践**：对于大规模管理，脚本自动化应遵循以下关键实践：

        +   **模块化**：开发模块化组件，以最少的更改来处理不同的组织。

        +   **可重用性**：创建可重用函数来执行常见权限任务。

        +   **测试与版本控制**：在受控环境中彻底测试脚本，并使用 `Git` 等版本控制系统管理脚本修订。

1.  持续监视和审核

    +   **定期审核访问权限**：定期审核谁有权访问存储库，可确保适当的安全性和合规性。

    +   使用存储库见解 （`Repository Insights`）：

        +   定期查看**依赖项图**（`Dependency Graph`）以识别潜在的安全漏洞，确保存储库保持安全。

        +   使用“参与者”部分来识别最关注的存储库的活动参与者和区域。

        +   使用“流量”部分了解用户如何与存储库交互并识别参与趋势。

    +   **利用审核日志**：

        +   组织所有者应查看**组织审核日志**中成员身份、存储库访问权限和权限的更改。

        +   如果管理多个组织，应使用**企业审核日志**跟踪所有组织和存储库中的更改，这对于合规性报告和大规模安全评审尤其有用。

    +   **集成自动化脚本**：将自动化脚本与 `CI/CD` 管道或安全仪表板集成，以持续监视和标记异常访问或权限。

## 在 GitHub 上对用户标识进行身份验证和授权

`GitHub` 通过集成多种现代身份验证（`Authentication`）和授权（`Authorization`）机制，确保了企业环境的高度安全性和合规性。这些机制旨在实现访问控制的集中化、用户生命周期的自动化以及权限的精细化管理。

### 实现机制

以下是 `GitHub` 确保企业安全性和合规性的主要机制：

1.  强大的身份验证和标识集成

身份验证是企业软件开发生态系统的入口。`GitHub` 支持并要求使用先进的方法来降低凭据攻击的风险：

+   `SAML` 单一登录 （`SSO`）：`SAML SSO` 是企业级身份验证的基础。它将 `GitHub` 与组织的标识提供者（`IdP`，例如 `Microsoft Entra ID` 或 `Okta`）集成。用户必须通过 `IdP` 进行身份验证，然后才能授予对 `GitHub` 组织资源的访问权限。

+   **合规性优势**：`SAML SSO` 允许集中访问控制，有助于提高合规性。

+   **强制范围**：管理员可以在 **组织级别** 或 **企业级别** 配置和强制实施 `SAML SSO`，以确保统一的策略并降低配置碎片化的风险。

+   **多重身份验证 （`2FA`）**：强大的企业安全性强制实施 `2FA`。`GitHub` 支持多种先进的 `2FA` 方法：

    +   `Passkeys` 和 `WebAuthn`：`Passkeys` 是一种无密码登录方法，可以防御网络钓鱼。`WebAuthn` 支持使用生物识别因素和硬件令牌（如 `YubiKey`）进行身份验证。

    +   `GitHub Mobile`：用户可以使用 `GitHub Mobile` 接收推送通知，以便进行快速、安全的 `2FA` 审批，避免中断工作流。

    +   **强制实施**：管理员可以要求组织成员、外部协作者和计费经理使用 `2FA`，从而增强安全性。

+   **企业托管用户 （`EMU`）**：`EMU` 是 `GitHub Enterprise Cloud` 的一项功能，为企业提供对用户身份和帐户生命周期的完全控制。

    +   **完全控制**：`EMU` 确保所有 `GitHub` 帐户都完全由企业的 `IdP`（如 `Microsoft Entra ID` 或 `Okta`）管理。

    +   **严格合规性**：`EMU` 非常适合具有严格合规性、审核或用户治理需求的组织。它有助于确保访问权限根据 `IdP` 成员身份自动授予或删除，并防止意外的外部协作。

1.  自动化授权和访问生命周期管理

为了确保用户访问权限始终与 `IdP` 中的角色保持一致，`GitHub` 依赖于自动化同步机制：

+   `SCIM` （跨域身份管理系统）：`SCIM` 是一种开放标准协议，用于自动化标识域和 IT 系统之间的用户身份信息交换。

    +   **完整的生命周期自动化**：**`SCIM` 专注于**用户和组的完整生命周期管理。它实现了帐户生命周期的完全自动化，包括自动创建（预配）、更新角色和部门，以及在用户离开时立即删除访问权限（取消预配）。

    +   **安全性提升**：及时停用访问权限可以减少手动干预和延迟撤销的风险，从而提高安全性。`SCIM` 还会撤销会话结束后过期的令牌。

    +   **一致性**：`SCIM` 通过跨系统标准化用户数据，帮助满足策略和审核要求。

    > **注意**：仅依靠 `SAML SSO` 不支持自动取消预配组织成员。若要实现完整的自动化，`IdP` 管理员必须同时启用 `SAML SSO` 和 `SCIM`。

+   团队同步 （`Team Sync`）：团队同步专注于将 `IdP` 中的组映射到 `GitHub` 团队，从而实现团队级的映射。

    +   **简化权限管理**：它可以让 `GitHub Teams` 与 `IdP` 组的成员身份保持一致，从而自动反映 `IdP` 组中的任何更改（例如，将 `Alice` 添加到 `IdP` 组会自动将其添加到映射的 `GitHub` 团队）。

    +   **前提条件**：要使用团队同步，`IdP` 管理员必须启用 `SAML SSO` 和 `SCIM`。

    +   **理想场景**：团队同步是按团队管理存储库访问权限的最佳解决方案。

1.  细粒度的授权和安全控制

`GitHub` 实施多层授权模型，以限制权限范围并降低攻击面：

+   细粒度个人访问令牌 （`PAT`）：与传统的 `PAT` 不同，细粒度 `PAT` 提供了增强的可跟踪性和合规性控制。

    +   **风险最小化**：它们限制对**特定存储库和范围**的访问。

    +   **有效期**：它们支持自动过期以降低风险。

    +   **凭据管理**：`PAT` 和 `SSH` 密钥必须经过明确授权并链接到 `IdP` 标识，才能安全地访问组织资源。

+   **自定义存储库角色**：**管理员可以定义**超出默认权限集的自定义角色，以针对独特的工作流定制委派访问权限。这有助于对敏感存储库执行最小特权原则。

+   **安全策略强制实施**：可以强制实施全局安全控制措施：

    +   **`IP` 允许列表**：限制对已批准网络的访问。

    +   `OAuth` 应用控制：阻止未经明确批准的未经身份验证的 `OAuth` 应用。

    +   **企业级治理**：包括集中式 `SAML` 强制措施和基于 `IdP` 的登录限制。

    +   **存储库可见性**：组织成员可以在**公共**、**专用**或**内部**可见性选项之间进行选择。**内部**可见性确保源代码、文档和其他资产对企业中的所有成员可见，但对外部用户隐藏，从而确保数据只与适当的利益相关者共享。

1.  合规性、审核和治理

这些机制共同作用，支持企业的合规性需求：

+   **集中控制**：`SAML SSO` 和 `EMU` 确保对身份、凭据和会话策略的集中控制。

+   **审核能力**：细粒度 `PAT` 提供了增强的可跟踪性。管理员可以查看和撤销活动的 `SAML` 会话，也可以通过筛选器识别和跟进未启用 `2FA` 的用户。

+   **自动化合规性**：`SCIM` 通过及时停用访问权限和标准化用户数据，帮助组织满足策略和审核要求。

### 最佳实践

**您好，`GitHub` 标识管理和访问控制的最佳实践围绕着集成标识提供者（`IdP`）、自动化用户生命周期和实施最小特权原则这三大支柱展开。**

以下是基于您提供的源材料总结的最佳实践和关键机制：

---

#### 最佳实践一：强制执行集中式身份验证（`Authentication`）

最佳实践要求将 `GitHub` 的访问控制集中到您企业的 `IdP`（如 `Microsoft Entra ID` 或 `Okta`），并要求使用最强的身份验证方法。

1.  实施 `SAML` 单一登录 （`SSO`）

`SAML SSO` 是企业级身份验证的基础，它将 `GitHub` 与您的 `IdP` 集成，实现集中访问控制和提高合规性。

+   **选择企业级别强制实施**：最佳实践是在**企业级别**配置和强制实施 `SAML SSO`。这可以确保跨所有组织采用统一的策略，并降低配置碎片化的风险。

+   **登录流程简化**：用户通过 `IdP` 身份验证后才能授予对组织资源的访问权限。

1.  启用多重身份验证 （`2FA`）

强大的企业安全性要求在用户名和密码之外添加第二个验证步骤。

+   **强制范围**：要求组织成员、外部协作者和计费经理必须使用 `2FA`。

+   **采用强方法**：建议采用无密码方法来抵抗网络钓鱼。

+   `Passkeys` 和 `WebAuthn`：`Passkeys` 是一种与物理设备绑定的无密码登录方法。`WebAuthn` 支持生物识别因素和硬件令牌（如 `YubiKey`），这是最安全的方法之一。`GitHub` 建议使用 `FIDO2/U2F` 密钥。

+   `GitHub Mobile`：用户可以使用 `GitHub Mobile` 上的推送通知进行快速、安全的 `2FA` 审批。

1.  严格控制用户身份 （`EMU`）

**对于具有严格合规性、审核或用户治理需求的组织，应使用**企业托管用户 （`EMU`）。

+   **完全托管**：`EMU` 确保所有 `GitHub` 帐户完全由企业的 `IdP` 管理。

+   **集中控制**：`EMU` 模型强制对标识、凭据和会话策略进行集中控制。

+   **限制范围**：托管用户无法推送到企业外部的存储库，只能与企业内的其他用户和资源交互，从而防止意外的外部协作。

#### 最佳实践二：自动化用户生命周期管理

手动管理用户访问权限容易出现不一致、延迟撤销和安全风险。最佳实践是使用自动化协议来管理用户生命周期。

1.  实施 `SCIM` 进行完整生命周期自动化

**跨域身份管理系统 （`SCIM`）** 是一种开放标准协议，用于自动化用户身份信息交换。

+   **核心功能**：`SCIM` 实现了帐户生命周期的完全自动化。

    +   预配 （`Provisioning`）：自动创建用户帐户。

    +   **更新**：同步角色和部门信息。

    +   取消预配 （`Deprovisioning`）：在用户离开时及时删除访问权限。这减少了安全风险。

    +   **令牌撤销**：`SCIM` 还能在会话结束后撤销过时的令牌，而手动管理则需要管理员手动执行此操作。

    +   **一致性**：`SCIM` 通过跨系统标准化用户数据，帮助满足策略和审核要求。

1.  利用团队同步 （`Team Sync`） 管理授权

团队同步将 `IdP` 中的组映射到 `GitHub` 团队，从而实现授权的自动化。

+   **简化权限**：团队同步会自动反映 `IdP` 组中的成员身份更改（例如，将 `Alice` 添加到 `IdP` 组会自动添加到映射的 `GitHub` 团队），从而简化加入、权限管理和访问吊销。

+   **集成要求**：要使用团队同步，`IdP` 管理员必须启用 `SAML SSO` 和 `SCIM`。

+   **理想场景**：团队同步是按团队管理存储库访问权限的最佳解决方案。

#### 最佳实践三：实施最小特权授权控制

限制权限范围并将攻击面降到最低，是企业管理员的核心职责。

1.  使用细粒度个人访问令牌 （`PAT`）

应使用细粒度 `PAT` 来替代经典 `PAT`。

+   **范围限制**：细粒度 `PAT` 限制对**特定存储库和范围**的访问。

+   **增强安全**：它们支持自动过期以降低风险，并提供增强的可跟踪性和合规性控制。

+   **凭据管理**：所有 `PAT` 和 **`SSH` 密钥必须显式授权并链接到 `IdP` 标识，才能安全地访问组织资源。

1.  使用自定义存储库角色

通过定义超出默认权限集的**自定义角色**，针对独特的工作流定制委派访问权限。

+   **最小特权**：此方法有助于对敏感存储库执行**最小特权原则**。

1.  强制实施全局安全策略

除了用户和团队级别的控制外，还要在企业层面实施安全策略：

+   **`IP` 允许列表**：限制对已批准网络的访问。

+   `OAuth` 应用控制：阻止未经明确批准的未经身份验证的 `OAuth` 应用。

+   **内部可见性**：当组织成员创建存储库时，应使用**“内部”**可见性选项。这确保源代码、文档和其他资产对企业中的所有成员可见，但对外部用户隐藏。

#### 最佳实践四：持续治理和审核

持续监控和审核用户活动是必不可少的。

+   **审核会话**：管理员应在设置中查看活动 `SAML` 会话，并根据需要撤销单个会话。

+   **审核 `2FA` 合规性**：通过“人员”选项卡中的筛选器，识别和跟进未启用 `2FA` 的用户。

+   **跟踪能力**：细粒度 `PAT` 提供了增强的可跟踪性，有助于合规性审核。

## 通过在 GitHub 上使用拉取请求管理存储库更改

“拉取请求”（`Pull Request`，简称 `PR`）是现代软件开发中用于协作和管理代码集成的重要机制。它主要在版本控制系统（如 `Git`/`GitHub`）中发挥作用，旨在确保代码质量并规范合并流程。

以下是根据来源提供的关于拉取请求的作用和流程的详细说明：

### 拉取请求的作用 （`Role of Pull Request`）

拉取请求的核心作用是**记录、沟通、审查和保障**代码质量，以便将独立开发的工作安全地集成到主代码库中。

1.  **记录和通知集成意图**：拉取请求是一种记录分支更改的方法。它向利益相关者传达开发人员分支中的更改已准备好合并到基础分支（通常是 `main` 分支）中。

1.  **实现代码审查与讨论**：通过 `PR`，利益相关者可以**审查和讨论**提议的更改。这有助于确保基础分支中的代码质量尽可能地保持最高水平。

1.  **管理独立工作集成**：在新式软件开发中，开发人员在独立的分支中工作，以开发功能、修复错误或安全地试验新想法，而不会影响存储库中的其他人。拉取请求用于跟踪和审查这些分支最终需要合并到一个公共分支（例如 `main`）的操作。

1.  **强制执行质量标准**：存储库可以配置**分支保护规则**，要求拉取请求在合并前满足某些条件。这些常见要求包括：

    +   **必需的评审**：要求至少获得来自另一位协作者的批准评审。

    +   **状态检查**：要求通过所有必需的状态检查，例如持续集成 （`CI`） 工作流（包括运行单元测试、检查代码格式、验证安全扫描等）。

### 拉取请求的流程 （`Process of Pull Request`）

拉取请求的流程通常包括创建、状态管理、评审以及最终合并。

1.  前提：分支的比较

拉取请求**比较**两个分支之间的更改：

+   **“比较”分支**：是开发人员自己的分支，其中包含他们所做的特定更改。

+   **“基础”分支**：也称为“主”分支，是需要将更改合并到的目标分支。 当启动 `PR` 时，`GitHub` 会自动显示分支比较视图。

1.  创建拉取请求

创建拉取请求的步骤如下（以 `GitHub.com` 为例）：

1.  导航到存储库的主页。

1.  在“分支”菜单中，选择包含提交的分支。

1.  **在文件列表上方**的黄色横幅中，选择“比较和拉取请求”按钮。

1.  在下拉菜单中，选择**要将更改合并到的基础分支**，然后选择**进行了更改的比较分支**。

1.  为拉取请求输入**标题和说明**。

1.  选择创建**可供评审的拉取请求**（选择“创建拉取请求”按钮）或创建草稿拉取请求。

1.  拉取请求的状态

拉取请求具有不同的生命周期状态：

+   **草稿拉取请求**：无法合并，系统不会自动请求代码所有者评审草稿拉取请求。

+   **开放的拉取请求**：表示拉取请求处于活动状态，但尚未合并到基础分支。仍可以进行提交，并与协作者讨论和评审可能的更改。

+   **关闭的拉取请求**：可以选择关闭拉取请求，不将其合并到基础/主分支。如果不再需要分支中建议的更改，或者在另一个分支中提出另一个解决方案，则此选项很有用。

+   **已合并拉取请求**：指来自比较分支的更新和提交已与基础分支相合并。

1.  高级选项和评审

在开放状态下，团队可以利用高级选项来确保代码质量：

+   **请求审阅者**：可以请求特定的协作者（必须对存储库具有写入访问权限）查看 `PR`。审阅者将收到通知。

+   **状态检查**：如果存储库使用 `CI` 系统（如 `GitHub Actions`），`PR` 可能会自动运行状态检查（例如单元测试）。通常，`PR` 必须传递所有必需的状态检查才能合并。

+   **分支保护**：如果设置了分支保护规则，必须满足所有必需的条件（例如批准评审、通过 `CI` 检查）后，合并按钮才会启用。

1.  合并拉取请求

对存储库具有推送访问权限的任何人都可以完成合并。合并 `PR` 时，通常有三种选项，用于控制提交历史记录：

在选择合并选项后，需要输入或接受默认的提交消息，并选择要**用作 `Git` 创作者的电子邮件地址，然后确认合并。

（可选）合并完成后，可以删除比较分支，以保持存储库中的分支列表整洁。

## 使用 GitHub 搜索和组织存储库历史记录

`GitHub` 提供了强大的搜索、筛选和组织工具，旨在帮助开发人员和团队管理存储库历史记录、跟踪进度并提高协作效率。以下是这些工具的关键功能和最佳实践：

### 搜索和筛选功能

`GitHub` 提供了两种主要的搜索方法，它们支持相同的语法和功能，但在搜索范围上有所不同：

1.  搜索方法

    +   全局搜索 （`Global Search`）：

        +   允许使用**完整的搜索语法**在整个 `GitHub` 范围内进行搜索。

        +   搜索结果是**全面的**，涵盖代码、问题、拉取请求 （`PR`）、市场甚至用户。

        +   **这是跨多个结果类型和存储库查找提及关键术语的最佳方法**。

        +   **若要创建**复杂的全局搜索，可以使用高级搜索。

    +   上下文搜索 （`Context Search`）：

        +   可在特定的选项卡（如“问题”和“拉取请求”）上使用。

        +   搜索范围**限定在当前存储库内**，并且只返回该类型的结果。

        +   优点是用户界面可以公开已知特定于类型的筛选器（如作者、标签、项目等）。

        +   在当前存储库中查找内容时，**首选**使用上下文搜索，因为它便于使用筛选器下拉列表进行优化。

1.  搜索筛选器和语法

可以使用完整的搜索语法进行搜索，但通常只需用到一些常见筛选器。这些筛选器提高了搜索查询的准确性。

**注意：** 只有**打开的里程碑**才会匹配，除非通过搜索 `milestone:*` 来包含关闭的里程碑。某些筛选器子句（如 `is:pr`）仅受某些搜索提供程序支持，会被其他提供程序忽略（例如，代码搜索会忽略它）。

### 组织和跟踪工具

`GitHub` 提供元数据和分组工具来组织问题和拉取请求：

1.  里程碑 （`Milestones`）

里程碑允许将问题和请求分组到**共享目标**中，例如冲刺 （`sprint`）、产品发布或项目阶段。

+   **功能：**

    +   有助于团队**跟踪进度并保持一致**。

    +   里程碑可以像项目一样排序，以便轻松设置优先级和可视化最重要事项。

    +   `GitHub` 会**自动跟踪每个里程碑的进度**（已完成或保留了多少问题/`PR`）。

    +   里程碑对于跟踪进入不同版本或阶段的工作特别有用。

    +   可以作为列添加到 `GitHub Projects` 布局中，或在开发板上显示为卡片，以便直接从规划委员会管理进度。

+   **最佳实践：** 里程碑在团队的规划工作流中**一致使用时效果最佳**。

1.  标签 （`Labels`）

标签是帮助团队组织问题和拉取请求的元数据工具。它们可以反映问题类型、优先级、团队或工作流状态，并提高搜索查询的准确性。

1.  被分配者 （`Assignees`）

**可以将一个或多个人员**分配给问题或拉取请求，以显示负责处理该问题的人员。

+   可以通过右侧栏或列表视图中的复选框直接分配人员。

+   可以使用 `assignee:` 筛选器在搜索中查找分配给您或其他人的项目。

### 协作、历史记录和效率工具

1.  `Git Blame` / 责任 （`Blame`）

尽管名为 `git blame`，**但它是一个显示文件提交历史记录的命令**，可以轻松查看到是谁在何时做出了哪些修改。

+   **功能：** `GitHub` 利用更可靠的用户界面扩展了基本的 `git blame` 功能。通过责任视图，可以快速找到处理手头任务的主题专家 （`SME`）。

1.  交叉链接和 `@提及`

`GitHub` 非常擅长支持将不同的信息链接在一起，这对快速掌握上下文非常有价值。

### 工作原理和机制

`GitHub Copilot` 的工作机制和原理主要围绕其作为集成开发环境 （`IDE`） 内部的 AI 助手，通过处理开发人员提供的自然语言提示并结合上下文信息来生成代码建议。

以下是根据源材料总结的 `GitHub Copilot` 的原理和工作机制：

#### 核心定位与输入机制

`GitHub Copilot` 被定位为可从 `IDE` 内部使用的 AI 助手，它能够生成代码等内容。

1.  **依赖提示 （`Prompt`）**

    +   **`Copilot` 的核心工作方式是使用提示 （`Prompt`）。**

    +   提示是你键入的**自然语言文本**，它本质上是一组**指令或准则的集合**，用于帮助 `Copilot` 生成代码。

    +   **开发人员可以使用**注释或代码向 `Copilot` 提供上下文和示例。

1.  **提示的识别：**

    +   `Copilot` 能够判断键入的内容是提示还是指令。

    +   识别方式包括：

        +   在文件结尾为 `.py` 或 `.js` 等的**代码文件中将内容键入作为注释**。

        +   在 `Markdown` 文件中键入文本，然后等待几秒钟让 `Copilot` 返回响应。

1.  **示例：**

    +   当你输入一个提示（例如：`# Create a web API using FastAPI with a route to products.`）时，`Copilot` 就会使用该提示生成响应。

#### 工作机制：上下文和建议生成

`Copilot` 结合开发人员的输入和现有环境信息来生成相关的建议：

1.  **利用附加上下文：**

    +   **`GitHub Copilot` 使用文本编辑器中已打开的文件作为附加上下文。**

    +   **这一点很有帮助**，因为它除了正在编写的提示或代码之外，还提供了其他有用信息。

    +   如果在使用 `GitHub Copilot Chat` 时需要 `Copilot` 根据其他文件提供建议，可以打开这些文件或使用 `@workspace` 提示。

1.  **建议的呈现和交互：**

    +   **从 `Copilot` 返回的内容是一个建议。**

    +   **如果你的**文本颜色设置为黑色，建议文本会显示为灰色代码。

    +   **接受建议：** 如果要接受建议，可以按 `Tab` 键。

    +   **循环选择：** `Copilot` 可能会建议**多个响应**。在这种情况下，你可以使用 `Ctrl + Enter`（或 `Mac` 上的 `Cmd + Enter`）**循环访问这些建议**，然后**选择最合适的建议**。

#### 影响输出质量的关键原则

`Copilot` 提供的建议质量与开发人员如何构建输入（提示工程）密切相关：

+   **质量依赖于提示：** `Copilot` 输出内容的质量取决于你制作的提示的好坏。

+   **清晰度至关重要：** **设计有效的提示**对于**确保实现所需结果**至关重要。具体的、清晰的提示（例如：`# Create an API endpoint using the FastAPI framework that accepts a JSON payload in a POST request`）能够让 `Copilot` 知道任务的目标和范围，从而确保模型生成高质量的输出。

+   **迭代和精炼：** 遵循最佳做法，可以先**确保提示简单明了**，然后在继续操作时**添加更详细的组成部分**。如果未获得所需结果，可以**重新组织提示的措辞**，或**开始编写代码**来让 `Copilot` 自动完成。

### 提示工程（`Prompt Engineering`）对输出质量的影响

提示（`Prompt`）是开发人员输入给 `Copilot` 的自然语言文本，作为指令或准则的集合，用于帮助生成代码。

1.  **决定输出质量的基础：**

    +   `Copilot` 输出内容的质量取决于你制作的提示的好坏。

    +   设计**有效的提示**对于**确保实现所需结果**至关重要。

1.  **明确的提示带来高质量的输出：**

    +   **具体的、清晰的提示**能够让 `GitHub Copilot` 知道任务的目标和范围，从而确保模型生成高质量的输出。

    +   **示例：** 像 `# Create an API endpoint using the FastAPI framework that accepts a JSON payload in a POST request` 这样的提示是具体而清晰的，能够引导 `Copilot` 给出符合要求的代码。

1.  含糊的提示导致质量不佳或不相关的输出：

    +   **含糊不清的提示**，例如 `# Create an API endpoint`，可能导致 `GitHub Copilot` 生成的结果不符合你的需要。

    +   例如，它可能会提供使用了你不熟悉的框架的代码，或者提供了需要你不了解的数据的终结点。

1.  **迭代和精炼提示：**

    +   **在提示工程中**，你可以使用注释或代码向 `Copilot` 提供上下文和示例。

    +   **你也可以利用 `GitHub Copilot Chat` 的聊天选项来增强自己的提示。**

### 提示词最佳实践

除了构建初始提示，开发人员在使用 `Copilot` 时的行为和方法（最佳实践）也直接影响最终代码的质量。

1.  **迭代式提示方法：**

    +   一种确保质量的最佳做法是：首先**确保提示简单明了**，然后在继续操作时**添加更详细的组成部分**。

    +   **示例：** 从一个简单的提示（如 `create an HTML form with a text field and button`）开始，然后通过进一步详细阐述（如 `Add an event listen to the button to send a POST request to /generate endpoint and display response in a div with id "result"`）来获取更具体的建议。

1.  **循环和选择最佳建议：**

    +   `Copilot` 可能会建议**多个响应**。

    +   开发人员应遵循最佳做法，在建议之间循环（使用 `Ctrl + Enter` 或 `Mac` 上的 `Cmd + Enter`），并选取最佳输出。

    +   在 `GitHub Copilot Chat` 中，你也可以使用聊天输入来添加提示并与输出交互。

1.  **重新组织提示或手动辅助完成：**

    +   如果开发人员**未获得所需结果**，最佳实践建议他们可以**重新组织提示的措辞**，或**开始编写代码**来让 `Copilot` 自动完成。

1.  **利用上下文信息增强质量：**

    +   **`GitHub Copilot` 使用文本编辑器中已打开的文件作为附加上下文。**

    +   **这一点很有帮助**，因为它除了正在编写的提示或代码之外，还提供了其他有用信息，有助于生成更相关的代码。
