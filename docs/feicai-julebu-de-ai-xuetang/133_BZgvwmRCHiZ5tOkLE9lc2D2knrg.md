
# Claude Code 新上了“自动记忆功能”

> 来源：[https://feicaiclub.feishu.cn/docx/A4wkdmI3hoxU9MxjIiqcCyh9nXb](https://feicaiclub.feishu.cn/docx/A4wkdmI3hoxU9MxjIiqcCyh9nXb)

![](img/96f2b7a3422771735fcbdc05b913d6e1.png)

如果你用过 Claude Code 超过一周，你一定经历过这件事。

你花了四个小时和 Claude 调试一个页面显示错乱的问题。你们一起踩了坑，绕了弯，最后搞定了。你关掉终端，去睡觉。

第二天早上打开新会话。

它对昨晚的一切一无所知。

你得从头解释你的项目结构。从头告诉它你们用 `pnpm` 不用 `npm`。从头提醒它每次改完代码要先跑一遍 `npm run build`。从头。每一次。

这个体验烂透了。

而你之所以忍了这么久，是因为你以为这就是 AI 编程工具的常态——每次对话都是一张白纸，你负责反复往上面写同样的字。

2 月 27 日，Anthropic 在 Claude Code v2.1.59 里正式上线了 Auto Memory。

它试图解决的就是这个问题。

但它解决得好不好，有没有新的坑，值不值得你现在就打开——这些问题没人替你想清楚。所以这篇文章的目的很简单：我把能挖的都挖了，你读完之后自己判断。

## I — 它到底是什么

先说清楚一件事：Claude Code 里的"记忆"不是一个东西，是两个。

第一种，是你写给 Claude 的。

就是 `CLAUDE.md` 文件。你在项目根目录放一个 `CLAUDE.md`，里面写上"我们用 TypeScript，测试框架是 Vitest，API 命名用 kebab-case"，Claude 每次启动会话都会读它。这是你主动维护的规则手册。

第二种，是 Claude 写给自己的。

这就是 Auto Memory。Claude 在和你协作的过程中，会自动把它觉得"下次还用得上"的东西记下来——你的项目用什么构建命令、测试怎么跑、哪些文件是关键入口、你踩过什么坑、你偏好什么编码风格。它把这些笔记写进一个本地的 Markdown 文件里，下次开新会话自动加载。

注意那个词：**自动。**

你不需要告诉它"记住这个"。你不需要手动维护任何文件。你只需要正常工作，它自己决定什么值得记、怎么记。

这就是 Auto Memory 的核心卖点，也是它最大的争议来源。

后面会讲为什么。先说它具体怎么运作。

## II — 它怎么运作，怎么用

### 存在哪

每个项目有自己独立的记忆目录，路径是 `~/.claude/projects/<project>/memory/`。这个 `<project>` 是从你的 git 仓库根目录推导出来的，同一个仓库的所有子目录共享一份记忆。

目录结构长这样：

```
~/.claude/projects/<project>/memory/
├── MEMORY.md          # 主入口，索引文件
├── debugging.md       # 调试相关的笔记
├── api-conventions.md # API 设计决策
└── ...                # 其他主题文件
```

`MEMORY.md` 是核心。每次你启动新会话，Claude Code 会自动加载这个文件的前 200 行到系统提示里。

200 行。硬上限。超出的部分不加载。

这是设计使然——它逼你（准确说是逼 Claude）把 `MEMORY.md` 保持精简，像一个目录，而不是一本百科全书。详细内容拆到 `debugging.md`、`api-conventions.md` 这些主题文件里，Claude 需要的时候再按需读取。

### 怎么管

三种方式，从轻到重：

**第一，被动模式。** 什么都不做，正常写代码。Claude 会在工作中自己判断"这个值得记"，然后默默写进去。你甚至不会注意到。

**第二，主动指示。** 直接跟 Claude 说人话：

+   "记住，我们用 `pnpm`，不用 `npm`"

+   "记住，每次提交代码之前要先跑 `npm test`"

它就会写进 `MEMORY.md`。

**第三，手动管理。** 在 Claude Code 里输入 `/memory`，会弹出一个文件选择器，你可以直接打开任何记忆文件编辑。里面还有一个开关，可以一键关闭 Auto Memory。

### 怎么关

如果你不想用（先别急着关，往下看完再决定）：

+   单项目关闭：在 `.claude/settings.json` 里加 `"autoMemoryEnabled": false`

+   全局关闭：在 `~/.claude/settings.json` 里加 `"autoMemoryEnabled": false`

+   强制覆盖一切：设环境变量 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`，适合 CI 环境

这三个控制层级是递进的，环境变量的优先级最高。

## III — 大家用下来到底怎么说

**功能上线后**，社区的反应可以用一个词概括：又爱又怕。

### 爱的部分

最直接的正面反馈是：**它真的消除了"金鱼记忆"问题。**

有开发者做了对照测试——同一个代码库，一个账号开了 Auto Memory，一个没开。开了的那个明显更好用，因为 Claude 会把之前踩过的坑自动记录下来，下次遇到同类问题直接避开，不再犯同样的错。

有人说得更具体：某些库的 API 在文档里写的和实际行为不一致，Claude 遇到一次报错之后把正确用法存进了记忆，后续生成代码再也没出过这个问题。

还有一个很实际的好处：它消除了 Claude 的"探索阶段"。以前每次新会话，Claude 要花好几步去 `grep` 你的项目结构、读 `package.json`、找入口文件。现在这些信息就在记忆里，零探索，直接干活。

这些是好消息。

### 怕的部分

坏消息也来了，而且来得很快。

### 第一个恐惧：控制权。

GitHub 上 #23750 这个 issue 把核心矛盾说得很清楚：用户不希望 Claude 自动往一个他无法控制、缺乏可见性的目录里写东西，然后这些东西变成影响所有未来会话的隐性规则。

直白点说就是：我写的规则我认，你自己记的东西凭什么也算数？

这不是无理取闹。如果 Claude 记录了一条错误的结论——比如误以为你的项目用 `npm` 而不是 `pnpm`——这个错误会在你毫不知情的情况下持续影响后续所有会话。沉默的错误是最危险的错误。

### 第二个恐惧：钱。

就在 v2.1.59 上线当天，GitHub 上出现了 issue #29178，有开发者报告说：同样的使用习惯，额度消耗速度明显加快了——18 分钟的轻度对话就烧掉了 8% 的会话额度。

怀疑的矛头直指 Auto Memory。道理很简单：每次新会话启动，`MEMORY.md` 的前 200 行会注入系统提示。你的 `CLAUDE.md` 也会加载。再加上 `.claude/rules/` 下面的规则文件。这些东西加在一起，你每次对话的"起步价"就比以前高了。

更何况 Claude 在会话过程中还会读写记忆文件，这些操作本身也消耗 token。

### 第三个恐惧：它"记住了"不等于它"学会了"。

Medium 上有一篇文章标题很到位：Automatic Memory Is Not Learning。

Auto Memory 记录的是模式的反复出现，而不是对因果关系的理解。它知道"我们用 `pnpm`"，但不知道为什么用 `pnpm`。它知道"部署之前要跑 `npm run build`"，但不知道你为什么选择这个构建方式、什么情况下应该换一种。

这意味着当你的项目发生重大变更——从 JavaScript 换成 TypeScript，或者把项目从一个框架迁移到另一个——旧记忆不会自动失效。它还在那里，安安静静地误导你的下一次会话。

## IV — 为什么这个功能会出现

Auto Memory 不是凭空冒出来的。在它上线之前，开发者社区已经喊了很久了。

往回翻 GitHub issue，需求脉络很清晰：

**2025 年 12 月，#14227。** 有人提了个 feature request，标题直说：Persistent Memory Between Claude Code Sessions。核心诉求一句话——"别让 Claude 每次启动都从零开始。"

**2026 年 1 月，#19291。** 另一个 issue 更明确：Add automatic memories like ChatGPT。言下之意，竞品已经有了，你们不能没有。注意那个关键词——automatic。手动维护 `CLAUDE.md` 可以解决问题，但开发者不想干这个活。

**2026 年 2 月，#28107。** 这个 issue 切到了一个更深的痛点：做了大量 web 搜索和文档研究之后，当 context window 触发压缩，那些昂贵的研究结果就被吞了。开发者希望 Claude 能在压缩之前主动把关键信息存进记忆文件。

把这三个需求拼在一起，你就能看到一条完整的进化线：

先是要"记住"，然后要"自动记住"，最后要"在关键时刻主动记住"。

Auto Memory 目前走到了第二步。第三步还没完全到，但已经在路上了。

社区对它的期待也很统一——要透明、要可控、要可审计。我能看到它记了什么，我能随时改或删，它不要偷偷膨胀到不可控的地步。

这些期待合理吗？合理。满足了吗？部分满足。

它用的是纯 Markdown 文件，你随时可以打开看、编辑、删除。这个设计决策值得称赞——没有黑箱数据库，没有加密格式，就是文本文件。

但"可控"这一条，还差点意思。后面讲。

## V — 它对你的工作流意味着什么

讲完背景，说点实际的。

如果你决定打开 Auto Memory（它现在默认就是开的），你的日常工作流会发生几个具体变化：

### 新会话不再从零开始

这是最直观的改变。以前你打开一个新终端，Claude 对你的项目一无所知，你得花前几轮对话做"热身"——解释项目结构、技术栈、测试方式。

现在 Claude 带着记忆启动。它知道你的构建命令、测试框架、关键文件的位置、你上次踩过的坑。这个"探索阶段"消失了，或者至少大幅缩短了。

### 踩坑一次，免疫永久

你在某次会话里调试了一个很诡异的 bug——比如某个第三方库在特定版本下有一个没写进文档的行为。Claude 把它记下来了。下次不管是你还是你的同事（如果你们把这条经验升级到了 `CLAUDE.md` 里）遇到同类问题，Claude 直接绕过去。

这不是小事。在长期项目里，这类"隐性知识"的积累效应是巨大的。

### 但——它是你个人的，不是团队的

Auto Memory 的作用域是"你 + 这个项目"。你的队友看不到你的记忆文件，你也看不到他们的。

这意味着同一个仓库，不同人的 Claude 行为可能不一致。你的 Claude 记住了某个坑，你队友的 Claude 还在那个坑里转圈。

解法是：Auto Memory 负责自动抓取经验，你定期审查，把稳定的部分迁移到项目级的 `CLAUDE.md` 或 `.claude/rules/` 里——这些文件进版本控制，团队共享。

让 Auto Memory 做侦察兵，让 `CLAUDE.md` 做宪法。

### 隐性成本真实存在

每次新会话启动，`MEMORY.md` 前 200 行加上你的 `CLAUDE.md`、规则文件，加在一起可能消耗 2000+ token。在 Opus 4.6 的上下文窗口里占比不到 1%——看起来不多。

但会话过程中 Claude 对记忆文件的读写也消耗 token。多个大型记忆文件同时存在时，叠加效应不可忽视。v2.1.59 发布当天就有用户反映额度消耗异常加快，虽然还没有定论，但这个信号值得注意。

## VI — 优点和缺点，说清楚

### 优点

**零配置起步。** 默认开启，不需要你做任何设置就开始积累项目知识。上手成本为零。

**完全透明。** 所有记忆都是本地 Markdown 文件，可读可编辑，没有黑箱。这一点比大多数竞品做得好。

**结构上有防线。** 200 行硬限制 + 主题文件拆分机制，防止 `MEMORY.md` 无限膨胀。它在设计上就不想让你的系统提示失控。

**分层架构设计清晰。** 全局偏好（`~/.claude/CLAUDE.md`）→ 项目约定（`./CLAUDE.md`）→ 条件规则（`.claude/rules/`）→ 自动积累（Auto Memory），四层递进，各司其职。

**控制手段充足。** `/memory` 命令、`settings.json`、环境变量，三条路径管理。CI 环境一个环境变量直接关闭，干净利落。

### 缺点

**记忆质量不可预测。** Claude 自己决定记什么，这意味着它可能遗漏你认为重要的东西，也可能记录错误的结论。一条错误的记忆比没有记忆更危险，因为你不知道它在那里。

**200 行可能不够。** 对于复杂项目，200 行很快就满了。虽然可以通过拆分主题文件来扩展，但那些文件不自动加载，Claude 需要的时候才去读——前提是它知道自己需要。

和 `CLAUDE.md` 的边界模糊。目前 UI 上 "writing memory" 和 "reading memory" 的提示不区分是在操作 Auto Memory 还是 `CLAUDE.md`。当两套系统的内容开始重叠甚至冲突时，排查起来很头疼。

**token 成本隐性上升。** 社区已有明确反馈。目前还没有官方回应确认或否认，但逻辑上是成立的——更多的系统提示内容，更多的文件读写操作，更多的 token 消耗。

**"记住"不等于"理解"。** 这是最根本的局限。Auto Memory 是模式记录器，不是学习引擎。它能记住"我们用 React"，但不理解你当初为什么选 React 而不是 Vue。项目发生重大变更时，旧记忆不会自动失效，需要你手动清理。

**团队一致性需要额外工作。** 每人一份记忆意味着同一个项目里，不同人的 Claude 可能表现不一致。必须靠人工定期将稳定经验迁移到团队共享的 `CLAUDE.md` 里。

## VII — 最后说句实话

Auto Memory 不是什么革命性的突破。

它解决的是一个本来就不应该存在的问题——AI 助手不应该每次对话都失忆。从这个角度说，它只是把一个严重的体验缺陷修补到了及格线。

但它修补的方式是聪明的。纯文本、完全透明、分层架构、多级控制——这些设计决策表明 Anthropic 至少想清楚了一件事：记忆系统最大的敌人不是遗忘，是失控。

所以我的建议很简单：

**打开它。让它跑。但每周花 10 分钟打开 `/memory`，审查一遍 `MEMORY.md`。** 删掉过时的、修正错误的、把经过验证的稳定规则升级到 `CLAUDE.md` 里。

不要完全信任它的判断。不要完全依赖它的记录。

像对待一个记忆力终于不为零的新同事一样对待它——很高兴你能记住点东西了，但我还是会检查你的笔记。

这就是 Auto Memory 现在该有的定位。

不多，不少。
