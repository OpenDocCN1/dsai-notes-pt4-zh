# Clawdbot 终于能"替你做事"了——但大多数人会用错

> 来源：[https://feicaiclub.feishu.cn/docx/A2NFdfMYgouz5yxGFpWcndtEnqd](https://feicaiclub.feishu.cn/docx/A2NFdfMYgouz5yxGFpWcndtEnqd)

![](img/8f324d228ae0361649027154076d65ca.png)

**如果你最近刷** X，**你大概率看到了两**个词：Cowork 和 Clawdbot。

一个是 Anthropic 官方推出的桌面代理，能读你的文件、动你的日历、替你整理下载文件夹。另一个是开源的个人助理，接入 WhatsApp、Telegram，帮你清邮箱、发邮件、管日程。

尤其是 Clawdbot，这几天几乎霸屏了。

它的 slogan 写得很直接："The AI that actually does things"——不是帮你想，是替你做。你在 Telegram 上给它发一句话，它就能替你清理收件箱、发送邮件、整理日历。开源、自托管、多渠道接入，release 节奏快到几乎每隔几天就有更新。

评论区炸了。

有人说这是"普通人的 AI 时刻"，有人说"程序员之后终于轮到我们了"，还有人已经开始卖 Skills 教程。

但我看到的是另一件事：大多数人会把这波机会用错，就像他们用错了之前每一波一样。

不是因为工具不够好。

是因为他们根本不知道自己每天在干什么。

# I — 编程浪潮的本质从来不是"写代码"

过去两年，AI 编程工具把"程序员要被替代"这个话题炒到了天上。

但如果你仔细看，被改变的从来不是"写代码"这个动作本身。

被改变的是：一大类劳动从"产出内容"升级为"驱动系统执行"。

以前你写一段代码，是为了让机器做某件事。现在 AI 替你写那段代码，但本质没变——你还是在驱动系统执行。只不过中间少了一层手工翻译。

编程之所以最先被代理化，是因为它最容易被结构化：输入明确、输出可验证、失败条件清晰。

现在，这个逻辑终于蔓延到了普通人的工作场景。

Cowork 的官方定位写得很直白："Claude Code for the rest of your work"——把开发者在终端里处理多步任务的方式，变成面向非编程工作的形态。它能在你授权的文件夹里读、写、新建文件，替你完成"从截图汇总报销表"、"从笔记生成报告草稿"这类事。

Clawdbot 走的是另一条路，而且更激进。

它不依赖某个大厂的客户端，而是让你自己跑起来——接入你已经在用的聊天软件，WhatsApp、Telegram、Slack、Discord，哪个顺手用哪个。你不需要打开一个新的 App，不需要学习一套新的操作界面。你只需要像给朋友发消息一样，告诉它"帮我把这周没回的邮件整理一下"，它就去做了。

这就是为什么 Clawdbot 这几天能火成这样——它把"AI 代理"的入口降到了几乎为零。

两者的共同点是：它们不只是回答问题，而是替你完成一串操作。

这才是真正的分水岭。

# II — "Builders 比 Users 多"——但这只是你看到的

如果你最近关注 Skills 生态，你大概看过这个梗：

> "Skills/MCP 大概是历史上第一个 builders 比 users 多出好几倍的技术。"

X 上有人拿这句话做 meme，LinkedIn 上有人写文章复读，甚至有专门分析"为什么这么多 MCP server 在吃灰"的帖子。

表面上看，这很荒谬。

但如果你只盯着"外部可见的 Skills"，你会得出错误的结论。

《The Pragmatic Engineer》的调查里提到一个被忽略的事实：大量 Skills 是在公司内部建给自己人用的，根本不会发出来。

所以"没有用户"可能只是观察偏差——你看到的是在外面吆喝的人，看不到闷头自用的人。

Clawdbot 的开源社区其实已经在印证这一点。你去看它的 GitHub，会发现很多人 fork 之后就消失了——不是因为项目不好，而是因为他们拿去改成了自己的版本，接入自己的工具链，解决自己的问题。他们不需要发出来，因为那本来就是给自己用的。

这不是在替那个梗辩护。

恰恰相反，这说明了一个更重要的事：

真正有价值的 Skills，往往不是拿来卖的——是自己先用起来的。

## III — Builder 本身就是 User

这是我想说的核心。

现在 Skills 市场的失衡，本质上是因为太多人跳过了第一阶段。

他们看到"Skills 可以卖"，就开始想"我能做什么卖给别人"。

但问题是：你自己都没用过的东西，凭什么觉得别人会用？

这跟 GPT Store 早期一模一样。TechCrunch 报道过它被 spam 填满、Wired 报道版权投诉、Hacker News 上的典型评论是"门槛趋近于 0，垃圾占比趋近于 100%"。

当创作门槛下降得太快，而"验收/评测/责任"机制没跟上时，供给会先爆炸，质量分布会变得极端长尾。

Skills 市场正在重演这个剧本。

但如果你换一个视角看，逻辑就通了：

+   第一阶段：**自用闭环**——你造的东西首先是给自己用的，解决你自己的问题。

+   第二阶段：**商品化**——可分发、可评测、可托管、可责任化。

现在大多数人卡在"想直接跳到第二阶段"。

而真正该做的是：**先当 User，再当 Builder。或者**说，Builder 本身就是 User。

你不需要急着想你的 Skills 以后能卖多少钱。

你需要先回答一个问题：你自己每天在干什么？哪些是重复劳动？哪些可以被抽象成流程？

如果你答不上来，你造的任何 Skills 都是空心的。

## **IV — 产品是壳，资产是核**

Cowork 会有竞品。Clawdbot 会有竞品。

事实上，Clawdbot 火了之后，已经有人在做类似的东西了——不同的入口、不同的连接器、不同的 UI。这只会越来越多。

你会看到各种各样的"个人代理"产品冒出来——不同入口、不同 UI、不同连接器。

**但它们本质上都是壳。**

我把这个逻辑拆成三层，你就能看清楚什么才是真正该沉淀的：

**第一层：交互层**这就是 Cowork、Clawdbot 这类产品——桌面、聊天入口、操作界面。它决定的是"用起来顺不顺手"。Clawdbot 选择了聊天软件作为入口，Cowork 选择了桌面客户端，但这只是交互偏好的差异。

**第二层：执行层**连接器、工具调用、文件/日历/邮箱权限、自动化动作。它会逐渐标准化（MCP 这类协议就是在做这件事）。Clawdbot 能接你的 Gmail、Google Calendar、Notion，Cowork 能动你的本地文件系统——但这些连接能力迟早会被拉平。

**第三层：资产层**这才是你真正该沉淀的——你的模板、口径、偏好、SOP、清单、约束规则、私域知识，以及评测与复盘机制。

壳会被快速复制，执行层会标准化，只有资产层才是长期复利。

同样一个代理产品，A 用起来像玩具，B 用起来像第二大脑。差别往往不在模型，而在：

+   你有没有把高频工作拆成可验收流程（输入是什么、输出长什么样、失败条件是什么）

+   有没有把个人/团队口径做成模板与规则

+   有没有持续复盘，让技能迭代

产品是车，沉淀是路书。

车决定你开得顺不顺。但你能不能到、能不能常到、能不能越开越快，取决于路书。

**这就是为什么我说 Clawdb**ot 火不火其实不是重点。重点是你有没有东西可以喂给它。

你可以今天用 Clawdbot，明天换成另一个更好的工具，但如果你沉淀的 Skills、Rules、模板是清晰的，迁移成本几乎为零。反过来，如果你什么都没沉淀，换什么工具都是从零开始。

## **V — 2026 年的真正趋势**

如果你问我"这波会往哪走"，我会给你四个判断：

趋势 A：从"对话式"走向"代理式"

Cowork 明确用"把复杂多步任务交接给 Claude 执行"来定义自己。Clawdbot 的整个设计哲学就是"你说一句，它做一串"。这不是聊天机器人的升级，是执行者的诞生。

下一步：代理会越来越"常驻化、可调度、可并行"，像一个团队成员，而不是一次性问答。

趋势 B：权限边界会成为产品分水岭

Cowork 之所以强调 research preview，是因为它触碰文件系统后，风险从"答错"升级到"做错"。媒体也直接点名提示注入与潜在破坏性操作的风险。

Clawdbot 也面临同样的问题——它能发邮件、能动日历，这意味着一旦出错，后果是真实的。这也是为什么它强调自托管、强调你自己控制权限。

下一步：谁能把"可控授权、可审计、可回滚、可验收"做得更好，谁就能进入更高价值的真实工作流。

趋势 C：Skills 模块化会成为护城河

Anthropic 已经在推进 Skills 这种可加载的模块（包含指令、脚本、资源），用来让 Claude 更贴合特定工作任务与组织规范。

Clawdbot 社区也在往这个方向走——你会看到越来越多人分享自己的"邮件处理流程"、"日程整理规则"、"周报生成模板"。这些就是 Skills 的雏形。

下一步：会出现"个人技能栈 / 团队技能库 / 行业技能市场"，以及围绕 Skills 的版本管理、评测、权限与合规体系。

趋势 D：接口标准化会加速生态扩张

MCP integrations 被放在 Cowork 的关键描述里，意味着它在为"更通用地接入外部系统"铺路。

下一步：真正的竞争不只在模型，而在"你能接入多少系统 + 你能把系统操作约束得多可靠"。Clawdbot 今天能接 WhatsApp 和 Telegram，明天可能能接你的 CRM、你的财务系统、你的项目管理工具。入口会越来越多，但标准会逐渐收敛。

## **VI — 你现在该做什么**

别急着造 Skills 卖钱。

也别急着跟风部署 Clawdbot 然后发一条"我也用上了"的推文。

先做三件事：

1.  **选 3 个高频场景做闭环**

比如周报、对账、日程整理。

每个写清楚：输入是什么、输出长什么样、失败条件是什么。

如果你连这个都写不出来，说明你从来没认真审视过自己的工作流。

你可以拿 Clawdbot 试试——让它帮你整理一周的邮件，看看输出是不是你想要的。如果不是，问题不在工具，在于你没告诉它"什么叫整理好了"。

1.  **把 Rules 写出来**

什么必须二次确认、什么不能外发、什么数据源可信。

这不是官僚主义。当 AI 能动你的文件和邮箱时，边界就是生命线。

Clawdbot 能替你发邮件，但哪些邮件可以自动发、哪些必须你过目？这个边界不是工具替你定的，是你自己要想清楚的。

1.  **建一个最小模板库**

邮件模板、会议纪要模板、日报周报口径。

不需要多，3-5 个就够。但它们必须是你真正在用的，不是想象中"可能有用"的。

然后做一次对比实验：

同一工具、同一模型——"无沉淀"vs"有沉淀（模板+规则+流程）"。

看节省多少时间，看错误率差多少。

你会得到最强的"非口嗨证据"。

## VII — 最后我想再次明确一下事情的本质

编程浪潮的本质不是让更多人写代码，而是让更多人拥有"可编排的执行力"。

当 AI 能读你的文件、动你的日历、发你的邮件时，每个人都在获得一层新的"数字手脚"。

Clawdbot 火了，Cowork 火了，接下来还会有更多类似的产品火。

但手脚只是工具。

**接下来决定差距的，不是谁买了更强的 AI，不是谁更早部署了 Cla**wdbot，而是谁把自己的工作与生活沉淀成了可复用、可控、可审计的Skills。

2026 年我们进入的是"可控代理"的早期扩张期。

入口会爆炸式增多。

但真正的分水岭不在入口——**在你有没有东西可以喂给它。**
