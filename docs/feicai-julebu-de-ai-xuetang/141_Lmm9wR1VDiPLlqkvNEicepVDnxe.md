# 你不需要另一个 App——你需要的是能力栈

> 来源：[https://feicaiclub.feishu.cn/docx/JmDhd510noONEjxLYtlcAFW3njF](https://feicaiclub.feishu.cn/docx/JmDhd510noONEjxLYtlcAFW3njF)

![](img/1a7f6014129172850d09cb5dd010b5bf.png)

如果你现在还在想"我要开发一个 App"，你可能已经落后了。

我知道这句话听起来有点刺耳。毕竟，过去十几年里，"做一个 App"几乎是创业者的标准动作。有了想法，就写代码，打包，上架，推广，变现。这条路径清晰得像一条流水线。

但最近我越来越强烈地感觉到：这条流水线正在被拆掉。

## **I — 我观察到的变化**

我在自己的社群里交付内容已经有一段时间了。最开始，我交付的是提示词框架——告诉用户怎么写 Prompt 能让 AI 输出更好的结果。后来，我开始交付 Agent 的系统提示词——一整套可以直接复制粘贴到 Claude 里使用的指令。

再后来，我交付的东西变得更复杂：Agent 加 Skills，或者整套的工作流解决方案。

但你知道最让我震惊的是什么吗？

我交付的所有这些东西，本质上都是文本文件。

用户只需要在自己的 Claude 里配置好，就能直接使用我搭建好的服务。而我搭建的整个过程，全是用自然语言完成的。没有写一行传统意义上的代码。

这让我开始思考一个问题：在这种新的服务交付模式下，我们真的还需要花几个月甚至几年去开发一个周期那么长的 App 吗？

## II — 正在发生的转变：从"产品"到"能力件"

如果你关注 Claude 的更新，你会发现一个明显的趋势：他们不是在做一个越来越强大的"聊天机器人"，而是在构建一套可组合的能力系统。

让我用几个关键概念来说明这个趋势。

**Agent**

Claude 的 Agent 不是一个固定的产品，而是一种可配置的智能体。你可以通过自然语言告诉它：你是谁，你擅长什么，你应该怎么处理任务。Agent 的行为完全由你定义的规则和上下文决定。

**Skills**

Anthropic 在 2025 年底把 Agent Skills 发布为开放标准。一个 Skill 本质上就是一个文件夹，里面包含 SKILL.md（用 YAML 和 Markdown 写的说明）加上相关的脚本、模板、资源。

这意味着什么？你可以把自己的专业知识、工作流程、最佳实践打包成一个"技能包"，然后分享给别人。别人把这个文件夹放进自己的环境，Agent 就能"学会"这项技能。

**Rules**

最近 Claude Code 开始支持 Rules——一种模块化的规则系统。原本你需要把所有提示词规则写在一个 CLAUDE.md 文件里。现在，你可以把规则拆分到 .claude/rules/ 目录下的多个文件中，还能用 YAML frontmatter 控制"什么时候生效"。

这不是一个小功能更新。这是把"指令注入"做成了可编排的规则系统。

MCP（Model Context Protocol）

MCP 是 Anthropic 提出的开放协议，用来标准化"AI 如何连接外部工具"。一个 MCP server 可以是数据库连接器、搜索引擎接口、工单系统的桥梁——任何你需要 AI 访问的能力，都可以封装成一个 MCP server。

更重要的是，Linux Foundation 已经成立了 Agentic AI Foundation（AAIF），把 MCP、AGENTS.md 等关键项目纳入中立治理。这说明行业正在围绕这些开放协议建立"新基础设施"。

## III — 为什么会走向这个方向？

你可能会问：为什么不继续做 App？App 不是很好吗？

**让我告诉你 App 模式的根本问题：当 AI** 让"使用代码"的门槛趋近于零时，"打包成产品"这件事本身的价值正在被稀释。

传统的 App 模式是这样的：开发者花几个月写代码，把功能封装成一个黑箱，用户付费使用这个黑箱。用户不需要知道里面是什么，也没法改变里面是什么。

但现在，情况变了。

用户可以把你的"能力包"放进 Claude Code 或者 Cursor，让 AI 学习、理解、甚至改造。你交付的不再是一个不可拆解的产品，而是一堆原材料。用户会拿着你的原材料，按自己的意图重新组装。

这就是为什么"文件化交付"开始变得比"App 交付"更有吸引力：

第一，**可审计**。用户能看到你的规则、你的逻辑、你的工作流是怎么写的。透明带来信任。

第二，**可改造**。用户不满意？他们可以自己改。有了 AI 辅助，改一个提示词文件的门槛，远低于 fork 一个代码库重新开发。

第三，**可组合**。不同的 Skills、Rules、MCP servers 可以像乐高一样拼在一起。你做一个"写作助手"的 Skill，别人做一个"SEO 优化"的 Skill，用户把它们组合起来，就有了一个"写作+SEO"的解决方案。

第四，**可迁移**。当这些能力件遵循开放标准（比如 MCP、AGENTS.md），用户就不会被锁定在某一个平台上。今天用 Claude，明天换别的工具，这些能力件还能用。

## **IV — 用户不再只是用户**

这是我认为最重要的转变。

传统模型里，有一条清晰的边界：开发者做产品，用户使用产品。开发者是创造者，用户是消费者。

**这条边界正在消融。**

当用户可以用自然语言配置 Agent，当用户可以把别人的 Skills 放进自己的环境并让 AI 帮忙理解和改造，当用户可以像搭积木一样组合不同的能力件——他们还只是"用户"吗？

他们同时也是创作者。

我在社群里已经看到这种现象了。有些用户拿到我的 Agent 配置后，不是直接用，而是先问 Claude："帮我理解一下这个配置在做什么，我想改几个地方。"然后他们真的改了，而且改出了比我原版更适合他们场景的版本。

这意味着什么？

意味着"产品"这个概念正在被重新定义。你交付的不再是一个完成品，而是一个起点。用户会从这个起点出发，走向他们自己的方向。

也意味着"开发者"这个身份正在泛化。你不需要会写代码，只需要会用自然语言描述你想要的东西，AI 就能帮你实现。每一个能清晰表达需求的人，都有潜力成为"开发者"。

## **V — 两个可能的世界**

这种趋势会走向哪里？我看到两种可能的未来。

**世界一：入口高度集中**

少数平台——Claude、ChatGPT、Microsoft Copilot——成为用户的主要入口。这些平台提供统一的运行时：账号体系、记忆、权限、审计、模型路由、成本控制。

在这个世界里，开发者的价值会从"做 App"迁移到"做能力件"。你不再开发独立的产品，而是开发可以上架到这些平台 marketplace 的 Skills、Agents、MCP servers。

这很像现在的 App Store 模式，只是"App"变成了"能力件"。

**世界二：入口多元，能力层开放**

通用入口解决通用任务，但大量垂直入口仍然存在——医疗、金融、法务、政务、科研。这些领域需要专业的 UI、严格的合规、特定的数据隔离。

但关键是：**能力层是共享的**。MCP、Skills、AGENTS.md 这些开放标准成为跨入口的"中间层"。你开发的能力件可以同时在 Claude 和其他工具里使用，降低了锁定。

这更像现在的 Web 模式——浏览器有很多种，但 HTML/CSS/JavaScript 是通用的。

我的判断是：**两者会并存**。入口的集中度会上升，但不会是赢家通吃。开放标准会抑制单一平台的垄断，同时让能力件市场变得更大、更繁荣。

## **VI — 飞轮与刹车**

如果你认同这个趋势，下一个问题是：这个生态能做多大？

我看到一个正在形成的飞轮：

**第一个齿轮：抽象层（UI）**。 Claude Desktop、Cowork 这类产品把复杂能力包装成对话+可视化任务+一键执行。非程序员也能用。

**第二个齿轮：模块层（能力件）**。 Rules、Skills、MCP 把能力做成可组合、可迁移的模块。开发者可以专注于沉淀自己的专业知识。

**第三个齿轮：分发层（市场）**。 Marketplace、自动更新、版本化。让供给能规模化流通，让好的能力件被更多人发现和使用。

第四个齿轮：治理层（安全/合规）。 权限系统、allowlist、审计日志。让整个生态可信赖、可持续。

这四个齿轮一起转，就会出现螺旋上升：更多用户 → 更多需求 → 更多开发者做能力件 → 更繁荣的市场 → 吸引更多用户。

但也有刹车。

最大的刹车是**安全与信任**。当能力件可以被任何人创建和分发，供应链风险就会上升。已经有报道说恶意 MCP server 窃取用户邮件，也有研究者发现官方 Git MCP server 存在漏洞。

如果治理跟不上，飞轮转两圈就会因为信任崩塌而停下来。

所以我的判断是：这个生态能做多大，最终取决于治理能做多好。权限系统、代码签名、审核机制、沙箱隔离——这些"无聊"的基础设施，会成为决定胜负的关键。

## VII — 所以，现在该做什么？

如果你认同我说的这些，下一步是什么？

**如果你是开发者：**

不要再只想着"做一个 App"。问问自己：我能沉淀什么能力件？我的专业知识、我的工作流程、我的最佳实践，能不能打包成一个 Skill 或者一套 Rules？

学习 MCP、Skills、Rules 的规范。这些东西现在看起来是"Claude 生态的东西"，但它们正在被推向开放标准。早点熟悉，就能早点占位。

把你的方法论变成可复用、可审计的文本资产。代码仍然重要，但它越来越像能力件的"内部实现"，而不是交付形态。

**如果你是用户：**

不要只是"使用"工具，学会"组合"工具。把别人的 Skills 放进你的环境，让 AI 帮你理解它在做什么。不满意就改。有了 AI，你有能力改。

你的工作流本身就是资产。你每天重复做的事情，能不能沉淀成一个 Agent 配置？能不能写成一套 Rules？如果能，你就从消费者变成了创作者。

**如果你是产品经理或创业者：**

重新思考"交付物"的定义。在某些场景下，"文件化交付"可能比"App"更适合：门槛更低、迭代更快、用户参与度更高。

关注治理。如果你想在这个生态里做平台，权限系统、审计机制、marketplace 治理能力会是核心壁垒。如果你想做能力件，建立可信赖的品牌和声誉会是关键。

## **VIII — 一个新名字？**

"插件"这个词太像传统 IDE 扩展了。它让人想到的是：主程序是核心，插件是附属。

但我们讨论的不是附属品。

这是一种新的交付形态——用文本、目录、协议来表达能力，让 AI 作为运行时来执行，让用户作为参与者来改造。

我不知道它最终会叫什么。也许是 Capability Bundle（能力包），也许是 Workflow Asset（工作流资产），也许是 Context Package（上下文包）。

或者，干脆就叫它本来的样子：

**一堆文件。**

听起来不够酷，但这恰恰是它的力量所在。文件是透明的、可读的、可改的、可分享的、可版本控制的。

当"产品"变成"一堆文件"，软件的权力结构就被重新分配了。

开发者不再是唯一的创造者。

用户不再是被动的消费者。

每个人都可以参与到这场重新定义"软件"的运动中来。
