# AI 接管开源项目 · 通用提示词模板

> 配套视频：《用 AI 编程工具接管一个完全陌生的开源项目》

> 作者：木羽Cheney（VibeCoding 实战课主讲老师） · 赋范大模型技术社区

> 用法：根据你当前所处的阶段，选择对应的提示词，复制粘贴给 AI 编程工具

---

## 使用说明

这份模板提供了 **6 个场景****的通用提**示词。它们不是视频里针对具体项目的提示词，而是泛化版本——你可以换成任何 GitHub 项目使用。

每个提示词都标注了：

+   **适用场景**：什么时候用

+   **使用前提**：需要满足什么条件

+   **预期效果**：AI 应该做什么

+   **如果没达到预期**：怎么追问

---

## 提示词 A：万能接管启动

**适用场景**：刚 clone 了一个陌生项目，什么都没看，想让 AI 直接帮你跑起来

**使用前提**：AI 编程工具的工作目录已经是项目根目录

```
请分析这个项目的技术栈和目录结构，找到启动方式，安装所有依赖，
把前后端服务全部启动。如果遇到报错，自行排查并修复。
启动成功后告诉我：
1. 前端访问地址
2. 后端 API 地址
3. 你做了哪些关键操作
```

**预期效果**：AI 会依次执行——读 README → 分析 package.json/requirements.txt → 安装依赖 → 启动前端 → 启动后端 → 报告访问地址

**如果没跑起来**，用下面的提示词 B 继续追问。

---

## 提示词 B：环境诊断排障

**适用场景**：提示词 A 没跑通，AI 报了错或者卡住了

**使用前提**：已经尝试过启动但失败了

```
项目启动失败了，请做全面诊断：
1. 检查所有依赖是否安装完整（前端和后端分别检查）
2. 检查是否缺少环境变量或配置文件（是否有 .env.example？）
3. 检查端口是否被占用（如果是，换一个可用端口）
4. 检查 Node/Python/其他运行时版本是否满足项目要求
5. 逐步修复，每修一个问题告诉我你修了什么、为什么这样修
修复完成后重新启动服务。
```

**预期效果**：AI 会逐项排查，找到失败原因并修复。关键是第 5 点——让它解释每一步修了什么，这样你也学到了排障方法。

**进阶用法**：如果 AI 修了一轮还没跑通，追加一句：

```
还是没启动成功。请仔细看报错信息，搜索类似问题的解决方案，
然后尝试不同的修复方法。如果你判断某个依赖版本有兼容问题，
可以尝试降级或升级该依赖。
```

## 提示词 C：项目规则文件撰写

**适用场景**：项目跑起来了，需要创建规则文件让 AI 后续操作更稳定

**使用前提**：前后端服务已成功启动

```
项目已经成功启动了。请帮我创建一个最小化的项目规则文件，遵循以下原则：

1. 只记录启动命令（前端启动、后端启动、同时启动）
2. 只记录你自己无法推断出来的关键信息
3. 不要写项目结构描述（你看代码就能知道）
4. 不要写技术栈说明（你从依赖文件就能判断）
5. 不要写代码规范（那是另外的 rules 文件该做的事）

如果有需要特别注意的&quot;高危操作&quot;（比如不能删某个目录、修改数据库前要备份），也写进去。

规则文件控制在 20 行以内。
```

**预期效果**：AI 会生成一个精简的规则文件，通常只有启动命令 + 1-2 条高危操作提醒

**为什么要刻意限制？**

+   规则文件太长 → AI 每次任务都要读一遍 → 注意力被稀释 → 重要规则被忽略

+   项目结构你写了但改了代码没更新规则 → AI 按过时信息操作 → 越改越乱

+   官方最佳实践：如果 AI 不需要某条规则也能做对，就删掉它

## 提示词 D：模型兼容性评估

**适用场景**：项目跑起来了，准备接入自己的模型，先确认兼容性

**使用前提**：项目前后端已运行

```
我想给这个项目接入自己的大语言模型，在修改任何配置之前，请先帮我确认：

1. 这个项目调用 LLM 的方式是什么？（OpenAI 兼容 API / 私有 API / SDK 直接调用？）
2. 调用时用了哪些参数？（temperature / max_tokens / function calling / 多模态输入？）
3. 是否需要模型具备多模态能力（图片理解、语音识别等）？
4. 配置文件在哪？需要修改哪些字段？（Base URL / API Key / 模型名 / 其他）
5. 修改配置后是否需要重启服务？

不要修改任何文件，只是分析和汇报。我确认后再动手改。
```

**预期效果**：AI 会分析项目的 LLM 调用代码，告诉你需要什么类型的模型，以及具体改哪些配置

**为什么先评估再动手？**

+   有些项目用了 function calling（函数调用），并非所有模型都支持

+   有些项目需要多模态能力，接了纯文本模型会报错

+   先评估能帮你避免"接入 → 报错 → 换模型 → 再接入"的反复折腾

## 提示词 E：模型接入配置

**适用场景**：已经确认了模型兼容性，准备动手接入

**使用前提**：已完成提示词 D 的评估，确认了模型类型和配置位置

```
请帮我接入以下大语言模型：

- Base URL: [填写你选择的模型 API 地址]
- API Key: [填写你的 API Key]
- 模型名: [填写模型标识符，如 deepseek-chat / qwen-plus]

请修改对应的配置文件，保存后重启相关服务。
重启后，用一条简单的问答测试模型是否正常工作：
发送&quot;请用 50 字介绍量子计算&quot;，确认能收到合理的回答。

如果测试失败，请分析错误原因并尝试修复。
```

不知道 Base URL 和模型名填什么？ 参考工具包里的《国产模型 OpenAI 兼容 API 速查表》，有 8 个模型的完整配置参数。

## 提示词 F：最小验证确认

**适用场景**：模型接入完成，做最终确认

**使用前提**：模型已接入，测试问答已通过

```
模型已经接入成功了。请帮我做一次端到端的最小验证，确认这个项目真的可用：

1. 找到这个项目的核心功能入口（不是设置页，是用户最常用的功能）
2. 用最简单的输入触发一次完整的业务流程
3. 检查输出结果：
   - 输出是否是模型实时生成的？（不是预设数据/缓存/Mock）
   - 输出格式是否符合预期？（不是乱码/截断/空响应）
   - 响应时间是否合理？（通常 3-15 秒）

测试完成后给我一个结论：
- 这个项目在当前配置下是否可以正常使用？
- 如果有问题，问题出在哪？你建议怎么修？
```

**为什么最小验证不能跳过？**

> 视频原话："很多人项目跑起来就直接去试功能了，但有一步不能跳——你得确认这个项目在你手里是真的能用。"

项目跑起来 ≠ 项目可用。常见的"假可用"状态：

+   前端页面正常，但发消息后后端报 500（模型没配对）

+   模型返回了响应，但内容是空字符串（API 参数不兼容）

+   看起来在工作，但用的是项目预设的 Demo 数据（没有走真实模型）

最小验证的目的，就是**排除这些假可用状态**。

## 提示词使用流程图

```
项目 clone 到本地
       │
       ▼
  [提示词 A] 万能接管启动
       │
       ├── 成功 ──→ [提示词 C] 创建规则文件
       │                  │
       │                  ▼
       │            [提示词 D] 模型兼容性评估
       │                  │
       │                  ▼
       │            [提示词 E] 模型接入配置
       │                  │
       │                  ▼
       │            [提示词 F] 最小验证确认
       │                  │
       │                  ▼
       │               接管完成!
       │
       └── 失败 ──→ [提示词 B] 环境诊断排障
                          │
                          └── 修复后回到 A
```

## 进阶技巧：组合使用

**当你熟练掌握这 6 个提示**词后，可以尝试把 A+C+D 组合在一起，一次性完成更多步骤：

```
请帮我完成以下三件事：

1. 分析项目结构，安装依赖，启动前后端服务
2. 启动成功后，创建最小化的规则文件（只记启动命令）
3. 分析项目的 LLM 调用方式，告诉我需要配置哪些字段

每完成一步，告诉我结果和下一步该做什么。
```

但建议新手**先逐步执行**，熟悉每一步的作用后再组合。
