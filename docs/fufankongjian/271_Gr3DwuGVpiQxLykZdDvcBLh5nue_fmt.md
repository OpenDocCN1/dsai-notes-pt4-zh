
# 01-全栈交付路线图-6阶段完整流程

## AI 全栈交付路线图：从技术调研到上线的 6 阶段

> 来源：[https://kq4b3vgg5b.feishu.cn/docx/AToDds47YocmtDxQlAycnyjJnBf](https://kq4b3vgg5b.feishu.cn/docx/AToDds47YocmtDxQlAycnyjJnBf)

> 作者：木羽Cheney （VibeCoding 实战课主讲老师）· 赋范大模型技术社区

## 总览：6 阶段 → 1 个可交付的全栈项目

```
阶段 1          阶段 2          阶段 3          阶段 4          阶段 5          阶段 6
技术调研    →   规范文档    →   后端 MVP   →    PRD 输出   →   前端开发    →   联调上线
                                    
选型报告        规范文档        可运行后端       产品需求文档     完整前端         前后端联调
                （给AI的底座）  （核心链路通）   （驱动前端）    （对接后端）     （端到端可用）
```

---

## 阶段 1：技术调研（0.5-1 小时）

### 目标

确定技术栈，不是凭感觉选，而是让 AI 做深度调研后给出有依据的推荐。

### 做什么

+   告诉 AI 你的项目需求（类型、规模、部署环境、团队情况）

+   让 AI 对比 2-3 套可选方案（前端框架、后端框架、数据库、部署方式）

+   输出一份技术选型报告，明确选了什么、为什么选、不选的理由

### 产出物

### 完成标准

+   前端框架确定（React/Vue/Next.js/...）

+   后端框架确定（Express/NestJS/FastAPI/...）

+   数据库确定（SQLite/PostgreSQL/MySQL/...）

+   部署方式确定（本地/Docker/云平台/...）

### 常见错误

+   不做调研直接选自己熟悉的 → AI 可能对这个技术栈的最佳实践不熟

+   让 AI 选完不问"为什么" → 选型依据不透明，后面改方向时不知道影响面

---

## 阶段 2：规范文档（1-2 小时）—— 最关键的阶段

### 目标

写一份给 AI 看的规范文档，让它在整个项目周期里保持一致性——不再"失忆"。

### 做什么

+   基于技术选型结果，生成项目规范文档

+   包含：技术栈锁定、目录结构约定、API 接口定义、数据模型、架构约束、非目标声明

+   把这份文档放到 `CLAUDE.md` 或 `.claude/rules/` 中

### 产出物

### 完成标准

+   文档中的每个字段都填了值（不留空）

+   "非目标"部分明确写了"本阶段不做什么"

+   AI 读完文档后能正确回答：这个项目用什么技术栈？API 接口格式是什么？数据库有哪些表？

### 为什么这是最关键的阶段？

> "规范文档在 AI 协作开发里，它不是给人看的，它是给 AI 看的。它是让 AI 在你整个项目周期里保持一致性的底座。" —— 视频原话

没有规范文档的 AI 协作：

```
会话 1: AI 用 RESTful 风格写了用户接口
会话 2: AI 换成了 GraphQL 风格写了订单接口
会话 3: 你让它联调，它一脸懵——两套接口规范对不上
```

有规范文档的 AI 协作：

```
每个会话: AI 先读规范 → 知道统一用 RESTful → 所有接口风格一致
```

## 阶段 3：后端 MVP（2-4 小时）

### 目标

搭一个能跑通核心链路的后端服务，不是完整后端，是最小可验证版本。

### 做什么

+   按规范文档中的 API 定义，实现核心接口（通常 3-5 个）

+   数据库建表 + 种子数据

+   用 Postman 或 `curl` 验证每个接口：请求 → 正确响应

### 产出物

### 完成标准

+   `npm start` 或 `python main.py` 能正常启动

+   每个 API 用 `curl` 测试通过

+   返回格式与规范文档中的定义完全一致（字段名、数据类型、状态码）

### 常见错误

+   一次性写完所有接口 → 太多了验证不过来，出了 bug 不知道是哪个

+   不对照规范文档验证 → 接口格式和文档不一致，联调时才发现对不上

+   跳过种子数据 → 前端开发时没有数据可展示，全是空页面

---

## 阶段 4：PRD 输出（1-2 小时）

### 目标

基于已验证的后端能力，输出产品需求文档来驱动前端开发。

### 做什么

+   把后端的 API 接口映射到前端页面：每个页面调哪些接口？展示什么数据？

+   定义页面清单 + 页面间跳转逻辑

+   定义每个页面的交互行为（按钮点击→调接口→展示结果）

### 产出物

### 完成标准

+   PRD 中的每个页面都标注了数据来源（对应的 API 端点）

+   页面间的跳转逻辑无死路

+   前端开发时只需看 PRD 就知道该做什么，不需要再问后端

### 为什么 PRD 在后端之后？

因为这是后端驱动前端的工作流。先把后端跑通，确认"技术上做得到"，再规划前端"产品上怎么呈现"。反过来做（先画界面再搭后端），容易出现"界面设计了一个功能，但后端实现不了"的尴尬。

---

## 阶段 5：前端开发（3-5 小时）

### 目标

按 PRD 开发完整前端，对接后端 API。

### 做什么

+   按 PRD 中的页面清单逐页开发

+   每个页面完成后立刻对接后端 API 验证（不要全做完再联调）

+   处理加载状态、错误状态、空数据状态

### 产出物

### 完成标准

+   所有页面可正常访问

+   核心功能流程（如：用户提问→后端调模型→前端展示回答）端到端可用

+   没有硬编码的 Mock 数据

### 常见错误

+   全部页面做完才联调 → 一次性出 20 个 bug，不知道从哪改

+   前端自定义了后端没有的字段 → 联调时前端有数据，后端返回 `undefined`

+   没有处理错误状态 → 用户看到白屏不知道发生了什么

---

## 阶段 6：联调上线（1-2 小时）

### 目标

前后端完整联调，确认端到端可用，准备部署。

### 做什么

+   完整走一遍核心业务流程（从开始到结束）

+   检查所有边界情况（空输入、超长输入、网络错误）

+   准备部署配置（环境变量、构建命令、启动命令）

### 产出物

### 完成标准

+   从浏览器打开 → 完成核心操作 → 得到正确结果，全程无报错

+   `README` 交给另一个人，他能按步骤跑通

+   规范文档中定义的所有核心 API 都已对接并验证

## 时间估算

| 阶段 | 预估时长 | 累计 |

| --- | --- | --- |

| 1. 技术调研 | 0.5-1h | 1h |

| 2. 规范文档 | 1-2h | 3h |

| 3. 后端 MVP | 2-4h | 7h |

| 4. PRD 输出 | 1-2h | 9h |

| 5. 前端开发 | 3-5h | 14h |

| 6. 联调上线 | 1-2h | **16h** |

**总计约 2 个工作日**，对应传统开发 2-4 周的工作量。

---

## 跳阶段的代价

| 跳了什么 | 后果 |

| --- | --- |

| 跳了技术调研 | 选了 AI 不擅长的技术栈，后面每一步都磕磕绊绊 |

| 跳了规范文档 | AI 每次"失忆"，接口风格不统一，联调时全对不上 |

| 跳了后端 MVP | 直接做前端，结果后端能力不支持，返工重写 |

| 跳了 PRD | 前端"想到哪做到哪"，页面之间逻辑断裂 |

| 跳了联调 | 以为能用，上线后用户第一次操作就报错 |

> 每个阶段的产出物，就是下一阶段的输入。跳一个，后面全部摇晃。
