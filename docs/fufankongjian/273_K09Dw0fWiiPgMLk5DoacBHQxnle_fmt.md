## 为什么选错方向代价这么大？

> "用 AI 写了三天代码，回头一看前后端接口全对不上，人类返工重写了一半以上的代码。问题不在 AI，在于你一开始就没想清楚该从前端起手还是从后端起手。" —— 视频原话

前端起手和后端起手是两条完全不同的流水线。选错了，后面每一步 AI 生成的代码都在往错的地方堆——你以为自己在往前推进，其实是在给自己挖坑。

## 5 个判断问题

按顺序回答，走到哪个分支就是你的答案：

### 问题 1：你是否已经清楚知道产品长什么样、用户怎么用？

+ 是 → 继续问题 2

+ 否 → 继续问题 3

### 问题 2：这个产品的核心价值在界面交互还是数据处理？

+ 界面交互为核心（如：设计工具、可视化仪表盘、编辑器）

→ → 前端起手

+ 数据处理为核心（如：知识库问答、数据分析、自动化流程）

→ → 后端起手

### 问题 3：你需要先验证技术可行性吗？

+ 是（如：不确定 AI 能不能做这件事、不确定某个 API 能不能用）

→ → 后端起手 —— 先证明技术上走得通

+ 否（技术方案确定，只是不知道产品形态）

→ 继续问题 4

### 问题 4：你有参考产品或竞品可以照着做吗？

+ 有明确的参考（如：做一个类似 Notion 的工具、做一个类似 ChatGPT 的问答界面）

→ → 前端起手 —— 照着竞品画 UI，再反推后端

+ 没有参考（全新产品形态）

→ 继续问题 5

### 问题 5：你更怕哪种翻车？

+ 更怕做出来的东西没人用（产品方向不确定）

→ → 前端起手 —— 先用 UI 原型验证用户是否买单

+ 更怕技术方案走不通（技术风险大）

→ → 后端起手 —— 先用 MVP 验证核心链路

## 两条流水线对比

### 前端起手流水线

```
UI 原型 → 页面交互定稿 → 反推 API 需求 → 搭后端适配 → 联调
```

适用场景：

+ 已有明确的产品形态（抄竞品/改良竞品）

+ 核心价值在用户体验和交互设计

+ 需要先给老板/投资人看到"长什么样"

+ 交互复杂但后端逻辑简单的产品（如 CMS、管理后台）

优势：

+ 用户/老板能尽早看到可感知的成果

+ 前端确定后，后端接口需求非常明确，AI 写后端时不会跑偏

风险：

+ 如果前端设计了后端做不到的功能 → 返工

+ 容易过度设计界面，忽略技术约束

---

### 后端起手流水线（视频中使用的方式）

```
技术调研 → 规范文档 → 后端 MVP → PRD → 前端开发 → 联调
```

适用场景：

+ 需要先验证技术可行性（AI 能力、第三方 API、数据处理链路）

+ 核心价值在数据处理和业务逻辑

+ 做知识库、问答系统、数据分析、自动化工具等

+ 企业内部工具（功能优先，界面其次）

优势：

+ 先跑通核心链路，确认"技术上做得到"

+ 规范文档锁住接口，前后端不会对不上

+ 前端开发时已有真实 API 可调用，不需要 Mock

风险：

+ 产出物在前期"看不到"（只有 API，没有界面），老板可能不理解进度

+ 如果对用户需求理解有偏差，可能后端做完了才发现方向不对

## 常见误区

| 误区 | 为什么是错的 | 正确做法 |
| --- | --- | --- |
| "AI 编程就是让 AI 从头到尾全部写" | AI 不知道你的业务逻辑，全部交给它会各模块互相矛盾 | 分阶段给 AI 任务，每阶段产出物确认后再进入下一阶段 |
| "先把前后端都做了再联调" | 两头各自跑了几天，联调时发现接口定义完全不一致 | 先写规范文档统一接口定义，或先做一头再做另一头 |
| "前端起手就是先画好看的 UI" | 好看的 UI 不等于好用的产品，先画交互流程再打磨视觉 | 线框图→交互稿→视觉稿，不要跳步 |
| "后端起手不需要考虑前端" | 后端接口设计时不考虑前端怎么调用，联调时会很痛苦 | 后端做完后先写 PRD 定义前端需求，确保接口匹配 |
| "无所谓哪头开始，AI 都能搞定" | 这是 95% 的 Vibe Coding 项目活不过两周的原因 | 30 秒做个决策，能省 3 天的返工时间 |

## 拿不准的时候

> 前端起手 = "产品形态驱动"，后端起手 = "技术可行性驱动"。拿不准的时候，选后端起手更安全——改界面比改架构容易得多。
