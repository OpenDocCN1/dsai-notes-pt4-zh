## 总体概述

### 1.1 什么是 Product Manager Skills？

这是一套**产品管理框架的数字化封装**，包含 46 个独立但相互关联的技能（Skill），每个技能对应产品管理工作中的一个具体环节。

**核心理念**：

> 用户不是买产品，而是"雇佣"产品来完成某项工作（Jobs-To-Be-Done）。

**设计目标**：

+   📚 将经典产品管理方法论（JTBD、OST、精益 UX 等）转化为可执行的 AI 工作流

+   🔗 打通产品发现→定义→交付→验证的完整链条

+   🎯 避免"功能工厂"陷阱，确保团队解决正确的问题

### 1.2 与 JTBD 的关系

JTBD (Job**s-To-B**e-Done) 是这套技能体系的核心思想基础：

```
JTBD 理论 → 理解用户&quot;雇佣&quot;产品完成的工作
    ↓
产品发现 → 搞清楚用户真正的需求是什么
    ↓
产品定义 → 决定做什么来解决这些需求
    ↓
产品交付 → 把解决方案做出来
    ↓
产品验证 → 检查是否真的解决了问题
```

**这 4**6 个技能就是沿着这个链条展开的工具箱。

## 核心技能详解

### 3.1 jobs-to-be-done（用户待办任务）

**核心功能**：系统性地探索用户真正想完成的工作，而非表面需求。

**解决的问题**：

+   用户说的"想要更快"到底是什么意思？

+   为什么有些功能上线后数据没变化？

+   如何避免做错功能？

**输出结构**：

```
## Jobs-to-be-Done 分析

### 1. Customer Jobs（用户想完成的事）
#### Functional Jobs（功能层面）:
- [任务 1]
- [任务 2]

#### Social Jobs（社会层面）:
- [用户希望被如何看待]

#### Emotional Jobs（情感层面）:
- [用户追求/避免的情感状态]

### 2. Pains（痛苦）
#### Challenges（障碍）:
- [障碍 1]

#### Costliness（代价）:
- [时间/金钱/精力成本]

#### Common Mistakes（常见错误）:
- [错误 1]

#### Unresolved Problems（未解决问题）:
- [现有方案未解决的问题]

### 3. Gains（收益）
#### Expectations（期待）:
- [超出期待的点]

#### Savings（节省）:
- [时间/金钱/精力节省]

#### Adoption Factors（采用因素）:
- [促使用户切换的因素]

#### Life Improvement（生活改善）:
- [用户生活如何变好]
```

**使用示例**：

```
场景：老板说&quot;用户想要更快的开票速度&quot;

调用 jobs-to-be-done 后，你发现：
- 表面需求：&quot;更快开票&quot;
- 真实 JTBD：&quot;从完工到收款的整个流程别耽误&quot;
- 真正机会：自动催款 + 收款跟踪，而不是&quot;一键开票&quot;按钮
```

### 3.2 opportunity-solution-tree（机会方案树）

**核心功能**：从模糊的需求到结构化的探索，避免"功能工厂"陷阱。

**解决的问题**：

+   老板/客户直接说"我要这个功能"怎么办？

+   如何确保团队在解决问题，而不是盲目堆功能？

+   如何系统性地探索多种解决方案？

**输出结构**：

```
                    期望结果 (Outcome)
                           │
           ┌───────────────┼───────────────┐
           │               │               │
      机会 1            机会 2          机会 3
    (问题/需求)        (问题/需求)      (问题/需求)
       │                 │               │
    ┌──┴──┐           ┌──┴──┐        ┌──┴──┐
    │     │           │     │        │     │
  方案 1 方案 2      方案 1 方案 2   方案 1 方案 2
    │     │           │     │        │     │
  实验  实验         实验  实验      实验  实验
```

**使用示例**：

```
场景：老板说&quot;我们要做 AI 功能&quot;

调用 opportunity-solution-tree：
1. 期望结果：提升用户留存率 20%
2. 机会探索：
   - 机会 1：用户不知道如何高效使用产品
   - 机会 2：用户遇到问题找不到帮助
   - 机会 3：用户完成关键流程太耗时
3. 方案发散（每个机会 3-5 个方案）
4. 选择 POC：基于影响力/可行性评分
```

### 3.3 prd-development（产品需求文档）

**核心功能**：将发现阶段的洞察转化为工程可执行的 PRD 文档。

**解决的问题**：

+   如何写一份工程师能看懂的 PRD？

+   如何避免需求歧义和范围蔓延？

+   如何确保 PRD 是"活文档"而非一次性交付？

**输出结构**：

```
**# [功能名称] PRD****

## 1. 执行****摘要
- 一句话概述****（问题 + 方案 + 影响****）

## 2. 问****题陈述
- 谁有问题****？
- 问题是什么？****
- 为什么痛苦？
- 证****据（用户原话、数据、调****研）

## 3. 目**标用户与画像
- 主要画像
- 次要画像
- Jobs-to-be-done

## 4. 战略背景
- 业务目标（OKR）
- 市场机会
- 竞争格局
- 为什么现在做？

## 5. 方案概述
- 高层描述
- 用户流程图/线框图
- 核心功能列表

## 6. 成功指标
- 核心指标
- 次要指标
- 目标值（当前 → 目标）

## 7. 用户故事与需求
- 史诗假设
- 用户故事 + 验收标准
- 边界情况、约束条件

## 8. 不在范围内
- 明确不做的（及原因）

## 9. 依赖与风险
```

**使用示例**：

```
场景：完成 JTBD 分析后，需要写 PRD 给开发团队

调用 prd-development：
1. 输入：JTBD 文档、用户调研笔记
2. 技能引导你填充每个章节
3. 输出：完整的 PRD 文档，可直接用于开发
```

+   为什么团队的优先级总达不成共识？

+   如何避免"框架跳跃"（频繁换方法）？

**推荐的框架**：

**使用示例**：

场景：团队在优先级上争论不休

调用 prioritization-advisor：

### 3.5 user-story（用户故事）

**核心功能**：将需求转化为开发可执行的用户故事卡片。

**解决的问题**：

+   如何写清晰的用户故事？

+   验收标准怎么写？

+   如何避免故事过大或过小？

**输出格式**：

```
**### 用户故事 [ID]**

**#### 用**例（**Mike Co**hn** 格式）:
-** ****作为** **[用**户角色]
-** ****我想要**** **[执行的动作**]
- **以便于** [期望的结果/价值]

#### 验收标准（Gherkin 格式）:
- **场景**: [场景描述]
- **给定**: [前提条件]
- **当**: [触发事件]
- **那么**: [期望结果]
```

**使用示例**：

```
场景：PRD 中有一个功能&quot;自动发送付款提醒&quot;

调用 user-story：
输入：功能描述、目标用户
输出：
- 作为 自由职业者
- 我想要 设置自动催款规则
- 以便于 不用手动追客户付款

验收标准：
- 给定 用户设置了催款规则
- 当 发票到期前 3 天
- 那么 系统自动发送催款邮件
```

## 技能协作工作流

### 4.1 标准产品开发生命周期

```
┌────────────────────────────────────────────────────────────────────┐
│                         完整工作流示例                              │
│                    做一个&quot;自动催款&quot;功能                             │
└────────────────────────────────────────────────────────────────────┘

阶段 1: 发现 (Discovery)
════════════════════════════════════════════════════════════════════
1. proto-persona
   → 定义目标用户：自由职业者（设计师/开发者）
   
2. jobs-to-be-done
   → 发现真实需求：不是&quot;更快开票&quot;，而是&quot;别耽误收款&quot;
   
3. customer-journey-map
   → 绘制旅程：发现&quot;催款&quot;环节最痛苦（平均延迟 15 天）
   
4. tam-sam-som-calculator
   → 评估市场：自由职业者发票工具市场约 50 亿
   
5. discovery-interview-prep + discovery-process
   → 访谈 10 个用户，验证假设

产出：用户洞察文档 + 机会评估报告

阶段 2: 定义 (Definition)
════════════════════════════════════════════════════════════════════
6. problem-framing-canvas
   → 定义问题：自由职业者平均晚收款 15 天，影响现金流
   
7. opportunity-solution-tree
   → 探索方案：
     - 机会 1：用户忘记催款 → 方案：自动提醒
     - 机会 2：客户弄丢发票 → 方案：自助查询
     - 机会 3：对账麻烦 → 方案：自动对账
   
8. prioritization-advisor
   → 选择框架：RICE（因为团队有数据）
   → 排序：自动提醒 (RICE=45) &gt; 自助查询 (32) &gt; 自动对账 (28)
   
9. positioning-statement
   → 定位：&quot;让自由职业者收款快 2 倍的专业发票工具&quot;

产出：优先级排序 + 产品定位文档

阶段 3: 交付 (Delivery)
════════════════════════════════════════════════════════════════════
10. prd-development
    → 写 PRD：完整的需求文档，包含所有细节
    
11. user-story-mapping
    → 故事地图：把大功能拆成可迭代的片段
    
12. user-story + user-story-splitting
    → 写用户故事：
      - 故事 1：设置催款规则
      - 故事 2：定时发送催款邮件
      - 故事 3：查看催款历史
    
13. storyboard
    → 画故事板：关键界面的用户流程
    
14. press-release
    → 写新闻稿：提前想好怎么对外说

产出：PRD + 用户故事 + 故事板

阶段 4: 验证 (Validation)
════════════════════════════════════════════════════════════════════
15. business-health-diagnostic
    → 上线后评估：收款周期缩短 40%？续费率提升？
    
16. feature-investment-advisor
    → 决定下一步：继续投入还是转向？
    
17. roadmap-planning
    → 更新路线图：基于验证结果调整

产出：健康度报告 + 更新后的路线图
```

## 完整案例演示

### 案例背景

**公司****：一****款面向自**由职业者的在线发票 SaaS问题：用户流失率高，老板要求"提升用户体验"你的角色：产品经理

---

### 第 1 步：理解用户（jobs-to-be-done）

**调用技能**：jobs-to-be-done

**输入**：

+   产品类型：在线发票工具

+   目标用户：自由职业者（设计师、开发者、顾问）

+   表面问题："用户说开票太麻烦"

**输出**（关键洞察）：

```
**## Jobs-to-b****e-Done 分析

### ****Customer ****Jobs
####** Functional:
- 月底 2 小时内搞定所有客户的发票
- 跟踪谁付了钱、谁还欠着
- 报税时能快速找到历史记录

#### Social:
- 让客户觉得我是正规公司，不是路边接私活的
- 看起来像有财务团队的专业人士

#### Emotional:
- 别再为发票这种破事焦虑
- 专心做项目，别被行政工作打扰

### Pains
#### Challenges:
- 客户总说&quot;发票没收到&quot;，其实是自己弄丢了
- 不同客户要不同格式的发票
- 记不住谁付了钱

#### Costliness:
- 每月花 6-8 小时折腾发票，时值 3000 元
- 因为发票问题晚收款，平均延迟 15 天

### Gains
#### Expectations:
- 开票时自动填充客户信息
- 一键催款，生成礼貌的提醒邮件

#### Life Improvement:
- 月底不再焦虑，能安心陪家人
- 收款更快，现金流更稳，敢接大项目
```

**洞察**：

> 用户说的"开票麻烦"，真实意思是"从完工到收款的整个流程太**折腾"。真正的机会不是**"更快开票"，而是自动催款 + 收款跟踪。

---

### 第 2 步：探索方案（opportunity-solution-tree）

**调用技能**：opportunity-solution-tree

**输入**：

+   期望结果：提升用户留存率 20%

+   来自 JTBD 的洞察

**输出**：

```
                    提升留存率 20%
                           │
           ┌───────────────┼───────────────┐
           │               │               │
    忘记催款          客户弄丢         对账麻烦
```
