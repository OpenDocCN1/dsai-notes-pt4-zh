# 面试官问：Agent的Function Call一直不稳？

> 来源：[https://qqs7y1hozd1.feishu.cn/docx/F2fhdkuuboMl22xduQkcljxjnTR](https://qqs7y1hozd1.feishu.cn/docx/F2fhdkuuboMl22xduQkcljxjnTR)

在 Agent 应用开发领域，一个被广泛提及的共性问题是：“模型频繁出现工具调用错误、参数缺失、字段胡乱补全、意图误判等情况，导致 Function Call 表现极不稳定，难以达到上线标准。”

这一现象在技术面试中也日益成为高频考察点。究其根本，Function Calling 并非仅仅是一个“会用即可”的简单特性，而是一套需要深度设计的完整工程体系。缺乏系统化设计，就会导致期望与现实严重脱节——例如用户请求“查询天气”，模型却执行“预订机票”的荒谬行为。

通过多个真实 Agent 项目的实践积累，我们越来越清晰地认识到：Function Call 的不稳定问题，其根源往往不在于模型本身，而在于系统架构设计的缺陷。本文将系统性地剖析 Function Call 不稳定的深层次原因，并指出关键瓶颈所在。

### 一、Function Call 不稳定：非偶然现象，而是系统性问题的必然结果

许多开发者存在一个认知误区，认为“Function Call 作为 ChatGPT 的内置功能，应该能够自动选择正确的函数并准确填充参数”。然而工程实践中的情况截然不同。

Function Call 不稳定的本质在于：模型需要在充满不确定性的上下文环境中，做出完全确定性的选择决策。 这种不确定性来源于多个维度：工具数量庞大、Schema 命名混乱、上下文存在歧义、模型输入被截断、输入长度过长、采样温度设置不当、提示词约束力不足等。

因此，系统中的任何细微模糊点，都会直接导致模型做出错误决策。可以说，Function Call 的不稳定并非偶发的 bug，而是系统设计不够完善的必然产物。

### 二、影响 Function Call 稳定性的四大核心因素

基于对大量失败案例的复盘分析，我们发现所有错误都可归结为以下四类根本原因：

① Schema 设计不规范：函数与参数命名歧义是首要元凶

这是最易被忽视却影响最为严重的问题。以旅行助手项目中的真实案例为例：

当工具集中同时存在：

+   search_flights

+   searchFlight

+   flightSearch

+   find_flight_info

模型会陷入困惑：这些是否代表同一功能？是否存在工具重复？究竟应该调用哪一个？

同样，参数命名如果出现：

+   from_city

+   origin

+   start_place

模型同样无法确定哪个才是正确字段。

Schema 不规范是 Function Call 不稳定性的首要根源。

② Prompt 上下文不严谨：系统消息歧义、截断与信息缺失

当上下文描述存在模糊性时，模型会倾向于“自主脑补”。例如：

用户询问：“明天北京天气怎么样？”

但系统同时提供了6个工具选项：

+   查机票

+   订机票

+   查酒店

+   订酒店

+   查天气

+   查用户偏好

面对“明天、北京”等关键词，模型可能错误关联到机票查询，甚至调用 search_flights。

上下文过度臃肿 → 工具数量增加 → 决策随机性增强。

一个有效的优化策略是实施动态函数路由——先进行意图识别，再动态缩小“可用工具列表”范围。这应当成为系统设计的必备模块，而非可选功能。

③ 采样策略配置不当：温度与 top-p 参数随机性过高

许多开发者在构建 Agent 时，直接沿用聊天模式的采样配置：

python

temperature = 0.7

top_p = 0.95

这在 Function Call 场景下极具风险。因为 Function Call 的本质不是生成创意内容，而是执行精确决策。

温度值越高，随机性越大，模型越容易产生参数幻觉或调用错误函数。

正确的配置策略应为：

python

temperature = 0 ~ 0.2

top_p = 0.8 左右

# 建议采用确定性模式

模型行为越严谨，Function Call 稳定性越高。

④ 缺乏运行时防御机制：重试与反思能力的缺失

模型本质上是概率模型，不可能保证100%准确率。工程能力的价值正体现在：模型可以犯错，但系统不能因此失效。

许多团队直接将模型的 Function Call 输出用于执行，导致各类问题：

+   参数缺失

+   参数类型错误

+   调用不存在函数

+   将日期填写为“明天后天之间”

+   将城市字段填为 None

如果系统缺乏以下防御层：

+   JSONSchema 校验

+   参数有效性校验

+   自动重试机制

+   将错误反馈给模型进行反思

那么 Function Call 的稳定性将永远无法保障。这也是为什么我们将“结果校验层”定位为 Agent 的核心标准组件。

### 三、真实场景分析：模型工具选择错误的典型案例

以旅行助手 Agent 为例：

场景： 用户询问：“查一下明天北京天气”

如果未采用动态路由策略，模型在看到全部工具选项后可能产生错误联想：

+   “北京，明天” → 误解为机票出发日期

+   “查一下” → 理解为航班查询

+   “北京天气” → 但 weather 工具在列表中位置靠后，可能被忽略

最终导致错误调用：

json

{"name": "search_flights","arguments": {"origin": "北京","destination": "明天"}}

这类错误案例在实际项目中极为常见。

而当我们引入意图分类 + 工具子集机制后，仅提供：

python

[get_weather]

模型就再也不会选错工具。

### 四、面试场景的专业回答框架

当面试官询问：“为什么 Function Calling 不稳定？”时，最专业的回答应包含以下逻辑层次：

1.  根本原因：模型在不确定的上下文中进行确定性决策的固有挑战

+   Schema 设计歧义

+   Prompt 描述模糊

+   工具集过度复杂

+   输入长度截断

+   采样随机性过高

1.  系统化解决方案：从四个维度入手

+   Schema 设计：确保唯一性、解耦性与无歧义性

+   Prompt 工程：严格结构化、消除模糊描述

+   采样策略：降低随机性参数

+   运行时防御：参数校验 + JSONSchema 验证 + 重试/反思机制

1.  实证支撑：结合真实案例说明优化效果

+   详细描述一个具体的 FunctionCall 错误案例

+   准确分析其根本成因

+   说明采取的优化策略

+   展示改进后的实际效果

只有具备这样完整的逻辑链条，才能在 Agent 相关岗位的面试中展现真正的技术深度。

### 五、总结

Function Calling 的不稳定问题，本质上反映的是系统设计的成熟度不足，而非模型能力的局限。所有问题均可追溯至四个核心维度：

+   Schema 不规范 → 模型选择困惑

+   Prompt 不严谨 → 模型意图理解偏差

+   采样随机性高 → 模型输出不可控

+   缺乏运行时防御 → 单点错误导致系统失效

只有当这四个方面都得到系统性完善后，Function Call 才能真正具备工程化可靠性，达到产品上线标准。这要求开发者从简单的功能实现思维，转向复杂的系统工程思维，构建真正健壮、可维护的 Agent 应用架构。
