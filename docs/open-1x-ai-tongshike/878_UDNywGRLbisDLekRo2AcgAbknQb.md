## 产品概述

### Manus 是什么？

Manus 在拉丁语中代表【手】，即使用所有工具的起始点，当你将脑和手分离开的时候，你会发现脑子提出需求，手来执行并回收结果，当一款产品以 Manus 命名时，其含义不言而喻，一款自主的通用型 Agent 产品。

`Chatbot` 类产品可以理解为是脑内对话，协助思考，而 Manuse 更像是人类同事，接受需求，分析工作，交付最终结果。

### Manus 能做什么？

诚如上文，你完全可以把 Manus 理解为一个实习生，他的工作流程大致如下：

+ **需求分析**：接受用户的需求，尝试理解，并将其拆分为 `todolist`

+ **执行任务**：根据需要选择合适的工具实现目标，包含不限于

+ 调用浏览器搜索网页

+ 进行代码编辑/数据分析工作

+ 生成文档/`ppt` 格式

+ **异步处理**：整个过程都运行在云端电脑，相当于实习生在自己电脑做事，对你没有任何影响

+ **进度可视化**：你可以实时看到 Manus 的执行情况，随时介入并调整方向

ps: 这一点胜过大多数实习生，带过新人就知道黑箱是最可怕的 ：（

+ **偏好记忆**：Manus 会尝试记住用户的一些偏好，例如偏向 AI 领域，展示喜欢用表格等，下次任务会优先采用表格

莫名有种养成系的感觉

## 技术介绍

如上文业务流程所述，Manus 的技术逻辑大致如下：

1. 根据需求制定计划

2. 执行并回收结果

3. 整合结果产出内容

### 计划阶段

计划阶段需要大模型理解用户需求，并将其拆分为可执行的小目标，列出 `checklist`，方便后续推进，这一步理论上任何的大模型都可以做到

有人推测 Manus 使用的是 `Steiner` 模型，由创始人自己基于 `qwen2.5-32b` 模型进行开发擅长"长期思考"（long horizon thinking）和"逐步执行"（step-by-step execution）

根据创始人自述，`Steiner` 是参考 `o1` 进行开发的，旨在实现推理能力的增长并拓展推理深度，但这款模型是 24 年 10 月左右推出的，从时间来看已经和现在的推理模型存在明显代差了，有理由相信在 `DS` 开源后，Manus 自己的模型还会更进一步

更重要的是，可以从这个现象观测到：Manus 团队在很早之前就开始研究拓展模型的推理能力，进而实现长期规划和逐步执行的效果

### 执行阶段

目标制定好之后就需要进入执行阶段，在这个阶段 AI 会根据需求调用不同的工具以收集相关信息

先说结论：Manus 并没有使用最常见的 `MCP` 方案，而是参考 `CodeAct` 概念自研了执行阶段方案

#### MCP 和 CodeAct

`MCP`，一个适用于大模型的接口协议，可以理解为各个工具提供对应的接口，大模型调用接口并获取信息，以查询天气为例，示范如下

```
//调用输入
POST /weather/get 
{&quot;api_key&quot;: &quot;xxx&quot;,      // 认证密钥（确保合法调用）
&quot;location&quot;: &quot;北京&quot;,    // 查询地点（城市名或经纬度）
&quot;date&quot;: &quot;2024-01-01&quot;,  // 查询日期（可选，默认当天）
&quot;unit&quot;: &quot;celsius&quot;      // 温度单位（celsius 或 fahrenheit）
}

//工具返回输出
{
  &quot;status&quot;: &quot;success&quot;,   // 或 &quot;error&quot;
  &quot;data&quot;: {
    &quot;location&quot;: &quot;北京&quot;,
    &quot;date&quot;: &quot;2024-01-01&quot;,
    &quot;temperature&quot;: 25.5, // 温度
    &quot;condition&quot;: &quot;晴&quot;,   // 天气状况
    &quot;humidity&quot;: 60,      // 湿度（百分比）
    &quot;wind_speed&quot;: 10     // 风速（km/h）
  },
  &quot;error&quot;: {             // 失败时返回错误信息
    &quot;code&quot;: &quot;404&quot;,
    &quot;message&quot;: &quot;地点不存在&quot;
  }
}
```

在实际场景中，大模型会根据目标自主选择需要什么工具，利用 `MCP` server 调用对应工具并接受结果，常见的工具包含：网页搜索，浏览器调用，代码编写，文档编写，命令行工具等等

类似的 Agent 产品基本都是使用 `MCP` 技术实现工具调用，但根据创始人推特阐述，Manus 的立项比 `MCP` 出现（2024.11.25）还要早，所以他们参考的是 `CodeAct`

`CodeAct`，简单解释就是让 LLM 生成 Python 代码作为动作，并通过 Python 解释器执行这些代码。它的运行机制包括：

1. **多轮交互**：代理接收来自用户或环境的观察（例如代码执行结果），生成 Python 代码作为动作，环境执行代码后返回新的观察，代理根据反馈动态调整。

2. **统一动作空间**：所有动作都通过 Python 代码表达，避免了传统方法中 `JSON` 或文本格式的限制。

`MCP` 和 `CodeAct` 的简单对比如下：

| 方面 | `MCP` (Model Context Protocol) | `CodeAct` |
| --- | --- | --- |
| 目的 | 标准化 AI 模型与外部工具和数据源的连接 | 使 AI 模型通过生成和执行代码完成任务 |
| 功能 | 提供统一接口，连接外部资源（如数据库、邮件、日历等） | 聚焦于代码生成与执行（如计算、逻辑操作） |
| 使用场景 | 需要从外部资源获取数据或触发动作的场景 | 需要计算或动态代码执行的任务 |
| 架构 | 客户端-服务器架构，AI 模型通过 `MCP` 服务器访问资源 | 可能直接集成到 AI 模型运行时 |
| 开发者体验 | 通过通用协议简化集成开发 | 需设置代码执行环境，确保安全性和上下文 |

#### Manus 的思考

逸超的推特中说明了 `CodeAct` 给他的三个启示，原文如下：

+ Coding is not the ultimate goal, but rather a universal approach for solving general problems.

+ Since LLMs excel at coding, it makes sense to have agents perform tasks that most closely align with their training distribution.

+ This approach significantly reduces context length and enables the composition of complex operations.

1. **编程是手段不是目的**

产品的最终输出必然不是代码本身，在这个过程中可以运用编程来实现各类需求，达成最终目的

这一点其实 `MCP` 和 `CodeAct` 很像，`MCP` 的思路是调用工具，而 `CodeAct` 是直接编写代码实现需求

2. **让 LLM 做擅长的事情**

大语言模型在训练过程中就接触了大量的代码数据，这意味着他们天生擅长编程；那最好的使用方式就是让他们做擅长的事情，即编写代码解决问题

3. **编程能减少上下文并提升上限**

这一点其实很好理解，`MCP` 需要比较冗长的上下文解释工具的用途及调用细节，而直接编码可以使用简洁的代码语言实现需求；此外，对于复杂需求，依赖外部工具必然存在限制，而直接编码可以根据需求定制化处理，上限更高

### 整合阶段

严格来说，这其实并不是一个独立的阶段，也可以把它理解为执行阶段的一个任务

只是这个任务目标明确，并且执行手段基本固定，包含：整合信息-以用户需求格式（`ppt`，`md` 文档等）展示

该阶段无特殊技术，不做过多说明

### 其他技术点

1. 异步处理：所有操作都在云端执行，不影响用户本地机器，同时还能保证服务稳定性

2. 记忆功能：记住用户的偏好，在执行具体任务时会有一定偏差（这点在 monica 新出的国内版也有尝试）

## 关于 Manus 个人思考

1. Manus 是不是纯追热点的营销产品？

不是

这一点从技术实现上可以看出来，Manus 从很早就开始深入 【推理模型】期望解决长期计划问题；并且执行方案也没有选择大家最常用的 `MCP`，而是基于 `CodeAct` 进行自研。

这些可以推断出 Manus 团队有着自己清晰的开发计划，并且愿意为之投入相应的开发资源。

2. **套壳产品有没有竞争力**

肯定有

所谓的套壳就是技术落地成产品的一系列工程化工作，这部分内容你可以说创新性不高，甚至是脏活累活，但一点一滴的工程化工作累计起来就是产品优势，这一点可以借用 曲凯的原话：

> 很多投资人都会问你的壁垒是什么，其实每次我都想回答同一句话：

> 我的壁垒就是我的人日。

> 一人日就是一个人一天的工作量，我多一些人日，就能多花一些心思在这些产品化的细节里，攒一些外人不知道的 secret sauce。我每天做的并不是革命性的大技术，而是非常工程化的小技术。比如大家都是做同一个功能，那我就会想办法比别人做得好一点点。

> 但日积月累，这些微小的细节最后就会形成我们的壁垒。

> 想 copy 我？没问题，那你就先花个三五年去追赶我日拱一卒做出来的这些东西吧。

3. 为什么其他人可以 3 个小时就做出 OpenManus？

首先，我十分钦佩开源行为，使得这个世界变得更加美好。虽然我还没有体验到 Manus，但就从目前观测到的案例和我自己体验 OpenManus 的感受，两个产品完全不在一个赛道上

OpenManus 只实现了基础业务流程，依旧存在 交互差，门槛高，效果不稳定 等诸多问题，详细可以参见文档：手把手教你体验 OpenManus | Blog

这也侧面证明了第二点【套壳产品也有竞争力，工程化也是护城河】

4. 为什么 Manus 不放开体验？这不就是饥饿营销？

因为贵

从目前体验 OpenManus 的数据来看，如果使用 `qwen-max` 模型，一个问题差不多要 2 人民币

按照收集到的情报，Manus 应该用的是 Claude，换算下来一个问题需要 20 人民币以上，在收费策略明确之前，只能用邀请码的形式进行内部测试

5. 其他思考

   1. 不用担心基座大模型的性能无法提升，无论是 `DS` 还是 Manus 都是从已存在的大模型中挖掘潜力，模型不知道自己会什么，需要人来探索

   2. 模型可以是产品，但绝不是唯一产品。大的厂商可以卷基座模型，其他玩家也可以卷应用；不要害怕模型能力突飞猛进导致业务被吃掉，就像 GPT 存在也不影响其他 chatbot 发展

   3. 不做被淹没的石碑，做水涨而高的船
