## 构思

在深入研究代码之前，让我们首先关注一下我们正在构建的系统级思考、设计目标和模块化。

我们的主要重点是使用 LangGraph 和 MCP 为深度研究助理构建一个复杂而模块化的架构。

![](img/fee65b2c740e205651bf7a7075302dbe.png)

助手必须设计成一个可扩展的代理系统，旨在跨工具、资源和提示进行推理、计划和行动，同时保持有状态的对话。

该系统必须将 LangGraph 的代理编排与 MCP 的结构化工具、提示和资源管理相结合。

该助手可以利用基于图的推理，在多个服务器之间切换，并接受来自用户的动态指令，用户通过查询和结构化元命令实际上保留了对流程的控制。

深度研究助手作为有状态的 LangGraph 代理运行，由双服务器 MCP 客户端驱动。该系统连接到：

> “状态化”意味着助手能够记住之前的交互，并据此调整自身行为——这对于多轮推理或复杂的工作流程至关重要。这里的双服务器是指 MCP 客户端配置为同时与两个不同的 MCP 兼容服务器进行通信，如下所述：

+   自定义研究服务器，公开向量存储工具、提示和基于 `FAISS` 的语义搜索。

+   Firecrawl MCP 服务器，能够实时搜索/抓取网页内容并从互联网提取数据。

![](img/7495d2c55581c7aafb3f7e671b31d053.png)

其核心是 `StateGraph`，它定义了消息如何流动、工具如何以及何时使用，以及对话状态如何随时间演变。

### 使用元命令进行用户引导的编排

该系统的定义方面之一必须是用户控制。

用户不应该将上下文管理隐藏在幕后，而应该能够使用直观的命令明确地引导助手，例如：

+   `@prompt:<name>`加载 MCP 提示。

+   `@resource:<uri>`加载 MCP 资源。

+   `@use_resource:<uri> <query>`使用 MCP 资源。

![](img/bae36c2bf268d7c586a4165a8f27427d.png)

> 请注意，上面定义的提示和资源的访问控制与 MCP 原则一致，并且与 Claude Desktop 中的操作方式类似。

### RAG 作为工具

我们没有构建固定的、一体化的 RAG 管道，而是采用了更灵活的方法。

我们将 RAG 视为一组可以在需要时使用的工具，例如保存数据、检索上下文或回答问题。

![](img/06cc9178857d55554a8f2050d375f596.png)

这使得系统更加模块化。RAG 并非每次都会默认运行。它只是代理在必要时可以使用的工具之一。

### 模块化工具和可扩展性

每个 MCP 服务器将充当功能提供者，独立地公开工具、提示和资源。这使得整个生态系统具有可替换性和可扩展性。

要添加新工具，只需将其添加到服务器，即可在代理工具集中随时使用。系统支持跨域水平扩展。

### LangGraph 作为协调器

LangGraph 将在赋予该系统结构化记忆和决策控制方面发挥至关重要的作用。

![](img/52d00841bc71c2abfbbe997adb20dfeb.png)

与无状态的 LLM 链不同，LangGraph 允许助手维护思路链，根据是否需要工具调用进行条件分支，并将工具输出重新整合到未来的决策中。

![](img/be8621ad7b9212661a125a1a011e226a.png)

这对于需要研究和探索的应用至关重要，因为早期对话、资源或工具输出的背景必须为当前的决策提供参考。它也为多步骤研究流程开辟了可能性。
