# Spec Kit 使用 AI 进行规范驱动的开发：从新的开源工具包开始

> 来源：[https://xatc0v8uz5m.feishu.cn/docx/XjUEdFmKfoNxeexBmoRcOyRPnDg](https://xatc0v8uz5m.feishu.cn/docx/XjUEdFmKfoNxeexBmoRcOyRPnDg)

随着编码代理功能越来越强大，一种模式也逐渐显现：你描述目标，然后返回一段代码，通常……代码看起来正确，但实际效果并不理想。这种“氛围编码”方法对于快速原型设计非常有效，但在构建严肃、关键任务应用程序或使用现有代码库时，可靠性较差。

有时代码无法编译。有时它解决了部分问题，但却没有达到实际目的。堆栈或架构可能不是您想要的。

问题不在于编码代理的编码能力，而在于我们的方法。我们把编码代理当成搜索引擎，而实际上我们应该把它们当成循规蹈矩的结对程序员。它们擅长模式识别，但仍然需要明确的指令。

这就是为什么我们要重新思考规范——不再将其视为静态文档，而是将其视为随着项目发展而不断演变的、活生生的、可执行的成果。规范将成为共享的真理之源。当某些内容不合理时，你可以重新审视规范；当项目变得复杂时，你可以对其进行改进；当任务过于庞大时，你可以将其分解。

Spec Kit 是我们用于规范驱动开发的全新开源工具包，它提供了一个结构化流程，通过包括 GitHub Copilot、Claude Code 和 Gemini CLI 在内的工具将规范驱动开发引入您的编码代理工作流程。

### 什么是规范驱动开发？

在规范驱动的开发中，你无需先编码，然后再编写文档，而是从一份（你猜对了）规范开始。这份规范是一份关于代码行为的契约，它将成为你的工具和 AI 代理生成、测试和验证代码的依据。这样做的结果是，更少的猜测、更少的意外，以及更高质量的代码。

## Spec Kit 的规范驱动流程是什么？

[Spec Kit](https://github.com/github/spec-kit)使您的规范成为工程流程的核心。规范并非编写后就搁置一旁，而是驱动实施、检查清单和任务分解。您的主要职责是掌控全局；编码人员负责大部分的编写工作。

它分为四个阶段，每个阶段都有明确的检查点。但关键在于：每个阶段都有特定的任务，并且只有在当前任务完全验证后才能进入下一个阶段。

该过程的具体细节如下：

1.  指定：您只需提供构建内容及其原因的高级描述，编码代理就会生成详细的规范。这并非技术栈或应用设计，而是关乎用户旅程、体验以及成功的样貌。谁会使用它？它能为他们解决什么问题？他们将如何与之互动？哪些结果至关重要？您可以将其视为您想要创建的用户体验的映射，并让编码代理充实细节。至关重要的是，这会成为一个鲜活的产物，随着您对用户及其需求的了解不断加深，它会不断发展。

1.  计划：现在开始技术层面。在此阶段，您需要向编码代理提供所需的技术栈、架构和约束条件，然后编码代理会生成一份全面的技术计划。如果您的公司已将某些技术标准化，您可以在此处说明。如果您要与遗留系统集成、有合规性要求或需要达到性能目标……所有这些都需要在此处说明。您还可以要求提供多种计划变体，以便比较和对比不同的方法。如果您将内部文档提供给编码代理，它可以将您的架构模式和标准直接集成到计划中。毕竟，编码代理在开始游戏之前需要了解游戏规则。

1.  任务：编码代理会将规范和计划分解成实际工作。它会生成可审查的小块，每个块负责解决难题的特定部分。每个任务都应该是可以单独实现和测试的；这一点至关重要，因为它为编码代理提供了一种验证其工作并保持进度的方法，几乎就像 AI 代理的测试驱动开发流程一样。您获得的不再是“构建身份验证”，而是诸如“创建一个用于验证电子邮件格式的用户注册端点”之类的具体任务。

1.  实施：你的编码代理会逐一处理任务（或在适用的情况下并行处理）。但不同之处在于：你（开发人员）无需审查上千行的代码转储，而是审查针对特定问题的重点更改。编码代理知道它应该构建什么，因为规范告诉了它。它知道如何构建，因为计划告诉了它。它确切地知道要做什么，因为任务告诉了它。

至关重要的是，你的角色不仅仅是掌舵，更要验证。在每个阶段，你都要反思和完善。规范是否涵盖了你真正想要构建的内容？计划是否考虑到了现实世界的限制？是否存在人工智能遗漏的遗漏或边缘情况？整个流程内置了明确的检查点，让你能够评估已生成的内容，发现差距，并在继续推进之前进行修正。人工智能生成工件；你负责确保它们正确无误。

## 如何在代理工作流程中使用 Spec Kit

Spec Kit 可与 GitHub Copilot、Claude Code 和 Gemini CLI 等编码代理配合使用。其关键在于使用一系列简单的命令来控制编码代理，然后由它为您完成生成工件的繁琐工作。

设置很简单。首先，安装specify命令行工具。此工具会初始化您的项目并设置必要的结构。

```
uvx --from git+https://github.com/github/spec-kit.git specify init &lt;PROJECT_NAME&gt;
```

项目初始化完成后，使用/specify命令提供高级提示，编码代理会生成完整的规范。专注于项目的“是什么”和“为什么”，而不是技术细节。

接下来，使用该/plan命令引导编码代理创建技术实施计划。在这里，您提供高级技术指导，编码代理将生成符合您的架构和约束条件的详细计划。

最后，使用该/tasks命令让编码代理将规范和计划分解成可操作的任务列表。然后，您的编码代理将使用此列表来实现项目需求。

这种结构化的工作流程将模糊的提示转变为编码代理可以可靠执行的明确意图。

但是为什么模糊提示失败而这种方法却成功了呢？

## 为什么这个方法有效

这种方法之所以成功，是因为“仅仅提示人工智能”是行不通的，因为语言模型的工作原理有一个基本道理：它们擅长完成模式，但不擅长读心术。像“在我的应用中添加照片分享”这样模糊的提示，会迫使模型猜测可能数千个未说明的需求。人工智能会做出合理的假设，但有些假设可能是错误的（而且你通常直到深入实现才会发现哪些假设不太正确）。

相比之下，预先提供清晰的规范、技术计划和重点任务，可以让编码代理更加清晰，从而提高其整体效率。它无需猜测你的需求，而是知道要构建什么、如何构建以及按照什么顺序构建。

这就是为什么该方法适用于不同的技术栈。无论您使用 Python、JavaScript 还是 Go 进行构建，根本的挑战都是相同的：将您的意图转化为可运行的代码。规范清晰地捕捉意图，计划将其转化为技术决策，任务将其分解为可实现的部分，而您的 AI 编码代理则负责实际的编码工作。

对于大型组织来说，这解决了另一个关键问题：你该如何看待所有关于安全策略、合规性规则、设计系统约束和集成需求的要求？通常，这些东西要么存在于某些人的脑海中，要么埋藏在无人阅读的维基百科中，要么散落在 Slack 对话中，日后难以找到。

有了 Spec Kit，所有这些内容都会被纳入规范和计划中，供 AI 实际使用。您的安全需求并非事后才想到的，而是从一开始就融入到规范中。您的设计系统也不是事后才添加的，而是指导实施的技术计划的一部分。

这种方法的迭代特性赋予了它强大的力量。传统开发会将你困在早期决策中，而规范驱动则让改变方向变得简单：只需更新规范，重新生成计划，剩下的交给编码人员处理即可。

## 这种方法在 3 个地方非常有效

规范驱动开发在以下三种情况下特别有用：

1.  绿地（从零到一）：当你开始一个新项目时，很容易直接开始编写代码。但是，少量的前期工作，例如创建规范和计划，可以确保人工智能能够构建出你真正想要的东西，而不仅仅是基于常见模式的通用解决方案。

1.  现有系统中的功能开发（N 到 N+1）：这是规范驱动开发最强大的地方。向复杂的现有代码库添加功能并非易事。通过为新功能创建规范，您可以明确它应该如何与现有系统交互。该计划随后会编码架构约束，确保新代码感觉是项目原生的，而不是附加的。这使得持续开发更快、更安全。为了实现这一点，可能需要高级的上下文工程实践——我们将另行介绍。

1.  遗留系统现代化：当您需要重建遗留系统时，最初的意图往往会随着时间的流逝而消失。借助 Spec Kit 提供的规范驱动开发流程，您可以捕获现代规范中的基本业务逻辑，在计划中设计全新的架构，然后让 AI 从头开始重建系统，而无需承担继承下来的技术债务。

其核心优势在于将稳定的“内容”与灵活的“方法”分离，从而实现迭代开发，无需昂贵的重写。这让您能够构建多个版本并快速进行实验。

## 我们的目标

我们正在从“代码是真理的来源”转变为“意图是真理的来源”。有了人工智能，规范就成为真理的来源，并决定了构建什么。

这并不是因为文档变得更重要了。而是因为人工智能让规范变得可执行。当你的规范自动转化为可运行的代码时，它决定了最终要构建的内容。

Spec Kit 是我们为实现这一转变而进行的实验。我们将其开源，是因为这种方法比任何单一工具或任何一家公司都更具影响力。真正的创新在于流程。我们很快会介绍更多内容，特别是如何将规范驱动的开发实践与情境工程相结合，从而在您的 AI 工具包中构建更高级的功能。
