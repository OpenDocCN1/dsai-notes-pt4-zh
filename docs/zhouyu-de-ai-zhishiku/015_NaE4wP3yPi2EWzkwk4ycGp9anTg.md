通用化外部记忆系统（Memory Bank）设计报告
I. 通用化设计目标与核心原理
通用版方案的目标是夺回 AI 记忆的控制权，并利用大模型的语义理解能力，通过结构化的 Markdown 文件实现项目关键信息的持久化存储。
1. 核心原理：基于提示词的角色扮演与结构化存储
在通用环境中，我们无法依赖像 Claude Code 或 Cursor 中那样内置的 Subagent 机制。因此，“Progress Recorder”的角色必须通过强大的系统提示词（System Prompt）或自定义指令来赋予给主 LLM 或一个独立的调用 LLM。
• 替代机制：无论使用哪个 LLM（Trae, GPT-5 等），系统都将要求其扮演“Progress Recorder”的角色，唯一职责是根据对话内容分析并更新外部的 Markdown 记忆文件。
• 存储格式：所有的项目记忆都必须保存在 Markdown (`.md`) 文件中，这是实现可移植性和可维护性的基石。
2. 系统的两大核心文件
该通用系统仍然由两个核心 Markdown 文件组成，用于实现记忆的活跃和永久管理：
1. `progress.md`：项目活跃记忆文件。用于存储当前项目所有的核心约束、决策、待办、完成事项和近期备注。
2. `progress.archive.md`：永久归档文件。当活跃记忆文件内容过多时，历史记录将只增不删地转移到此文件，以保持 `progress.md` 的简洁可读性。
II. 通用 Progress Recorder 的核心逻辑与结构化存储
通用方案的核心在于语义识别和分级保护机制，这部分逻辑需完全嵌入到 LLM 的系统提示词中。
1. 记忆内容的结构化分区（`progress.md`）
`progress.md` 文件应包含以下六个核心分区，确保信息分类清晰，并支持主模型随时通过读取文件快速回到项目上下文：
区块名称 | 作用 | 写入要求/保护等级
---|---|---
`Pinned` | 关键约束，如“必须/不能/要求”。 | 高置信写入；不可被自动修订或删除。
`Decisions` | 历史决策，如“决定使用/最终选择”。 | 高置信写入；按时间顺序追加，历史记录不可修改。
`TODO` | 权威待办清单，如“需要/应该/计划”。 | 任务应具有唯一编号和状态流转（`OPEN`→`DOING`→`DONE`）。
`Done` | 已完成事项，如“完成了/实现了”。 | 记录最近完成的，超量时需归档。
`Risks & Assumptions` | 潜在风险和关键假设。 | 风险（`Risk`）需记录缓解措施（`Mitigation`）；假设（`Assumption`）需记录置信度。
`Notes` | 临时笔记或需要确认的低置信信息。 | 低置信内容，如包含“可能、建议、或许”的弱化词，需标注 `Needs-Confirmation`。
2. 语义识别与置信度判断的通用矩阵
Progress Recorder 必须通过语义理解来判断信息的类型和重要性，并将其写入正确的分区。这个逻辑是独立于工具的，只需要在 LLM 指令中明确定义：
语义类型 | 触发词示例 | 目标区块 | 置信要求
---|---|---|---
约束语义 | 必须/不能/要求/强制 | `Pinned` | 高置信
决策语义 | 决定使用/最终选择/将采用 | `Decisions` | 高置信
完成语义 | 完成了/实现了/修复了 | `Done` | 中置信
任务语义 | 需要/应该/计划/待 | `TODO` | 中置信
风险/假设语义 | 风险/假设/前提/基于 | `Risks & Assumptions` | 低置信
• 冲突处理：当新信息与既有约束矛盾时，通用 Recorder 不应覆盖历史记录，而应在 `Notes` 区块中标注冲突，等待人工裁决。
III. 通用化操作指令与流程
在通用 LLM 环境中，自动触发机制可能缺失。因此，核心操作将依赖于标准化的指令，这些指令可以作为用户输入或外部脚本的调用：
1. 记忆回溯（替代 `/recap`）
• 指令：用户输入一个明确的指令，例如：请回顾项目状态 或模拟 `/recap` 指令。
• 执行：主 LLM 必须主动读取 `progress.md` 文件，并根据其中的 `Pinned`、`Decisions`、`TODO` 等信息，快速重构当前的项目上下文和潜在风险。
2. 实时记录（替代自动唤醒）
• 指令：用户输入明确的记录指令，例如：`/record [记录内容]`，或者在对话中明确要求 LLM “请将此内容写入记录文件”。
• 执行：Progress Recorder 角色（由 LLM 扮演）启动语义分析，并输出更新后的 `progress.md` 文件内容或提供要写入的修改内容。
3. 自动归档（替代 `/archive`）
• 指令：用户输入归档指令，例如：`/archive`。
• 执行：LLM 扮演的 Recorder 角色将 `progress.md` 中已完成（`Done`）的内容和备注（`Notes`）转移到 `progress.archive.md` 文件中永久保存。
IV. 通用 LLM 环境下的实施（系统提示词核心）
驱动通用 Progress Recorder 稳定运行的关键，在于其八层系统提示词架构，尽管具体的提示词内容是定制的，但其设计原则必须保留：
1. 角色定义：严格界定 LLM 的角色是记录员，不负责决策或执行代码，只负责维护两个 MD 文件。
2. 任务原子化：明确任务只有记录和归档，避免指令冲突。
3. 技能定义：强调语义抽取和高置信判定两项关键技能，以确保只有准确的信息才被结构化存储。
4. 总体规则：必须包含核心规则，例如：约束（`Pinned`）和决策（`Decisions`）不可自动修订或删除；归档文件只增不删。
5. 功能实现：详细定义触发词矩阵和降级处理逻辑，使任务可控可验证。
6. 模板定义：强制要求 LLM 按照 `progress.md` 的指定 Markdown 格式稳定输出和更新内容。
7. 输出规范：确保写入记录的质量符合预期，防止错误累积。
通过遵循这套可移植、可维护的设计原则，无论采用哪种 LLM 作为编程助手，都可以通过一致的 MD 文件结构和强大的系统指令，解决 AI 编程中的“失忆”问题。

# Claude 开发指南

## 一、核心理念（Philosophy）

### 核心信念（Core Beliefs）

+ 渐进式迭代优于 “大爆炸” 式开发：优先选择可编译、能通过测试的小幅变更

+ **向现有代码学习**：先研究、规划，再动手实现

+ **务实优于教条**：根据项目实际情况灵活调整

+ **清晰意图优于 “聪明” 代码**：选择直白、易懂的实现，拒绝晦涩技巧

### 简洁性原则（Simplicity Means）

+ 每个函数 / 类仅承担单一职责

+ 避免过早抽象（Premature Abstraction）

+ 拒绝 “炫技”：优先选择 “ boring 但可靠” 的解决方案

+ 若需额外解释才能理解，说明代码过于复杂

## 二、开发流程（Process）

1. 规划与分阶段（Planning & Staging）

将复杂需求拆分为 **3-5 个阶段**，并在 `IMPLEMENTATION_PLAN.md` 中记录，格式如下：

markdown

```
## 阶段 N：[阶段名称]
**目标**：[具体可交付成果]
**验收标准**：[可测试的结果]
**测试用例**：[具体测试场景]
**状态**：[未开始|进行中|已完成]
```

+ 推进过程中实时更新 “状态”

+ 所有阶段完成后，删除该计划文件

1. 实现流程（Implementation Flow）

遵循 “理解→测试→实现→重构→提交” 五步走：

1. **理解（Understand）**：研究代码库中已有的设计模式和实现逻辑

1. **测试（Test）**：先写测试用例（确保初始状态为 “红”，即测试失败）

1. **实现（Implement）**：编写最小化代码，仅满足 “让测试通过”（转为 “绿”）

1. **重构（Refactor）**：在测试通过的前提下，优化代码结构（保持 “绿”）

1. **提交（Commit）**：撰写清晰的提交信息，并关联到对应阶段计划

1. 卡壳处理规则（When Stuck - After 3 Attempts）

> ⚠️ **关键限制**：同一问题最多尝试 3 次，若仍未解决，立即停止！

1. **记录失败细节**：

+ 已尝试的具体方案

+ 完整的错误信息（含日志、堆栈）

+ 你对失败原因的判断

1. **调研替代方案**：

+ 找到 2-3 个类似场景的实现案例

+ 记录不同方案的核心思路

1. **质疑基础假设**：

+ 当前抽象层级是否合适？

+ 能否拆分为更小的子问题？

+ 是否存在更简单的实现路径？

1. **切换解决角度**：

+ 能否用框架 / 库的其他特性？

+ 是否需要调整架构模式？

+ 能否 “移除抽象” 而非 “新增抽象”？

## 三、技术标准（Technical Standards）

### 架构原则（Architecture Principles）

+ **组合优于继承**：优先使用依赖注入（Dependency Injection）

+ **接口优于单例**：保障测试性和扩展性

+ **显式优于隐式**：数据流向、依赖关系需清晰可见

+ **尽可能测试驱动**：绝不禁用测试，失败时优先修复测试

### 代码质量（Code Quality）

#### 提交必须满足（Every Commit Must）

+ 代码可成功编译

+ 所有现有测试用例通过

+ 新增功能必须包含对应的测试

+ 符合项目代码格式 `/lint` 规则

#### 提交前检查（Before Committing）

+ 运行格式化工具 `/linter`

+ 自我 Review 代码变更

+ 确保提交信息说明 “为什么做”（而非仅描述 “做了什么”）

### 错误处理（Error Handling）

+ 快速失败（Fail Fast），并返回描述性强的错误信息

+ 包含调试上下文（如参数、状态）

+ 在合适的层级处理错误（避免 “错误冒泡” 过深）

+ 绝不静默吞掉异常（Never Swallow Exceptions Silently）

## 四、决策框架（Decision Framework）

当存在多个有效方案时，按以下优先级选择：

1. **可测试性**：能否轻松为该方案编写测试？

1. **可读性**：6 个月后，他人能否快速理解？

1. **一致性**：是否与代码库现有模式匹配？

1. **简洁性**：是否是 “能工作的最简单方案”？

1. **可逆转性**：后续若需修改，成本有多高？
