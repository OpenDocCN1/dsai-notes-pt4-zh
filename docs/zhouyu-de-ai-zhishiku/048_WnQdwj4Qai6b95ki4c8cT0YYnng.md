在本节课中，我们将讲解MCP如何让AI开发变得不再碎片化，以及它如何标准化AI应用与外部数据源的连接。我们来回答“为什么需要MCP（模型上下文协议）？”这个问题。我们常说，模型的能力取决于它所获得的上下文。你可以拥有非常智能的前沿模型，但如果它无法连接外部世界、获取所需的数据和上下文，那它的作用就会大打折扣。MCP是一个开源协议，它标准化了你的大语言模型如何与工具和数据源连接并协作。这里的目标不是重新发明轮子，比如工具调用方式，而是要标准化AI应用与数据源的连接方式。就像我们用REST标准化Web应用与后端及其他系统的通信一样（包括协议、无状态性等），我们希望通过MCP实现类似的目标。你将在MCP中看到的所有事情其实都可以不用MCP来做，但在一个有许多不同模型与许多不同数据源，甚至模型之间互相通信的世界里，我们希望大家“说同一种语言”。我们要标准化AI应用与外部系统的交互方式，而不是针对每个数据源、每个模型反复实现集成，而是“写一次，到处用”。

MCP借鉴了许多其他协议的思想。例如，微软2016年推出的LSP（语言服务器协议）标准化了集成开发环境与语言相关工具的交互方式。当你为特定语言和开发环境创建扩展时，你不想为每个开发环境都重复写一遍。所以MCP虽然很新颖，但它是建立在众多标准化协议和思想基础上的。

让我们来看一个简短的演示，只需几行代码，我们就能为AI应用引入上下文。在左侧，我用Claude Desktop发起一个关于获取GitHub仓库issue的问题，右侧是该GitHub仓库。通过自然语言，我可以直接和这个数据源交互，这就是MCP的威力。我已连接到一个提供GitHub数据的MCP服务器，同时也连接到了另一个Asana（流行的项目管理工具）的MCP服务器。我在这里读取GitHub数据，然后让Asana分配任务，实现了从一个数据源读取、向另一个数据源写入。在界面中，有“人类在环”来验证我要执行的操作。只需极少的代码，我就能轻松和外部数据源通信。

MCP支持任何模型厂商的完全开源集成，实现了不同模型和数据源的无缝对接。可以看到我创建了这些任务，浏览器自动更新，我还能继续用自然语言迭代任务。我把任务分配给某个人，看到实时更新。通过智能模型（如3.5 Sonnet）、MCP提供的工具和反复运行的环境，我们实际上在为应用赋能一个轻量级的智能体。

正如我前面提到的，MCP能做的，理论上不用MCP也能做。但你会发现，随着集成增多，工具、定制提示词、数据访问层和认证逻辑要存放在哪里？我们和很多团队都发现，大家在为类似数据源重复造轮子。MCP不仅与模型无关，而且完全开源，这些工具和数据连接能力可以由开源社区提供，也可以自己构建。

MCP让我们能更清晰地分离责任和关注点。我们可以构建或使用兼容MCP的应用，并根据需要连接到不同的数据访问服务器。可以有数据存储服务器、CRM工具（如HubSpot、Salesforce）服务器，甚至版本控制服务器。目标是用自然语言和这些数据源交流，而无需自己写所有底层逻辑。

MCP服务器的美妙之处还在于它能被多个应用复用。我们可以用参考服务器，也可以内部自建服务器，在多个应用间共享。比如为Google Drive构建或使用MCP服务器，不管是AI助手、代理还是桌面应用，只要兼容MCP，都能用同一个服务器和其他所需服务器。你可以尽情发挥想象，把各种数据访问能力用极少代码和精力集成进应用。

MCP对不同用户群体都有巨大优势。应用开发者只需很少工作即可连接MCP服务器；API开发者只需构建一次服务器即可广泛适配；AI应用用户甚至无需关心底层细节，只需输入MCP服务器URL即可获得所需数据接入。对于企业和大型组织，分离关注点、构建可复用的独立集成也带来诸多好处。

你可能注意到，MCP生态正在快速发展。不仅有大公司在推动，也有前沿初创公司。越来越多的服务器在私有和开源社区被开发出来。MCP的软件开发工具包（SDK）支持多种语言，由开源社区和众多公司、AI开发者共同推进。我们已经看到MCP兼容的Web应用、桌面应用，甚至智能体产品。

# 3. MCP架构

MCP基于客户端-服务器架构。本节课将介绍MCP能提供哪些功能，以及客户端与服务器之间的通信方式。

MCP遵循类似其他协议的客户端-服务器架构，MCP客户端与MCP服务器保持一对一连接。两者之间通过MCP定义的消息进行通信。客户端通常运行在“宿主”中，比如Claude Desktop或Claude AI。宿主负责存储和维护所有客户端及其与MCP服务器的连接。宿主其实就是希望通过MCP访问数据的LLM应用。服务器则是通过协议暴露具体能力的轻量级程序。很快我们就会开始构建自己的服务器和客户端，以及包含多个客户端的宿主。相关代码会稍微底层一些，但目标是帮助大家理解整个架构。这样当你使用像Claude Desktop、Cursor或Windsurf等工具时，就能明白底层发生了什么。

在讲客户端和服务器的职责之前，先介绍协议中的几个基本概念（原语）：

+   **工具（Tools）**：类似于函数，由客户端调用，支持数据检索、搜索、发送消息、更新数据库等。通常用于需要POST请求或数据修改的场景。

+   **资源（Resources）**：类似于GET请求，是服务器暴露的只读数据或上下文。应用可以选择是否使用这些资源，比如数据库记录、API响应、文件、PDF等。

+   提示模板（Prompt Templates）：用于减轻用户的提示词工程负担。比如有的MCP服务器负责查询Google Drive并总结内容，但用户不需要自己写复杂的提示词，而是直接用服务器预设的模板。

客户端负责查找资源和工具，服务器负责向客户端暴露这些信息。接下来通过一个例子展示实际效果：使用Claude Desktop作为宿主，连接到一个暴露工具、资源和提示模板的SQLite MCP服务器。连接后，可以用自然语言与数据对话，比如查询表结构、统计记录数等。人类在环的机制由宿主界面决定，服务器只负责返回工具，客户端负责调用并执行。

比如，利用Claude的artifacts功能，可以生成数据可视化。比如让AI分析products表的数据，自动生成价格分布等图表。通过MCP，将外部数据和系统引入AI应用，可以轻松构建更有趣、更强大的应用。

再比如，服务器还可以提供用于初始化数据库的提示模板，用户只需填入动态数据即可自动生成文本或操作，而无需自己编写完整提示词。通过这些模板，用户可以获得经过实践验证的高质量提示，大大提升效率。

资源是动态的，会随着应用数据变化实时更新。比如可以让AI自动更新业务分析备忘录，或者根据新数据调整内容。这样，工具、资源和提示模板结合，为AI应用赋能，远超出厂默认的能力。

MCP还提供多种开发工具包（SDK），支持多种语言。在本课程中，我们将使用Python的MCP SDK，非常方便地声明工具、资源和提示模板。比如声明工具时，只需装饰一个函数，指定参数和返回值，SDK会自动生成工具的schema。资源则通过指定URI或位置，让客户端可以直接获取所需数据，无需额外工具调用。对于动态资源，可以像Python的f-string那样用模板参数。

提示模板与工具和资源类似，也是通过装饰器声明，定义名称、描述和返回的消息列表。这样用户可以选择使用高质量的模板，而不用自己做繁琐的提示词工程。

客户端与服务器通信时，先初始化连接，完成请求、响应和通知的流程，然后开始消息交换。客户端和服务器都可以发送请求和通知，通信结束时连接终止。

MCP还涉及“传输层”（Transport）的概念，即消息在客户端和服务器之间的具体传递方式。常见的有本地运行时的标准输入输出（Standard IO），远程部署时的HTTP+服务器推送事件（Server-Sent Events），以及支持有状态和无状态连接的Streamable HTTP。在本地通常用标准IO，远程则可以选择HTTP+SSE或Streamable HTTP。后者支持更灵活的有状态和无状态连接，适合不同规模和需求的应用。

本节课总结：你已经了解了MCP架构、客户端与服务器、宿主的概念，见识了工具、资源、提示模板等核心功能，以及不同的通信机制。接下来，你将开始实际操作，学习如何用代码实现这些功能，逐步搭建自己的MCP服务器、客户端和宿主。

# 连接MCP聊天机器人到参考服务器

在上一节课中，你已经学会了如何将自己的聊天机器人连接到一个自建的MCP服务器。本节课将进一步升级，让你的聊天机器人可以连接到任意服务器，并介绍Anthropic团队开发的参考服务器及其下载和使用方法。

目前为止，我们已经了解了如何构建MCP服务器和客户端，并实现一对一的连接。接下来，我们要引入多个客户端与多个服务器协作，并探索MCP生态中的丰富服务器资源。首先，讲师带领大家在GitHub上浏览Anthropic官方维护的参考服务器。这些服务器种类繁多，几乎涵盖了你能想到的所有数据源。除了官方服务器，还有许多第三方服务器和集成，任何你想要对接的数据源，基本都有对应的MCP服务器。

以fetch服务器和文件系统服务器为例，fetch服务器可以抓取网页内容并将HTML转换为markdown，便于LLM处理；文件系统服务器则支持读取、写入、搜索文件、获取元数据等操作。fetch服务器采用Python编写，通过uvx命令一键运行；文件系统服务器用TypeScript编写，通过npx命令运行，并可指定允许访问的路径。每个参考服务器都有相应的配置方式，包括名称、运行命令及参数等。

为了让聊天机器人灵活连接多个服务器，课程建议将服务器参数写入一个JSON配置文件，机器人读取该文件即可自动识别和连接所有服务器。这样，不仅可以连接文件系统服务器、研究服务器、fetch服务器，还能方便地扩展和组合多种服务器，实现强大的AI能力。

接下来，代码部分需要进行相应调整。聊天机器人要维护所有已连接会话及各自的工具列表。由于涉及多个异步连接，需要用异步上下文管理器（async exit stack）来管理读写和会话生命周期。机器人会从JSON配置文件读取所有服务器信息，遍历每个服务器并建立连接。虽然代码略显底层，但核心思想是让大家理解像Claude Desktop、Cursor、Windsurf等工具在底层是如何实现多服务器对接的。

连接成功后，用户可以在聊哦，那么就开始啦。哈喽，哇！Hello，how are你在这里呢，在这里呢。我们不去过多深入的探讨天界面输入指令，比如让机器人抓取Model Context Protocol的内容，保存为MCP summary文件，并生成一张总结内容的可视化图表。机器人会调用fetch服务器获取网页内容，再用文件系统服务器保存文件，最后生成可视化结果。用户也可以让机器人抓取DeepLearning.AI网站内容，提取关键词，搜索相关论文，总结后写入results.txt文件。通过组合不同服务器的工具，AI可以完成跨数据源、跨任务的复杂操作。

这种多服务器协作的方式极大拓展了AI应用的能力。你可以根据实际需求，灵活组合和扩展各种MCP服务器，只需简单配置即可将模型与外部世界高效连接。即使遇到模型混淆概念的情况，也可以通过优化提示词来提升效果。
